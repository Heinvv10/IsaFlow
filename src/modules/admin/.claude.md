# Admin Module

Platform administration for ISAFlow SaaS operations — company management, user management, billing, feature flags, and system analytics.

| Service | Purpose |
|---------|---------|
| `adminCompanyService.ts` | Company CRUD, suspension, metadata management |
| `adminUserService.ts` / `adminUserActionsService.ts` / `userImpersonationService.ts` | Platform user management, role assignment, impersonation |
| `adminDashboardService.ts` | System-wide metrics and KPIs |
| `adminWebhookService.ts` | Outbound admin webhooks (events, retries) |
| `analyticsService.ts` / `trendsService.ts` | Usage analytics, company activity, trend rollups |
| `announcementService.ts` | System-wide announcements to all users |

| `dataExportService.ts` | Platform data export for compliance |

| `healthAlertService.ts` | Tenant health/anomaly alerts |

## Key Rules

- All admin APIs live under `pages/api/admin/`
- Admin middleware uses `withAdmin()` (NOT `withCompany()`)
- Admin pages at `pages/admin/`
- Separate from accounting module — different auth scope
- Feature flags stored in `platform_features` table
- Plans stored in `platform_plans` table
- **`logAdminAction` fails closed.** `BEST_EFFORT_ACTIONS` is empty, so an audit-write failure — including for an action nobody has added to a list yet — raises `CriticalAuditError`, `withPlatformAdmin` ROLLBACKs the request transaction and the route answers 4xx/500. An unaudited admin mutation must not commit.
- **Fail-closed rolls back the DB, not the outside world.** Actions whose side effect has already left the process before the audit write — `invoice.send` (email dispatched), `user.reset_password` / `user.force_logout` (GoTrue already mutated) — leave that effect done with no DB trace when the audit INSERT fails. An operator reading such a 500 must assume the email or the password change DID happen. Where a route allows it, order the external call AFTER the audit write. Since 2026-10-08 ANY 5xx rolls the admin action back (its own audit row with it), and `withPlatformAdmin` records the attempt as an `admin_request_failed` row after the rollback (`src/lib/auth/adminFailureAudit.ts`): that row is the DB trace of a failed action.

- 2026-09-26 (R-032 re-check 2): `supersedePasswordResetTokens` retires only tokens issued BEFORE the delivered one (`(created_at, id) <` the kept row): two interleaved resets each superseding "every other" token left the user two dead links. A supersede failure after a successful send is logged (user id only) and the admin still gets "sent". `/api/auth/logout` reads the Login-as scope inside a try: if the session store cannot be read it signs out with `scope=local` and still clears the cookies (the route has no withErrorHandler). **Known limit (infra, not code):** GoTrue is reachable on the tailnet, so a Login-as admin holding the target's access token can call GoTrue `PUT /auth/v1/user` directly (change the target's password or email) and bypass every route guard. Mitigations for Hein: bind GoTrue to localhost (reached only through IsaFlow), or set `GOTRUE_SECURITY_UPDATE_PASSWORD_REQUIRE_REAUTHENTICATION=true`. Not changed here.
- 2026-09-26 (R-032 (f)): **a Login-as session changes none of the target's credentials or recovery.** `/api/auth/change-email`, `change-password`, `2fa-enroll`, `2fa-confirm` and `2fa-disable` run outside withAuth, so they call `refuseImpersonatedSession` (`src/lib/auth/impersonationGuard.ts`) first: it classifies the cookie's own access token by its verified `session_id` through the platform_admin pool (`sessionActorOfToken`) and answers 403 `IMPERSONATION_FORBIDDEN` for a Login-as session AND for a token with no session id (these routes accept only GoTrue cookies). `/api/auth/profile` PUT (phone / mobile, withAuth) calls `assertNotImpersonating()`. `/api/auth/logout` from a Login-as session revokes only that session (GoTrue `scope=local`); the global default would sign the target out everywhere. Not guarded, deliberately: `forgot-password` is unauthenticated and emails the TARGET's inbox, `do-reset-password` / `verify-email` are token flows with no session, and `2fa-challenge` is the login step (it needs the target's TOTP). There are no recovery codes. Tests: `tests/integration/r-032-account-security.int.test.ts`.
- 2026-09-26 (R-032 re-check LOWs): the impersonation-session record uses a one-off `pg.Client` (`newPlatformAdminClient`, 5s connect timeout) instead of a second connection from the platform_admin pool the request already holds — that deadlocked once the pool was exhausted (`tests/integration/r-032-session-record-pool.int.test.ts`). The admin password reset now runs its token writes outside the request transaction (`als.exit` in `passwordResetEmail.ts`): the token is committed before the email goes out, the user's outstanding links are retired (`supersedePasswordResetTokens`) only after a successful send, and an unsent token is withdrawn (`issue` / `supersede` / `withdraw` replace `createPasswordResetToken`).
- 2026-09-26 (R-032 M2): **the admin "Reset password" action no longer returns a link.** `resetPassword` used GoTrue's admin `generate_link('recovery')`, which sends no email and returned the `action_link` — a working recovery session for the user — in the admin's JSON; the user was never emailed. It now calls `sendPasswordResetEmail` (`src/lib/auth/passwordResetEmail.ts`, shared with forgot-password): our single-use token from `passwordResetService`, emailed to `/reset-password#token=...`. The route answers `{ message: 'Password reset email sent' }`, writes the audit row before the send, and answers 503 "could not be sent" when `sendEmail` reports failure. No GoTrue recovery call remains. Tests: `tests/unit/api/admin/adminResetPassword.test.ts`, `tests/integration/r-032-admin-reset-password.int.test.ts`.
- 2026-09-26 (R-032): "Login as" (`pages/api/admin/users/[id]/impersonate.ts`) records the target session's GoTrue `session_id` in `impersonation_sessions` (migration 709, `src/lib/auth/impersonationSessions.ts`) after minting the proof and BEFORE any cookie is issued; if the insert fails the impersonation does not start. **The insert runs on its OWN autocommit connection (platform_admin pool), not `withPlatformAdmin`'s request transaction** — that transaction COMMITs only after the handler returns (and, since 2026-10-08, rolls back on a 5xx), so a row written inside it would be lost with a rollback, and was invisible when the cookies went out while the response was not yet held (it is held until COMMIT since PR #659; the audit row is still awaited before the cookies are set). An orphan row left by a later rollback only over-refuses. A failed insert leaves the request transaction usable: the stash is deleted, the rethrow answers 500, which rolls the `impersonation_start` row back, and `withPlatformAdmin`'s `admin_request_failed` row (target_id = the user id in the path) records the refused attempt. Grants: app_user SELECT (own session only, RLS), platform_admin SELECT + INSERT; the default-privilege INSERT/UPDATE/DELETE from 348/352 are revoked. Rows are never deleted — the target session outlives the stash. Approval decisions (`gl/approvalAuthority.assertMayDecide`) refuse any session recorded there.
- 2026-09-09: **`trialService.bulkExtendTrials` told the admin every company moved.** It read `.count` off a tagged-template result (`src/lib/neon.ts` resolves to `res.rows`, so `.count` is always undefined) and fell back to `companyIds.length`, over an UPDATE whose `status IS DISTINCT FROM 'deleted'` predicate skips rows — so extending a list containing deleted companies reported full success. Now `RETURNING id` + `rows.length`. Any bulk mutation here must count what the predicate matched, never the length of the id list.

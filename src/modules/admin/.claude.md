## Key Rules

- All admin APIs live under `pages/api/admin/`
- Admin middleware uses `withAdmin()` (NOT `withCompany()`)
- Admin pages at `pages/admin/`
- Separate from accounting module — different auth scope
- Feature flags stored in `platform_features` table
- Plans stored in `platform_plans` table
- **Plan-level feature gating reads the plan from the company's current subscription**, never `companies.plan_id` (vestigial). One SQL fragment, `CURRENT_PLAN_ID_SQL` in `services/currentPlanSql.ts`, is spliced into all three readers in `featureFlagService.ts`. Current = the latest LIVE subscription ordered by `created_at DESC, id DESC` (NOT `updated_at`, which any admin edit bumps). Live = `active`, or `past_due` (dunning grace: the billing runner keeps retrying it), or `trial` whose end (the later of `current_period_end` and `companies.trial_ends_at`) is in the future; a trial with neither date is not live. Cancelled, paused and expired-trial rows never grant. Current is the latest LIVE row, not the latest row, so when a newer row is cancelled an older LIVE row becomes current again (intended). An old onboarding trial cannot resurface once its end date (the later of `current_period_end` and `companies.trial_ends_at`) has passed; before that, up to 30 days from signup or longer if an admin extended it, it can. Precedence: override > global > plan. `tests/integration/feature-flag-plan-via-subscription.int.test.ts` pins it (incl. RLS member/non-member). Gate routes by calling `hasFeature` in the handler (the dead `withFeature` wrapper was removed).
- **One metrics module for revenue (goal §2a, admin audit 2.x).** `services/metrics/metricsSql.ts` is the only place a subscription is priced (`subscriptionAnnualUnits`: annualised, discounted, exact integer hundredths of a cent) and the only place that decides which companies count (`companyOutOfMrr`: deleted, suspended, `is_demo` or the Demo id). MRR = active only, trials never; ARR summed from unrounded units; ARPU = MRR / paying companies (an active sub worth more than R0). The overview, dashboard, revenue intelligence, MRR trend, revenue by plan, company list/detail, subscription list and CSV read it (`loadSubscriptionFacts` + `revenueMath.ts` / `timeSeriesMath.ts`, or the SQL fragments). Never write another `monthly_price_cents` CASE. A rate with a zero denominator is `null` (UI dash), never 0 or 100. Trial counts live in `trialQueries.ts`: deleted companies are not listed; internal ones (`companyOutOfMetrics`: `is_demo`, the Demo id) are listed with an Internal badge and left out of every count. Tests: `tests/integration/admin-metrics-*.int.test.ts`, `tests/unit/services/admin/metrics*.test.ts`.
- **Health alerts run every 5 minutes on a timer (admin audit OP-1).** `scripts/isaflow-health-alerts.{service,timer}` (the mirror-scan pair's shape) POST `/api/cron/health-alerts` with `X-Cron-Secret` → `healthAlertRun.runScheduledHealthAlert`: the same snapshot as the route (`systemHealthService.buildSystemHealth`, platform_admin pool, read-only tx); once the snapshot exists it records `health_alerts_last_scheduled_run`, then runs the same `checkAndAlert` outside any ALS context on the app pool, as the route's `runAfterCommit`. The Health page shows "Scheduled check: last ran <time>" while that is under 15 minutes older than the snapshot, else "Scheduled check is not running: alerts only fire while this page is open" (timer not installed, stopped, or its snapshot failing). Every send records its outcome (`health_alerts_last_delivered_at` / `_last_delivery_failed_at`); when the later one is the failure, the page adds "Last alert could not be delivered: check the alert email/webhook settings".
- **One alert per change, whoever checks (`healthAlertState.ts`).** The route and the timer both call `checkAndAlert`. The decision is a CLAIM: one transaction takes `pg_advisory_xact_lock` on a fixed key, reads `health_alert_last_status` / `_last_sent_at`, decides (status change, else at most once an hour), and writes the new state BEFORE sending; the send runs after COMMIT. A racing pass waits on the lock and is suppressed. If no enabled channel delivers (email not accepted and the webhook absent or failed), the claim is released (previous state written back, only if still this claim's: a newer claim or a healthy reset is never undone) and `checkAndAlert` throws, so the next pass retries and the cron answers 500. **A partial delivery (one channel OK) counts as sent, by design: the claim stands and the failed channel is not retried** (retrying would re-send on the channel that worked). Never send before claiming, and never save state after the send. `healthAlertState` refuses to run inside a request transaction (ALS store): there `withTransaction` is a savepoint that commits only with the request, which would bring the double send back.
- **Limit: a total outage cannot alert from inside the app.** With the database or the app down, neither the cron route nor `checkAndAlert` can run (`db.status = error` alerts only while the app reaches its own pool for `admin_settings`). An external uptime monitor must cover a total outage (`scripts/ops/uptime-probe.sh`); the stale "last ran" line shows it after the fact.

- **Membership case rule (decision 2026-10-16, re-confirmed by Hein 2026-11-15).** `company_users.user_id` is TEXT and its unique key is case-sensitive, so one person can hold case-variant rows for a company (`pair-x` and `PAIR-X`). Membership code (`companyMembershipService` link / role / remove, `adminUserActionsService.assertOwnsNoCompanyAlone`'s sole-owner check) matches `lower(user_id::text) = lower(<id>)` and treats those rows as ONE link: removing `pair-x` also removes `PAIR-X`'s membership, re-roling one re-roles both, an owner row among them makes the link an owner's, and an owner count counts `DISTINCT lower(user_id)`. Intended, not a bug: do not narrow these to an exact match. GoTrue ids are lower-case UUIDs, so such pairs cannot arise from sign-up; they exist only in hand-seeded or legacy rows. The orphan path is the same rule seen from `users`: `removeOrphanMembership` matches the membership row on exactly the given id, but its under-lock re-check of `users` is `lower(id) = lower(<id>)` on purpose: a `users` row for ANY case variant of the id means the person exists, so the membership is not an orphan and the normal (case-insensitive) path runs. `users` rows are different: an admin route names one stored row exactly (`findStoredUser`, below).
- **Status codes (audit 2026-11-14 section 6).** A 4xx COMMITS the request transaction, so a route answers 4xx only for a known refusal raised before any write: `AdminRequestError` (`middleware/adminRequestErrors.ts`; withAdmin answers it, so routes need no catch), or a Postgres integrity refusal a route maps itself when the failing statement is its first write (`isPgError(err, sqlState, constraintName)`: name the constraint, so another one's failure stays a 500). A missing target is refused before the write and the audit row (an UPDATE/DELETE ... RETURNING that matched nothing, or a locked existence check first), never after; the statement that writes decides, not an earlier read, so the loser of two concurrent DELETEs is a 404 and is not audited. A catch that answers 4xx must END with `throw <err>`; never call a validator inside a try whose catch does not rethrow. Everything unexpected is withErrorHandler's 500, which rolls back; a bulk action does not turn a thrown error into a per-item `errors[]` entry. withAdmin refuses a repeated query parameter, a NUL in a query name or value, and a NUL in any JSON body string or key with a 400. A bulk id list is `adminDistinctUuids(max)`: a repeated id is a 400. Path ids, uuid/date filters and page/limit/offset are validated before SQL; a UUID comes back in its canonical lower-case spelling (`adminUuid`, `AdminUuid` for zod path and body ids, `adminDistinctUuids`), so a route queries and audits one spelling; `logAdminAction` lower-cases a UUID-shaped non-user target_id itself. A 'user' target is written exactly as given and never re-mapped (two TEXT ids can differ only in case; after a delete a look-up named the survivor): every user route takes its id from `adminStoredUser` (`services/storedUserId.ts`, over `findStoredUser`, the one resolver for TEXT user ids) and acts and audits on that stored id (census: `tests/unit/ci/adminUserAuditTargetCensus.test.ts`). One named exception: remove-from-company's orphan path removes a membership whose user has no users row, matched on exactly the given id, and audits it under that id with `{ orphan: true }` (`removeOrphanMembership`, which re-checks under the membership lock that no users row appeared; if one did, the normal path runs); company-role on an orphan is a 404. `findStoredUser` answers 409 'Ambiguous user id' when no id matches exactly and two or more match case-insensitively. A row about a company's subscription, invoice, webhook or a promoted waitlist lead carries `details.company_id` so the company's view lists it. A bulk action writes one row per item it changed (companies, trials, job queue), never one row with no target; the company audit view (`entity_type=company`) also lists rows naming the company in `details.company_id` / `details.company_ids` (`adminUuid`, `adminUserId` for users' TEXT ids, `adminOptionalUuid`, `adminOptionalDate`, `adminOptionalTimestamp`, `adminPaging`, `adminPositiveInt`, `adminNonNegativeInt`, int4-bounded); body ids are `UUID` from `@/lib/schemas/common`, never a bare `z.string()`. Census: `tests/unit/ci/adminRouteStatusCensus.test.ts`; behaviour: `tests/integration/admin-route-statuses.int.test.ts`, `admin-route-refusals-write-nothing.int.test.ts`, `admin-route-input-400s.int.test.ts`, `admin-route-races-round2.int.test.ts`.
- **Refuse before minting or mailing (audit 2026-11-14 F-11, F-13).** Company impersonation refuses everything impersonate-exchange would, before any token is minted or audited: 404 for a company that is missing, deleted, suspended (status or `suspended_at`) or inactive (`companyCanBeImpersonated`, the `listLiveCompanies` predicate), and the exchange's own 403 when the admin is not a member (`isMemberForImpersonation`, `src/lib/auth/impersonationMembership.ts`, shared with the exchange). Admin reset-password answers 404 for a missing user, 403 for a super admin and 409 for a user whose stored id is not a UUID (`resetPasswordRefusal`; `auth_password_reset_tokens.user_id` is uuid, so such an account cannot hold a reset token, and minting one was a 22P02 500, OP-3) before the audit row, any reset token or any email, and logs each refusal (user id and reason, never the address); `resetPasswordRefusal` resolves the URL's id to the stored id first (`findStoredUser`: an exact match wins over a case variant, and two case variants with no exact match are a 409), and `resetPassword` then matches that stored id exactly; the route resets and audits by the stored id (never the URL's spelling). Tests: `tests/integration/admin-impersonate-reset-refusals.int.test.ts`.
- **Fail-closed rolls back the DB, not the outside world.** Actions whose side effect has already left the process before the audit write — `user.reset_password` / `user.force_logout` (GoTrue already mutated) — leave that effect done with no DB trace when the audit INSERT fails. An operator reading such a 500 must assume the email or the password change DID happen. Where a route allows it, order the external call AFTER the audit write. Since 2026-10-08 ANY 5xx rolls the admin action back (its own audit row with it), and `withPlatformAdmin` records the attempt as an `admin_request_failed` row after the rollback (`src/lib/auth/adminFailureAudit.ts`): that row is the DB trace of a failed action.
- **Platform invoice Send is claim -> email -> finalise** (`services/invoiceSendService.ts`, migration 993). Claim and finalise each COMMIT on their own one-off platform_admin connection (`src/lib/auth/platformAdminOwnTx.ts`: actor and claims from the request context, lock_timeout 5 s, outside PLATFORM_ADMIN_POOL_MAX); the email goes out between them, outside every transaction, so its `email_log` row (bare pool; isaflow_service in production) can never be rolled back. The request transaction stays open, idle, holding no row lock of the flow. Never send from inside a transaction that can still roll back.
- **A claim (`admin_invoices.send_claimed_at`) means "a send is in flight or its outcome is unknown".** A Send on a claimed invoice is a 409. Release it automatically only when nothing can have left: the mail server provably refused (`EmailResult.provablyNotSent`) or the email failed before `sendEmail` ran (`InvoiceEmailNotStartedError`). Any ambiguous end (timeout, deadline, finalise failure after the email left) KEEPS the claim; it is never re-sent automatically.
- **Hard send deadline:** `SEND_DEADLINE_MS` (45 s, `invoiceSendTiming.ts`) closes the transport and reports the outcome unknown. nodemailer's connection/greeting/socket timeouts are inactivity timers, not a ceiling.
- **Settle only after `SEND_SETTLE_AFTER_MS`** (10 min): it must exceed the hard deadline plus the claim/finalise lock bounds with wide margin. `settle-send.ts` ('sent' or 'released', audited `invoice.send_settled`) refuses a younger claim (409) in the UPDATE's own predicate; the list says "Sending…" until then and offers Settle after.
- **Send carries `confirmed_to`,** the billing address its confirm dialog showed; the claim refuses a changed billing email (409). Platform invoice VAT is computed server-side (`invoiceAmounts.ts`, 15% from `@/lib/vat/standardRate`); a client tax or total is refused.
- **Every admin CSV export goes through `services/adminCsvExport.sendAuditedCsv`.** It writes the audit row (`user.export`, `company.export`, `subscription.export`, `web_analytics.export`, `audit.export`: who, which export, the filters applied, the row count, never the data; a free-text filter is recorded as present/absent only, `textFilterSet`) BEFORE any byte is sent, so the file is built in memory, never streamed, and refused (400) above `ADMIN_EXPORT_MAX_ROWS`, never truncated. Text cells go through `csvRow` -> `@/lib/csv` `csvCell` -> `@/lib/csvSafe` `neutralizeCsvCell`; numbers and plain signed decimal strings are quoted but not neutralised (-5 stays -5); a dropdown filter value outside the page's options is a 400, so the audit row only records known values; browser-built CSVs use `csvCell` too. An export applies the same filters as its list (`tests/integration/admin-audited-exports.int.test.ts`); the page builds the link with `components/admin/adminExportHref`.
- **Trial state comes from one query** (`trialQueries.loadTrials`): the Trials list, its cards, the billing overview's `trial_count` and health's `expiring_in_7d` all derive from its rows. A company is `converted` (an active/past_due subscription on a plan other than `trial`), else `expired` or `active` by `trial_ends_at`; `companies.status` does not decide it. The conversion date in the stats is the `trial.convert_to_paid` audit row with `target_type = 'company'`.
- **Convert to Paid** (`trialService.markAsConverted`) runs in one `withTransaction` under a `FOR UPDATE` on the company row. It is refused (409) unless the company is `trial`/`active`, for a company that already pays, and for a company with any paused subscription; internal plans (`trial`, `payg`: `types/trialPlans.ts`) and archived plans are refused (400).
- **Convert writes:** it converts the newest live trial row, cancels any other live trial rows of the company, inserts a subscription only when there is none (there is no unique index on `subscriptions.company_id`, so never ON CONFLICT), starts a monthly period now, and never touches `suspended_*`. The 200 returns `firstChargeAt` and `hasActiveMandate`: billing needs an active Paystack mandate.
- **Extending a trial** (single, bulk, `companies/bulk-action`) counts from the later of the current end and today, moves the trial subscription's period end, is refused (409, single) or skipped (bulk) for a paying company, and is 404 for an unknown or deleted one.
- **Nothing enforces trial expiry:** tenant access does not depend on `trial_ends_at`.

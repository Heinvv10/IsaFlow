Platform administration for ISAFlow SaaS operations — company management, user management, billing, feature flags, and system analytics.

## Key Rules

- All admin APIs live under `pages/api/admin/`
- Admin middleware uses `withAdmin()` (NOT `withCompany()`)
- Admin pages at `pages/admin/`
- Separate from accounting module — different auth scope
- Feature flags stored in `platform_features` table
- Plans stored in `platform_plans` table
- **Plan-level feature gating reads the plan from the company's current subscription** (latest created of trial/active/past_due), never `companies.plan_id` (vestigial). Precedence: override > global > plan. All three readers in `featureFlagService.ts` share that subquery; `tests/integration/feature-flag-plan-via-subscription.int.test.ts` pins them. Gate routes by calling `hasFeature` in the handler (the dead `withFeature` wrapper was removed).
- **`logAdminAction` fails closed.** `BEST_EFFORT_ACTIONS` is empty, so an audit-write failure — including for an action nobody has added to a list yet — raises `CriticalAuditError`, `withPlatformAdmin` ROLLBACKs the request transaction and the route answers 4xx/500. An unaudited admin mutation must not commit.
- **Fail-closed rolls back the DB, not the outside world.** Actions whose side effect has already left the process before the audit write — `user.reset_password` / `user.force_logout` (GoTrue already mutated) — leave that effect done with no DB trace when the audit INSERT fails. An operator reading such a 500 must assume the email or the password change DID happen. Where a route allows it, order the external call AFTER the audit write. Since 2026-10-08 ANY 5xx rolls the admin action back (its own audit row with it), and `withPlatformAdmin` records the attempt as an `admin_request_failed` row after the rollback (`src/lib/auth/adminFailureAudit.ts`): that row is the DB trace of a failed action.
- **Platform invoice Send is claim -> email -> finalise** (`services/invoiceSendService.ts`, migration 993). Claim and finalise each COMMIT on their own one-off platform_admin connection (`src/lib/auth/platformAdminOwnTx.ts`: actor and claims from the request context, lock_timeout 5 s, outside PLATFORM_ADMIN_POOL_MAX); the email goes out between them, outside every transaction, so its `email_log` row (bare pool; isaflow_service in production) can never be rolled back. The request transaction stays open, idle, holding no row lock of the flow. Never send from inside a transaction that can still roll back.
- **A claim (`admin_invoices.send_claimed_at`) means "a send is in flight or its outcome is unknown".** A Send on a claimed invoice is a 409. Release it automatically only when nothing can have left: the mail server provably refused (`EmailResult.provablyNotSent`) or the email failed before `sendEmail` ran (`InvoiceEmailNotStartedError`). Any ambiguous end (timeout, deadline, finalise failure after the email left) KEEPS the claim; it is never re-sent automatically.
- **Hard send deadline:** `SEND_DEADLINE_MS` (45 s, `invoiceSendTiming.ts`) closes the transport and reports the outcome unknown. nodemailer's connection/greeting/socket timeouts are inactivity timers, not a ceiling.
- **Settle only after `SEND_SETTLE_AFTER_MS`** (10 min): it must exceed the hard deadline plus the claim/finalise lock bounds with wide margin. `settle-send.ts` ('sent' or 'released', audited `invoice.send_settled`) refuses a younger claim (409) in the UPDATE's own predicate; the list says "Sending…" until then and offers Settle after.
- **Send carries `confirmed_to`,** the billing address its confirm dialog showed; the claim refuses a changed billing email (409). Platform invoice VAT is computed server-side (`invoiceAmounts.ts`, 15% from `@/lib/vat/standardRate`); a client tax or total is refused.
- **Trial state comes from one query** (`trialQueries.loadTrials`): the Trials list, its cards, the billing overview's `trial_count` and health's `expiring_in_7d` all derive from its rows. A company is `converted` (an active/past_due subscription on a plan other than `trial`), else `expired` or `active` by `trial_ends_at`; `companies.status` does not decide it. The conversion date in the stats is the `trial.convert_to_paid` audit row with `target_type = 'company'`.
- **Convert to Paid** (`trialService.markAsConverted`) runs in one `withTransaction` under a `FOR UPDATE` on the company row. It is refused (409) unless the company is `trial`/`active`, for a company that already pays, and for a company with any paused subscription; internal plans (`trial`, `payg`: `types/trialPlans.ts`) and archived plans are refused (400).
- **Convert writes:** it converts the newest live trial row, cancels any other live trial rows of the company, inserts a subscription only when there is none (there is no unique index on `subscriptions.company_id`, so never ON CONFLICT), starts a monthly period now, and never touches `suspended_*`. The 200 returns `firstChargeAt` and `hasActiveMandate`: billing needs an active Paystack mandate.
- **Extending a trial** (single, bulk, `companies/bulk-action`) counts from the later of the current end and today, moves the trial subscription's period end, is refused (409, single) or skipped (bulk) for a paying company, and is 404 for an unknown or deleted one.
- **Nothing enforces trial expiry:** tenant access does not depend on `trial_ends_at`.

Any other failure in the suspend or role-change route is a 500 that rolls back (the old catch answered 400, which committed the suspension with no audit row). `superAdminRosterService.assertSuperAdminRemains` runs first in PATCH `users/[id]` (when `role` is sent) and `suspend`: one transaction-scoped advisory lock (`isaflow.admin.super_admin_roster`) for the whole roster, then a count of the OTHER active super admins (active = `isActiveUserAccount`); the last one is a 409 `reason: LAST_SUPER_ADMIN` and nothing is written. Only a real removal is refused: a PATCH that sends the target's role unchanged (the edit form sends it with every save; `super_admin` is accepted in the body only as the target's own role, never a promotion: 400) is no role change. Needs READ COMMITTED (refuses to judge otherwise). Delete already refuses any super admin. A super admin acting on another (or on themselves) stays allowed while one remains; the audit row carries `target_super_admin: true` (and `previous_role`/`role` on a role change). Anything short of complete is a 424 (`DEPENDENCY_ERROR`, commits), never 200. Suspend holds the roster lock across its GoTrue revocation (≤5 s) until COMMIT: accepted. MFA for super admins (3.9) is not enforced (report only).

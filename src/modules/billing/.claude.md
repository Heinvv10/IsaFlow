# Module — `src/modules/billing/`

## Purpose
PAYG Flow wallet, subscription billing, and Stitch Express payments. Owns mutations of `flow_wallet`, `flow_ledger`, `flow_purchases`, and the recurring-debit lifecycle. Spec: `docs/superpowers/specs/2026-04-19-payg-flows-pricing-design.md`.

## Services

| Service | Purpose |
|---------|---------|
| `flowOperationCatalog.ts` | Single source of truth for Flow costs per operation code (`bank.import`=1, `invoice.create`=3, `report.tb`=10, `afs.generate`=50). Categories: `basic` / `standard` / `advanced` / `premium`. |
| `flowWalletService.ts` | Wallet CRUD + ledger writes. Balance/ledger writes for `deductFlows`, `refundFlows`, `adminAdjust`, `setAutoTopup`, and bundle-purchase complete-paths run inside `withTransaction`. `recalculateNudge` and `failBundlePurchase` use bare `sql` (single-row UPDATEs, no ledger row). |
| `stitchClient.ts` | Stitch Express REST client (NOT GraphQL). OAuth2 `client_credentials` → bearer token cached in-memory; cache invalidated 60s before expiry. |
| `paystackMandateActivation.ts` | Promotes a captured Paystack authorization onto the mandate its checkout was started for. Shared by the `charge.success` webhook handler and `GET /api/billing/paystack/mandate/verify` so the two cannot drift. |
| `subscriptionBillingService.ts` | Recurring-debit lifecycle: `generateDueCharges` (queue) → `runQueuedCharges` (execute via `debitFromMandate`). |
| `subscriptionBillingService.ts` | Recurring-debit lifecycle: `generateDueCharges` (queue a charge per due subscription, then void/close-out subscriptions flagged `cancel_at_period_end`) → `runQueuedCharges` (claim the attempt, then execute via Paystack `chargeAuthorization`). |
| `subscriptionPeriod.ts` | Subscription period transitions, shared by the cron and the Paystack webhook: `advancePeriodForSettledCharge`, `settleSubscriptionCharge`, `markPastDueIfExhausted`, `voidChargesForCancellingSubscriptions`, `closeOutCancelledSubscriptions`, plus `MAX_ATTEMPTS`. |

## Caller contract
- Wrapped metered API routes call `getFlowCost(code)` from `flowOperationCatalog` — NEVER hard-code Flow integers in route handlers.
- Wallet mutations always take `companyId` first; routes live under `pages/api/billing/`.
- Admin routes for plan/invoice/PAYG management live under `pages/api/admin/billing/`.

## Main function signatures (verified against source)
- `getWallet(companyId) → FlowWallet | null`
- `deductFlows(companyId, flowCost, operationCode, referenceId?)` — atomic balance↓ + `debit` ledger row; throws `InsufficientFlowsError` when balance < flowCost.
- `refundFlows(companyId, flowCost, operationCode, referenceId?)` — atomic balance↑ + `refund` ledger row; also unwinds `month_flows_used` so the nudge isn't punished. **Note:** the caller passes the refund cost — this is NOT a "reverse-by-ledger-id" helper.
- `adminAdjust(companyId, flows, reason)` — emergency credit/debit (`flows` non-zero integer); writes `admin_adjustment` ledger row.
- `startBundlePurchase / completeBundlePurchase / failBundlePurchase / purchaseBundle / getPurchaseStatus` — Stitch payment-link lifecycle.
- `triggerAutoTopup(companyId)` — separate function, NOT auto-invoked inside `deductFlows`. Returns `AutoTopupResult` with `reason` ∈ `disabled | no_payment_method | no_bundle | gateway_unavailable`.
- `setAutoTopup(companyId, enabled, bundleId)` — sets the auto-topup flag/bundle. Does NOT update `payment_method_token`.
- `recalculateNudge(companyId) → NudgeLevel` — `none|yellow|orange|red` based on `month_flows_used`.
- `resetMonthlyCounter()` — cron tick that resets `month_flows_used` for all companies.
- `createPaymentLink(amount, reference, redirectUrl)` / `getPaymentStatus(paymentId)` — Stitch.
- `debitFromMandate(input: DebitFromMandateInput)` — single-object arg (`bankAccountId`, `amountCents`, `currency?`, `payerReference`, `beneficiaryReference`, `externalReference`); returns `Promise<never>` — currently always throws (see Gotchas).
- `generateDueCharges(now?)` / `runQueuedCharges(now?)` — subscription cron.

## Business rules
- Ledger types: `purchase | debit | refund | admin_adjustment`. Each balance-changing function writes one ledger row; `recalculateNudge` and `failBundlePurchase` change non-balance state and write no ledger row.
- Nudge levels are recomputed on every deduct/refund and exposed via `recalculateNudge`. **Auto-topup is a v2 hook**: callers that want auto-topup must explicitly invoke `triggerAutoTopup` (e.g. from a route after `deductFlows` raises `InsufficientFlowsError`). It is not fired inside `deductFlows`.
- Subscription charge state: `queued → succeeded | failed`. `failed` rows are retried up to `MAX_ATTEMPTS=3` with `RETRY_BACKOFF_HOURS=24` backoff.
- **A paystack authorisation activates exactly ONE mandate: the one its checkout was started for.** `paystack_payment_requests.mandate_id` (migration 651) records the link; rows written before it are NULL and fall back to the company's newest pending/active paystack mandate. `resolveAuthorisedMandate` / `activateAuthorisedMandate` in `paystackMandateActivation.ts` are the only sanctioned way to do this — do not re-open a company-wide `UPDATE subscription_mandates SET status='active'`.
- **`ux_sub_mandates_company_active` (unique on `company_id WHERE status='active'`) stays the arbiter, and 23505 must never escape.** A company can reach a second completed authorisation (an abandoned checkout's Paystack access code stays payable), and in the webhook a throw rolls the whole event back, leaves `processed = FALSE`, answers 500 and makes every redelivery repeat forever with the card already charged. The activation is a conditional UPDATE inside a SAVEPOINT; the outcomes are `activated | already_active | already_active_other_code | not_pending | blocked`, and every outcome but the first two is a settled state that gets a `log.error` plus a `failure_reason` on the payment request — never a throw. Only `ux_sub_mandates_company_active` is absorbed: the 23505 handler matches the constraint NAME, so any other duplicate reaches the caller.
- A `revoked` / `expired` / `failed` mandate is never resurrected by a payment event (`not_pending`).
- **The pre-651 fallback prefers the company's ALREADY-ACTIVE mandate** so a webhook redelivery resolves idempotently. That is only safe while the code matches: an active row carrying a DIFFERENT `paystack_authorization_code` means a SECOND checkout was paid, and it is reported `already_active_other_code`, never success.
- **`blocked` is never concluded from a stale read.** `verify` and the webhook are two observers of one transition, and the window between them is the outbound `verifyTransaction` call. The conditional UPDATE writing zero rows (or raising the 23505) does NOT identify which row holds the active slot: `reclassifyAfterNoUpdate` re-reads the row and reports `already_active` when the other observer activated it, `blocked` only when it is still pending.
- **`paystack_payment_requests.failure_reason` is read back, so a wrong one is durable and payer-visible.** `GET /api/billing/paystack/mandate/verify` answers `status: 'failed'` + `failureReason` when it is set, so a completed-but-unattached authorisation tells the payer to contact support instead of showing 'pending' forever — but a reason NEVER outranks this reference's own mandate being `active`, and a reason attached to a fallback resolution suppresses the whole mandate view (id, bank, card, ceiling), not just the id: the row it landed on belongs to another checkout.
- `POST /api/billing/flows/purchase` answers **503** when `PAYSTACK_SECRET_KEY` is absent: a missing gateway secret is an outage, not a free top-up. `ALLOW_UNPAID_FLOW_PURCHASE=true` opts a local/dev process into the admin-recorded fallback and is ignored when `NODE_ENV=production` (so every deployed environment ignores it).
- Mandate must be `active` AND have `stitch_bank_account_id` set; otherwise the charge is marked `failed` with `failure_reason='mandate_not_active'` (NB: the file-header comment says `'no_mandate'` — the runtime string is `'mandate_not_active'`, see `subscriptionBillingService.ts:181`).
- Subscription charge state: `queued → submitted | settled | failed | cancelled`. `failed` rows are retried up to `MAX_ATTEMPTS=3` with `RETRY_BACKOFF_HOURS=24` backoff; `runQueuedCharges` claims each attempt with a status- and attempt_count-predicated UPDATE, so two overlapping cron runs cannot both spend the same attempt.
- Mandate must be `active` AND have `paystack_authorization_code` set; otherwise the charge is marked `failed` with `failure_reason='mandate_not_active_or_missing_authorization'`.
- **The subscription period moves only on settlement**, never when a charge is queued. Every period/status write is keyed on `subscription_charges.subscription_id` (migration 624) — a company may hold several subscription rows, and keying on `company_id` alone made one charge move all of them. Charges predating 624 have a NULL `subscription_id` and move nothing.
- After `MAX_ATTEMPTS` failures the subscription is set `past_due` and no further charge is raised for that period. `past_due` currently gates no feature — dunning (suspend / notify) is not implemented.

## Gotchas
- **Recurring debits run through Paystack, not Stitch.** `runQueuedCharges` calls
  `paystackClient.chargeAuthorization` against the mandate's `paystack_authorization_code`; that
  path is live in production. The Stitch `debitFromMandate` stub in `stitchClient.ts` is a
  dependency-boundary guard for the ungranted `client_recurringpaymentconsentrequest` scope and is
  no longer on the subscription path — do not delete it or replace it with a fake success.
- **A charge stuck in `submitted` needs `resolveStaleSubmittedCharges`.** Only a webhook moves a
  charge out of `submitted`; the cron calls the resolver first each run so a charge whose webhook
  never arrived is verified against Paystack after `STALE_SUBMITTED_HOURS` and settled or failed.
- Stitch token cache is process-local; in serverless contexts each cold start re-auths. Acceptable today (low call volume).
- `flowOperationCatalog` is `as const satisfies Record<...>` — adding a new op code MUST update the type-narrowed map; do not push to it dynamically.
- The subscription lifecycle is covered by `tests/integration/k-033-*.int.test.ts` and `k-034-*.int.test.ts` (28 cases against the production schema, Paystack mocked) plus `tests/unit/services/billing/` and `tests/unit/api/admin-subscription-cancel-at-period-end.test.ts`. The Flow wallet and Stitch paths are still uncovered — do not read the subscription coverage as module-wide.

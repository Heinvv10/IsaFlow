## Recent changes

- 2026-10-12 (migration 889): `dimensionBankSync.ts` MIRRORS a journal's tags onto the bank row allocated to it (`bank_transactions.matched_journal_line_id` → its STANDING journal: `status='posted' AND reversed_at IS NULL AND reversal_of_id IS NULL` and no POSTED entry naming it in `reversal_of_id` — a reversal never changes status, the service stamps `reversed_at` and posts a contra; a re-reversed chain's original keeps `reversed_at` and is skipped too; **named limit, fails closed:** in J → C → D (D reverses C) the head D stands but has a `reversal_of_id`, so J, C and D are all skipped — chain parity lives in `shared/journalInForceAsAt` as a recursive walk with `$1/$2` placeholders that cannot be spliced into this static fragment, and is not hand-rolled; a bank row CAN reach D through the real manual MATCH endpoint (`matchTransaction` / `assertMatchTargets` accept a re-reversed chain); it is then neither synced nor mirrored and the Banking list shows the row's OWN tags (blank if none) although D is tagged — no wrong write or display, it just does not follow D). **Mirror semantics (Hein): the bank row's cc1/cc2/bu equal the journal's agreed set, NULLs included — a journal tagged CC1-only BLANKS the row's CC2 and BU, intended.** The agreed set is taken over the journal's DIMENSION LINES: every line but the bank leg that is not on a control account (`isControlSubtype`: bank, cash, card, AP, AR, VAT, payroll clearing) — one rule, `journalDimensionSetSql.ts`, shared by the sync and the Banking list (`DIMENSION_JOINS`) so the screen and the sync cannot disagree. A VAT-bearing allocation to one expense is ONE set; two expenses in two projects, or one tagged and one not (a partial tagging), are a split: no sync, the screen says "Split". Write-through (`applyDimensionTags`, the batch's journals): a journal whose tags were all removed agrees on (NULL, NULL, NULL), so the bank row is cleared. Back-fill (`applyBankSyncBatch`, a date window): a journal carrying no dimension at all (supplier payment = AP + bank; an untagged expense) is left alone — the bank row's own tags are all it has. `sync_bank_dimensions` dry run lists EVERY row where a held value would become NULL (`would_blank`, per-row `blanks`) and the total; a live run changes at most `MAX_BANK_SYNC_ROWS` (2000) rows (`BankDimensionSyncRefusal`, code `BANK_DIMENSION_SYNC_REFUSED`: narrow the window). The control-account test in SQL (`isControlSubtypeSql`) uses JS's whitespace set, not btrim's, so it equals `isControlSubtype` (NBSP, line terminators, Unicode spaces, BOM). A dry run's sample and cut are the EARLIEST rows of the window (`ORDER BY transaction_date, id`); the live path locks in `ORDER BY id`. The live path locks the candidate rows (`FOR UPDATE OF bt ORDER BY bt.id`) and writes each only while it still holds the old values it was planned from; a short write throws so the registry's savepoint rolls the whole batch back. A sync batch records its window (`sync_date_from/to`, 889): an idempotency key that names a batch of the other kind, or a sync of another window, is refused (`assertKeyIsFor`). The candidate read runs under `withBoundedStatements` (statement_timeout tightened to 20s, never loosened past the caller's; JIT off; both restored): a read or lock wait that outruns it is cancelled as a `BankDimensionSyncRefusal` (narrow the window), so a bad plan cannot hang a request. Measured: 2001 candidate rows 23ms (no stats, as RLS app_user), 63ms beside 100k other-company journals; the Banking list's `DIMENSION_JOINS` adds ~25ms per 2000 rows scanned. Old/new per bank row in `dimension_tag_batch_bank_rows`; `planTagBatchReversal` refuses on bank-row drift and returns the bank-row count beside the line count, `applyTagBatchReversal` restores them. Dimension columns only — trigger 675 guards none of them. The delete / move guards (`costCentreUsageGuard`, `businessUnitService`, `countCc2Carriers`) count an un-reversed batch's `dimension_tag_batch_bank_rows.old_cc1_id / old_cc2_id / old_bu_id` as they count `dimension_tag_batch_lines.old_*` (reversal restores the id onto the bank row, behind the 878 FK). `planTagBatchReversal` locks the batch's journal LINES (`FOR UPDATE ORDER BY id`) and then its bank rows (`lockBatchBankRows`, `ORDER BY bt.id`, the sync's order) before its drift checks, inside `withBoundedStatements`: tagging writes lines then bank rows, so every path takes lines before bank rows (no 40P01 between a tag and a reversal), and a lock wait is cancelled as a `BankDimensionSyncRefusal`. `withBoundedStatements` (`boundedStatements.ts`, split from `dimensionBankSync.ts` for the 300-line cap) restores statement_timeout and jit on every path, a thrown error included; a restore that fails because the transaction is already aborted (25P02) is logged at debug, any other restore failure at warn. `planDimensionTags` locks its lines `ORDER BY jl.id` and the reversal does the same, so every path takes lines lowest id first, then bank rows lowest id first. Not handled (decided): a bank row whose journal later BECOMES a split keeps its stale own tags (and the list shows them, the bank row's own tags win).

# src/modules/accounting/services/gl/dimensions

## Purpose

The CC1 / CC2 / BU analysis dimensions (dimensions plan, Phase 1; Lew's ledger
brief §5.3–§5.5). **CC1 = FNO / client** (`cost_centres.cc_type 'cc1'`),
**CC2 = project** (`cc_type 'cc2'`, `parent_id` → its CC1, or → a programme CC2
whose parent is the CC1), **BU = function** (`business_units`, with `division`).
The canonical line columns are `gl_journal_lines.cc1_id / cc2_id / bu_id`
(migration 285); documents carry the same three (migration 870). The legacy
`cost_center_id` / `project_id` stay readable; new code writes cc1/cc2/bu.

## Caller contract

- `applyJournalDimensionPolicy` runs inside `createJournalEntry` for every NEW
  journal (`dimensionAssignmentMode` 'new-assignment'): settlement / receipt /
  transfer / VAT-payment sources (`NO_DIMENSION_SOURCES`) with any dimension are
  REFUSED, and CC1 is DERIVED from CC2. Reversals and reclassifications run in
  'historical-copy' mode and skip it — they copy history.
- No query is sent unless a line names a CC2 (derivation) or a dimension at all
  (resolution, customer FNO, document validation). Existing callers that pass no
  dimensions see no extra round trip.
- Every refusal is a `DimensionRefusal` (code `DIMENSION_REFUSED`, in MCP's
  `REFUSAL_CODES`), raised from reads before any write.

## Business rules

- **A draft edit keeps what it does not send.** When a draft's lines are
  replaced (customer invoice PUT, `update_supplier_invoice`) a key sent wins and
  null clears it; a key left out keeps the value EVERY stored line shares, and
  is refused (`DimensionRefusal`, a 400 / tool error) when they differ — a
  replacement line cannot be matched to its stored line. A CC2 sent leaves CC1
  to derivation. The digest covers all three (migration 873).
- **Derived never typed (§5.5).** A CC1 that conflicts with the CC2's FNO is
  refused, never resolved either way. On revenue the FNO comes from
  `customers.default_cc1_id`; a project under another FNO is refused.
- **Settlements carry none (§5.3).** Bank allocation stamps dimensions on the
  cost/revenue line only — never bank, AP, AR, VAT or payroll clearing
  (`isControlSubtype`). Explicit input there is refused; card defaults
  (`gl_accounts.default_cc1_id / default_cc2_id / default_bu_id` on the bank
  account) are simply not applied.
- **Transaction beats default, default beats blank**, per dimension; a CC2 on
  the transaction is never paired with the card's default CC1.
- **Tagging changes dimensions only.** `dimensionTagApply` is the one place
  (besides the account merge and the late-claim split) that UPDATEs
  `gl_journal_lines`, and only `cc1_id / cc2_id / bu_id`, only on POSTED lines
  (a draft manual journal's approval digest hashes its dimensions). Unlike a
  reclassification this moves no figure, so the TB, AFS and VAT201 reproduce
  exactly; each batch keeps every line's old values and is reversible. A line in
  a closed period is allowed and the batch is flagged `is_restatement` (§8.4).
  The census in `manualJournalApprovalCensus.test.ts` pins this.

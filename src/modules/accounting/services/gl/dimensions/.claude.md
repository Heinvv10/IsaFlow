# src/modules/accounting/services/gl/dimensions

## Purpose

The CC1 / CC2 / BU analysis dimensions (dimensions plan, Phase 1; Lew's ledger
brief §5.3–§5.5). **CC1 = FNO / client** (`cost_centres.cc_type 'cc1'`),
**CC2 = project** (`cc_type 'cc2'`, `parent_id` → its CC1, or → a programme CC2
whose parent is the CC1), **BU = function** (`business_units`, with `division`).
The canonical line columns are `gl_journal_lines.cc1_id / cc2_id / bu_id`
(migration 285); documents carry the same three (migration 870). The legacy
`project_id` stays readable; new code writes cc1/cc2/bu. The legacy line
`cost_center_id` is read by NO report (PR #688 round 2). Writers that take a
cost-centre pick put it in its slot with `costCentrePick.placeCostCentres`
(round 3) and never write the legacy column; a historical copy carries
cc1/cc2 exactly as stored.

## Caller contract

- `applyJournalDimensionPolicy` runs inside `createJournalEntry` for every NEW
  journal (`dimensionAssignmentMode` 'new-assignment'): settlement / receipt /
  transfer / VAT-payment sources (`NO_DIMENSION_SOURCES`) with any dimension are
  REFUSED, and CC1 is DERIVED from CC2. Reversals and reclassifications run in
  'historical-copy' mode and skip it — they copy history.
- No query is sent unless a line names a CC2 (derivation) or a dimension at all
  (resolution, document validation) — except the one customer read every
  revenue-line writer makes to store the customer's FNO (2026-10-08).
- Every refusal is a `DimensionRefusal` (code `DIMENSION_REFUSED`, in MCP's
  `REFUSAL_CODES`), raised from reads before any write.

## Business rules

- **A document posts what it stores (873).** Every revenue-line writer stores
  the customer's FNO at save (`deriveRevenueDimensions` always applies it;
  `revenueLineDefaults` for writers with no dimension source), so the approval
  digest covers it. Every document posting passes `POST_AS_STORED`
  (historical-copy), so createJournalEntry copies the stored dimensions and
  never re-derives. APPROVING (from draft / pending_approval) refuses, "re-save
  the draft", a line posting would once have added a CC1 to (customer FNO, or
  the project's FNO after a re-parent), a stored CC1 its project contradicts,
  or an inactive / foreign master. A document already past draft (Post to GL,
  the backfill route) posts exactly what it stores and refuses nothing.
- **A draft edit keeps what it does not send.** When a draft's lines are
  replaced (customer invoice PUT, `update_supplier_invoice`) a key sent wins and
  null clears it; a key left out keeps the value EVERY stored line shares, and
  is refused (`DimensionRefusal`, a 400 / tool error) when they differ — a
  replacement line cannot be matched to its stored line. A CC2 sent leaves CC1
  (or clears one) to derivation. On a customer change a CC1 equal to the old
  customer's FNO is re-derived for the new one. The digest covers all three (873).
- **Derived never typed (§5.5).** A CC1 that conflicts with the CC2's FNO is
  refused, never resolved either way. On revenue the FNO comes from
  `customers.default_cc1_id`; a project under another FNO is refused.
- **Settlements carry none (§5.3).** Bank allocation stamps dimensions on the
  cost/revenue line only — never bank, AP, AR, VAT or payroll clearing
  (`isControlSubtype`). Explicit input there is refused; card defaults
  (`gl_accounts.default_cc1_id / default_cc2_id / default_bu_id` on the bank
  account) are simply not applied.
- **Transaction beats default, default beats blank**, per dimension; a CC2 on
  the transaction is never paired with the card's default CC1.
- **Tagging changes dimensions only.** `dimensionTagApply` is the one place
  (besides the account merge and the late-claim split) that UPDATEs
  `gl_journal_lines`, and only `cc1_id / cc2_id / bu_id`, only on POSTED lines
  (a draft manual journal's approval digest hashes its dimensions). Unlike a
  reclassification this moves no figure, so the TB, AFS and VAT201 reproduce
  exactly; each batch keeps every line's old values and is reversible. A line in
  a closed period is allowed and the batch is flagged `is_restatement` (§8.4).
  The census in `manualJournalApprovalCensus.test.ts` pins this.

## 2026-10-08 — master edit / delete

- `dimensionMasterEdit` refuses, from reads: a parent on a CC1; a parent loop (itself or a
  descendant); an inactive or FNO-less parent; a code or alias that is another centre's code or
  alias; deactivating a node with ACTIVE children; reactivating under an inactive parent.
- **A CC2 (or a programme with its subtree) cannot move to another FNO while anything carries it**
  (`costCentreUsageGuard.countCc2Carriers`: journal lines, bank lines, invoice / credit-note items,
  account defaults, un-reversed tag-batch `old_cc2_id`). Each of those stored the CC1 derived when
  it was written; moving the project would leave it wrong. Re-tag first. A rename never needs this:
  lines carry ids, so it re-labels history and moves no figure.
- Delete = `assertCostCentreUnused` (counted). The tag-batch `old_*` columns have no FK — an
  un-reversed batch would restore the id on reversal — so they are counted too.

## 2026-10-09 — #678 review

- **One writer at a time per company.** Every create / edit / deactivate / delete of a cost centre or BU
  (accounting routes, payroll routes, MCP tools incl. dry_run) first takes
  `core/dimensionMasterLock.lockDimensionMasters` — `pg_advisory_xact_lock` on
  `'dimension-master:' || company_id`, refused outside a request transaction. Never `FOR UPDATE` on cost_centres:
  it would block every journal insert's FK key-share check. Journal posting does not take the lock, so a CC2
  carried by a line committed during a move is still possible (the move counts carriers from a snapshot).
  That race is DETECTED, not locked (Hein): the `project_fno_mismatch` integrity check
  (`gl/integrityChecks/dimensionChecks.ts`, MCP `data_integrity_checks`) flags such a carrier: posted journal
  lines, un-allocated bank lines, issued invoice lines and credit notes (see its header for exactly what).
- **The payroll routes are the same writer.** `/api/payroll/cost-centres` POST and `[id]` PATCH / DELETE go
  through `planCreate` / `planUpdateDimensionCostCentre` (parentId is a UUID; a centre with a parent is created
  as a CC2; PATCH / DELETE on an id that is not this company's is a 404). There is no other writer of
  `cost_centres` in `src/`.
- A plan that changes nothing returns `changed: []` and apply writes nothing; routes and MCP tools both answer
  success (an idempotent toggle; MCP `nothing_changed: true`, not billed).
- A parent re-sent unchanged is kept as it is (inactive, or reaching no FNO); only a NEW parent is checked. The
  "under an inactive parent" check applies to a reactivation only.
- Deactivation is refused while `customers.default_cc1_id`, `gl_accounts.default_cc1/cc2_id`,
  `supplier_coding_rules.default_cost_centre_id` (BU: `gl_accounts.default_bu_id`) name it, with the counts.
- References: id, then code ignoring case, then alias. A code that matches MORE than one centre — two case
  variants, or a CC1 and a CC2 — is refused even when one matches exactly: send the id, or the `cc_type`
  (update / delete plans and `update_cost_centre` / `delete_cost_centre` take it). BUs: send the id. A rename
  is clash-checked whenever the code changes at all (a case-only rename too). (#683 round 2)
- Applies write inside their own savepoint and turn a 23505 into the refusal; deletes run the DELETE in a
  savepoint and turn the 23503 into "used by other records". Migrations 878 (bank) and 882 (journal) give
  the cc1/cc2/bu columns RESTRICT FKs (NOT VALID; no DROP; one big table per file, so neither holds one while
  waiting on the other); 879 indexes the bank columns. `payroll_employee_history` is NOT counted by the delete guard: display-only text, and counting
  it made any ever-assigned centre undeletable. MCP delete dry_run runs the real DELETE in a savepoint that is
  always rolled back (`core/rolledBackSavepoint`), so it meets the same FKs; a no-op MCP update succeeds
  (`nothing_changed`), as the routes do.

# src/modules/accounting/services/gl/reclassification

## Purpose

Move posted amounts from one GL account to another, as one reversible batch.
Behind `propose_reclassification` (read) and `post_reclassification_batch`
(write) in `src/lib/mcp/tools/`.

## The constraint the whole module is built around

**A reclassification NEVER mutates a posted line.** For each source line it posts
a PAIR — a contra on the source account and the same amount re-applied to the
target — and leaves the original exactly as posted.

```
original   DR 49775627 Unallocated Expense   1,000
contra     CR 49775627 Unallocated Expense   1,000
applied    DR 5100     Materials & Supplies  1,000
```

`UPDATE gl_journal_lines SET gl_account_id = …` produces the same closing
balances and destroys three things: a trial balance somebody signed stops
reproducing, the original classification is gone from the audit trail, and there
is nothing to reverse — the reclassification itself becomes invisible. The pair
IS the record that it happened, and it is what makes the batch undoable through
the ordinary `reverse_journal_entry` path rather than through a bespoke un-edit.

Nothing in this directory issues an UPDATE or a DELETE against
`gl_journal_lines`. If a change here wants to, that is the signal to stop.

The mirror is direction-agnostic by construction (the contra swaps debit and
credit), so a credit-balance move needs no branch and cannot get one wrong.

## Caller contract

- `plan.ts#planReclassification` is the ONE entry point for both tools, and is
  entirely READ-ONLY. That is what makes the dry run honest: every row-state
  guard the live path runs has already run before the two diverge, and only the
  write itself is skipped.
- `post.ts#postReclassBatch` is the only writer. It has no try/catch anywhere:
  `registry.call()` gives a write tool ONE savepoint which unwinds on a THROW,
  so any `catch → toolError` after the first write would RELEASE it and let the
  transport commit a half-moved account.
- A REFUSAL is about the REQUEST (`ReclassRefusal`, rendered as a pre-write
  `toolError`); a SKIP is about the DATA (`ReclassSkip`, one line, never costing
  the rest of the batch).
- `company_id` is on every query. `gl_journal_lines` has no composite
  `(id, company_id)` key, so an id-only lookup would read across tenants.

## Business rules

- **Skip reasons**, machine-stable, in the order they are reported:
  `entry_reversed`, `reclassification_contra`, `already_reclassified`,
  `zero_amount`, `vat_period_locked`, `source_period_missing`,
  `source_period_closed`.
- **Periods.** With no `posting_date`, one journal per distinct source entry
  date — period-neutral, and every line whose own period is CLOSED is skipped
  because a closed period cannot be posted into. With a `posting_date`, ONE
  journal on that day; nothing is skipped for a closed source period, and the
  charge moves between periods. The posting date's own period is validated
  pre-write, `no_period` and `closed` getting different messages because the
  remedies differ.
- **`fiscal_period_id` is asserted non-null** on every journal before it is
  recorded. `createJournalEntry` leaves it NULL for a date no period covers, and
  `postJournalEntry` skips its closed-period check behind `if
  (entry.fiscalPeriodId)` — so such an entry POSTS, permanently outside the trial
  balance, the VAT201 and the AFS.
- **VAT locks bind only when the move touches a VAT control account**
  (`vat_input` / `vat_output`). A move between two ordinary expense accounts
  changes no box on a return already filed.
- **`is_active` is not a filter on any figure query** (it is a picker flag), but
  BOTH accounts must be active to be POSTED to — a deactivated account refuses
  every posting, so that is a request-level refusal, not a per-line skip.
- **The contra leg of an earlier reclassification is never a candidate** —
  moving it moves the correction, not the amount. Identified as
  `(journal_entry_id in reclassification_batch_lines) AND (account = that
  batch's source_account_id)`, not by a recorded line id: `createJournalEntry`
  returns no line ids and lines in one entry share a `created_at`. The TARGET leg
  IS a candidate: an amount moved onto an account may be moved on again.
- **A reversed reclassification frees its source lines again**, or a corrected
  mistake would be permanently unfixable.
- **`source` is `auto_adjustment`**, not a new value. `gl_journal_entries.source`
  is CHECK-constrained, and widening it takes an ACCESS EXCLUSIVE lock and a full
  validation scan on the busiest table in the schema.
- **The impact's two sides are independently derived.** Both are full
  aggregations over the same window — the second with the moved lines projected
  onto the target — folded by the ONE owned classifier
  (`gl/accountClassification#aggregateFigures`). `after = before + delta` would be
  a tautology. The `before` side is then compared band by band against
  `financialFiguresService`, and a disagreement surfaces as the
  `basis_disagreement` warning. **That check is necessary and not sufficient:** it
  proves this query has not drifted from the owning service; nothing independent
  computes the AFTER side, so read the journals, not only the delta.
- **`universeTotal` is its own `COUNT`**, never `movable.length +
  skipped.length` — a universe synthesized from the quantities `buildEnvelope`
  checks it against cannot fail, and `scripts/ci/check-self-defining-universe.sh`
  is a blocking gate on that shape.
- **`grossMoved`/`netMoved` are DEBIT-POSITIVE raw ledger movement**;
  `account_movement` is normal-balance signed. A credit-side move therefore shows
  a negative `netMoved` against a positive movement on a revenue target.

## The caveat this module is obliged to state

On the Velocity Fibre books, 36 of the 37 unclassified expense accounts are NOT
misfiled — `COS - Direct Material - EX2001`, `COS - Sub-Contractors - EX2005`,
`Salaries & Wages - EX4000` carry the right amounts under the right names and
merely lack an `account_subtype`. Moving them onto a generic target collapses
Direct Material, Sub-Contractors and Wayleave into one line and destroys analysis
that exists today, while SETTING THE SUBTYPE achieves the reporting goal and
moves nothing.

`warnings.ts` is therefore load-bearing, not copy. `subtype_remedy_available`
fires on exactly that shape; `collapses_named_accounts` when the target already
carries value from elsewhere; `no_profit_and_loss_effect` when every band is
identical before and after — which is what the live `49775627 → 5100` move
actually is: 414 lines and R11.3m moved, no reported figure changed, and the
source account's name lost.

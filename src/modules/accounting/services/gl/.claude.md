It is `null` under a line-level filter (`sources`/`minAmount`/`search`), because a running total over a subset of an account's lines is not a balance the account ever held; account-level filters preserve it. `balanced` is `null` under ANY filter. ## Caller contract
Invoked by `withAuth`-wrapped API routes in `pages/api/accounting/gl/*` and by every posting service in AR/AP/bank/payroll/expense/FAR. Every public function takes `companyId` as first arg.

## Main function signatures
- `createJournalEntry(companyId, input, userId, meta?): Promise<JournalEntry>` — draft with lines (calls `validateJournalEntry`).
- `postJournalEntry(companyId, id, userId): Promise<JournalEntry>` — balance + period guards, UPDATE status → posted.
- `reverseJournalEntry(companyId, id, userId, opts?: { postingAgent?, reversalDate? }): Promise<ReversalEntry>` — mirror entry, original marked reversed. `ReversalEntry` is `JournalEntry & { foreignDimensionDroppedLines }`: the contra drops a project/cost-centre/business-unit id this company does not own rather than refusing the reversal (`reversalLines.ts`). `opts.postingAgent` stamps the CONTRA; omit it and the contra keeps `defaultHumanMeta(userId)` (`human:<userId>`). Automated callers must pass it or their correction is invisible to every `posting_agent` review surface.
- `getTrialBalance(companyId, fiscalPeriodId, costCentreId?): Promise<TrialBalanceRow[]>` — flat array; API wraps as `{ rows, totalDebit, totalCredit }`.
- `getChartOfAccounts(companyId, includeInactive?)`; `createAccount / updateAccount / deleteAccount`.
- `closePeriod / lockPeriod / reopenPeriod / closeYear(companyId, fiscalYear, userId)`.
- `getSystemAccount(key, companyId)` / `getSystemAccountId` — resolves via `account_subtype`; `clearSystemAccountCache(companyId)` after COA mutations.

## Business rules
- Posting runs under `withTransaction` — balance check (Σ debits = Σ credits) + fiscal-period open check atomic with UPDATE.
- Period state machine: `open → closed → locked`; only `open` accepts postings. `reopen` requires recompute.
- BL-13 / mig 329: `gl_journal_lines` has own `company_id`; every query filters both `je.company_id` AND `jl.company_id`.
- JE `source` has a CHECK constraint — add new values (e.g. `auto_expense_claim` mig 422) via migration.
- Evidence: header stamps `posting_agent` = `human:<userId>` or `ai:<agent>` + optional `source_document_id` → `documents.id`. Do NOT pass an AR invoice/payment id as `sourceDocumentId` (2026-04-24 fix).
- `journalEntryService.ts` is a facade only — add new logic to `journalEntryCrudService` or `journalEntryPostingService`.
- `postJournalEntry('')` (empty userId) silently resolves to zero-UUID system user (legacy pattern in 10 services).
- Year-end closing entry: every P&L account with a non-zero net balance, plus retained earnings, in one tx; locks all periods. **The SIDE of each line comes from the SIGN of the net balance, never from the account type** — a contra revenue account (net debit) closes with a CREDIT. `netIncome` of exactly zero appends NO retained-earnings line (a 0/0 line is illegal), and a dormant year writes no journal at all while still locking the periods.
- The year-end close reads `findClosingJournal` BEFORE its dry-run return, so a preview of a closed year says `alreadyClosed` with the existing journal instead of the empty journal a DORMANT year shows (K-113 — the two are otherwise byte-identical, because the first close is what flattened the P&L). A `year_end` header that is NOT posted (reversed, or draft) is neither: the year is open in substance, but `uq_gl_je_company_entry_number` is unique on `(company_id, entry_number)` with no status predicate and the closing number is the fixed `YE-<year>`, so it cannot be closed again while that row exists — hence the typed `closing_journal_not_posted` refusal rather than a false `alreadyClosed` or a raw 23505. `CloseYearResult.periodsLockedInYear` is a COUNT — of the periods locked in the year NOW, never a literal and never "locked by this call": an already-closed re-run locks nothing and still reports twelve, which is why the MCP tool derives its own `periods_locked` from `alreadyClosed`.
- `yearEndJournalPoster.postClosingJournal` INSERTs at `status = 'posted'`, so `createJournalEntry`'s validation never runs over it and `trg_gl_je_balanced` (BEFORE UPDATE only) never fires for it. It therefore calls `validateJournalEntry` itself, before the transaction opens. **That call is the reason migration 627 may admit `source = 'year_end'`; do not remove it without putting the value back on the dead list in `tests/unit/services/glEntrySourceConstraint.test.ts`.** It deliberately does NOT apply `assertNoInactiveAccountLines`: closing a withdrawn account is how its balance is zeroed, and the equity side is already covered because `systemAccountResolver` only caches `is_active = true` accounts.

- **Known limit (R-035 PR2, authors):** bills that existed before migration 712 record only their CREATOR as author. Edits made before 712 were never recorded and are not reconstructed (no seeding — there is no source to seed from), so such an editor may approve that bill until their next digest-moving edit records them. Every edit from 712 on is recorded.
- The author refusal names an approval path only when one exists: it counts the other members of the demanded rank who authored nothing and did not raise the request; when none remain it mentions the requester only if they hold the rank and authored nothing; if the DECIDER is the only member of the rank (and enforcement is on) it names the sole-approver route — reject, submit it yourself, approve your own request (assertMayDecide's Q2 exception does not look at authorship; tested end to end); otherwise it says no eligible approver remains (cancel and re-enter the bill, or have someone of the rank who did not author it approve).

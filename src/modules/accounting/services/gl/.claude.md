## Caller contract
Invoked by `withCompany`-wrapped API routes in `pages/api/accounting/gl/*` and by every posting service in AR/AP/bank/payroll/expense/FAR. Every public function takes `companyId` as first arg.

## Main function signatures
- `createJournalEntry(companyId, input, meta?): Promise<JournalEntry>` — draft with lines (calls `validateJournalEntry`).
- `postJournalEntry(companyId, id, userId): Promise<JournalEntry>` — balance + period guards, UPDATE status → posted.
- `reverseJournalEntry(companyId, id, userId, opts?: { postingAgent? }): Promise<JournalEntry>` — mirror entry, original marked reversed. `opts.postingAgent` stamps the CONTRA; omit it and the contra keeps `defaultHumanMeta(userId)` (`human:<userId>`). Automated callers must pass it or their correction is invisible to every `posting_agent` review surface.
- `getTrialBalance(companyId, fiscalPeriodId, costCentreId?): Promise<TrialBalanceRow[]>` — flat array; API wraps as `{ rows, totalDebit, totalCredit }`.
- `getChartOfAccounts(companyId, includeInactive?)`; `createAccount / updateAccount / deleteAccount`.
- `closePeriod / lockPeriod / reopenPeriod / closeYear(companyId, fiscalYear, userId)`.
- `getSystemAccount(key, companyId)` / `getSystemAccountId` — resolves via `account_subtype`; `clearSystemAccountCache(companyId)` after COA mutations.

## Business rules
- Posting runs under `withTransaction` — balance check (Σ debits = Σ credits) + fiscal-period open check atomic with UPDATE.
- Period state machine: `open → closed → locked`; only `open` accepts postings. `reopen` requires recompute.
- BL-13 / mig 329: `gl_journal_lines` has own `company_id`; every query filters both `je.company_id` AND `jl.company_id`.
- JE `source` has a CHECK constraint — add new values (e.g. `auto_expense_claim` mig 422) via migration.
- Evidence: header stamps `posting_agent` = `human:<userId>` or `ai:<agent>` + optional `source_document_id` → `documents.id`. Do NOT pass an AR invoice/payment id as `sourceDocumentId` (2026-04-24 fix).
- `journalEntryService.ts` is a facade only — add new logic to `journalEntryCrudService` or `journalEntryPostingService`.
- `postJournalEntry('')` (empty userId) silently resolves to zero-UUID system user (legacy pattern in 10 services).
- Year-end closing entry: revenue (credits) + expense (debits) → retained earnings in one tx; locks all periods.

- Continuous close reads bank work queues by `bank_transactions.status`, not by a boolean. There is no `matched` or `gl_account_id` column and `'pending'` is not a legal status: the CHECK allows `imported | provisional | allocated | matched | reconciled | excluded`. "Awaiting work" is `status = 'imported'`, matching `bankReconciliationService.unmatched_count`.

## Recent changes

- 2026-09-03: **Fiscal periods stopped being calendar-shaped, and the close grew a gate.** `fiscalYearCalendar.ts` is now the ONE place a company's `financial_year_start` becomes period boundaries — pure, no DB, no `Date` arithmetic that crosses a timezone, and following the labelling convention `afs/pisCalculatorService` already used (a fiscal year is named for the calendar year it ENDS in, so FY2027 on a March start runs 1 Mar 2026 → 28 Feb 2027). `createFiscalYear` moved to `fiscalYearCreateService.ts` and reads that. Four things worth not re-deriving. (1) **`resolveFiscalYearStartMonth` follows the layout the company's EXISTING periods use, and only falls back to `financial_year_start`.** Every production company declares a March start and every one of the 288 fiscal periods runs January–December; building the NEXT year on March would interleave two layouts inside one company, which is worse than being consistently wrong — every range report would double-count one span and miss another. Migrating a live tenant's periods is a data correction with its own approval and is explicitly out of scope; making the misalignment VISIBLE is what `list_fiscal_periods.alignment` does. A company with no periods yet — every newly provisioned tenant — gets its own financial year from the first period on. (2) **`FiscalPeriodOverlapError` refuses up front and names the conflicts.** The `fiscal_periods_no_overlap` EXCLUDE constraint would raise 23P01, which surfaces to a caller as an unattributed generic failure. (3) **`ensureFiscalPeriodForDate` derived the fiscal year from `entryDate.slice(0, 4)`** — the CALENDAR year, wrong for ten months out of twelve on a March start. A June 2026 date belongs to FY2027; creating FY2026 builds Mar 2025 – Feb 2026 and leaves the date uncovered, so the journal posts with `fiscal_period_id` NULL and is invisible to the trial balance, the VAT201 and the AFS — the defect migration 501 was written to clean up. It now uses `fiscalYearOfDate`, and returns NULL rather than throwing when the derivation fails, because this runs on every journal write and turning a post that succeeds today into a 500 is the outcome the module exists to avoid. (4) **`fiscalPeriodCloseService.closePeriodWithReadiness`** composes `closePeriod` with `getCloseReadiness` and refuses with the itemised blockers; the UI's advisory close is untouched. A check that could not be COMPUTED (`warn` with reason "Could not compute — check the relevant module.") blocks, because that is exactly the state in which closing unattended is unsafe.
- 2026-09-03: **`yearEndCloseService.ts`** split out of `yearEndService` with a dry run that returns the whole closing journal and an `open_periods` refusal that NAMES the periods rather than counting them. Two latent defects fixed with it: the `retained_earnings_account` lookup read `app_settings` with no `company_id` predicate on a view that HAS that column (zero rows today, so a single configured row would have picked every tenant's equity account), and the retained-earnings account lookup was `LIMIT 1` over `account_code = X OR account_name ILIKE '%retained earnings%'` with no `ORDER BY` — decided by physical row order, the same shape as migration 525. `openingBalanceReadService.ts` is the read side `set_opening_balance` never had: it reports the posted journal and the `gl_accounts.bank_opening_balance` metadata SEPARATELY, because the bank-account editor can write the second with no journal behind it and the disagreement is the finding. A stored `0.00` reads as "not set" — the column defaults to zero rather than NULL and `set_opening_balance` refuses a zero amount.

- 2026-09-02: **`source_record_id` splits "the record behind this journal" off `source_document_id`** (migration 526). Migration 409 gave `source_document_id` an FK to `captured_documents`, which is right for OCR provenance and silently killed two callers that had been using the column as a generic pointer: `createAdjustmentEntry` wrote the reconciliation id and `applyDRCVat` wrote the supplier invoice id, so both threw `fk_gl_je_source_document` on INSERT and neither path could post at all (the bank-recon adjustment action 400'd; it has no UI caller, which is why it went unnoticed). 409 also NULLed the old values, so those links are unrecoverable. `JournalEntryCreateInput.sourceRecordId` is the replacement: POLYMORPHIC and deliberately without an FK, because which table it points at is decided by `source` (`auto_bank_recon` → `bank_reconciliations`, `auto_vat_adjustment` → `supplier_invoices`); one FK cannot express that and a typed column per source grows a column per feature. `sourceDocumentId` now means captured document and nothing else — `pages/api/accounting/journal-entries.ts` checks a caller-supplied one against `captured_documents` SCOPED BY COMPANY before the insert, so another tenant's id reads as invalid rather than linking this company's journal to their document. `glSourceRecordIdDb.test.ts` pins both halves against a real Postgres (accepted on one column, refused on the other).

- 2026-09-02: **`systemAccountResolver` chooses deterministically between duplicate system rows** — a row whose type can carry the subtype (`typeFitsSubtype`, from `glAccountSubtypes.ts`) beats a mistyped one, then newest `created_at`, then id (`preferSystemAccount`); duplicates for a resolved role log an error naming every candidate. It was last-row-wins over an un-ordered SELECT: prod had Velocity Fibre with two `vat_input` system rows (one a LIABILITY "VAT Payable"), Brightsphere with doubled `receivable`/`payable`/`default_expense`, Dotbiz with two `depreciation_expense`; heap order happened to pick the right row everywhere. Migration 525 unflags the 11 losers (subtype → NULL) in those three companies only; deploy integrity check "One system account per role" fails on any duplicate or type-mismatched system row from now on.

- 2026-09-02: `openingBalanceEquityService` — per-company "Opening Balance Equity" system account (subtype `opening_balance_equity`, RESERVED in `glAccountSubtypes.ts` so `subtypeErrorFor` refuses it on user accounts and the resolver's by-subtype lookup cannot be displaced). Created on first use at 3300 (falls through 3310/3320/3390, refuses beyond) under the 3000 header. Seventh close-readiness check `openingBalanceEquityCheck` (`opening_balance_cleared`, advisory warn) reports the account's posted balance at period end; the period cut is a `CASE WHEN je.id IS NOT NULL`, not the LEFT JOIN — a join-side filter still sums the line. Close-run advisory kind `opening_balance_residual`.

- 2026-09-02: `journalEntryListService.listJournalEntriesPage` — agent-facing listing across all accounts with a keyset cursor over `(entry_date DESC, created_at DESC, id DESC)`; one null-safe query instead of `getJournalEntries`'s four branches, and it includes `auto_%` sources. The cursor carries `created_at` as Postgres TEXT (`::TEXT`), never a JS Date — millisecond truncation skips same-millisecond rows. `status='reversed'` means `reversed_at IS NOT NULL`, as in the CRUD service.
- 2026-08-31: **`inputVatDenial` is ADVISORY, and the flag is `gl_accounts.vat_input_denied` — NOT `default_vat_code`.** Reusing `default_vat_code = 'none'` as the denial marker conflated two facts: `5800 Insurance Expense` carries that default in production and is standard-rated and CLAIMABLE, so the first cut blocked a legitimate claim. `default_vat_code` says what to default to; `vat_input_denied` says the claim itself is denied. `shouldWarnOnVatCode(flag, requested)` is the pure predicate the SCREENS use — they warn and leave the user's choice alone, because s17(2)(a)(i) lets a vendor who continuously supplies entertainment claim the tax and only the user knows whether that is them. `applyVatDenial` COERCES and is for UNATTENDED callers only: `autoPostRuleLine` is the sole one, and it reports the coercion as `RuleApplyResult.autoPostVatDenied` rather than swallowing it. `resolveVatCodeForAccount` (one id) and `fetchVatDenialFlags` (batched per sweep) are the I/O wrappers; `autoPostRuleLine` treats an ABSENT flag as "look it up here", never as "guard off". The flag is edited per account on the Chart of Accounts screen, so a tenant the migration back-fill wrongly flags clears it in one click. Only `'standard'` is ever denied — s17(2)(a) denies INPUT TAX, it does not un-zero-rate a supply, and `gl_journal_lines.vat_type` feeds VAT201.

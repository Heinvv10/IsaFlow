## Caller contract
Invoked by `withAuth`-wrapped API routes in `pages/api/accounting/gl/*` and by every posting service in AR/AP/bank/payroll/expense/FAR. Every public function takes `companyId` as first arg.

## Main function signatures
- `createJournalEntry(companyId, input, userId, meta?): Promise<JournalEntry>` — draft with lines (calls `validateJournalEntry`).
- `postJournalEntry(companyId, id, userId): Promise<JournalEntry>` — balance + period guards, UPDATE status → posted.
- `reverseJournalEntry(companyId, id, userId, opts?: { postingAgent?, reversalDate? }): Promise<ReversalEntry>` — mirror entry, original marked reversed. `ReversalEntry` is `JournalEntry & { foreignDimensionDroppedLines }`: the contra drops a project/cost-centre/business-unit id this company does not own rather than refusing the reversal (`reversalLines.ts`). `opts.postingAgent` stamps the CONTRA; omit it and the contra keeps `defaultHumanMeta(userId)` (`human:<userId>`). Automated callers must pass it or their correction is invisible to every `posting_agent` review surface.
- `getTrialBalance(companyId, fiscalPeriodId, costCentreId?): Promise<TrialBalanceRow[]>` — flat array; API wraps as `{ rows, totalDebit, totalCredit }`.
- `getChartOfAccounts(companyId, includeInactive?)`; `createAccount / updateAccount / deleteAccount`.
- `closePeriod / lockPeriod / reopenPeriod / closeYear(companyId, fiscalYear, userId)`. Close, lock and close-year queue, after commit, the automatic snapshot and the budgets rolling-forecast roll (`budgets/drivers/budgetRollQueue.ts`, P4 §6); neither can block or roll back the close.
- `getSystemAccount(key, companyId)` / `getSystemAccountId` — resolves via `account_subtype`; `clearSystemAccountCache(companyId)` after COA mutations.

## Business rules
- Posting runs under `withTransaction` — balance check (Σ debits = Σ credits) + fiscal-period open check atomic with UPDATE.
- Period state machine: `open → closed → locked`; only `open` accepts postings. `reopen` requires recompute.
- BL-13 / mig 329: `gl_journal_lines` has own `company_id`; every query filters both `je.company_id` AND `jl.company_id`.
- JE `source` has a CHECK constraint — add new values (e.g. `auto_expense_claim` mig 422) via migration.
- **Journal numbers are serialised per company + year (migration 857).** `generate_journal_entry_number` (BEFORE INSERT, only when `entry_number` IS NULL) takes `pg_advisory_xact_lock(hashtextextended('<company_id>:<year>', 857))` — 64-bit, seed 857 is the namespace — before its MAX(seq)+1, so a second writer waits for the first to commit and mints the next number (it used to mint the SAME number and die 23505 on `uq_gl_je_company_entry_number`). Held to COMMIT (released by a ROLLBACK TO SAVEPOINT taken around it). **The cost, stated plainly:** a burst for one company+year now QUEUES instead of failing — writer k holds a pool connection for the sum of the k-1 transactions ahead of it — and since migration 858 the wait is bounded at 5 s, tighten-only: the trigger lowers `lock_timeout` to 5 s only when the caller's is 0 or longer and puts the caller's value back (55P03; it was unbounded — the app pool sets none). The same lock now numbers eight document types too (858). The lock is a SUPERSET of the old index wait and is taken EARLIER, before the row's pkey and `uq_gl_je_capture_source_document` entries: known residual (brk-jenum A3/A4/A5, no in-app path today) — a writer waiting on another's uncommitted duplicate capture-source document (A3) or duplicate journal id (A4) now holds the number lock, so if the other then numbers a journal for that company+year the pair deadlocks (40P01, the innocent writer can be the victim) where the old code answered the duplicate 23505; and after a committed draft is deleted (A5) a writer waits on any holder where the old code minted the freed number without waiting. Numbers past 99999 keep all their digits (JE-<y>-100000; the old LPAD(…,5) truncated). Explicit numbers (`YE-<year>`, `DEP-…`, imports) skip the trigger and still collide on the index; READ COMMITTED only. The per-route 23505 mappings for this index are now unreachable for generated numbers and were left in place. Tests: `tests/integration/jenum-numbering-{concurrency,route,keys}.int.test.ts`.
- Evidence: header stamps `posting_agent` = `human:<userId>` or `ai:<agent>` + optional `source_document_id` → `documents.id`. Do NOT pass an AR invoice/payment id as `sourceDocumentId` (2026-04-24 fix).
- `journalEntryService.ts` is a facade only — add new logic to `journalEntryCrudService` or `journalEntryPostingService`.
- `postJournalEntry('')` (empty userId) silently resolves to zero-UUID system user (legacy pattern in 10 services).
- Year-end closing entry: every P&L account with a non-zero net balance, plus retained earnings, in one tx; locks all periods. **The SIDE of each line comes from the SIGN of the net balance, never from the account type** — a contra revenue account (net debit) closes with a CREDIT. `netIncome` of exactly zero appends NO retained-earnings line (a 0/0 line is illegal), and a dormant year writes no journal at all while still locking the periods.
- The year-end close reads `findClosingJournal` BEFORE its dry-run return, so a preview of a closed year says `alreadyClosed` with the existing journal instead of the empty journal a DORMANT year shows (K-113 — the two are otherwise byte-identical, because the first close is what flattened the P&L). A `year_end` header that is NOT posted (reversed, or draft) is neither: the year is open in substance, but `uq_gl_je_company_entry_number` is unique on `(company_id, entry_number)` with no status predicate and the closing number is the fixed `YE-<year>`, so it cannot be closed again while that row exists — hence the typed `closing_journal_not_posted` refusal rather than a false `alreadyClosed` or a raw 23505. `CloseYearResult.periodsLockedInYear` is a COUNT — of the periods locked in the year NOW, never a literal and never "locked by this call": an already-closed re-run locks nothing and still reports twelve, which is why the MCP tool derives its own `periods_locked` from `alreadyClosed`.
- `yearEndJournalPoster.postClosingJournal` INSERTs at `status = 'posted'`, so `createJournalEntry`'s validation never runs over it and `trg_gl_je_balanced` (BEFORE UPDATE only) never fires for it. It therefore calls `validateJournalEntry` itself, before the transaction opens. **That call is the reason migration 627 may admit `source = 'year_end'`; do not remove it without putting the value back on the dead list in `tests/unit/services/glEntrySourceConstraint.test.ts`.** It deliberately does NOT apply `assertNoInactiveAccountLines`: closing a withdrawn account is how its balance is zeroed, and the equity side is already covered because `systemAccountResolver` only caches `is_active = true` accounts.

The links an author is derived through must not move: a converted quote is terminal (`updateQuoteStatus` refuses leaving `converted` / `converted_to_order`, 409 `QuoteConvertedError`; both conversion claims refuse a quote already holding a link); an invoiced order and a billed entry cannot be billed again (pinned in `r035-pr4-links`). **Accepted dead end (decision 1):** when every member of the rank authored or raised it — e.g. two owners, one priced the quote and the other converted it — nobody may approve; the customer-invoice refusal (`approvalAuthors` wording, the SI / credit-note text unchanged) says to have the source's author — including whoever set a billed time entry's rate or hours — perform the conversion, run or invoicing themselves, so the other can approve (never "leave it to another member": the invoicer is an author too). KNOWN LIMIT, follow-up for Hein: a SUPPLIER invoice minted from a `recurring_transaction_templates` row is not stamped — doing so changes live supplier-invoice enforcement — so a bill template's author may still approve the bill another user's run minted. The import GUC `isaflow.approval_gate_exempt` is an ordinary setting: a raw-SQL app_user session can set_config it itself and pass both invoice backstops (PR4 review REPRO 2) — the N3 class; it joins the N1/N3 SECURITY DEFINER follow-up for Hein (the exemption, like request/decide, behind a definer function). The legacy "Post to GL" (`customer-invoices-gl.ts`) stays ungated (Q7) and still refuses a draft (R-118). A soft-deleted draft is no document to the gate: approving one under enforcement fails closed at the backstop (500), and its detail GET shows no approval state. Invoices that existed before migration 865 record only their creator as author (a non-uuid `created_by` adds nobody).
- **Known limits (R-035 PR3, credit notes):** a rule or request of the legacy `credit_note` type governs NEITHER `customer_credit_note` nor `supplier_credit_note` and `credit_note` is never enforceable — re-create such rules under the new types before switching enforcement on. Notes that existed before migration 862 record only their creator as author (as bills before 712). The supplier merges (`supplier-merge.ts`, `duplicateMergeService.mergeSuppliers`) do not move credit notes at all (pre-existing), so they stamp none; the customer merge moves and stamps them.
- **Known limit (R-035 PR2, authors):** bills that existed before migration 712 record only their CREATOR as author. Edits made before 712 were never recorded and are not reconstructed (no seeding — there is no source to seed from), so such an editor may approve that bill until their next digest-moving edit records them. Every edit from 712 on is recorded.
- The author refusal names an approval path only when one exists: it counts the other members of the demanded rank who authored nothing and did not raise the request; when none remain it mentions the requester only if they hold the rank and authored nothing; if the DECIDER is the only member of the rank (and enforcement is on) it names the sole-approver route — reject, submit it yourself, approve your own request (assertMayDecide's Q2 exception does not look at authorship; tested end to end); otherwise it says no eligible approver remains (cancel and re-enter the bill, or have someone of the rank who did not author it approve).
- **System roles and sub-accounts (Hein, 2026-10-01 / 2026-10-02): one split, `roleTargetRules.isBalanceSheetType` (asset / liability / equity; `HOLDER_NO_CHILDREN_TYPES` in SQL).** A BALANCE-SHEET role (bank, receivable, payable, VAT, retained earnings, OBE) may neither be held by an account that has sub-accounts nor be ASSIGNED to one; an INCOME-STATEMENT role (default revenue, cost of sales / `default_expense`, other income, admin expense…) may do both. `roleBarringChildren` (may this holder gain a child) and `roleTargetRefusal` (may this account take the role — the save, the COA import's role map, reactivation into an empty role) both ask it; callers pass the raw `hasChildren` and never mask it themselves.

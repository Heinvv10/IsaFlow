## Business rules
- **Foreign-currency invoices are refused until the FX programme lands (FX PR0, migration 871).** `shared/documentCurrency.resolveDocumentCurrency` (create) / `checkDocumentCurrency` (draft edit): ZAR at a rate ≠ 1 → `EXCHANGE_RATE_INVALID`; any other currency while `companies.fx_documents_enabled` is false → `FOREIGN_CURRENCY_DISABLED`; both 400, pre-write. The DB refuses the same (`fx_document_currency_gate`) and refuses ANY `amount_paid` change on a foreign invoice (`fx_settlement_refusal`). `functional_total` is written by `public.fx_functional(total, rate)` in SQL, never a JS multiplication (`fxConversionCensus` test). Payment links, Paystack checkout and `enableOnlinePayment` refuse a foreign invoice permanently (they charge rands); a gateway receipt that still arrives is banked unapplied with hold `invoice_foreign_currency`.
- **Lock order**: the canonical sequence for every settlement path (bank line → payment → invoices → GL) lives in `bank/.claude.md`. Read it before adding a lock here; a path that takes two of these rows out of sequence deadlocks against one that does not (40P01 → 500).

- **A customer merge leaves the merged account's running credit at or above zero, on EVERY date, whichever customer is the source (2026-11-15, symmetric after review round 1; closes the gap #1354 left).** `customerMergeCredit.assertMergeKeepsCredit` runs inside `mergeInSavepoint`, after every move and before the source is soft-deleted, under the customer locks the merge already holds. It reads the target's REAL rows after the move (`customerCreditDays` through the merge's own `tx`; receipts less refunds, each at its unapplied remainder, cancelled rows out) and refuses when the running credit is below zero on any date (`mergeCreditShortfall`, one pass, whole cents, oldest date first). The verdict cannot depend on direction: A into B and B into A produce the same ledger. An earlier cut judged only the dates the merge lowered and let B into A through where A into B was refused; do not reintroduce it. Consequences: a customer already negative on some date cannot be merged (either way, even with no receipt moved) until the refund no receipt covers is reversed or the receipt it returned is recorded; one side's receipts cover the other's refunds only on or before the refund's date (judged by date, never on the total; a day nets). `CustomerMergeCreditRefusal` is an `ArRequestError` (400) whose error carries the code `CUSTOMER_MERGE_CREDIT_REFUSED`; the routes answer its message only. It names both customers, the first date and the figure, and is thrown inside the merge's savepoint, so the WHOLE merge rolls back before `withAuth` COMMITs the 4xx (digest-proven in `ar-customer-merge-running-credit.int.test.ts`). The recurring mover lives in `customerMergeRecurring.ts` (file cap).
- **Lock census of the merge against the #1354 receipt cancel / application (2026-11-15): no new wait, no new 40P01 cycle.** The credit check adds SELECTs only. The merge takes bank lines (`suggested_client_id` = source) → source receipts → source invoices → both recurring stores → both customers `FOR NO KEY UPDATE` (the only customer wait, `lock_timeout` 5 s), and UPDATEs the bank lines BEFORE the receipts (unchanged from the base: a receipt UPDATE first would hold a row a settlement reaches after its bank line, for rows created after the lock pass). A cancel or application takes bank line → receipt → invoices → the customer TRIED (`SKIP LOCKED`, never waits), then its invoice UPDATEs and journal rows, which the merge never takes; so neither can wait on the other while holding what the other needs. The tried customer lock serialises them: a cancel that committed first is read by the merge's judgement (refused if the cancelled receipt was what covered a moved refund); a merge that committed first makes the cancel's own #1354 judgement refuse it, and an overlap makes the cancel's tried lock fail (retryable `PaymentLockTimeoutError`, 503) (`ar-customer-merge-running-credit.int.test.ts`: both orders held apart by a barrier, plus a staggered race). The cycle #1354 recorded as (2) is unchanged: a merge holding the SOURCE's receipts and waiting for the TARGET customer, against a bulk reversal that holds the target and reaches a later line whose receipt is one of the source's — a retryable 40P01, which the merge answers 409 `CUSTOMER_MERGE_CONTENDED` (`isMergeContention`).
- **Invoice line coding** (migration 874): a line may name a revenue account (this company's, `account_type = 'revenue'`, leaf, active) and a JOB (`projects`: this company's, not cancelled — what Project Profitability, WIP and time read). Its CC1 / CC2 / BU are migration 870's (`gl/dimensions`: resolver, CC1 derived from CC2, the customer's FNO via `customers.default_cc1_id`, `assertDocumentDimensions`). **Two project models, labelled apart (Hein, 2026-10-08):** the job (`project_id`) and the CC2 project (`cc2_id`) both post; the UI calls them "Job (Project Profitability)" and "CC2 project", never two pickers both called "Project"; Hein rules later whether CC2 replaces projects. **Ruling 2026-10-10:** Project Profitability offers BOTH, side by side — `basis: jobs | cc2`, `jobs` (project_id against `projects`) the default on the report route, the MCP `project_profitability` tool and the page; `cc2` reads cc2_id against cost centres. Never COALESCEd, ids never mixed; whether CC2 replaces jobs is still open. Checked before the first write by create (HTTP + MCP single/bulk), draft edit and recurring-transaction templates; quote lines on quote create/update and again at conversion (before its claim); re-checked on the STORED lines by approve (under the row lock, BEFORE the status UPDATE — the account / job rules, then `applyCustomerFno` + `assertDocumentDimensions`, so an FNO set on the customer since that conflicts is a 400, not a 5xx), bulk finalize (a skip, dry run alike) and `postCustomerInvoiceToGL` (before `createJournalEntry`). **One refusal**: `InvoiceLineCodingRefusal`, code INVOICE_LINE_CODING_REFUSED — HTTP 400 with `details.code`, MCP the registered refusal (bulk create prefixes `invoices[i]:`), bulk finalize a skip. A refusal raised by posting AFTER approve's status UPDATE is re-raised as `ArPostingAfterWriteError` (5xx). **Lock race**: the FOR SHARE read of the line accounts can lose to a GL account merge; 40P01/55P03 there → `InvoiceLineAccountLockError`: REST 503 + Retry-After, MCP registered refusal, bulk finalize a retryable skip. **Posting** (`buildInvoiceRevenueLines`): no line names an account, job or CC1 / CC2 / BU → the single `default_revenue` credit of the subtotal, unchanged, carrying the customer's FNO as cc1 when it has one (lines not read); otherwise every line without a CC1 takes the FNO (a different one is refused), and the credit is split BY WEIGHT over (account ?? default_revenue, job, CC1, CC2, BU), residual to the largest group, a negative group (a discount on its own tags) posting as a debit on its own leg; refused if the lines are more than 1c/line off the subtotal or total zero. **Changed from #663's builder** (its tests now pin the new behaviour, `tests/unit/services/documentDimensionPosting.test.ts`): (1) a group netting ≤ 0 used to collapse the whole invoice to ONE line carrying only the FNO, silently dropping every CC2 / BU; (2) items not footing to the subtotal used to post the difference on the last group; (3) rounding went to the last group, now to the largest. `credit` is passed separately from the document subtotal (the FX path). VAT and AR legs untouched.
- **Credit notes and the five tags (874; D1 revised 2026-10-08).** A customer note LINKED to an invoice with a journal debits that JOURNAL's revenue-type legs pro rata (not the lines — pre-874 invoices credited default_revenue whatever their lines said), on all five tags (account, job, CC1, CC2, BU), each leg capped at what it still carries — its net less what the LIVE (approved, not cancelled) earlier notes TOOK, as `credit_note_revenue_allocations` (874) records it: one row per leg taken plus an `is_excess` row, written in the approval's transaction (`recordCreditNoteRevenueAllocations`); a cancelled note's rows stay but stop counting; capacity groups by the referenced invoice journal line's CURRENT account and tags, so an account merge or a `tag_journal_lines` re-tag (both move the line in place) carries it. Notes approved before 874 have no rows and ARE replayed, in approval order — that fallback only; the excess posts UNTAGGED to `default_revenue`. A linked note's OWN header job / CC1 / CC2 / BU are REFUSED (`creditNoteHeaderTags`, CREDIT_NOTE_DIMENSIONS_REFUSED) at create and at approve, before any write — they could never post, and ignoring them would leave the note contradicting the ledger; a stored linked draft carrying one (pre-874 `project_id`, never validated) must be cancelled and raised again. An UNLINKED note posts one `default_revenue` debit carrying its header job (checked: this company's, not cancelled, at create and approve) and CC1 / CC2 / BU (870). Supplier notes (892, 2026-10-13): mirror this on the expense side (`ap/supplierCreditNoteExpenseLines.ts`) — a note LINKED to a bill with a journal CREDITS that journal's legs other than AP / VAT (picked by role: the payable / vat_input accounts, any AP/AR control subtype, the VAT class — not by account type, a bill may debit an asset or COS account) pro rata on all five tags, capped per leg by `credit_note_expense_allocations` (pre-892 notes on the bill replayed); the excess, or the whole net when unlinked or the bill has no journal, goes to the note's own `credit_notes.gl_account_id` (optional, bill-line account rule at create and approve) else `default_expense`. Header CC1 / CC2 / BU are refused on a linked supplier note (CREDIT_NOTE_DIMENSIONS_REFUSED) and posted on an unlinked one. AP debit and the single VAT credit unchanged. Before 892 every supplier note credited default_expense whatever the bill debited (Velocity re-pointed R8.54m off 5100 by journal, 13 Oct 2026); existing rows elsewhere need a reclassification from `auto_credit_note` lines on default_expense joined to `credit_notes.supplier_invoice_id`. Decided before the journal is written: a leg whose account was deactivated since is debited on default_revenue keeping its tags. Any failure after `createJournalEntry` in `approveCreditNote` is `ArPostingAfterWriteError` (5xx).
- **Per-line VAT on customer invoices (migrations 1008 columns, 1009 digest; the readers, and since 2026-11-20 the writers: see "Per-line VAT WRITERS" below).** `customer_invoice_items.vat_type` + `tax_amount` (both or neither, CHECK) and `customer_invoices.amounts_are` (`exclusive` | `inclusive`, NULL = exclusive). **`amount` is the line's NET (ex-VAT) on EVERY invoice, typed or legacy, inclusive or exclusive** (every reader of `cii.amount` assumes it): a typed line's `tax_amount` is its VAT and its gross is amount + tax_amount. `amounts_are` says how `unit_price` reads (VAT-inclusive as entered on an inclusive invoice), never what `amount` means; so qty × unit_price ≠ amount on an inclusive typed line, and nothing on the read / approve / post / PDF paths re-prices a stored line from unit_price (the edit form's `editInvoiceLoad` reads an inclusive line's discount off its GROSS, amount + tax_amount; the portal, the detail page and the preview modal head an inclusive invoice's price "incl. VAT" and its amount "excl. VAT"). **Writer conventions (the writers follow them, invoiceLineVatPricing):** an EXCLUSIVE (or unset) invoice stores each rated line's VAT exactly as `vatLineAmounts` gives it (posting refuses a cent off); an inclusive one may differ by a cent (the VAT is backed out of the gross). a typed invoice's header `tax_rate` = the highest line rate (0 when no line is rated); each typed line's `tax_rate` = its type's rate on the invoice date (`shared/vatTypes.vatRatePctOn`). `reports/vatTaxCodeIssues.ts` (a header rate above zero with no VAT is a BLOCKING exception) and `portalInvoiceService.ts` (prints each line's tax_rate) depend on both. A line is TYPED when both are set; an invoice is typed when every line is (`invoiceVatLegs.lineVatShape`). LEGACY (no typed line) posts, prints and reads exactly as before. TYPED: `postCustomerInvoiceToGL` posts DR AR = header total; one revenue leg per (account ?? default_revenue, job, CC1, CC2, BU, VAT type) at the sum of its lines' amount (net), coded with the type; one VAT Output leg per type for the sum of its lines' tax_amount, coded with it; zero legs dropped, a negative group a debit (`typedInvoiceCreditLegs`). **What may post (PR #1648 review):** only `POSTABLE_LINE_VAT_TYPES` = `DOCUMENT_LINE_VAT_TYPES` (standard, zero_rated, exempt); the DB CHECK keeps the full ledger list. A sales line typed reverse_charge, bad_debt or imported would post a coded leg the readers put in field 1 at full base or in no field (vat201NilRatedSupplies reads only zero_rated / export / exempt / no_vat), so the WRITER PR widens this list deliberately, type by type, each with a reader proof. Open point for it: `no_vat` moves no VAT figure per `gl/journalVatLockGuard.lineMovesVatFigure` but counts as exempt in `reports/vat201NilRatedSupplies` (EXEMPT_TYPES); settle that before allowing it. A rated line's tax_amount must equal `vatLineAmounts(amount, type, invoice date).vat` exactly, or be within one cent of it when `amounts_are` is 'inclusive' (the VAT was backed out of a gross; `amounts_are` is read for this tolerance alone); a rated type whose lines carry net but VAT rounding to nothing, or VAT on no net, is refused (a coded base with no VAT leg reaches no field); the header total must be subtotal + VAT. PARTLY typed, an unknown type (`storedVatType`: canonical spelling only, the one reader the poster, PDF and credit-note legs share), a type not postable, an unrated line carrying VAT, a rated line whose VAT is not its own, or lines whose Σ amount / Σ tax_amount / total do not equal the header subtotal / tax_amount / total_amount to the cent (whatever amounts_are says) are refused (`typedLinesProblem`, InvoiceLineCodingRefusal) at approve before its status UPDATE (`storedLinesRefusal`), at bulk finalize (a skip), and at Post to GL before `createJournalEntry`. The three columns are approval content (`approval_document_digest_pre_payroll_951`'s customer_invoice arm; migration 1009 re-bound pending/approved requests as 874 did). Adding `amounts_are` / `vat_type` / `tax_amount` to the PDF model's fields also changes every invoice's shown and draft digests: during the blue/green window the colours compute different ones, and each page open at the switch answers STALE_VIEW once. A linked customer credit note's revenue debit carries the `vat_type` of the invoice journal leg it reverses (merge key includes it). Against a TYPED invoice (every revenue leg coded; `creditNoteTypedSplit.legsAreTyped`) a customer note is PROPORTIONAL ONLY (Hein's ruling, 2026-11-19, replacing four review rounds of inferring the note's rated part from its VAT, each of which found a new stranding edge): R = the invoice's remaining net over EVERY revenue leg (each leg's net less what live earlier notes took, `remainingCarries`); the note's subtotal S must be > 0 and <= R; its debits are pro rata over every leg by remaining net (allocateCreditNote), each on its leg's VAT type, and S = R takes exactly what each leg has left. V = the invoice's remaining VAT (its VAT Output legs less the tax_amount of its live (not draft, not cancelled) earlier customer notes; read only for a typed invoice; `invoiceRevenuePosting.invoiceCreditBasis`). The note's tax_amount must be EXACTLY `requiredCreditNoteVat(R, V, S)`: V = round-half-away(V x S / R) in exact (BigInt) integer cents, which is V itself when S = R; no tolerance, no rate lookup, no date. V < 0 (hand-made data) is refused (a journal is needed). Stranding is impossible: every partial note's VAT is at most V, and the note that brings R to 0 takes exactly V, so R = 0 implies V = 0 (the argument is in the module header; a seeded property test proves it). LIMITATION: the standard lines of a mixed invoice cannot be credited alone until credit notes have lines. Any other note is refused before any write, naming the required VAT (`CreditNoteVatSplitRefusal`, CREDIT_NOTE_VAT_SPLIT_REFUSED: REST 400, an MCP registered refusal, a per-note `vat_split_refused` skip in bulk_approve_credit_notes, which its dry run foresees since #1701); create_credit_note's description says so too. On both the subtotal, rate and VAT figure must be JSON numbers (#1701 round 2: Number() read "" / [] / false as 0), in whole cents, the figure within the subtotal, the rate to at most two decimals (NUMERIC(5,2): 15.005 was stored 15.01; round 8), and a figure and a rate together only when the rate gives the figure: ONE function (`creditNoteRequestMoney.creditNoteMoneyProblem`) for both, the same words with each surface's own field names (round 3).

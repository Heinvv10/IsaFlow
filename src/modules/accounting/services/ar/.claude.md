## Caller contract
Invoked by `withCompany`-wrapped API routes in `pages/api/accounting/ar/*` and `pages/api/portal/*`. Every public DB function takes `companyId` first (portal functions additionally verify `client_id` against the calling company).

## Main function signatures
- `createQuote(companyId, input, userId?) / updateQuoteStatus / convertQuoteToInvoice`.
- `createCustomerPayment(companyId, input)`; `confirmCustomerPayment(companyId, id, userId)` — GL: DR Bank, CR AR; updates invoice balances atomically. `cancelCustomerPayment` — reverses JE.
- `raiseDispute / resolveDispute / withdrawDispute / getOpenDisputeTotals(companyId)`.
- `loadInvoiceCtx(companyId, invoiceId)`, `renderTemplate(tpl, ctx)`, `sendDunning(input)` — inserts immutable `dunning_sends` row with rendered subject/body.

- `authenticatePortalUser(email, password)`, `getClientInvoices(clientId, companyId)`, `createPaymentLink(invoiceId, clientId, amount)`.

## Business rules
- `customer_invoices.status`: `draft | sent | partial | paid | void | written_off`. All AR invoice queries MUST use `COALESCE(ci.client_id, ci.customer_id)` — both columns exist (legacy mig artefact).
- Confirm/cancel-payment uses ALS-bound `sql` (NOT `withTransaction`) — the outer `withAuth` transaction provides atomicity. Using `withTransaction` here caused idle-in-transaction timeouts because it opened a second pool connection while the ALS client sat idle.
- 2026-04-24: JE link-back uses ALS-bound `sql` instead of `withTransaction` to avoid nested-tx issues. Do NOT pass invoice id as JE `sourceDocumentId` (FK is to `documents`).
- Dunning: render applies `{{token}}` substitution; send writes an immutable row (subject/body frozen for audit).
- Dispute state: `open → resolved | rejected | withdrawn`. Re-raising after resolution creates a NEW row — history preserved.
- Portal auth is bcrypt against `portal_users` — never route portal endpoints through the main `withAuth` middleware.
- PRD-06 Phase 1: invoice-as-evidence — sealed PDF snapshot is persisted on approve/send for audit.
- `smartCollectionsService` is pure; R50 000 threshold is hard-coded (not per-company).
- `recurringInvoiceService.generateDueInvoices` creates but does NOT post — caller must post.

## Recent changes
- 2026-09-09: **`customer_invoices` row locks — `customerInvoiceLock.ts`, and the two paths that write `amount_paid`.** Both writers used to compute their cap from an UNLOCKED read and then write the money. `applyCreditNoteToInvoice` also wrote `amount_paid` ABSOLUTELY from that stale read, so a second credit note or a receipt committing in between was erased outright; `planAllocationLines` writes relatively but its `outstanding` cap was equally stale, so a receipt planned against R200 landed its full R200 on top of a credit note's R100 and left R300 on a R200 invoice. Both now take `FOR UPDATE` and the credit-note write is relative. **The lock ORDER is note-then-invoice / payment-then-invoice / bank-line-then-invoice.** (Not "the invoice is last" — `customerInvoiceCancelService` holds an invoice and then locks `gl_journal_entries`; that stays acyclic because the only path holding a journal row when it reaches an invoice is `cancelCreditNote`, and the journal it holds is the NOTE's.) Reversing the order above anywhere deadlocks (40P01, which surfaces as GENERIC_FAILURE and does not read as retryable to an agent), so never take a credit-note or payment lock while holding an invoice one. `planAllocationLines` orders its candidates `ORDER BY ci.id` for the same reason across rows. `withCustomerInvoiceLock` carries the 5s `lock_timeout` and the typed `CustomerInvoiceLockTimeoutError`, restoring `DEFAULT` on the SUCCESS PATH ONLY — same rule and same reasons as `creditNoteLock.ts`. **Still open:** approval credits AR for a note's FULL `total_amount` while `applyCreditNoteToInvoice` caps at the invoice's outstanding and then marks the note `applied`, so a partial application strands the remainder and the GL diverges from the subledger by it. `credit_notes` carries ONE `customer_invoice_id`, which is also how cancel un-applies, so spreading a note over two invoices needs a link table — not fixable in place.
- 2026-09-03: **Cash application — `receiptApplicationService` + `receiptAllocationLines` + `receiptMatchConfirmService` + `unappliedReceiptService`/`unappliedReceiptOrigin`.** `allocateTransaction(allocType='customer')` posts DR Bank / CR AR and inserts a CONFIRMED `customer_payments` row, then writes NO `customer_payment_allocations` and never touches `amount_paid` — the cash sits on the control account attached to no document. Re-derived against production 2026-09-03: **R42,759,565.12 unapplied system-wide, of which R39,486,371.68 (92.3%) carries an `mcp:` posting stamp and every one is `bulk_allocate_bank_transactions`** (Velocity Fibre's R37,050,347.68 is 100% agent-made). The bucket is FILLED BY THE TOOLING, not historical. Four things worth not re-deriving. (1) **PLAN and APPLY are separate functions over ONE set of guards.** `planReceiptApplication` takes the `FOR UPDATE` lock (`core/paymentLock.ts`), runs every guard, writes nothing; `applyReceiptPlan` writes and guards nothing. A dry run is the first without the second, so it cannot pass where the live call refuses — and every refusal can be answered before the first write, which is what both the MCP idempotency contract and `withAuth`'s COMMIT-under-500 rule require. (2) **`COALESCE(ci.client_id, ci.customer_id)` is the counterparty.** The inline SQL in `customer-allocations.ts` compared `client_id` alone, so an invoice populated on `customer_id` had `client_id` NULL and could never be allocated through the only UI path that exists — a plausible direct cause of the receipts never being applied. That route also wrote `amount_paid` absolutely (lost update), returned `badRequest` from inside its write loop, and took no row lock; all four are fixed and the route now calls the service. (3) **`confirmReceiptMatch` moved to `receiptMatchConfirmService.ts` and takes an allocations ARRAY.** One journal posts for the FULL bank line; allocating less is allowed and leaves a real unapplied remainder, allocating more is refused. Both bank paths refuse a closed or missing fiscal period PRE-write, because `postJournalEntry` only raises after `createJournalEntry` has INSERTed the draft. **`pages/api/accounting/ar/receipt-match/confirm.ts` must keep `validateBankReceiptApplication` and `confirmReceiptMatch` in SEPARATE try blocks**: the widened service calls `planReceiptApplication` a second time post-write as a race guard, throwing the same message shapes the route's old regex matched, so a race returned 400 and `withAuth` COMMITTED the posted journal. Only the pre-write half may be caught. (4) **`list_unapplied_receipts` splits the total by origin** — `agent` / `system` / `notStampedAsAgent` / `noJournal`. A receipt with no journal is its OWN bucket, and the human bucket is never called human: `createJournalEntry` stamps `human:<userId>` whenever a caller omits the meta.

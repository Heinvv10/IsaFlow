## Business rules
- **Foreign-currency invoices are refused until the FX programme lands (FX PR0, migration 871).** `shared/documentCurrency.resolveDocumentCurrency` (create) / `checkDocumentCurrency` (draft edit): ZAR at a rate ≠ 1 → `EXCHANGE_RATE_INVALID`; any other currency while `companies.fx_documents_enabled` is false → `FOREIGN_CURRENCY_DISABLED`; both 400, pre-write. The DB refuses the same (`fx_document_currency_gate`) and refuses ANY `amount_paid` change on a foreign invoice (`fx_settlement_refusal`). `functional_total` is written by `public.fx_functional(total, rate)` in SQL, never a JS multiplication (`fxConversionCensus` test). Payment links, Paystack checkout and `enableOnlinePayment` refuse a foreign invoice permanently (they charge rands); a gateway receipt that still arrives is banked unapplied with hold `invoice_foreign_currency`.
- **Lock order**: the canonical sequence for every settlement path (bank line → payment → invoices → GL) lives in `bank/.claude.md`. Read it before adding a lock here; a path that takes two of these rows out of sequence deadlocks against one that does not (40P01 → 500).

- **Invoice line coding** (migration 874): a line may name a revenue account (this company's, `account_type = 'revenue'`, leaf, active) and a JOB (`projects`: this company's, not cancelled — what Project Profitability, WIP and time read). Its CC1 / CC2 / BU are migration 870's (`gl/dimensions`: resolver, CC1 derived from CC2, the customer's FNO via `customers.default_cc1_id`, `assertDocumentDimensions`). **Two project models, labelled apart (Hein, 2026-10-08):** the job (`project_id`) and the CC2 project (`cc2_id`) both post; the UI calls them "Job (Project Profitability)" and "CC2 project", never two pickers both called "Project"; Hein rules later whether CC2 replaces projects. **Ruling 2026-10-10:** Project Profitability offers BOTH, side by side — `basis: jobs | cc2`, `jobs` (project_id against `projects`) the default on the report route, the MCP `project_profitability` tool and the page; `cc2` reads cc2_id against cost centres. Never COALESCEd, ids never mixed; whether CC2 replaces jobs is still open. Checked before the first write by create (HTTP + MCP single/bulk), draft edit and recurring-transaction templates; quote lines on quote create/update and again at conversion (before its claim); re-checked on the STORED lines by approve (under the row lock, BEFORE the status UPDATE — the account / job rules, then `applyCustomerFno` + `assertDocumentDimensions`, so an FNO set on the customer since that conflicts is a 400, not a 5xx), bulk finalize (a skip, dry run alike) and `postCustomerInvoiceToGL` (before `createJournalEntry`). **One refusal**: `InvoiceLineCodingRefusal`, code INVOICE_LINE_CODING_REFUSED — HTTP 400 with `details.code`, MCP the registered refusal (bulk create prefixes `invoices[i]:`), bulk finalize a skip. A refusal raised by posting AFTER approve's status UPDATE is re-raised as `ArPostingAfterWriteError` (5xx). **Lock race**: the FOR SHARE read of the line accounts can lose to a GL account merge; 40P01/55P03 there → `InvoiceLineAccountLockError`: REST 503 + Retry-After, MCP registered refusal, bulk finalize a retryable skip. **Posting** (`buildInvoiceRevenueLines`): no line names an account, job or CC1 / CC2 / BU → the single `default_revenue` credit of the subtotal, unchanged, carrying the customer's FNO as cc1 when it has one (lines not read); otherwise every line without a CC1 takes the FNO (a different one is refused), and the credit is split BY WEIGHT over (account ?? default_revenue, job, CC1, CC2, BU), residual to the largest group, a negative group (a discount on its own tags) posting as a debit on its own leg; refused if the lines are more than 1c/line off the subtotal or total zero. **Changed from #663's builder** (its tests now pin the new behaviour, `tests/unit/services/documentDimensionPosting.test.ts`): (1) a group netting ≤ 0 used to collapse the whole invoice to ONE line carrying only the FNO, silently dropping every CC2 / BU; (2) items not footing to the subtotal used to post the difference on the last group; (3) rounding went to the last group, now to the largest. `credit` is passed separately from the document subtotal (the FX path). VAT and AR legs untouched.
- **Credit notes and the five tags (874; D1 revised 2026-10-08).** A customer note LINKED to an invoice with a journal debits that JOURNAL's revenue-type legs pro rata (not the lines — pre-874 invoices credited default_revenue whatever their lines said), on all five tags (account, job, CC1, CC2, BU), each leg capped at what it still carries — its net less what the LIVE (approved, not cancelled) earlier notes TOOK, as `credit_note_revenue_allocations` (874) records it: one row per leg taken plus an `is_excess` row, written in the approval's transaction (`recordCreditNoteRevenueAllocations`); a cancelled note's rows stay but stop counting; capacity groups by the referenced invoice journal line's CURRENT account and tags, so an account merge or a `tag_journal_lines` re-tag (both move the line in place) carries it. Notes approved before 874 have no rows and ARE replayed, in approval order — that fallback only; the excess posts UNTAGGED to `default_revenue`. A linked note's OWN header job / CC1 / CC2 / BU are REFUSED (`creditNoteHeaderTags`, CREDIT_NOTE_DIMENSIONS_REFUSED) at create and at approve, before any write — they could never post, and ignoring them would leave the note contradicting the ledger; a stored linked draft carrying one (pre-874 `project_id`, never validated) must be cancelled and raised again. An UNLINKED note posts one `default_revenue` debit carrying its header job (checked: this company's, not cancelled, at create and approve) and CC1 / CC2 / BU (870). Supplier notes (892, 2026-10-13): mirror this on the expense side (`ap/supplierCreditNoteExpenseLines.ts`) — a note LINKED to a bill with a journal CREDITS that journal's legs other than AP / VAT (picked by role: the payable / vat_input accounts, any AP/AR control subtype, the VAT class — not by account type, a bill may debit an asset or COS account) pro rata on all five tags, capped per leg by `credit_note_expense_allocations` (pre-892 notes on the bill replayed); the excess, or the whole net when unlinked or the bill has no journal, goes to the note's own `credit_notes.gl_account_id` (optional, bill-line account rule at create and approve) else `default_expense`. Header CC1 / CC2 / BU are refused on a linked supplier note (CREDIT_NOTE_DIMENSIONS_REFUSED) and posted on an unlinked one. AP debit and the single VAT credit unchanged. Before 892 every supplier note credited default_expense whatever the bill debited (Velocity re-pointed R8.54m off 5100 by journal, 13 Oct 2026); existing rows elsewhere need a reclassification from `auto_credit_note` lines on default_expense joined to `credit_notes.supplier_invoice_id`. Decided before the journal is written: a leg whose account was deactivated since is debited on default_revenue keeping its tags. Any failure after `createJournalEntry` in `approveCreditNote` is `ArPostingAfterWriteError` (5xx).
- **The invoice header's project is explicit or NULL** — `createDraftCustomerInvoice` used to take `LIMIT 1` (no ORDER BY) of the client's projects, swallowing a failed read. The new and edit pages have a header Project picker; a line ADDED after it starts on that project (a visible default, not a posting fallback). **Draft edit (PUT)**: a coding key ABSENT from a line keeps the stored value when every stored line carries the same one, and is refused (bad_line → 400) when they differ — lines share one created_at, so there is no stable position to match on; null clears; '' is refused by the schema. The header `projectId` is absent = keep, null = clear. **Writers that carry NO line coding** (they post the single default_revenue leg): sales-order conversion (`customer_sales_order_items.gl_account_id` exists, nothing writes it, the conversion does not copy it) and recurring-invoice runs (`parseLineItems` drops a template line's glAccountId) — pinned by invoice-line-revenue-writers.int.test.ts. **Follow-up (Hein's lead, 2026-10-07), not in the 870 PR:** carry line coding through both — `salesOrderWorkflowService.ts` (`convertSalesOrderToInvoice`, the `customer_invoice_items` INSERT: copy `customer_sales_order_items.gl_account_id`, held to `assertLineAccountIds` before its claim, as `quoteConvertService.convertToInvoice` is) and `recurringInvoiceTemplate.ts` (`parseLineItems`: keep `glAccountId`, then `recurringInvoiceRun.ts` writes it and checks it before the number is reserved).
- **Credit-note approval lock order** (migration 874 review round 2; census before the advisory lock was added). `approveCreditNote` takes, in order:
  1. its own `credit_notes` row, `FOR UPDATE` (`creditNoteLock`, 5 s `lock_timeout` → 503);
  2. **NEW** `pg_advisory_xact_lock(hashtextextended('isaflow.credit_note_approve.invoice:<invoice id>', 0))` — only for a note linked to a customer invoice or (892) a supplier bill (the bill's id under the same key), as the very next statement (`creditNotePostingChecks.lockInvoiceCreditNotes`);
  3. reads only (approval gate, the 988 mirror_bill VAT re-check — runs while this approval HOLDS its note row (1) and the bill's key (2), so its cost (document_vat_history's tie and chain reads plus the heuristic search, bounded to the bill's own VAT accounts, dated on or after the bill, hand journals only, 101 rows) is paid under both; it takes no lock of its own —, system accounts, the invoice's journal legs, its earlier notes and their allocation rows, the pre-write checks);
  4. `createJournalEntry`: the journal-number advisory lock (company+year, migration 857's insert trigger), `FOR KEY SHARE` on the referenced accounts / period, `gl_account_balances` rows via the line trigger;
  5. `postJournalEntry`: its own new journal header; then INSERTs of its own `credit_note_revenue_allocations` (customer) or `credit_note_expense_allocations` (supplier, 892) rows (new rows, no waits);
  6. `applyCreditNote`: the linked invoice and its FIFO candidates `FOR UPDATE` (`lockInvoicesForUpdate`, id order);
  7. the UPDATE of its own note row (already held).
  `ap/supplierCreditNoteMirror.planMirroredSupplierNote` (MCP `create_credit_note` with `mirror_bill`, 2026-11-13) takes the same key for the bill as its FIRST lock, holds no note row, then reads and INSERTs the new draft (the credit-note number lock, as approve's step 4 order: key before number), so it cannot wait on anything an approval holding the key needs. Same residual as below for a bulk approval holding a number lock.
  `applyCreditNoteToInvoice` (PR #685 review round 2) takes the same key for the invoice it applies to, as the next lock after its note row and before the invoice row — the same order, so no cycle with an approval.
  **No existing lock was moved.** Only approveCreditNote, applyCreditNoteToInvoice and the mirrored supplier-note create take the key, right after their note row, so a waiter there is always another approval of a note on the same invoice, holding nothing of this approval's but its own note row (step 1) — which the holder never needs (steps 3–7 touch the holder's note, journals, accounts and invoices, never another note's row). Single approvals therefore cannot deadlock on it. **Residual, bounded:** a request that approves several notes in one transaction (bulk_approve_credit_notes, sorted by note id) can hold an earlier element's journal-number lock or invoice rows while it waits at step 2 for a peer that is about to need one of those — a cycle the deadlock detector breaks (40P01 → that bulk unwinds with "retry the batch", or the peer's request answers 503); the same class the invoice row locks in step 6 already had.
- `customer_invoices.status`: `draft | sent | partial | paid | void | written_off`. All AR invoice queries MUST use `COALESCE(ci.client_id, ci.customer_id)` — both columns exist (legacy mig artefact).
- Confirm/cancel-payment uses ALS-bound `sql` (NOT `withTransaction`) — the outer `withAuth` transaction provides atomicity. Using `withTransaction` here caused idle-in-transaction timeouts because it opened a second pool connection while the ALS client sat idle.
- 2026-11-01 (master plan wave 3 P): `pages/api/accounting/invoice-pdf.ts` takes `disposition=inline|attachment` (default attachment; anything else is a 400 before rendering). `InvoicePdfPreview` (components/accounting/customer-invoices) frames the inline PDF through a blob: URL: the route itself cannot be framed (`X-Frame-Options: DENY`), and `frame-src` carries `blob:` for this alone. Rendering has no side effect, so a draft can be previewed freely. A render is not metered; it is rate-limited per member (`checkReportRateLimit(companyId, `invoice-pdf:u:<user>`, INTERACTIVE_REPORT_LIMIT)`), so a 429 reaches the preview as its Retry state and one member cannot use up a colleague's previews.

- `smartCollectionsService` is pure; R50 000 threshold is hard-coded (not per-company).
- **`fetchInvoiceCandidates` (`receiptAllocationLines`) LOCKS the invoices it decides from** — `ORDER BY ci.id`, `FOR UPDATE OF ci`, 5s `lock_timeout`, 55P03 → `ReceiptRefusal`. It THROWS outside a request transaction rather than skipping the lock (`core/requestTransaction`): an implicit transaction releases `FOR UPDATE` at the end of the statement and discards the `SET LOCAL lock_timeout`, so the check-then-act ran unprotected and unbounded while reading as locked. `lock_timeout` is restored on the SUCCESS path only — a `finally` would raise 25P02 over the refusal. `ap/fetchBillCandidates` is the mirror.
- `recurringInvoiceService.generateInvoiceFromRecurring` inserts the invoice at `draft`, writes one
  `customer_invoice_items` row per template line, then approves it through `approveCustomerInvoice`
  — so it DOES post the GL journal. Never post again on top of it. R-035 PR4: unless an enforced
  approval rule governs it — then it stays the draft, the request is raised as the runner and the
  schedule still advances; `runRecurringInvoice` reports it `heldForApproval`. It requires a request
  transaction (`FOR UPDATE` on the template), refuses a template that is not yet due, and derives
  the header totals from the lines rather than the stored aggregate. The savepoint opens BEFORE the
  lock: the 5s `lock_timeout` raises 55P03, which aborts the whole request transaction, and outside
  a savepoint that silently turns the batch runner's COMMIT into a ROLLBACK. `assertTxUsable` does
  NOT see this — `txUnusable` is set only when a savepoint's own rollback fails.

- **Write-offs are judged against the invoice as it is at approval (AR audit C1/C2, K-055, 2026-10-20).** `approveWriteOff` takes the invoice `FOR UPDATE` (`withCustomerInvoiceLock`), then the write-off row `FOR UPDATE`, then refuses with `WriteOffInvoiceRefusedError` (REST 409, write-off stays `draft` and cancellable, nothing written: `withAuth` COMMITs a 4xx) when the invoice is soft-deleted, has no posted AR (`documentInPopulation`: draft / pending_approval / cancelled) or owes less than the write-off. The `amount_paid` increment carries `amount_paid + x <= total_amount` and a zero-row result throws (5xx, rolls back); status and `paid_at` come from `recomputeInvoiceStatus` (partial -> `partially_paid`, cleared -> `paid`, dated; `disputed` is left alone). `createWriteOff` runs the same refusal up front (400). Lock order is invoice then write-off, the order `customerMergeService` already uses; nothing locks a write-off and then an invoice.

- **Invoice due date (migration 960).** `createDraftCustomerInvoice` stores the `dueDate` the caller named, else the customer's terms (`customerTermsDueDate`: `shared/paymentTerms.dueDateFromTerms` over `customers.payment_terms` / `payment_terms_type`, company-scoped), else NULL: a customer whose terms are not set gets no derived date. The recurring run (`recurringInvoiceRun.runDueDate`) uses the same terms from the database's CURRENT_DATE (the invoice date it writes), and keeps +30 days ONLY for a customer whose terms are not set: nobody enters a date on an unattended run, and a bill with no due date would sit outside every ageing bucket. The new-invoice page fills the date client-side (`useContactDefaults`).
- **Due-date source, the draft re-date and the open-invoice date edit (migration 962, payment-terms Part A + AR parity, 2026-11-08).** `customer_invoices.due_date_source` is `terms | manual | document | legacy` (`shared/dueDateSource.ts`; the detail GET returns it). *Draft edit:* `editDraftCustomerInvoice` reads the row under its FOR UPDATE and calls `customerInvoiceDraftDueDate.draftEditDueDate`: when the edit moves the invoice date or the customer, the stored source is `terms`, and the edit's `dueDate` is absent, the stored date re-sent, or the new terms' date (`dueDateForContact`: customer terms, else the company default), the due date becomes the terms' date for the NEW date and customer and stays `terms` (`shared/draftDueDate.redatedDueDate`, shared with AP); any other `dueDate` is the caller's (`manual`); `manual` / `document` / `legacy` never move. Named limit: to KEEP the old terms date after changing the invoice date, save the date change, then change the due date. The edit page shows the same date (`useDueDateFollowsTerms`) and sends `dueDate` only when the user touched it or the page recalculated it; a body that names none leaves the stored date and source alone. *Open-invoice edit:* `invoiceDueDateEdit.setOpenInvoiceDueDate` (`PUT /api/accounting/customer-invoices-due-date {id, dueDate}`): approved / sent / overdue / partially_paid only, with something still owing (total - paid > `REAPPLY_EPS`, else 400 "has nothing owing") (status values are those of `customer_invoices_status_check`), row-locked by `customerInvoiceRowLock.lockCustomerInvoiceForUpdate` (bounded 5s, `CustomerInvoiceLockTimeoutError` answered 409), date >= invoice date, any other body key refused whole, source `manual`; the due date is outside the approval digest (865). UI: `components/accounting/terms/DueDateEditor.tsx` (`kind="invoice"`) on the invoice page; it hides when the balance is at or under half a cent. Tests: `tests/integration/invoice-due-date-edit.int.test.ts`, `draft-due-date-redate.int.test.ts`.
- **Re-apply payment terms to customer invoices (AR parity with `ap/reapplyTerms`).** `ar/reapplyTerms.ts`: `previewReapplyCustomerTerms` lists open invoices (draft / pending / approved / sent / overdue / part-paid, owing, not deleted; the customer is `COALESCE(client_id, customer_id)`) whose CUSTOMER's own terms give a different due date (never the company default: a customer with no terms is skipped and listed in `skippedCustomers`, balance in the functional currency); `terms` / `legacy` pre-ticked, `manual` / `document` unticked with a note; each row carries its `currencyCode` (balance is in the invoice's own currency). `applyReapplyCustomerTerms` locks each invoice in id order, re-reads status, date, source and the customer's terms under the lock and writes only what `reapplyDecision` allows (skips: not_found / not_open / date_changed / terms_not_set / terms_changed / already_dated); a written invoice's source becomes `terms`. A lock timeout is re-thrown (503, the request rolls back). Route `customer-invoices-reapply-terms`; page `/accounting/customer-invoices/reapply-terms` (Sales → Customers); MCP `reapply_customer_payment_terms` (separate from `reapply_payment_terms`). Shared with AP: `shared/reapplyTermsShared.ts`. Test: `tests/integration/reapply-customer-payment-terms.int.test.ts`.

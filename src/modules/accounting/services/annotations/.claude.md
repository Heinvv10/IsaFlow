# annotations/

## Purpose
Internal working notes pinned to a row of a statement, for one period. Table `report_annotations`, migration 611.

## Caller contract
Called only by `pages/api/accounting/annotations/*` under `withAuth`. Company and author both come from the session; a body field naming a different author or company is ignored, not honoured.

**INTERNAL ONLY, and that is a hard boundary.** Nothing here is reachable from a share link: `sharedPackService.ts` never queries `report_annotations`, and `SharedPackProps` has no field a note could travel in. A note is a working comment between colleagues, not a disclosure to a bank. Guarded by `tests/unit/services/annotations/annotationsNeverShared.test.ts` — if you add a share-side reader for these rows, that test is the one telling you not to.

## Main signatures
- `listAnnotations(companyId, rowIds, periodStart, periodEnd) → Annotation[]` — resolved notes included.
- `createAnnotation({ companyId, userId, authorName, rowId, periodStart, periodEnd, body }) → Annotation`.
- `resolveAnnotation(companyId, id, userId) → boolean` — false when the id is not this company's or is already resolved; the route answers 404 either way.
- `resolveAuthorName(companyId, userId, fallbackEmail) → string | null`.
- `annotationRateLimitKey(action, userId) → string`.
- Constants: `MAX_BODY_CHARS` (4000), `MAX_ROW_IDS` (500).

## Business rules
- Every statement carries `company_id`, the resolve UPDATE included, so a cross-tenant id matches zero rows rather than mutating a row the caller cannot see.
- `resolveAuthorName` joins through `company_users` — without it, a note create would resolve any user id on the platform to a real name, which is a directory lookup. `cu.user_id::TEXT` casts the UUID side, because `users.id` is TEXT and `::UUID` on it throws at runtime.
- A long body is TRUNCATED at `MAX_BODY_CHARS`, not rejected: a long paste should still land.
- `rowIds` is capped at `MAX_ROW_IDS`; an unbounded id list is how one request reads the whole table. Row ids are opaque adapter strings (`acc:4000`, `total:grossProfit`) and are parameterised, so length is the only guard needed.
- Resolved notes are still returned. A thread that hides its own history is worse than one that shows it settled.
- The rate-limit bucket is per company AND per user — `checkReportRateLimit` adds the company, `annotationRateLimitKey` adds the user — so one colleague cannot spend a teammate's capacity.

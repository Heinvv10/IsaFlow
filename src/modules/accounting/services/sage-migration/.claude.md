# Sage migration (Phase D)

Moves a Sage Business Cloud Accounting (SA, API v2) export into ONE company: categories -> items -> purchase orders, through
the MCP write tools (`upsert_item_category`, `bulk_upsert_items`, `bulk_create_purchase_orders`) and their real registry.
Assumed export shape and field mapping: `docs/design/sage-migration-export-format.md`. CLI: `scripts/sage-migration/run.ts`.
Local throwaway databases only.

## Files

| File | Role |
|---|---|
| `sageExportTypes.ts` / `sageValues.ts` | Typed rows, `RowRefusal`, `ParsedExport`; the field readers (every fault of a row is collected, not the first). |
| `sageItemParser.ts` / `sagePurchaseOrderParser.ts` / `sageExportParser.ts` | PURE. Row parsers, then the file-level checks (duplicate id / code / number refuse every row sharing it; category conflicts; unknown status; a PO line naming an item the export lacks). |
| `sageTaxTypes.ts` / `sagePoStatus.ts` | The two assumed tables: tax type 1 standard, 2 zero, 3 exempt; Pending/Overdue -> open, Invoiced -> billed (closed), Cancelled. Anything else is refused, never guessed. |
| `sageItemMapping.ts` / `sagePurchaseOrderMapping.ts` | PURE mapping to the tools' arguments (the table is in each header). |
| `sageSuppliers.ts` | Supplier by Sage reference (`find_by_external_ref`), else exact name (`list_suppliers`); none or two is a refusal of the PO. |
| `sageMigrationPlan.ts` | PURE. What is sent and what is refused first: each row goes through the tool's own pure validator (`validateItemFields`, `parsePurchaseOrder`) and against what the company already holds (`sageSnapshot.ts`: a code another item carries, a deleted item, a taken PO number), so one bad row costs that row, not its batch. A PO naming a refused item is refused (`line_item_refused`). |
| `sageBatches.ts` / `sageBatchRun.ts` | Batches (items 500, POs 100: the tools' own caps, pinned equal by a test), stable order, deterministic keys `sage-mig-<entity>-<n>-<hash of the rows>`; the one call that sends a batch. |
| `sageToolSession.ts` | One request transaction as `app_user` with the member's claims, the real `mcpRegistry.call`; `commit: false` rolls the lot back. What keeps a run inside its company is NOT the `company_id` argument sent on writes (the registry only compares it with the context's own company: it selects nothing): it is the membership check (the user must be an active member of the named company), `app_user` under RLS with that company's claims, and the tools' own ownership checks. |
| `sageMigrationRunner.ts` | Dry run, then live; `sageSnapshot.ts` + `sageReconciliation.ts` + `sageReportSummary.ts` measure and print the result. |
| `localGuard.ts` | The runner starts only on a local throwaway database (127.0.0.1/localhost, explicit port outside 7770-7776, db `isaflow_schema_fixture` / `isaflow_test` / `isaflow_sagemig_*`), for DATABASE_URL and every other database URL set. |

## Rules

- **The migration only updates items it owns.** `bulk_upsert_items` matches by code and updates what it matches, so a Sage code equal to any other item (no reference, another reference, deleted) is refused `code_held_by_existing_item` in the plan and the item named.
- A supplier carrying another Sage reference is never matched by name. A PO in a foreign currency, or with a description that would pass 500 with its item suffix, is refused.
- A partial export (no container, unknown top-level key, `$totalResults` above the rows, `$next`) is refused whole; `--live` needs `--expect-items` and `--expect-pos`.
- A replayed batch whose rows are gone is `replayed, rows absent` (failed); `--run-tag` salts the keys for a deliberate fresh import.
- Pending/Overdue go in through one constant, `OPEN_SAGE_PO_IMPORTED_AS`.

- **`QuantityOnHand` is NEVER imported** (Hein). It is not on the typed row (`hadQuantityOnHand` only), not on any mapped row, and
  no `stock_movements`, `opening_qty` or `current_qty` is written; the report counts the movements before and after.
- `inventory_tracked` is always false; a Sage service code (`Physical` false) is a service.
- The dry run is one rolled-back transaction. Categories and purchase orders are written LIVE inside it (items' preview needs the
  categories; PO batch k's budget check must see batches 1..k-1, as the live run's does); items use `dry_run`. Its idempotency and audit
  rows roll back with it (a test proves it). A dry run that is not clean stops the run: nothing is written, even with `live`.
- Exit 0 needs a clean dry run or a live run that booked everything it sent, `--expect-*` figures that match what was SENT (dry) or
  BOOKED (live), and no refused row unless `--allow-refusals`.
- Item codes and PO numbers are unique case-sensitively (plain unique indexes), so the checks against what the company holds are exact.
- A PO line is "No budget" (never blocked) unless the run is given `--po-gl-account`, which posts EVERY line to that one account: the budget figures are then only as right as that choice. Opt-in only.
- Named limit: what the company holds is read once before the dry run; a writer racing in between can still make a tool refuse a batch (the dry run reports it, writes nothing).
- A live batch is one committed registry call. A failed batch is reported with the tool's message and nothing of it is written;
  the other batches of its phase run, the next phase does not. Running again resumes: finished batches replay under their keys.
- The PO tool has no `item_id` on a line; the link to the item is " [item CODE]" in the description until it has one.
- PDFs are listed in the report, not uploaded.
- The reconciliation is measured in the database (before and after), never taken from a tool's answer.

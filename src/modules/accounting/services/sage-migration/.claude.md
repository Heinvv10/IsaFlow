# Sage migration (Phase D)

Moves a Sage Business Cloud Accounting (SA, API v2) export into ONE company: categories -> items -> purchase orders, through
the MCP write tools (`upsert_item_category`, `bulk_upsert_items`, `bulk_create_purchase_orders`) and their real registry.
Assumed export shape and field mapping: `docs/design/sage-migration-export-format.md`. CLI: `scripts/sage-migration/run.ts`.
Local throwaway databases only.

## Files

| File | Role |
|---|---|
| `sageExportTypes.ts` / `sageValues.ts` | Typed rows, `RowRefusal`, `ParsedExport`; the field readers (every fault of a row is collected, not the first). |
| `sageItemParser.ts` / `sagePurchaseOrderParser.ts` / `sageExportParser.ts` | PURE. Row parsers, then the file-level checks (duplicate id / code / number refuse every row sharing it; category conflicts; unknown status; a PO line naming an item the export lacks). |
| `sageTaxTypes.ts` / `sagePoStatus.ts` | The two assumed tables: tax type 1 standard, 2 zero, 3 exempt; Pending/Overdue -> open, Invoiced -> billed (closed), Cancelled. Anything else is refused, never guessed. |
| `sageItemMapping.ts` / `sagePurchaseOrderMapping.ts` | PURE mapping to the tools' arguments (the table is in each header). |
| `sageSuppliers.ts` | Supplier by Sage reference (`find_by_external_ref`), else exact name (`list_suppliers`); none or two is a refusal of the PO. |
| `sageMigrationPlan.ts` | PURE. What is sent and what is refused first: each row goes through the tool's own pure validator (`validateItemFields`, `parsePurchaseOrder`), so one bad row costs that row, not its batch. |
| `sageBatches.ts` | Batches (items 500, POs 100), stable order, deterministic keys `sage-mig-<entity>-<n>-<hash of the rows>`. |
| `sageToolSession.ts` | One request transaction as `app_user` with the member's claims, the real `mcpRegistry.call`, `company_id` asserted on every write; `commit: false` rolls the lot back. |
| `sageMigrationRunner.ts` | Dry run, then live; `sageSnapshot.ts` + `sageReconciliation.ts` + `sageReportSummary.ts` measure and print the result. |
| `localGuard.ts` | The runner starts only on a local throwaway database (127.0.0.1/localhost, explicit port outside 7770-7776, db `isaflow_schema_fixture` / `isaflow_test` / `isaflow_sagemig_*`), for DATABASE_URL and every other database URL set. |

## Rules

- **`QuantityOnHand` is NEVER imported** (Hein). It is not on the typed row (`hadQuantityOnHand` only), not on any mapped row, and
  no `stock_movements`, `opening_qty` or `current_qty` is written; the report counts the movements before and after.
- `inventory_tracked` is always false; a Sage service code (`Physical` false) is a service.
- The dry run is one rolled-back transaction (categories are created inside it so the items' preview finds them). A dry run that is
  not clean stops the run: nothing is written, even with `live`.
- A live batch is one committed registry call. A failed batch is reported with the tool's message and nothing of it is written;
  the other batches of its phase run, the next phase does not. Running again resumes: finished batches replay under their keys.
- The PO tool has no `item_id` on a line; the link to the item is " [item CODE]" in the description until it has one.
- PDFs are listed in the report, not uploaded.
- The reconciliation is measured in the database (before and after), never taken from a tool's answer.

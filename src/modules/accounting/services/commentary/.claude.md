# commentary/

## Purpose
Generated commentary on a report pack, held as a DRAFT until a named person approves it. Table `report_commentary`, migrations 611 and 612.

## Caller contract
Called by `pages/api/accounting/commentary/*` under `withAuth`; company always from the session. Consumed on the public side by `share/sharedPackService.ts`, which selects `approved_text` and filters `status = 'approved'`. Every statement here carries `company_id`, including the UPDATEs.

## Main signatures
- `listCommentary(companyId, params) → CommentaryRow[]` — the whole pack, unfiltered. There is no section parameter on the route or the hook; `CommentaryBlock` owns the per-section filter.
- `generateDrafts({ companyId, userId, params, data, replace? }) → { written, skipped }`.
- `approveCommentary(companyId, id, userId)` / `rejectCommentary(...)` → `CommentaryResult`, failing with `not_found` (404), `empty_draft` (400) or `invalid_state` (409) — the route must not collapse them.
- `nextStatus(current, action) → Transition`; `buildDraftSentences(data) → DraftSentence[]`; `buildManagementPackData(companyId, params)`.

## Business rules
- **Status machine** (`commentaryState.ts` is the only place a status changes): `draft → approved` (approve), `draft → rejected` (reject), `* → draft` (generate). `generate` on an approved row FAILS.
- **The `replace` gate.** `replace: true` is the only path that re-drafts a row a person already ruled on: it withdraws an approval and revives a rejection. Without it both are left alone and reported in `skipped` — a discarded sentence does not come back because somebody pressed Generate again. The route restricts `replace` to owner/admin; `CommentaryPanel` puts an explicit, single-use confirmation in front of it.
- A withdrawal is STAMPED, not erased: `withdrawn_by`/`withdrawn_at` are set and `approved_text`/`approved_by`/`approved_at` survive, so the row still says who signed off. Nothing leaks — the published query filters on status.
- The `ON CONFLICT ... DO UPDATE ... WHERE` repeats the decision at the write, on the row's state at write time, because another session can approve or reject inside the read-to-write window.
- An empty or whitespace-only draft is never approvable. The 611 CHECK would store the blank.
- Approval writes status, text, approver and timestamp in ONE statement so the CHECK never sees a half-approved row; the WHERE repeats the guard so two racing approvals cannot both write.
- The draft builder never writes `approved_text`. Nothing generated reaches a share link without a person.

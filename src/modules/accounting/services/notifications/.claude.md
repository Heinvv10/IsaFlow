# Notifications (`services/notifications/`)

Per-user in-app notifications (migration 954 `user_notifications`; budgets P5-1). Read by the header bell (`src/components/layout/NotificationBell.tsx`) through `GET /api/accounting/notifications` and `POST /api/accounting/notifications/read`.

## Caller contract
- `listNotifications(companyId, userId)` → `{ items: latest 20, newest first; unread }`. `markRead(companyId, userId, { ids } | { all: true })` → `{ updated }` (only the caller's own unread rows; others' ids are ignored). `notifyUsers(companyId, userIds, { kind, refId, title, body, href, dedupeKey })` → void; one row per user per dedupe key, a rerun writes nothing.
- Every query names company AND user. RLS also limits app_user's reads/updates to `user_id = auth.uid()`, but the service pool's mirrors are USING (true), so the query must hold alone (tested as app_service).
- Writing for OTHER users as app_user: `ON CONFLICT DO NOTHING` with NO conflict target and NO `RETURNING`. Either one makes Postgres check the new row against the read policy and the insert fails 42501.
- `href` is an in-app path only (`src/lib/inAppPath.ts`, same rule as the table CHECK); the bell never follows anything else.
- `kind` ∈ budget_alert | budget_slice | budget_reminder (table CHECK). Producers: P5-4 alerts, P5-6 slices/reminders.

## Business rules
- All queries scope by `company_id`; trial-balance-derived reports filter both `je.company_id` AND `jl.company_id` (mig 329).
- VAT return uses GL journal lines tagged with `vat_code` + `vat_amount`; don't double-count by joining `customer_invoices` or `supplier_invoices`.
- Consolidation: eliminations scoped to parent company; intercompany balances removed via `intercompanyService` before roll-up.
- **Group listing must use `listGroupsForUser(userId)`, never `listGroups()`** — the latter is unscoped and returns every tenant's groups. `listGroupsForUser` admits a group when the caller belongs to a member company **OR** created it; the creator clause exists because a group created without a holding company has no members, and an INNER JOIN made it invisible to its own creator — permanently orphaned, only fixable by direct DB access. `createGroup` does auto-enrol a holding company as the first member, so the orphan only occurs when that optional field is left empty.
- Custom reports: `customReportRunner` compiles user-defined field defs into parameterised SQL — all params bound, no interpolation.
- **A bank account is a `gl_accounts` row with `account_subtype='bank'`, never a `bank_accounts` row.** `bank_transactions.bank_account_id` FKs to `gl_accounts(id)`; `bank_accounts` is vestigial metadata (0 rows in production). Cash = `SUM(bank_transactions.amount)` over active bank-subtype GL accounts.
- **Outstanding AR/AP is `total_amount - COALESCE(amount_paid,0)`.** There is no `balance_due` column on either invoice table. Always gate on the shared `AR_OPEN_STATUSES` / `AP_OPEN_STATUSES` from `@/lib/constants/invoiceStatuses` — `'partial'` is not a legal status on either table, and `supplier_invoices` has no `'overdue'`.
- **As at any date but today, outstanding comes from the aged report (R-059).** `total_amount - amount_paid` over the open statuses is TODAY's figure: it nets settlement made since and drops what was settled since. A year-end note, a period report's outstanding column or an integrity check's `as_at` takes the ageing's population and `shared/agingRewind`, or sums `getARAging`/`getAPAging` through `agedBucketTotals.ts`.
- **`approveVATAdjustment` holds the adjustment row `FOR UPDATE` (5s bound) and refuses before any write** (`VatAdjustmentRefusal`: `not_found` 404, `not_draft` 400, `contended` 409); the journal create + post + stamp run in ONE `withSavepoint`, because `postJournalEntry` refuses a closed period only after the draft exists and the route's 400 is COMMITted by `withAuth` (R-051). Needs a request transaction. `cancelVATAdjustment` takes the same bounded wait and the same typed refusals. The route maps contention and a 23505 on `uq_gl_je_company_entry_number` to 409.
- Facade files (`sarsService`, `kpiService`) re-export; add logic to the split services.
- Date handling: pg returns `Date` objects from timestamp columns — all report formatters accept both `Date` and ISO string.

## Pre-deploy step: size the VAT-gaps blocking surface

`scripts/vat/size-input-support-blocks.sql` (read-only, not a migration) —
run it against production BEFORE deploying the input-VAT support check
(`vatInputSupport.ts`) or the unposted-invoice block (`vatUnpostedInvoices.ts`)
for the first time: `psql "$DATABASE_URL" -f scripts/vat/size-input-support-blocks.sql`.
It counts, per company and (approximate, bimonthly-bucketed) VAT period, the
journals that would newly read as `unsupportedInputVat` and the unposted
invoices/bills carrying VAT — so Hein knows the blast radius before real
tenants' eFiling starts refusing on either check. The unsupported-journal
half is an ESTIMATE (per-journal, not reversal-chain-rooted the way the app
is); the unposted-invoice half mirrors `vatUnpostedInvoices.ts` exactly.

## One P&L layering, shared — the convergence happened (B75)

`incomeStatementService#getIncomeStatement` and
`gl/accountClassification#aggregateFigures` band through the SAME exported
functions, `expenseBand` and `revenueBand`. Turnover, other income, cost of
sales, operating expenses, other expenses, gross profit, operating profit and
net profit agree to the cent, and `incomeStatementConvergence.test.ts` asserts
every band — so a future edit to either side fails rather than silently
re-diverging.

**Do not re-implement either layering locally.** They previously diverged: the
page counted other income as turnover and put finance cost and tax inside
operating expenses, so it reported a different GROSS profit while the registry
claimed the two agreed to the cent — true of net profit, false of gross, and
nothing tested it. That was finding B75.

The operating line is the one finance cost and tax sit BELOW: other income is
ABOVE it. `aggregateFigures.operatingProfit` is the single definition; the
`profit_and_loss` tool reads that field rather than recomputing it, because a
local copy of the formula is exactly how the first divergence happened.

Consumers that render this shape must show every band or their statement stops
footing. **Seven surfaces do**: the income-statement page
(`components/accounting/IncomeStatementSections`), the management pack
(`components/accounting/ManagementPandLRows`), the CSV and XLSX exports,
`components/accounting/afs/AfsStatementsTab`, and the report pack's HTML and PDF
renderers (`reports-html.ts` / `reports-pdf.ts`, fed by `reportPackService`).

**Finding them all took three review rounds, and the misses rhymed.** AFS is not
in `services/afs/` — it is a component — so grepping that directory says AFS is
unaffected when it is not. The report pack renders from `ReportPackInput`, whose
optional `otherIncome`/`otherExpenses` `getReportPackInput` simply never
populated, so the pack's P&L was short by `otherIncome - otherExpenses` and
`buildProfitWaterfall` suppressed both its steps on every pack ever produced.
When this shape changes, grep for the CONSUMERS of the figures — `grossProfit`,
`totalRevenue`, `netProfit` — across `src/` and `pages/`, not for a directory
name.

Every surface is pinned by a test, though not all in the same way, and the
distinction matters when you add one:

- **Rendered components** — the page, the management pack and the AFS tab — have
  render tests asserting the bands AND their order
  (`incomeStatementRenderSurfaces.test.ts`). These are possible only because
  `vitest.config.ts` loads `@vitejs/plugin-react`; `tsconfig`'s
  `jsx: "preserve"` otherwise makes any `.tsx` unimportable from a test, which
  is why a whole section could vanish from a statutory statement with the full
  suite green. Importing a PAGE still fails on Next's font loader, so the
  renderable body belongs in `src/components/**`.
- **The HTML and PDF packs** render from one shared row list,
  `incomeStatementPackRows`, tested directly
  (`incomeStatementPackRows.test.ts`) — one list is one fewer place to omit a
  band. The WIRING is tested separately (`packRendererWiring.test.ts`): a
  correct list does not protect a renderer that filters a row out or drops a
  table cell, so `renderSectionHtml` and `renderSection` are exported and their
  output asserted, the PDF one with an injected fake `autoTable`.
- **The CSV and XLSX exports** are tested through their handler and workbook
  builder (`incomeStatementExportDisclosure.test.ts`,
  `incomeStatementRenderSurfaces.test.ts`).
- **The data behind the packs** is pinned at `getReportPackInput`'s own boundary
  (`reportPackInputCarry.test.ts`) — asserting `toFinancialData` instead left
  the carry mutations green, because that is not the function that drops them.

`classificationCoverageService` is what makes either safe to read. Every band is
chosen from `account_subtype`, and on these books the subtypes barely exist —
100% of Velocity Fibre's revenue and 97.6% of its expenses are on unclassified
accounts. `profit_and_loss` reports it at every detail level and it is not
suppressible.

`priorPeriod.ts` owns the comparative window. Pure, `'YYYY-MM-DD'` in and out,
constructs no `Date`. The income-statement PAGE still computes its own in
milliseconds and compares March against 29 January – 28 February; that fix
belongs with the convergence PR.

## `trendRowsService` duplicates the balance sheet's shape rules

`getMonthlyBalances` re-implements two rules `balanceSheetService` already
owns: the signing convention (by `normal_balance`, then negate the
contra-asset) and the leaf filter (`level >= 3 OR no children`). They are
copies, not a shared helper, so a change to one is silently a divergence.

What keeps them honest today is `tests/integration/accountTrends.int.test.ts`,
which foots the series against `getBalanceSheet` itself rather than against a
SUM written in the test: the last month must equal the printed balance at
as-of, and month 6 the printed balance at that month end, for every line on
both tenants. Mutating either rule in the service turns both red.

Know how that test reaches you. The FILE refuses to skip: with no real
`DATABASE_URL` its `beforeAll` throws and the suite fails rather than
reporting green on nothing. But the CI STEP that runs it is itself gated —
`scripts/ci/run-ci.sh` runs `test:integration` only when `DATABASE_URL` is
set, and prints `[skip] integration-tests` otherwise. So it runs in GitHub CI,
where the connection string is a secret, and a local `bun run ci` skips it
silently. Locally it has to be asked for:

```bash
DATABASE_URL=... bun run test:integration
```

**Follow-up:** extract the leaf predicate and the sign expression into one
shared helper both services call, AFTER WS3 merges. WS3 changed the
`gl_accounts` join lines in `balanceSheetService.ts`; doing it before then is
a conflict for no gain, and the footing test above is what makes waiting safe.

# intercompany/

Intercompany mirror posting (plan: `docs/plans/2026-11-17-intercompany-mirror-posting.md`). P1 = group connections (migrations 1000, 1002). **P2 (migration 1013) = the invoice + credit-note mirror**: an approved customer invoice / customer credit note leaves a message in the SENDER's outbox, the RECEIVER accepts it in the Bills > Intercompany inbox (a DRAFT supplier invoice / supplier credit note), and the auto-accept worker does the same as the receiver for a group side that asked for it. Tables: `intercompany_connections`, `intercompany_connection_sides`, `company_connection_keys`, `intercompany_messages`, `intercompany_document_links` (keys and the payment / allocation kinds wait for P4 / P6).

## Modules
- `connectionService.ts` — barrel plus `createGroupConnection`, `revokeConnection`, `connectionView`. `connectionSettingsService.ts` — `updateConnectionSettings` (the pair's agreement). `connectionSideService.ts` — `updateOwnSide`. `connectionRead.ts` — `listConnections`, `listGroupCandidates`. `connectionOptions.ts` — the side form's pick-lists.
- `connectionValidation.ts` — pure: request shapes (`parseCreateInput`, `parseSideInput`, `parsePairInput`), `autoAcceptRefusal`, `orderedPair`, `computeChecklist`. `connectionTypes.ts` — types and `ConnectionRefusal` (status 400/403/404/409). `connectionRoute.ts` — the routes' answer for a refusal.

## Caller contract
Called by `pages/api/accounting/intercompany/*` inside `withAuth`: `sql` is the request's transaction as app_user with the session company's GUCs, so RLS limits every read and write to the session company. Service functions take the session `companyId` (and `userId` where a role check needs it). A refusal is thrown as `ConnectionRefusal` before anything is written; a refused write inside a savepoint (`withSavepoint`) does not poison the request's transaction.

## Main function signatures
- `listConnections(companyId, connectionId?)` — this company's connections, each with the pair `settings`, `canEditSettings` (write role in both companies), ITS OWN side and setup checklist only.
- `createGroupConnection(userId, companyId, partnerCompanyId)` — write role in both; both current members of one group (asked of `intercompany_in_one_group`, the definer helper); a revoked group connection is re-activated by one `UPDATE ... WHERE status = 'revoked'`, never duplicated; a concurrent create is a 409.
- `updateConnectionSettings(userId, companyId, connectionId, input)` — mode / cut-over / interest, write role in BOTH companies, not once revoked.
- `updateOwnSide(companyId, connectionId, input)` — partial update (absent key unchanged, null clears) of the session company's side; upsert on (connection, company).
- `revokeConnection(companyId, connectionId)` — either party.

## Business rules
- The pair is stored ordered (`company_low_id < company_high_id`, `orderedPair`); at most one LIVE (not revoked) row per pair (partial unique index). Kind never changes. External connections cannot be created until P6 (the guard refuses the INSERT).
- Settlement mode, cut-over date and interest rate belong to the PAIR (the connection row), not to a side. A group connection's change needs a write role in both companies (service and `intercompany_connections_guard`).
- A company never reads or writes its partner's side: RLS is `company_id = session company`. Customer/supplier must be the company's own (non-deleted) and linked to one connection per company (partial unique indexes: a second link is a 409); loan and default expense accounts its own, active and non-header (`isHeaderSql`). The database re-checks ownership in `intercompany_sides_guard`, and refuses any change once the connection is revoked.
- `auto_accept` only on a `group` connection, and only while both companies are in one group: `autoAcceptRefusal` in the service, `intercompany_sides_guard` (ENABLE ALWAYS trigger) in the database.
- A revoked connection releases its sides' customer and supplier links (`intercompany_release_links`, a registered definer fired by the status change, including the group-leave revocation); re-activating does not restore them.
- Group membership holds for the life of a group connection, and the group must be ACTIVE (`company_groups.is_active`, which `deleteGroup` clears). `intercompany_in_one_group(a, b)` (SECURITY DEFINER, registered in `app_definer_reviews`) is checked on create, re-activate, message insert and auto-accept. It answers only for a signed-in user of one of the two companies (never the session's company GUC), so it is false when `auth.uid()` is NULL and the P2 auto-accept worker needs its own definer path; it is no membership oracle. A pair that does share a group takes the two companies' rows of `intercompany_company_locks` (closed to every app role, one row per company, made by a trigger on `companies`) FOR SHARE until commit; a join takes ALL the group's members' rows FOR SHARE; the changers are STATEMENT-level triggers with transition tables on `company_group_members` and `company_groups` (UPDATE and DELETE) that take their whole set (the leavers, the parties of the connections the change would end, the members connected to a leaver) FOR UPDATE NOWAIT all or nothing, retrying, so a waiting changer holds nothing and a multi-row statement locks one set; the wait is bounded (`app.intercompany_changer_budget_ms`, default 10 s) and then fails with SQLSTATE 55P03, which withErrorHandler answers 503 + Retry-After from any route. They never return before locking except for a change that changes nothing. The protocol needs READ COMMITTED: `intercompany_in_one_group`, every changer, the joiner and the sides guard refuse with 40001 at REPEATABLE READ / SERIALIZABLE (as migration 886 does for `company_users`). A leave, a bulk leave, a deactivation or a group deletion at the same moment waits and then revokes what was created, two of them serialise, and a stranger can hold nothing (lock protocol in the 1002 header). app_user has no table-level UPDATE/DELETE/TRUNCATE on the group tables (it could `LOCK TABLE` them): UPDATE is granted by column, to what `groupCrudService` writes; a new writer of another column needs a column grant in a migration. They revoke the active group connections whose companies no longer share a current active group (`revoked_by` = `system:group-membership`, accepted by the connections guard only from migration_admin with a transaction-local flag) and switch their sides' `auto_accept` off. Whatever writes on a connection later (the P2 auto-accept worker) re-checks through the same helper at action time, not on its own read of `company_group_members`.
- Viewers read only: every app_user write on the five tables needs `intercompany_user_can_write(<acting company>)` in the guard (status changes, sides, sending and handling a message, links, keys).
- Messages: UNIQUE (from company, source doc type, source doc id, kind); for the allocation and payment kinds the source doc is the allocation / payment ROW id; inserted only on an ACTIVE connection between its two companies; the sender only inserts, the receiver moves a pending message on (a dismissal can be restored, accepted and rejected are final, accepting, rejecting and restoring need the connection active; an invoice / credit_note / interest_invoice names a source document of the SENDING company that fits its kind, and an accepted one names a target of the RECEIVING company that fits it: supplier invoice, or supplier credit note for a credit note; the kinds that create no document carry no target; a receiver document is the target of ONE accepted message per RECEIVING COMPANY, whatever the connection; a side's first save, a message send and a link insert read their connection FOR SHARE); `handled_via` is `auto` only when the session sets `app.intercompany_handled_via = 'auto'` AND the receiver's side has auto-accept on an active group connection; `error` holds a generic sentence, never raw SQL or exception text.
- Links (`intercompany_document_links`) are the authoritative pair record: a mirror link is made by the receiver of an accepted message and joins exactly its source and target documents (active at once; both are re-checked against the message's two companies, so a forged message row cannot link a third company's document); a manual pairing starts `pending_confirmation`, names a document that exists in the inserter's own company, and goes active when the other party confirms (a user with a write role in both companies of a group may confirm both); either party may unlink. A company document is in one live link at a time whatever the connection and the position (`intercompany_document_slots`, kept by a definer trigger: an active link holds both documents, a pending pairing only the side its inserter confirmed, so a partner cannot squat a document by proposing it; 1002 refuses to apply over duplicates; active links and their slots survive a revoke until a party unlinks); confirming needs the connection active and the confirmed side's document to exist in its company; one mirror link per message.

## P2: the mirror (messages in, drafts out)
Files: `mirrorPayload.ts` (PURE: build the sender's cents-exact snapshot; `parseMirrorPayload` validates what a receiver reads as untrusted input, `payloadBlocker` = ZAR only), `outboxRead.ts` + `outboxService.ts` (the sender: `mirrorApprovedInvoice`, `mirrorApprovedCreditNote`), `inboxRead.ts` / `inboxTypes.ts` / `inboxValidation.ts` (the receiver's list, counts, request shapes), `acceptContext.ts` (this company's side, account suggestions, duplicate lookup), `acceptBlockers.ts` (PURE), `acceptDocuments.ts` (the draft + the PDF copy), `acceptService.ts` (`previewAccept`, `acceptMessage`), `handleService.ts` (reject / dismiss / restore / `markMessageFailed`), `linkOrder.ts` (PURE), `receiverTx.ts` + `autoAcceptWorker.ts` (the worker), `mirrorErrors.ts`.

### Caller contract
- `approveCustomerInvoice` calls `mirrorApprovedInvoice(companyId, invoiceId)` after the PDF seal; `approveCreditNote` calls `mirrorApprovedCreditNote` for a CUSTOMER note. Both run on the approval's own transaction inside a savepoint and NEVER throw: a mirror that cannot be written (a refusal of the database, a session without a write role, a revoked connection) is logged (`warn`, the SQLSTATE only) and the approval stands. Known limit: nothing re-sends one that failed.
- The inbox routes (`pages/api/accounting/intercompany/inbox*`) call the receiver services inside `withAuth` as the session company; `acceptMessage(userId, companyId, messageId, input, { auto })` is the one accept, for a person's click and for the worker.

### Business rules
- **Messages only from the sender.** The sender writes its own outbox row and, for a GROUP pair, its own side of `intercompany_transactions` (one `sale` row, `unmatched`; a credit note is negative); it never writes in, or reads, the receiver's books. The sender's customer decides who is the partner (the side's `customer_id`, one connection per company); a message needs an ACTIVE connection, a cut-over date (none = nothing mirrors) and `document date >= cut-over`. One message per (from company, source doc type, source doc id, kind): an existence check first, the DB's UNIQUE behind it, so a retry or re-approval sends no second message and no second group row. A foreign-currency document IS sent (its currency is in the payload); the receiver refuses to accept it.
- **The payload is the sender's, untrusted.** `parseMirrorPayload(raw, kind, from_company_id)`: version 1, bounded strings and counts, every amount a 2 dp number, lines multiply out, line totals sum to the subtotal, line VAT to the VAT, subtotal + VAT = total, and a PDF path is exactly `<from_company_id>/<uuid>.pdf` (never another company's prefix). An invalid payload lists with its reason and can only be rejected or dismissed. The sender's `buildInvoicePayload` makes each line multiply out (else one unit at the line amount) and puts a header-VAT rounding gap of at most 5 cents on the largest line.
- **Accept = DRAFT only; nothing is approved or posted**, in ONE savepoint (a refusal, answered 4xx, commits nothing). It locks the message row, refuses a handled / dismissed one, re-checks the connection (active), the membership of a group pair (`intercompany_in_one_group`) and, for the worker, the side's `auto_accept`; needs the supplier linked on THIS company's side; refuses a duplicate (same supplier + number; credit notes by a `[IC <number>]` marker in the reason) before writing; chooses an account per line (the person's choice, else the account last used for the same sender description on this connection's accepted bills, case and spacing ignored, else the side's default expense account), all checked to be this company's, active, non-header (`accountsUsable`, then the bill's own account rules); creates the draft through `createSupplierInvoice` (`trustSourceTax`: the sender's exact line VAT; `externalRef` is NOT set, so the unique supplier + number index still catches a repeat) or `createCreditNote` (unlinked; the sender's exact VAT); copies the sealed PDF (best effort); marks the message accepted with its target; records the mirror link (`origin = mirror`, active); marks the sender's group row matched. The side's default dimensions ride on the draft's lines.
- **PDF copy.** Bytes are read through `downloadCapturedDocument(bucket, path, <sender company id>)`, which refuses a path outside the SENDER's prefix, must hash to the payload's `sha256`, and are stored under the RECEIVER's prefix as a captured document (`source_document_id` of the bill). A failure leaves the draft without it.
- **Reject** needs a reason (trimmed, at most 2000; the DB also requires it) and goes back to the sender's outbox row; it touches nothing else. **Dismiss** sets aside, **restore** brings it back (needs an active connection). Accepted and rejected are final. Viewers read only (`withWriteAccess` and the guard).
- **Auto-accept worker** (`autoAcceptWorker.ts`, `POST /api/cron/intercompany-auto-accept`, `scripts/isaflow-intercompany-auto-accept.{service,timer}`, every 10 minutes; installing the units is an ops step). It has no user and no company, and `intercompany_in_one_group` is false without a signed-in user, so it has its OWN definer path: `intercompany_auto_accept_queue(limit)` (1013; owner migration_admin; EXECUTE for app_service and migration_admin only, never app_user) lists pending invoice / credit-note messages whose RECEIVER side has `auto_accept` on an ACTIVE GROUP connection whose companies still share a current active group (`intercompany_shared_group`), with the receiver company and one write-role user in good standing (owner, then admin, then manager; `users.is_active`, status active, not suspended; company not suspended / deleted). It returns ids only. For each message the worker opens `withReceiverTx`: app_user, the claims of THAT user and the RECEIVER's company GUC (never the sender's), one transaction per message, lock_timeout 5 s, statement_timeout 60 s, and runs `acceptMessage(..., { auto: true })`: the same service, guards and RLS as a click. `handled_via = 'auto'` is set by the transaction-local GUC `app.intercompany_handled_via` (the guard honours it only with the side's flag on an active group connection). A refusal marks the message `failed` with the refusal's own sentence (or a generic one for a defect), once; a transient lock / serialisation fault leaves it pending for the next run. Auto-accept creates DRAFTS (the side form says "they go through your normal approval"): it never approves.
- A message accepted by the worker is attributed to the chosen write-role user (`handled_by`, the draft's `created_by`) with `handled_via = 'auto'`.
- Limits: messages that arrived before a side turned auto-accept on are accepted on the next run; recurring-invoice approvals by a user without a write role send no message; a message whose PDF could not be sealed at approval carries no PDF.

# services/audit/ — audit snapshots, comparison, check runs, sealed packs

## Purpose
Forensic-controls step 4 (migration 890, Hein's decisions D1–D4 2026-10-12). A **snapshot** freezes a company's
books at an accounting-date cutoff — the trial balance, every POSTED journal and line dated ≤ cutoff as canonical
rows with a material hash, ageing and control totals, the master-data high-water mark and a sealed **check run** —
and seals it: SHA-256 over canonical JSON + HMAC-SHA256 with a server key the database never sees. Later, a
**comparison** shows what changed behind it (backdated / changed / removed / reversed journals, TB movement,
master-data changes), and an **audit pack** (ZIP) is built from it with a manifest citing its hash.
Every snapshot carries the caveat: current values of records dated ≤ cutoff, as at taken_at — not the historical
database state.

## Caller contract
- `takeSnapshot(principal, { cutoff, trigger, maxLines? })` — ONE REPEATABLE READ transaction on its own pooled
  connection as app_user with the person's claims (`auditTx.runAuditTx`); refuses over `MAX_SNAPSHOT_LINES`
  (`SnapshotTooLargeError`) or without the key (`SigningKeyMissingError`) before anything is written.
  `principalFromRequest()` gives the principal inside withAuth / MCP.
- `verifySnapshot(companyId, id)` — in the request transaction (RLS: owner / admin / manager). Recomputes every
  row hash, the check run hash and the canonical hash from the stored rows, checks both seals with THOSE.
- `compareSnapshotToLive(principal, id)` / `compareSnapshots(principal, a, b)` (b later, cutoff ≥ a's; read at a's).
- `takeCheckRun(principal, asAt)` — a standalone run; `runAllChecks(window)` = 15 integrity (runIntegrityChecks,
  not forked) + 4 anomaly (runAnomalyScan, shared with the anomaly-scan route) + 5 journal-risk leads.
- `scheduleAutoSnapshot(trigger, cutoff)` (`autoSnapshotQueue.ts`) — called by closePeriod, lockPeriod, closeYear,
  closeFiscalYear, lockVatPeriod; queues after-commit work, never throws; one snapshot per trigger per request.
- `buildSnapshotPack` / `storePack` / `verifyPack` (`packExport.ts`) — the audit-exports route's pack.
- Who: `auditAccess.ts` — read owner / admin / manager; take / run / build owner / admin (web: own session only).

## Business rules
- Rows are spelled by the database (ids/dates text, amounts numeric::text 2 dp, timestamps UTC µs) so a hash
  recomputes years later; canonical JSON refuses fractional JS numbers and Dates (`canonical.ts`).
- Written only through 890's definers `audit_snapshot_record` / `audit_check_run_record` (one call, every row): they
  bind taken_by = auth.uid(), the company GUC + membership, taken_at = now(), the channel from the claims, and the
  role the trigger needs. Append-only for every role; purge cascade only. A forged row fails verification (no key).
- Automatic snapshots run after the lock COMMITs; a failure records a `failed` attempt with the reason; a lock that
  did not stand (rolled-back savepoint) takes nothing; a lost one (restart) shows as `unrecordedLocks`.
- Verify decides integrity before the key (a rotated key never hides tampering) and checks the filing columns (line
  `journal_id`, journal `entry_date`, TB `account_id`) against the sealed rows. Line rows carry the account id only.
- Packs: `manifest.sig.json` seals the manifest (`PACK_SEAL_DOMAIN`); `verifyPack` reports `missing` for a ZIP without it.
- Bulk reads and the check run run with nested loops off (`bulkPlan`): stale statistics after a bulk load made
  50 000 lines take 65 s. Measured cap and storage: `docs/evidence/audit-snapshots/size-cap-measurement.txt`.

- Chain: sealed snapshots carry `seq` + `prev_hmac`, both signed; `verifyChain` finds a missing or replaced link.
  One snapshot per company at a time (`runAuditTx` chainLock, before BEGIN), two per process (`snapshotSlots`).
- Automatic snapshots of an unchanged ledger record `unchanged` (`snapshotAttempts.unchangedSince`, ledger fingerprint).
- Key rotation: `AUDIT_SNAPSHOT_RETIRED_KEYS` (`id=secret,…`) keeps old keys for verification; a key id with no key is `invalid`.

## Known limits
- The N1/N3 boundary (raw SQL that RESETs ROLE; the owner can disable guards) — but no one without the key can make a
  seal verify. Old seals verify only while their key is listed in `AUDIT_SNAPSHOT_RETIRED_KEYS`.
- Master-data high-water and changes are read under the reader's own RLS (a manager sees fewer types).
- Storage: ~520 bytes per frozen line, per snapshot; every close / lock takes one.

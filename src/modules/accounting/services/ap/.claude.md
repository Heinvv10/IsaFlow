## Caller contract
Invoked by `withAuth`-wrapped API routes in `pages/api/accounting/ap/*`. Every public DB function takes `companyId` first. Workflow functions additionally take `userId` for stamping.

## Main function signatures
- `getSupplierInvoices(companyId, filters?) / getSupplierInvoiceById(companyId, id) / createSupplierInvoice(companyId, input)`.
- `approveSupplierInvoice(companyId, id, userId)` — posts JE: DR Expense + DR VAT Input, CR AP.
- `performThreeWayMatch(companyId, invoiceId, userId)` — links PO ↔ GRN ↔ invoice; persists via parent `supplier_invoices` scope (2026-04-22 fix).
- `createSupplierPayment / approveSupplierPayment / processSupplierPayment(companyId, id, userId)` — JE: DR AP, CR Bank.
- `generateStandardBankEFT(batch) / generateFNBEFT / generateABSAEFT / generateNedbankEFT` — pure, return fixed-width strings.
- `submitNetcashBatch(payload) / getNetcashBatchStatus(ref)`.
- `getApAging(companyId, asOfDate)`.
- `getSupplierStatementBalances(companyId, asAtDate)` preserves gross ageing and reports unallocated payments/credit notes separately as `onAccount`; `netBalance = total - onAccount`. The supplier-statements list and CSV use the net figure; AP ageing itself remains invoice-based.

## Business rules
- **Lock order**: the canonical sequence for every settlement path (bank line → payment → invoices → GL) lives in `bank/.claude.md`. Read it before adding a lock here; a path that takes two of these rows out of sequence deadlocks against one that does not (40P01 → 500).

- `supplier_invoices.status`: `draft → approved → posted → paid`, plus `void`. `match_status`: `unmatched | partial | matched`.
- PO state: `draft → sent → partial → received → closed`.
- Posting runs inside the REQUEST transaction (withAuth, PR #264) — the services open none of their own; JE header gets `source='supplier_invoice'` but NOT the invoice id as `sourceDocumentId` (2026-04-24 fix — FK is to `documents`).
- 4-way match uses separate qty + price tolerances; Phase 6 expectation engine + missing-invoice chase triggers when POs lack invoices (PRD-05).
- Two PO families exist in the current schema: `purchaseOrderService` uses `supplier_purchase_orders`; flat purchase-order and GRN routes use `purchase_orders`/`po_items`. Child rows derive company scope through their parent; `po_items` and `grn_items` have no `company_id`. Do not interchange these families.
- EFT amounts are centified (×100) inside `formatEFTAmount` — pass Rands, not cents.
- `netcashService` returns `mock: true` when `NETCASH_API_KEY` missing — production must not gate on absence.
- `validatePaymentAllocations` (shared with AR, in `utils/paymentAllocation`) throws if allocations ≠ payment total before any DB write.
- **`fetchBillCandidates` (`supplierAllocationLines`) LOCKS the bills it decides from** — `ORDER BY si.id`, `FOR UPDATE OF si`, 5s `lock_timeout`, 55P03 → `SupplierPaymentRefusal` ("retry in a moment"). Paying a bill is a check-then-act on `amount_paid` and nothing else on the AP path locks it: `lockSupplierPaymentForUpdate` protects a payment this request created, `bankTxLock` a bank LINE. Without it two lines against one bill both passed, and the only thing that stopped the second was a collision on `uq_gl_je_company_entry_number` — a 500 where the answer is a 400. The AR mirror is `fetchInvoiceCandidates`; keep the two identical. It THROWS outside a request transaction (`core/requestTransaction`), because an implicit one releases the lock at the end of the statement and discards the `SET LOCAL`.

Same 5s lock_timeout and the same `isLockContention` mapping as the payment lock. **The regression test drives the PLANNER, not two whole allocations**: two concurrent `allocateTransaction` calls collide on the journal-number unique index first, so the run fails for a reason that has nothing to do with refunds and the race is never reached. (2) `supplierStatementBalancesService`'s per-row `GREATEST(total - alloc, 0)` floored a refund to zero and `HAVING SUM(...) > 0` compounded it, so that API and the aged netting disagreed by exactly the refund. - 2026-09-19 (refund ceiling): the back-fill reads the SAME ceiling as the live path. `planSupplierRefund` refuses a refund larger than the supplier's on-account credit; the batch path minted `create_refund` regardless, so two writers were creating one document under two rules. - 2026-09-19: **The supplier refund DOCUMENT — `ap/supplierRefundDocument`, migration 681.** A money-IN line against a supplier posts DR Bank / CR Accounts Payable and created NO document: `allocateTransaction`'s supplier arm gates `recordSupplierBankPayment` on `isSpent` (correctly — a positive payment document for a refund is cash the company never paid) and nothing took its place. The control account moved, the subledger did not, the journal surfaced under `posting_with_no_document`, and the supplier's on-account credit stayed OVERSTATED by the whole refund. It is now a **negative on-account entry**: a `supplier_payments` row at `payment_method = 'refund'` with a NEGATIVE `total_amount`, carrying the bank line's journal, never allocated and never auto-applied. **It is not a credit note** — a credit note is the supplier reducing what it billed, a refund is cash physically back in the bank. Four things worth not re-deriving. (1) **The sign is a CONSTRAINT, not a convention.** 681 pins it to the method in both directions, which is what lets every reader discriminate on `payment_method` instead of on whether a number happens to be negative. (2) **The ceiling is decided BEFORE the journal posts.** `withAuth` COMMITs on a 4xx and rolls back only on a 5xx, so a refund exceeding the supplier's on-account credit had to be refused while there was still nothing to unwind — hence the plan/record split, with `planSupplierRefund` called from the supplier arm before `createJournalEntry`. A refund past the credit would leave the supplier owing the company, which is a receivable and belongs on no payable document; it refuses rather than clamping. (3) **The allocation cap is `GREATEST(total, 0)`, everywhere.** The old `LEAST(allocated, total_amount)` caps a refund's allocations at its own NEGATIVE total, so the remainder computes to exactly zero and the row vanishes from every figure built on `shared/unappliedPaymentBasis` — the credit then reads as though the cash never came back. Same fix in `shared/agedNetting`, where the threshold also had to become `ABS(...) > EPS`. (4) **It is never applied.** Applying a negative remainder to a bill un-pays it; `autoApplyBackfillSkips` reports it under `SKIP_REFUND` rather than filtering it out, so the plan still reconciles line for line against `list_unapplied_payments`. The AR mirror (`ar/customerRefundDocument`) is the same shape on `customer_payments` — money OUT to a customer, DR Accounts Receivable / CR Bank — and had the identical hole for the mirror-image reason.

- **Supplier payments**: `supplierPaymentService.ts` (CRUD), `supplierPaymentWorkflowService.ts` (approve/process), `batchPaymentService.ts` (bulk EFT runs).

- **Subledger snapshot (point-in-time)**: `apSubledgerService.ts` — every open bill as at a date, on the same population and rewind as `apAgingService`. Consumed by `services/reconciliation/`; see `ar/.claude.md` for why the two must not diverge.
- **Migration**: `migrationApService.ts` — import from staging tables.
- `index.ts` — barrel re-export (workflow files excluded due to symbol conflicts).

## Caller contract
Invoked by `withAuth`-wrapped API routes in `pages/api/accounting/ap/*`. Every public DB function takes `companyId` first. Workflow functions additionally take `userId` for stamping.

## Main function signatures
- `getSupplierInvoices(companyId, filters?) / getSupplierInvoiceById(companyId, id) / createSupplierInvoice(companyId, input)`.
- `approveSupplierInvoice(companyId, id, userId)` — posts JE: DR Expense + DR VAT Input, CR AP.
- `performThreeWayMatch(companyId, invoiceId, userId)` — links PO ↔ GRN ↔ invoice; persists via parent `supplier_invoices` scope (2026-04-22 fix).
- `createSupplierPayment / approveSupplierPayment / processSupplierPayment(companyId, id, userId)` — JE: DR AP, CR Bank.
- `generateStandardBankEFT(batch) / generateFNBEFT / generateABSAEFT / generateNedbankEFT` — pure, return fixed-width strings.
- `submitNetcashBatch(payload) / getNetcashBatchStatus(ref)`.
- `getApAging(companyId, asOfDate)`.
- `getSupplierStatementBalances(companyId, asAtDate)` preserves gross ageing and reports unallocated payments/credit notes separately as `onAccount`; `netBalance = total - onAccount`. The supplier-statements list and CSV use the net figure; AP ageing itself remains invoice-based.

## Business rules
- `supplier_invoices.status`: `draft → approved → posted → paid`, plus `void`. `match_status`: `unmatched | partial | matched`.
- PO state: `draft → sent → partial → received → closed`.
- Posting runs inside the REQUEST transaction (withAuth, PR #264) — the services open none of their own; JE header gets `source='supplier_invoice'` but NOT the invoice id as `sourceDocumentId` (2026-04-24 fix — FK is to `documents`).
- 4-way match uses separate qty + price tolerances; Phase 6 expectation engine + missing-invoice chase triggers when POs lack invoices (PRD-05).
- Two PO families exist in the current schema: `purchaseOrderService` uses `supplier_purchase_orders`; flat purchase-order and GRN routes use `purchase_orders`/`po_items`. Child rows derive company scope through their parent; `po_items` and `grn_items` have no `company_id`. Do not interchange these families.
- EFT amounts are centified (×100) inside `formatEFTAmount` — pass Rands, not cents.
- `netcashService` returns `mock: true` when `NETCASH_API_KEY` missing — production must not gate on absence.
- `validatePaymentAllocations` (shared with AR, in `utils/paymentAllocation`) throws if allocations ≠ payment total before any DB write.

## Recent changes
- 2026-09-09: **Soft-deleted bills leave AP aging, the AP subledger snapshot and the supplier statement** (audit K-053). Mirror of the AR entry — see `ar/.claude.md` for the reasoning, including why the aging service and `apSubledgerService` had to gain `deleted_at IS NULL` in the same change and why soft-delete now reverses the approval journal. Two AP-only notes. (1) `reports-supplier-ledger` gained `si.deleted_at IS NULL` on its invoice leg and NOTHING ELSE: round 3 added a `status NOT IN ('draft','cancelled')` filter and round 4 reverted it, because the payment leg lists whole `supplier_payments` rows rather than allocations, so anything dropped from the invoice leg leaves its payment behind with no matching debit and drives the running balance negative. A soft-deleted bill cannot carry one — `assertInvoiceDeletable` refuses — so the `deleted_at` filter is safe where a status filter is not, and excluding draft/cancelled bills from a supplier ledger is a report contract change outside K-053 in any case. (2) A bill carrying payments can no longer be soft-deleted, which is what stops the statement showing a payment whose bill has been hidden. The dated as-at predicate is the AR entry's point (3) and applies identically here.
- 2026-09-09: **`postSupplierInvoiceToGL` takes `lockSupplierInvoiceForUpdate` before its read** (audit K-014). It decided on `glJournalEntryId` from a plain SELECT and then overwrote it, so two overlapping "Post to GL" calls both read NULL, both posted an Expense/VAT/AP journal, and the second UPDATE stranded the first where `cancelSupplierInvoiceInner` (which reverses only the id on the row) can never reach it — AP, expenses and input VAT doubled. `approveSupplierInvoice` had locked since the C1 sweep; this path was the remaining asymmetry, and an approve holding the lock did not block it. The loser now blocks, re-reads settled state and returns `{ alreadyPosted: true }` with the winner's journal id. Consequence worth knowing: the lock carries a 5s `lock_timeout` whose 55P03 ABORTS the request transaction, and the whole batch is one transaction — so `supplier-invoices-bulk-action.ts` now wraps every id in its own `withSavepoint('bulk_supplier_invoice_item')`. Without it a single contended bill discarded the entire batch while the route still answered 200 with a success count, because withAuth's COMMIT on a <500 response is executed as ROLLBACK without raising. If the savepoint's own rollback fails (`ctx.txUnusable`) the route now throws instead of reporting per-id results.
- 2026-09-09: Supplier statement balances now reconcile invoice ageing with on-account funds, using live `payment_allocations` and credit-note `applied_amount` to avoid deducting applied settlement twice. Credit-only suppliers remain visible. List links and detail queries share the selected date cutoff. No ledger balances or allocations are changed.
- 2026-09-08: `goodsReceivedService` restores GRN creation through company-owned locked PO/item rows, pre-write line/quantity/status validation and atomic receipt/PO updates. `goodsReceivedValidation` accepts finite nonnegative two-decimal quantities (matching numeric15,2 storage). Same-company GRN numbers are serialized. Rejected quantities do not increment accepted quantities. The receipt form uses the PO detail route and supports successive partial receipts; no GL posting, stock valuation or historical repair is introduced.
- 2026-09-07: **The supplier-invoice line editor now warns when a taxed line is coded to an account where no supply can arise.** `approveSupplierInvoice` posts `vatType: 'standard'` on every line whenever the invoice's tax amount is non-zero, against whatever GL account the line names — and no invoice screen said a word about it, while the bank screens have warned since the guard shipped. An approver clicking through a captured invoice miscoded to Salaries & Wages got no signal at all. `BillLineItemsTable` classifies each line with `classifyNonSupplyAccount` from the pure `gl/nonSupplyAccounts` module (the same one the bank screens and the report use, so the screen and the ledger cannot disagree) and shows the amber `NON_SUPPLY_LABEL`/`NON_SUPPLY_ADVICE` copy. **Warns, never blocks** — same reasoning as the bank screens: the classification is name-matched and a handful of real names are ambiguous (labour-broker wages, investment property, payroll software), so the choice stays the approver's. Unlike the bank screens there is no unattended twin to coerce: nothing posts a supplier invoice on a schedule. No warning when the line carries no tax, and none before an account is chosen. **Be precise about what the screen covers**: `approveSupplierInvoice` posts ONE combined VAT line from the stored header `taxAmount` and the expense lines carry no vatType at all, so the posting decision is invoice-wide and blind to which line's account is non-supply. On the creation screen the two agree because the header tax is the sum of the per-line tax; on an invoice captured or edited elsewhere they need not, and a screen with no warnings is not proof the posted claim is clean. The exceptions report checks the posted side. `supplierInvoiceWorkflowService` stays on the trip-wire's ATTENDED allowlist with that caveat written into the entry.
- 2026-09-03: **Cash application — `supplierPaymentApplicationService` + `supplierAllocationLines` + `supplierBankPaymentService`.** The AP mirror, and the AP defect is worse than the AR one. `allocateTransaction(allocType='supplier')` inserts NOTHING: it posts DR Accounts Payable / CR Bank and calls `fourWayMatchService#recordPaymentMatch`, which sets a `payment_matched` BOOLEAN and never moves `amount_paid` or `status`. There is no payment document at all, so a bill can never be reconciled to the cash that paid it — 17 Brightsphere bills read as open at R613,641.77 against a Sage book showing every one paid, and **397 Velocity Fibre bills are flagged `payment_matched = true` while still showing R16,151,543.00 outstanding**. `supplierBankPaymentService` creates the missing `supplier_payments` row at status `processed` carrying the allocation's journal. Four things worth not re-deriving. (1) **`payment_allocations` is the LIVE table.** Migration 201's `supplier_payment_allocations` holds zero rows in dev AND prod and is read by nothing; `processSupplierPayment`, `voidSupplierPayment` and `batchPaymentService` all use `payment_allocations`. `pages/api/accounting/supplier-allocations.ts` used to read and write the dead one, so every allocation it made was invisible downstream — it now calls this service, on both halves. (2) **`payment_matched` is DERIVED, never preserved.** `recordPaymentMatch` flags the FIRST invoice named using the FULL bank-line amount, so a R1,000 line allocating R300 to a R600 bill flags it matched before the apply runs. A `CASE … ELSE payment_matched` kept that lie; the column is assigned from the settlement state and `payment_matched_at` is cleared when the flag goes false. (3) **A partly applied payment KEEPS its status.** The old route set a PROCESSED payment back to `'approved'`, walking a posted payment backwards — and `voidSupplierPayment` accepts only `processed`, so it also quietly became un-voidable. Only a FULLY applied payment moves, to `reconciled`. (4) Plan/apply split, row lock, guards-before-writes and the closed-period pre-check all mirror the AR side exactly; see `ar/.claude.md`.

## Caller contract
Invoked by `withAuth`-wrapped API routes in `pages/api/accounting/ap/*`. Every public DB function takes `companyId` first. Workflow functions additionally take `userId` for stamping.

## Main function signatures
- `getSupplierInvoices(companyId, filters?) / getSupplierInvoiceById(companyId, id) / createSupplierInvoice(companyId, input)`.
- `approveSupplierInvoice(companyId, id, userId)` — posts JE: DR Expense + DR VAT Input, CR AP.
- `performThreeWayMatch(companyId, invoiceId, userId)` — links PO ↔ GRN ↔ invoice; persists via parent `supplier_invoices` scope (2026-04-22 fix).
- `createSupplierPayment / approveSupplierPayment / processSupplierPayment(companyId, id, userId)` — JE: DR AP, CR Bank.
- `generateStandardBankEFT(batch) / generateFNBEFT / generateABSAEFT / generateNedbankEFT` — pure, return fixed-width strings.
- `submitNetcashBatch(payload) / getNetcashBatchStatus(ref)`.
- `getApAging(companyId, asOfDate)`.
- `getSupplierStatementBalances(companyId, asAtDate)` preserves gross ageing and reports unallocated payments/credit notes separately as `onAccount`; `netBalance = total - onAccount`. The supplier-statements list and CSV use the net figure; AP ageing itself remains invoice-based.

## Business rules
- **Bill currency (FX PR0, migration 871):** `createSupplierInvoice` and the POST route (before the number reservation) call `shared/documentCurrency.resolveDocumentCurrency(…, 'bill')` — `companies.functional_currency` is the one authority (`default_currency` is only a form default). A foreign bill needs `fx_documents_enabled`; no `amount_paid` may move on one (DB `fx_settlement_refusal`). `functional_total` = `public.fx_functional(total, rate)` on create and draft update.
- **Lock order**: the canonical sequence for every settlement path (bank line → payment → invoices → GL) lives in `bank/.claude.md`. Read it before adding a lock here; a path that takes two of these rows out of sequence deadlocks against one that does not (40P01 → 500).

- `supplier_invoices.status`: `draft → approved → posted → paid`, plus `void`. `match_status`: `unmatched | partial | matched`.
- PO state: `draft → sent → partial → received → closed`.
- Posting runs inside the REQUEST transaction (withAuth, PR #264) — the services open none of their own; JE header gets `source='supplier_invoice'` but NOT the invoice id as `sourceDocumentId` (2026-04-24 fix — FK is to `documents`).
- 4-way match uses separate qty + price tolerances; Phase 6 expectation engine + missing-invoice chase triggers when POs lack invoices (PRD-05).
- Two PO families exist in the current schema: `purchaseOrderService` uses `supplier_purchase_orders`; flat purchase-order and GRN routes use `purchase_orders`/`po_items`. Child rows derive company scope through their parent; `po_items` and `grn_items` have no `company_id`. Do not interchange these families.
- EFT amounts are centified (×100) inside `formatEFTAmount` — pass Rands, not cents.
- `netcashService.submitEftBatch` refuses (nothing sent) when a key is missing - production must not gate on absence; only the status poll and connection test still answer a mock.
- `validatePaymentAllocations` (shared with AR, in `utils/paymentAllocation`) throws if allocations ≠ payment total before any DB write.
- **`fetchBillCandidates` (`supplierAllocationLines`) LOCKS the bills it decides from** — `ORDER BY si.id`, `FOR UPDATE OF si`, 5s `lock_timeout`, 55P03 → `SupplierPaymentRefusal` ("retry in a moment"). Paying a bill is a check-then-act on `amount_paid` and nothing else on the AP path locks it: `lockSupplierPaymentForUpdate` protects a payment this request created, `bankTxLock` a bank LINE. Without it two lines against one bill both passed, and the only thing that stopped the second was a collision on `uq_gl_je_company_entry_number` — a 500 where the answer is a 400. The AR mirror is `fetchInvoiceCandidates`; keep the two identical. It THROWS outside a request transaction (`core/requestTransaction`), because an implicit one releases the lock at the end of the statement and discards the `SET LOCAL`.

- **Supplier bank verification** (opt-in: `approval_enforcement` row `supplier_bank_details`): verified iff the latest `supplier_bank_verifications` row's fingerprint equals `supplier_bank_fingerprint()` of the supplier's current five bank columns — DERIVED, never a flag; app code never hashes bank details itself. Only money LEAVING is gated (EFT file, Netcash); recording a payment, a batch, a bank allocation or an import never is. The gate reads the file's bank columns WITH their fingerprint, then share-locks the payees (id order) and refuses a payee not verified now or whose read details are not its current ones. A verifier: cookie session (not impersonated, not MCP), role ≥ the verifier role — `supplierBankVerifierRole`: the strictest active supplier_payment/payment_batch rule's role, never below admin (a rule only raises it) — falling back to admin only when nobody who did not set the details holds a raised role and every setter holds it (`ap/supplierBankVerifiers.ts`); own role and standing read from the DB; not in `bank_details_setters` unless no OTHER active member reaches admin (`self_verified` + roster, re-checked by the 876 guard). Disabling needs `mayWeakenAtLevel` at the verifier role. Only the company's FIRST switch-on baselines (`bankVerificationEverOn`; 876 guard too), and it skips soft-deleted suppliers and those whose current details the switcher set. "Latest" is by `seq`, which the 876 guard always draws itself.
- **An approved batch is paid only as it was approved (migration 922), enforcement ON OR OFF.** `approveBatch` stores the batch's `payment_batch` digest (`approval_document_digest`, the approval gate's own — never a second definition) in `supplier_payment_batches.approved_digest`, in the UPDATE that approves it, payees share-locked in id order first. `batchBankFileGate.assertBatchMayBeSent` (eft-generate, netcash/submit) and `processBatch` call `batchApprovedDigest.assertBatchUnchangedSinceApproval` — payees share-locked, then 409 `BATCH_CHANGED_SINCE_APPROVAL` (`details: { reason, batchId }`) when the current digest differs; processed batches are compared at file time too (the file uses live bank details). Under enforcement the approval gate runs FIRST, so its `APPROVAL_STALE` answer is unchanged. NULL digest (approved before 922) passes with a `log.warn`; no backfill. Way out: re-approve — `approveBatch` accepts an approved or processed batch whose stored digest no longer matches, keeps its status, re-runs the gate, stores the new digest, moves the members' `approved_by` to the re-approver and writes an `audit_log` `approve` row (`supplier_payment_batch`, `metadata.reapproved`); an unchanged (or legacy) one stays `BATCH_NOT_APPROVABLE`. A re-approve must name what the approver saw: the batch GET returns `contentDigest` (read BEFORE the payments it lists) and the page sends it as `expectedDigest`; missing or different → 409 `BATCH_CONTENT_NOT_AS_SHOWN`. A draft's first approve checks it only when given (the list page approves drafts without one). The batch GET returns `changedSinceApproval`; the batch page shows the re-approve notice (re-approve is on the detail page only). **Named limit:** the digest does not cover the supplier NAME (EFT beneficiary / Netcash account holder) nor the paying GL account's number and branch (EFT originator) — a change to either after approval is not refused, enforcement on or off; widening `approval_document_digest` is the follow-up (`.claude/handoffs/2026-10-23-payment-digest-name-originator-goal.md`).

## Caller contract
Invoked by `withCompany`-wrapped API routes in `pages/api/accounting/**`. Most functions take `companyId` first; exceptions: `companyService.listCompanies` (admin, returns all), `jobQueueService` (job rows carry their own `company_id`), `userInvitationService` (invitations are orgless at create time).

## Business rules
- **User identity is a STRING, never a uuid.** `users.id` is `character varying`; `company_users.user_id` is `text`. NEVER write `user_id = ${x}::UUID` or `users.id = ${x}::UUID` — Postgres has no `text = uuid` operator, so it throws at RUNTIME (500), and neither `tsc` nor eslint can see inside a SQL template string. When joining a uuid column onto `users.id`, cast the **uuid** side: `ON u.id = t.approved_by::TEXT`. `company_id` IS a uuid and keeps its cast. Guarded by `scripts/ci/audit-user-id-casts.ts` (static) + `tests/integration/user-id-join-compat.int.test.ts` (schema probe).
- **Tenant-membership guards live in `companyAccessService`** — `userBelongsToCompany` / `userBelongsToGroup`. Do not re-inline them into API routes; four routes each kept their own broken copy before this was extracted.
- `listCompanies` and other admin-only calls must NOT appear in tenant-scoped API paths — enforce via route selection.
- `logAudit` is fire-and-forget: callers don't await failure; service swallows its own errors to keep write-paths unblocked (but no empty `catch` — logs via `log`).
- `documentStorageService`: magic-byte check runs before S3 put; entity ownership verified against `companyId` before linking.
- `jobQueueService`: concurrent workers safe via `SELECT ... FOR UPDATE SKIP LOCKED`; lifecycle `pending → running → completed|failed`.
- PayFast ITN: validated via HMAC signature in `paymentGatewayCore`; idempotency via PayFast transaction id.
- Evidence graph is read-only — joins GL lines back to `captured_documents` / `extracted_data`.
- Sage import uses savepoints per record so one bad row doesn't roll back the whole run; dates coerced Date→ISO (2026-04-24 fix).
- **Migration opening balances are signed against the account's normal side.** In `ParsedAccount.openingBalance` a positive figure sits on the account's own normal side and a negative one on the opposite side (a bank in overdraft, a supplier in debit, a negative contra). `migrationOpeningBalanceService.postOpeningBalances` and `migrationExecuteService.verifyBalances` (`isaflowBalance = normal_balance === 'debit' ? net_debit : -net_debit`) share that convention — change one and you must change the other. A debit-signed source export is not importable and the totals check refuses it. `postOpeningBalances` is all-or-nothing: an unresolved account, an account this source does not own (`imported_from !== source`, which is also how a rolled-back account is released back to the company), or a source that does not foot throws before anything is written. The separate wizard path (`migrationImportService.importOpeningBalances` → `openingBalancePostingService`) takes explicit debit/credit columns instead and rejects negatives outright.

## Recent changes

- 2026-09-09: **A document the migration wizard imports is a TAKE-ON, not an origination** (audit K-015 / R-001, R-002, R-020). `importARInvoices` and `importAPInvoices` post ONE two-line entry at `total_amount - amount_paid` — DR the control account, CR `opening_balance_equity` (mirrored for AP) — and **no revenue, expense or VAT line at all**. `buildTakeOnLines` in `migrationPostingSupport` is the single place that shape is decided; a document settled in full before the cutover creates the document and posts nothing, leaving `gl_journal_entry_id` NULL. The deciding reason is VAT: `getVATReturn` is GL-based and sweeps every posted `vat_input`/`vat_output` line with a NULL `vat_type` into boxes 1 and 15, so posting the invoice in full re-declared its VAT in a period that is usually already filed. Lines that are never written need no filter. Consequences worth knowing: (a) every take-on file now needs an `opening_balance_equity` account on the chart — `resolveTakeOnClearingAccountId` refuses the step up front, once, naming the role and the remedy; (b) `subtotal + tax` no longer has to equal `total` to the cent — up to 5c imports with a warning (persisted on the session as an `errors` entry with `severity: 'warning'`, so it survives a reload), beyond that the row is refused; (c) the trial balance may carry an AR or AP control total **instead of** the documents (a summary-only take-on) but never as well — `importOpeningBalances` records which control totals it accepted in `steps_completed` (`opening_balances_ar_control` / `_ap_control`) and `assertNoOpeningControlTotal` refuses the matching document step, and vice versa. The refusal in that direction is gated on `{ar,ap}_invoices_imported > 0` — documents actually TAKEN ON — not on the step flag, which is written even by a run that imported nothing and would otherwise bar the summary-only route for good; (d) `completeSession` records, but does not enforce, the `opening_balance_equity` residual for entries posted since the session started — it is a warning, and the message says the residual is expected when the whole trial balance was balanced on that account rather than accusing the operator of a double count. Both document steps AND `importOpeningBalances` take `lockMigrationImport` (a transaction-scoped advisory lock keyed on the company) before reading the session: the interlock is a read-then-write both sides perform, and without it an overlapping pair each read a session without the other's mark and both post. `importOpeningBalances` (now in `migrationWizardOpeningBalanceService.ts`) is NOT a one-way door: it rewrites BOTH control flags from each run's own trial balance — including `false` — and reverses the entry its previous run posted for this session before posting the new one, so the remedy `assertNoOpeningControlTotal` prints ("remove the control account row and re-run the opening balances step") actually clears the refusal instead of posting a second full trial balance. Both invoice routes validate the body ROW BY ROW (`parseInvoiceRows` in `migrationRowSchemas`) rather than with one `safeParse`: a single bad line used to 400 all 5000 with a `fieldErrors` key of `invoices` and no row number. The rows that parse still import, and the services take an `ImportRowContext` so every `row` they report is a position in the operator's FILE, not in the shortened array. The persisted `severity: 'warning'` entries are read back by the migration hub (`SessionIssues` on `pages/accounting/migration/index.tsx`), which is what makes the durability real. WIZARD PATH ONLY: the Sage commit path posts its own journals and still re-declares VAT.
- 2026-09-09 (review round 3): **the counted refusal never reached the operator, and a scoped delete that matched nothing reported success.** Three layers each threw the message away. The page (`pages/accounting/cost-centres/index.tsx`) called `apiFetch` with no `res.ok` check inside an empty catch — `apiFetch` RESOLVES on 4xx, so the 400 was never an exception and Delete looked like a silent no-op. And the whole page read `json.message`, but `apiResponse.error()` nests it at **`json.error.message`** — the convention `cashbook.tsx` and `my-account.tsx` already use. A browser run against a dev server is what caught the last two; the integration test asserting only `statusCode === 400` passed throughout. `deleteCostCentre` now carries `RETURNING id` and throws `Cost centre not found` when nothing matched, mirroring `toggleCostCentre` — a nonexistent id, an already-deleted id and another tenant's id used to return 200 `{ deleted: true }`. The guard also counts **`bank_transactions.cc1_id/cc2_id`** (no FK, written by `bankAllocationService` and the `save_selection` route; `bankAllocationService` copies the id onto the journal line at allocation, so a dangling value here becomes a dangling value in the ledger), and migration 660 makes `cost_centres.parent_id` RESTRICT — the children count is company-scoped and nothing constrains a parent and child to the same tenant, so a cross-tenant child was silently orphaned to NULL.
- 2026-09-09: **deleting a cost centre used to unassign every employee on it (K-110), and three counts were structurally always zero (K-111).** `deleteCostCentre` counted `gl_journal_lines` only, while `payroll_employees.cost_centre_id` (mig 450) was ON DELETE SET NULL and `assets.cost_centre_id` (mig 361) had no action clause — a payroll-only centre deleted cleanly and nulled every assignment, writing no `payroll_employee_history` row, so the assignment is unrecoverable. The writes always landed — only the operator's feedback was wrong, and an operator reading "0 reassigned" as a failure who reverses the merge by hand moves live documents to the wrong supplier.
- 2026-09-09: `migrationOpeningBalanceService.postOpeningBalances` posts a balance on the side its SIGN implies, at its absolute value.

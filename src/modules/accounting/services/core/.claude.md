## Caller contract
Invoked by `withCompany`-wrapped API routes in `pages/api/accounting/**`. Most functions take `companyId` first; exceptions: `companyService.listCompanies` (admin, returns all), `jobQueueService` (job rows carry their own `company_id`), `userInvitationService` (invitations are orgless at create time).

## Main function signatures
- `createCompany(input) / updateCompany(id, input)`; `createInvitation(companyId, email, role, invitedBy)` (no `acceptInvitation`: both accept routes accept; S-07c).
- `logAudit({ companyId, entity, action, before?, after?, userId })` — never throws.
- `requireRequestTransaction(fnName)` (`requestTransaction.ts`) — the ALS-bound client, or a THROW naming the caller. Every `FOR UPDATE` helper needs it: outside a request transaction Postgres runs the SELECT in an implicit one, releases the lock at the end of the statement and discards the surrounding `SET LOCAL lock_timeout`, so the lock reads as taken, protects nothing, and waits forever. `paymentLock`, `bankTxLock`, `creditNoteLock` and `supplierInvoiceLock` predate it and keep their own copies.
- `uploadDocument({ companyId, file, entityId?, entityType? })` — validates magic bytes, enforces entity ownership.
- `entityIdsWithDocuments(companyId, entityType, ids)` (`documentQueryService.ts`) → the subset of `ids` with at least one active document, direct or via `document_links`; one query per page; an id counts only when it is a row of `entityType`'s own table in this company (the `owned` CTE fence).
- `resolveAccountEvidence(companyId, accountId, period)` / `resolveJournalEntryEvidence(companyId, jeId)` — PRD-05 drill.
- `categorizeBankTransaction(companyId, tx) / bulkCategorize(companyId, txs)` — pre-loads rules/patterns once per bulk.
- `enqueueJob({ jobType, payload, companyId })` / `getNextJob(jobTypes?)` / `markJobComplete / markJobFailed`.
- `enableOnlinePayment(companyId, invoiceId)` → payment link URL, or null (nothing written) for an invoice that is not this company's, cancelled, soft-deleted or fully paid; `handleITN(payload)` → payment confirmation + GL post.
- `importLedgerTransactions(companyId, userId) / importSupplierInvoices(companyId, userId)` — Sage Phase 6 importers.

## Business rules
- **Cost centres and business units have ONE write path each** (#678 review, 2026-10-09): `gl/dimensions/dimensionMasterService` / `dimensionMasterEdit` for cost centres (the payroll routes too — `createCostCentre` / `updateCostCentre` / `deactivateCostCentre` / `createGlCostCentre` / `updateGlCostCentre` / `toggleCostCentre` are gone), `businessUnitService` plan/apply for BUs (`toggleBusinessUnit` is gone; create validates in `planCreateBusinessUnit`). Every one takes `dimensionMasterLock.lockDimensionMasters(companyId)` first. See `gl/dimensions/.claude.md`.
- **Lock order**: the canonical sequence for every settlement path (bank line → payment → invoices → GL) lives in `bank/.claude.md`. Read it before adding a lock here; a path that takes two of these rows out of sequence deadlocks against one that does not (40P01 → 500).

- **User identity is a STRING, never a uuid.** `users.id` is `character varying`; `company_users.user_id` is `text`. NEVER write `user_id = ${x}::UUID` or `users.id = ${x}::UUID` — Postgres has no `text = uuid` operator, so it throws at RUNTIME (500), and neither `tsc` nor eslint can see inside a SQL template string. When joining a uuid column onto `users.id`, cast the **uuid** side: `ON u.id = t.approved_by::TEXT`. `company_id` IS a uuid and keeps its cast. Guarded by `scripts/ci/audit-user-id-casts.ts` (static) + `tests/integration/user-id-join-compat.int.test.ts` (schema probe).
- **Tenant-membership guards live in `companyAccessService`** — `userBelongsToCompany` / `userBelongsToGroup`. Do not re-inline them into API routes; four routes each kept their own broken copy before this was extracted.
- `listCompanies` and other admin-only calls must NOT appear in tenant-scoped API paths — enforce via route selection.
- `logAudit` is fire-and-forget: callers don't await failure; service swallows its own errors to keep write-paths unblocked (but no empty `catch` — logs via `log`).
- **`audit_log` is append-only (R-035 N1b A, migration 880).** No role but the table's owner holds UPDATE, DELETE, TRUNCATE or TRIGGER; INSERT and SELECT stay. Never write an app path that updates, deletes or locks (`FOR UPDATE`/`FOR SHARE`) audit rows — it 500s with 42501, and `tests/unit/services/core/auditLogAppendOnlyCensus.test.ts` fails first. A later migration that re-grants an erase privilege, grants app_user/platform_admin a role, moves the owner, or rewrites audit rows is refused by the same census (a real data repair changes the census on purpose). A forged extra INSERT is still possible: append-only, not authenticated. "No role but the owner" is a statement about the catalogue, not the app's login role: the app logs in as a member of the owner and drops to app_user with `SET LOCAL ROLE`, so a connection that never does (a script, a cron pool) or SQL that can `RESET ROLE` still erases (the N1 boundary, N3); a company delete still cascades its rows. POPIA erasure of audit rows now needs the owner (a migration or an owner-equivalent connection).
- **company_users and company_invitations enforce the app's role rules in the database (R-035 N1b C, migration 883).** BEFORE row guards judge `current_user`: as `app_user` the actor (`auth.uid()`) must be an owner or admin of the company; roles come from the allow-lists (members: owner/admin/manager/viewer; invitations: also storeman/technician); only an owner grants `owner` — by role change, membership insert, or invitation, and only an owner re-points (email, token, GoTrue user) or re-opens (accepted_at, expires_at) an invitation that stays `owner` (Hein, 2026-10-09: the company-invitations route refuses an admin's owner invite too); the last owner is never demoted or removed — counted by person (a case-variant duplicate row is the same user) under a per-company advisory lock, so two owners demoting each other at once cannot both pass; nobody removes themselves; only `role` of a membership ever changes; an invitation records its sender. As `platform_admin` (admin portal): never `owner` (ALLOWED_COMPANY_ROLES), and no invitation writes. Every other role (the owners, migration_admin for invite-accept and provisioning, the definer functions, seed scripts) is not judged. A new writer of either table must say which role it writes as — `tests/unit/services/core/companyMemberWriteCensus.test.ts` fails until it is classified. Unchanged on purpose (allowed today): an admin changing their own role below owner, demoting or removing a non-last owner; the admin portal has no last-owner rule (it takes the same lock, so an app demotion racing it is judged after it). 883 refuses to apply while any live, unaccepted owner invitation exists (its sender cannot be trusted: `invited_by` was writable) — cancel them first; an owner re-issues them afterwards. Named limits: a phantom owner row (a `user_id` that is no user, written by an owner's raw SQL) still counts as an owner. Raw SQL that forges the claims GUC or can `RESET ROLE` is the N1 boundary (N3). Since 886 (PR #691 round 5, PR #693 reviews): every `app_user` write to either table is refused (40001) at any isolation level but READ COMMITTED / READ UNCOMMITTED (Postgres runs it as READ COMMITTED) — every rule reads the snapshot, which only READ COMMITTED re-takes; SERIALIZABLE too, as SSI cannot see the app's READ COMMITTED writers. The refusal comes after the rule checks, so a rule's own code (RC001–RC009) wins; the admin portal is not refused. Owner-ness has one definition, `public.company_member_role_is_owner(role)` (lower-cased, every ASCII and Unicode whitespace character removed — an explicit class, as `\s` depends on the collation — all under COLLATE "C", so the result never does), used by both guards and by the two invite-accept routes (`/api/invite/[token]`, `/api/invitations/[token]/accept`), which never overwrite an owner's role (`ON CONFLICT … DO UPDATE … WHERE public.company_member_role_is_owner(company_users.role) IS NOT TRUE`) — an admin may re-invite any address at a lesser role, the owner's own included; the invitation is still accepted. 886 refuses to apply while any row of either table holds an owner-ish role other than exactly `owner` (correct by hand; it locks company_users, then company_invitations — an invite acceptance's order, so a deploy waits for one instead of deadlocking), which is what keeps the exact allow-lists, the exact count of the other owners and the portal's exact lock sound.
- `documentStorageService`: magic-byte check runs before S3 put; entity ownership verified against `companyId` before linking. Entity type `supplier_invoice` is a `supplier_invoices.id` (the bill page's id) — never `sage_supplier_invoices`, which is Sage import staging. The fence, the extraction predicate, the PO/GRN auto-link and the `procurement_documents` RLS policy must name the same parent table per type.
- `jobQueueService`: concurrent workers safe via `SELECT ... FOR UPDATE SKIP LOCKED`; lifecycle `pending → running → completed|failed`.
- PayFast ITN: validated via HMAC signature in `paymentGatewayCore`; idempotency via PayFast transaction id.
- Evidence graph is read-only — joins GL lines back to `captured_documents` / `extracted_data`.
- Sage import uses savepoints per record so one bad row doesn't roll back the whole run; dates coerced Date→ISO (2026-04-24 fix).
- **Migration opening balances are signed against the account's normal side.** In `ParsedAccount.openingBalance` a positive figure sits on the account's own normal side and a negative one on the opposite side (a bank in overdraft, a supplier in debit, a negative contra). `migrationOpeningBalanceService.postOpeningBalances` and `migrationExecuteService.verifyBalances` (`isaflowBalance = normal_balance === 'debit' ? net_debit : -net_debit`) share that convention — change one and you must change the other. A debit-signed source export is not importable and the totals check refuses it. `postOpeningBalances` is all-or-nothing: an unresolved account, an account this source does not own (`imported_from !== source`, which is also how a rolled-back account is released back to the company), or a source that does not foot throws before anything is written. The separate wizard path (`migrationImportService.importOpeningBalances` → `openingBalancePostingService`) takes explicit debit/credit columns instead and rejects negatives outright.

- **Payment terms (migration 960 EXPAND, 2026-11-05; plan `docs/plans/2026-11-05-payment-terms-due-by-date.md`).** `suppliers` and `customers` carry `payment_terms` (N) + `payment_terms_type` (`invoice_days` | `statement_days` | `statement_months`); both NULL = not set = **the company's default terms** (the `accounting_settings` row `default_payment_terms`, JSON `{days,type}`: 30 invoice_days for every company, edited on Company settings → General, `GET/PUT company-settings?type=payment-terms`; **PUT is owner/admin only** (`withRole('admin')`, the repo's company-wide admin gate; GET is open to every member), and every change is recorded in the entity history (migration 961: entity type `company_setting`, three narrow ENABLE ALWAYS triggers on `accounting_settings` for the `default_payment_terms` key only; actor, channel, old → new, owner/admin read; the capture and projection are unchanged, so no definer-registry entry). A contact's own terms win; NEW documents (UI capture, `createDraftCustomerInvoice`, `createSupplierInvoice`, scanned bills, recurring runs and templates, quote/order/time/WIP conversions, Sage and MCP) use `paymentTermsResolver.dueDateForContact` (or the pure `shared/paymentTerms.dueDateWithDefault`): contact, else company default, so a document is not left undated. Bill precedence (`ap/billDueDate`): a due date given > the bill's OWN terms when someone chose them (`net30`, `immediate`; the new-bill page no longer sends a silent net30) > the supplier's terms > the company default. **960 is the expand half**: it drops the column DEFAULTs and changes NO contact row, because the old code (live colour during the build, a code-only rollback) writes `(30, NULL)`, `'days'` and `?? 30` AND reads only `days` / `end_of_month` (master's `ar/paymentTerms.dueDateFromTerms` returns null for anything else, so a rewrite would leave its new invoices undated); `shared/paymentTerms.readTerms` reads every legacy shape ('days' = invoice_days, 'end_of_month' = statement_days, a number with no type = invoice_days; a negative, over-999 or unknown-type row is not terms). **PR 1b (migrations 963 / 964, 2026-11-07)** is the tighten half: default-30 -> not set (except in a company whose default is no longer 30 days from invoice: there an explicit 30 invoice_days), the legacy type names mapped, bad values -> not set, and the CHECK `{suppliers,customers}_payment_terms_shape` (both NULL, or N 0..999 with one of the three types; each arm NULL-safe); 964 VALIDATEs the entity_changes type CHECK. Its UPDATEs fire the entity-history capture (the undo path). Since 963 no contact can hold a legacy shape; `readTerms` still reads them. `parseTermsWrite` is the one parser of a write: N alone = `days_only` (an update keeps the stored type; a create reads invoice days), `payment_terms_type: 'not_set'` with no N clears, a type without N or an unknown type is a `ContactValidationError` (`contactTerms.termsColumns`) before any SQL. A create with neither stores not set; the forms make a new contact CHOOSE (no pre-selection; "Use company default" is a valid choice). `migrationContactService` (CSV take-on) writes N as invoice days or not set. No importer updates an existing bill's due date on re-import: a matched bill/invoice is returned as is.

## Smart-categorize sweep scope (Hein, 2026-10-21: the server is overloaded)
`smartCategorizeForAccount` (the "Apply rules" click) categorizes only `selectSweepLineIds`: status `imported`, no `suggested_gl_account_id` / `suggested_category`, no `categorization_decisions` row, dated (SAST day) OR imported in the last 30 days, newest first, max 200 **per bank account per request** (a company is bounded only by the AI rate limit, 20 requests). Lines an earlier sweep tried in the last 24 h (`categorizeSweepAttempts.ts`, in-process, forgotten on restart) sort last, so unmatchable lines cannot hold the batch and older untried lines get reached. The LLM residual pass reads only the sweep's first-attempt lines. An explicit `transactionIds` request is refused above 200 ids (400) but is not held to the recent / uncoded filters. Limits: `categorizeSweepScope.ts`.

Side effect to know before reading the metrics: a line that already carries a low-confidence suggestion is no longer re-sent to the LLM on a later click (the sweep skips suggested lines). Before 21 Oct it was. A dip in auto-coded % or accepted % after this change is the scope, not the LLM.

### Widening the sweep later
- Set `CATEGORIZE_SWEEP_RECENT_DAYS` (default 30), `CATEGORIZE_SWEEP_MAX_LINES` (default 200) and/or `CATEGORIZE_SWEEP_RETRY_HOURS` (default 24) in the service env and restart; a bad or non-positive value falls back to the default. Change the `*_DEFAULT` constants only to move the baseline for everyone.
- Widen one step at a time. Watch box load (`uptime`), smart-categorize request time (the client aborts at 15 s), LLM spend (the residual pass follows `MAX_LLM_CALLS_PER_RUN` / `DAILY_LLM_CEILING`), and the coding metrics (auto-coded %, suggestions accepted %).
- To give old low-confidence suggestions an LLM second opinion again, add a bounded second selector for recent lines with `suggested_confidence < RESIDUAL_CONFIDENCE_CEILING`; do not drop the uncoded filter.
- Index candidates: idx_bt_company_date `(company_id, transaction_date DESC, amount DESC)` (bank account and status are filtered after it), the (company_id, status, created_at) index, categorization_decisions_tx_idx. No EXPLAIN on a large tenant is recorded yet: run one before widening, and before dropping the date window altogether.

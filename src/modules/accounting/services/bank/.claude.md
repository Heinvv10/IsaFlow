## Caller contract
Invoked by `withCompany`-wrapped API routes in `pages/api/accounting/bank/*`. Every DB function takes `companyId` first. VLM services are stateless (no tenant storage); caller persists output under their `companyId`.

## Main function signatures
- `importBankStatement(companyId, bankAccountId, parsed) / importParsedTransactions(...)`.
- `startReconciliation(companyId, input) / completeReconciliation / createAdjustmentEntry(companyId, reconId, input)`.
- `allocateTransaction(companyId, txId, allocationInput, userId)` — posts JE; VAT account via `systemAccountResolver` (subtype) then fallback codes 1140/2120.
- `splitAllocateTransaction`.
- `reverseReconciledTransaction(companyId, bankTxId, userId, opts?: { postingAgent? })` — posts the contra, then resets the tx to `imported`. `opts.postingAgent` is forwarded to `reverseJournalEntry`; omit it and the contra stays `human:<userId>`.
- `listAgentPostings(companyId, from, to, limit?)` (`agentActivityService`) — journals with `posting_agent LIKE 'mcp:%'`. Returns `reversed` (from `reversed_at`, NOT `status` — reversal never flips status) and `reversalOfId`.
- `importStatementForAgent(args)` / `undoImportBatch(companyId, batchId)` / `bankGlAccountBelongsToCompany(companyId, accountId)` (`bankStatementImportService`) — parse → hash-dedup → persist, for the MCP import tools. `undoImportBatch` returns `null` for another company's batch and deletes only `status='imported'` rows, reporting the allocated ones it refused.
- `findBankTransactionsByReference(companyId, bankReference, bankAccountId?)` (`bankTransactionLookupService`) — EXACT match after trimming both sides (`btrim(bank_reference) = $ref`), oldest first, capped at 25. Returns every candidate: the caller decides what more-than-one means (the MCP tools refuse it). Never LIKE — a prefix match resolves `INV-1` onto `INV-10`.
- `applyRules(companyId, txId)` — rule evaluation by priority ASC (lowest = highest).
- `buildExpenseJournalFromReceipt(extracted, mapping)` — pure.
- `extractWithVlm(file) / extractBankStatementWithVlm / extractStatutoryDocWithVlm` — vLLM HTTP call, 120 s default timeout.

## Business rules
- **A bank account is a `gl_accounts` row with `account_subtype='bank'`.** `bank_transactions.bank_account_id` FKs to `gl_accounts(id)` — the column name misleads. Every row in dev and production honours this. The separate `bank_accounts` table is vestigial metadata (1 row dev, **0 rows production**): `bank_feed_connections.bank_account_id` still points at it, but nothing else may. Use `hasBankAccount` / `countBankAccounts` rather than counting `bank_accounts`; migration 446 dropped `bank_import_batches`' FK to it for the same reason.
- `bank_transactions.status`: `imported → matched → allocated → reconciled`.
- Allocation runs under `withTransaction`: JE post + transaction status update atomic.
- VAT account resolution: `account_subtype` first, then hard-coded codes 1140 (input) / 2120 (output) for pre-mig-327 companies — fallback must stay.
- Dedup primary key is `bank_reference`; amount+date+description fallback can miss duplicates on same-day equal-amount txns (known limitation).
- **Known limitation — the 2026-08-27 `parseAmount` comma fix moves the dedup content hash.** A CSV row written SA-style ("1 234,56") used to parse as 123456 and hashes on the amount, so the same file re-imported after the fix hashes differently: the corrected row lands as a NEW transaction beside the wrong one rather than replacing it. Re-importing such a file is therefore a two-step job — delete the mis-parsed rows (or undo the batch) first, then re-import. Production carried no exposure as of 2026-08-27: there were zero CSV-sourced `bank_transactions`, and all 38 ABSA batches were PDFs, which go through `bankPdfParserUtils.parseAmount` and are untouched by this change.
- `autoMatch` is NOT atomic — each tx updated individually; mid-run crash leaves partial matches, next run picks up the rest.
- PRD-06 Phase 4: receipt → invoice auto-match links unallocated receipts to open AR invoices.
- Open-banking providers (Basiq/Tink/Plaid) stubbed when API keys absent — responses do NOT flag `mock: true` (can't distinguish in calling code).
- VLM: `VLLM_BASE_URL`, `VLM_MODEL`, `VLLM_API_KEY`, `VLLM_TIMEOUT` env vars; `isVlmAvailable()` for health.

## Recent changes
- 2026-08-28: **the three bank-allocation write paths take a row lock on their first read** (`bankTxLock.lockBankTransactionForUpdate` — `SELECT … FOR UPDATE`, company-scoped). `allocateTransaction`, `splitAllocateTransaction` and `reverseReconciledTransaction` each read `status`, refuse on the wrong one, then post; unlocked, two concurrent REQUESTS (UI double-click, agent retry with a fresh idempotency key) both passed the check and both posted — one transaction, two journals. Since PR #264 every request runs in a single transaction on the ALS client, so the lock is held for the rest of the request and the second session blocks until the first commits, then re-reads `allocated` and refuses. Write paths only — never add `FOR UPDATE` to a list/query service. The DB-gated test asserts more than the lock error: without the lock the second session still fails 55P03, because it blocks on the status UPDATE — *after* posting its second journal.
- 2026-08-28: `bankTransactionLookupService.getBankTransactionStatus(companyId, txId)` — returns the row's status, or `null` for a missing row or another tenant's. Exists so the MCP allocate/reverse tools can answer their pre-write refusals from a READ: both services write BEFORE they can fail (`allocateTransaction` posts the entry then updates the row; `reverseReconciledTransaction` posts the contra then resets the row), so a `catch → toolError` around them cannot tell a refusal from a half-done write — and since a refusal frees the idempotency key, the retry writes a second time.
- 2026-08-28: `getAllocationBatchLines` LEFT-joins `bank_transactions` and returns `transactionExists`. An INNER join dropped a line whose transaction had since been deleted, so the batch silently reported fewer lines than it posted — the vanished one being exactly what a human needs to see.
- 2026-08-27: **`allocateTransaction`, `splitAllocateTransaction` and `reverseReconciledTransaction` CLEAR `bank_transactions.allocation_batch_id`.** The stamp says the row belongs to a bulk batch; that stops being true the moment the row is reversed or re-allocated, and nothing cleared it. Left set, `reverse_bank_allocation_batch` would walk the stamp and reverse whatever journal is on the row NOW — unwinding a posting the batch never made. `bank_allocation_batch_lines` (mig 515) is the second line of defence: it records the journal each line posted, so the reverse tool compares rather than trusting the column.
- 2026-08-27: statement import parser fixes. QIF — a `!Type:Bank` header shares the first `^` block with transaction #1, and filtering blocks that start with `!` silently dropped that transaction from every headed export; header LINES are stripped now, not whole blocks. ABSA — moved to `utils/bankCsvParserAbsa.ts` and mapped by header name: the current `Account Number,Transaction Date,Description,Amount,Balance` layout was undetectable (only the legacy Description1/Description2 one was), so the import was rejected outright. `detectBankFormat` now scans the first few lines for the header (exports carry a title row) and `parseAmount` reads SA-style "1 234,56" as 1234.56 rather than 123456. All of this reaches `import_bank_statement` unchanged — the MCP tool already routes through `parseStatement`.
- 2026-08-27: PRD-11 §4 — `bankAllocationBatchService` (`createAllocationBatch` / `recordAllocationBatchLines` / `getAllocationBatchLines` / `clearAllocationBatch`) backs the MCP bulk allocate + batch reverse tools. Mig 514 adds `bank_allocation_batches` and `bank_transactions.allocation_batch_id`. The stamp is on the TRANSACTION, not the journal: reversal starts from the transaction and must CLEAR the stamp so the row can be re-allocated into a later batch, which a posted-journal column could not allow. `recordAllocationBatchLines` throws unless every id was stamped — a posted journal outside the reversible set is exactly the failure the batch id exists to prevent — and `getAllocationBatchLines` returns `null` for another tenant's batch so the caller renders the generic NOT_FOUND.

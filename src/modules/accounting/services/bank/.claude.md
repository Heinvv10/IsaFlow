## Caller contract
`withAuth`-wrapped routes in `pages/api/accounting/bank/*` (+ `bank-match-confirm.ts`); migrations `327_*` (VAT subtype), `514/515/519/520/526`, `*bank_*`. Every DB function takes `companyId` first. VLM services are stateless; the caller persists under its own `companyId`.

## Main function signatures
- `lockBankTransactionForUpdate(companyId, txId)` — company-scoped `FOR UPDATE`; `null` for missing/other tenant; THROWS outside a request transaction (an implicit one locks nothing); 5s `lock_timeout` → `BankTransactionLockTimeoutError` (test with `isBankTransactionLockTimeout`, structural).
- `allocateTransaction(companyId, txId, …, opts?)` / `splitAllocateTransaction` — post the JE; VAT account via `systemAccountResolver` (subtype) then codes 1140/2120. Its two pre-write refusals (missing row, status ≠ `imported`) throw `BankAllocationRefusal` — `isBankAllocationRefusal`.
- `reverseReconciledTransaction(companyId, txId, userId, opts?: {postingAgent?, reversalDate?})` — unwind, contra, reset to `imported`, ALL in one savepoint. Contra date = original entry's when that period is open, else today. Refuses PRE-WRITE on a closed/locked period; `no_period` is not refused (`createJournalEntry` auto-creates the year). Omit `postingAgent` and the contra stays `human:<userId>`.
- `validateBankSupplierPayment` / `planSupplierAllocationLines` (in `ap/`) throw `SupplierPaymentRefusal` for a refusal and NOTHING ELSE — catch that, re-throw the rest, or a dropped connection reaches the browser as a 400.
- `findBankTransactionsByReferences(companyId, refs[], acct?)` — ONE query (join on `unnest($refs)`, two arms, one per column), `Map` by trimmed reference, 25 candidates per reference, each carrying `matchedReference`+`matchedColumn`. Returns every candidate; the caller decides what >1 means. `findBankTransactionAllocationStates(companyId, ids[])` — `{id,status,matchedJournalLineId}` for a whole set in one query; it reads BOTH columns deliberately — a row carrying `matched_journal_line_id` is in the ledger whatever `status` says, and **a fixture that sets only the status passes while production fails**. `getBankTransactionStatus` stays for one-line tools, and exists so an MCP refusal can be answered from a READ: both write services write BEFORE they can fail, and a refusal frees the idempotency key, so the retry writes a second time.
- **Bulk/batch path**: `contactDirectoryService.suppliersBelongToCompany(companyId, ids[])` / `customersBelongToCompany` — ONE query per set, empty set skipped; the bulk allocate loop depends on them, and checking a counterparty per line is 500 round trips. `partitionAllocationLines` (`allocationApplyRoute`) is what REFUSES on that path, pre-write, splitting the lines into postable and skipped — `invoiceSkipReason` beside it is exported and called by nothing.
- `importBankStatement` / `importParsedTransactions(…, {skipAutoPost, skipPostImportEffects})`, `importStatementForAgent`, `undoImportBatch` (null for another company; deletes only `imported` rows, reports the rest), `startReconciliation`/`completeReconciliation`/`createAdjustmentEntry`, `applyRules` (priority ASC = highest), `listAgentPostings` (`reversed` from `reversed_at`, never `status`), `buildExpenseJournalFromReceipt` (pure), `extractWithVlm`/`extractBankStatementWithVlm`/`extractStatutoryDocWithVlm`.

## Business rules
- **A bank account is a `gl_accounts` row with `account_subtype='bank'`** — `bank_transactions.bank_account_id` FKs to `gl_accounts(id)`; the name misleads. The `bank_accounts` table is vestigial (0 rows prod); only `bank_feed_connections` may point at it. Use `hasBankAccount`/`countBankAccounts`, never a count of `bank_accounts`.
- Status flow `imported → matched → allocated → reconciled`; allocation is atomic under `withTransaction` (JE + status).
- **Direction follows the SIGN of the line, on every arm.** `isSpent = amount < 0` decides DR/CR for supplier and customer allocations too — a refund booked as a payment moves the bank by TWICE the line (R261,651.64 found on Velocity). The VAT KEY follows the alloc TYPE, not the direction (a refund reverses INPUT tax). The 4-way match runs only when `isSpent`; a `customer_payments` row is minted only when `!isSpent`. Every settler asks `signMismatchReason` (`bankLineDirection`) — it refuses a ZERO line outright, because the downstream throw it fronts would land mid-write.
- **A VAT code on a supplier/customer allocation posts NO VAT** (control-account settlement): one predicate, `gl/settlementVat.isControlAccountSettlement`, read by `allocateTransaction` and by `gl/ruleVatResolution` for the sweep. `allocateTransaction` ANDs it with `Boolean(entityId)` (an entity-less call falls through to the account arm); the rule path picks on `allocType` alone. `gl/bankContraVat` drops the code on a `bank`-subtype contra — pass that flag as `undefined` when the account is absent from the map, never `?? false`.
- **Attended paths never coerce a VAT choice; `autoPostRuleLine` (unattended) does** and returns `vatDenied` (from the account's `vat_input_denied` flag, tallied into `autoPostVatDenied`); the unattended line builder is `buildAutoCreateLines` (`bankRulesMatchingHelpers`), which is where the `netAmount` defect lived. `auto_create_entry=false` rules are suggestion-only. BOTH directions are pinned by `tests/unit/services/bankVatDisplayAgreesWithJournalDb.test.ts` (real Postgres) — it is the only gate on this rule, so don't delete it when a mock would be quicker.
- **A settlement must write its payment DOCUMENT and its ALLOCATION row** — `supplier_payments` + `payment_allocations` on the AP side, `customer_payments` + `customer_payment_allocations` on the AR side. Those are the only tables `bankAllocationUnwind` reads, so a bare `amount_paid` write is irreversible — and, computed in JS, a lost update too. Both arms of `bank-match-confirm` obey this: `confirmSupplierMatch` → `applyBankLineToSupplierInvoices`, `confirmCustomerMatch` → `confirmReceiptMatch`. Never assign `supplier_invoices.balance` (GENERATED since mig 201 → 428C9). **An over-payment is REFUSED, not capped, on both arms**: `apAgingService` and `debtorsManagerService` read the invoice tables alone, so the excess would part the control account from the aging invisibly. A caller that HANDS IN allocations (the MCP apply tool) may leave a remainder; a screen deriving them may not.
- **`withAuth` COMMITs below 500**, so every refusal must be decided from READS before the first write; past the first write the only safe answer is 500. Exception, and it must be shown: a refusal raised before any write may keep a 4xx (`bank-match-confirm` answers 409 on a contended line).
- **Every pg error aborts the transaction**, not just 40P01/40001/25P02 — so a swallowed failure needs a SAVEPOINT, not a code whitelist (`bankTransferAutoLink`, the import auto-post sweep). If the savepoint's own ROLLBACK fails, rethrow: nothing saves that case. Give each savepoint a unique name; a duplicate SHADOWS rather than errors.
- **Row locks**: LOCKED — `allocateTransaction`, `splitAllocateTransaction`, `reverseReconciledTransaction`, `matchTransaction`, `unmatchTransaction`, `excludeTransaction`, each auto-post candidate. NOT locked, deliberately — read-only paths, the post-UPDATE re-read, `deleteTransactions` (its `status='imported'` predicate is the guard) and `bulkAcceptTransactions` (it knowingly relabels allocated rows). `SET LOCAL lock_timeout` is re-issued EVERY call, never memoised: it is subtransaction-aware and `ROLLBACK TO SAVEPOINT` restores `0`. Bulk loops sort by transaction id — a total lock order turns a deadlock into a wait. A raced/locked row is SKIPPED and counted (`skippedRaced`, `autoPostSkippedLocked`, `autoPostTruncatedRules`; `MAX_RULE_CANDIDATES`=500), never allowed to abort the run, and every counter reaches the UI.
- **CANONICAL LOCK ORDER — every path takes these rows in this sequence, always**: (1) `bank_transactions`, (2) `customer_payments`/`supplier_payments`, (3) `customer_invoices`/`supplier_invoices` (a SET of them `ORDER BY id`), (4) `gl_journal_entries`/`gl_journal_lines`. Two paths taking any pair in opposite orders deadlock: Postgres kills a victim with **40P01**, which `withAuth` answers as a 500 — the money path reporting a server fault to a user whose only mistake was arriving at the same instant as somebody else.

  **Build this table MECHANICALLY, never by reasoning about which pairs can run together.** An `UPDATE` and a `DELETE` take a row lock exactly as `FOR UPDATE` does, so enumerating only the explicit `FOR UPDATE`s is what hid three inversions across rounds 7–9 — `voidSupplierPayment` was missing from this very table while it deadlocked. The enumeration walks every function that touches more than one of these relations (`FOR UPDATE`, `LOCK TABLE`, the `lock*ForUpdate` helpers, `fetch{Invoice,Bill}Candidates`, and every `UPDATE`/`DELETE`), records the ORDERED sequence, and derives the cycles from that LIST. A path you did not list cannot be checked.

  **Rebuild the table with the census, not by reading.** `UPDATE`/`DELETE` sites are what hid the
inversions, and they do not look like locks. The round-9 enumeration walked every `sql` template in
`src/`, `pages/` and `scripts/`, tagged each by relation family (BANK / PAY / INV / GL), and kept
every file touching more than one — 14 files, of which four were missing from this table and three
of those were inverted. Re-run it before claiming a path is safe.

  **`archiveExecutionService`'s old order was an FK bug as well as a lock inversion**, and the
canonical lock order is also the FK-safe one: `bank_transactions.matched_journal_line_id` and
`{customer,supplier}_payments.gl_journal_entry_id` are both **NO ACTION**, so children must go
first. Measured on the fixture — deleting a pre-cutoff `gl_journal_lines` row while a `reconciled`
bank line still pointed at it raised `bank_transactions_matched_journal_line_id_fkey`, on exactly
the pair the step exists to archive. **STILL OPEN, named not fixed:** archive deletes
`gl_journal_entries` but never the `{customer,supplier}_payments` that reference them, so a
pre-cutoff journal carrying a payment document still violates its FK whatever the order. Widening
what archive covers is a scope change, not a lock fix.

  **The one exemption, and it is structural rather than an unreachability argument**: a row INSERTed by this transaction cannot be locked by any other transaction, because no other transaction can see it. So `createJournalEntry` + `postJournalEntry` on a brand-new entry does not put `gl_journal_entries` into a path's ordering; a `FOR UPDATE` or reversal of a PRE-EXISTING entry does. That is the difference between `confirmCustomerPayment` (exempt) and `cancelCustomerPayment` (not).
  Five paths take a lock they would not otherwise need, purely to fix the order, and REMOVING ANY RE-OPENS THE DEADLOCK: both `confirm*Match` arms call `lockBankTransactionForUpdate` before reading the document they settle; `voidPaymentDocument` resolves its bank line from an UNLOCKED peek so it can lock the LINE before the payment; and `confirmCustomerPayment` / `processSupplierPayment` / `cancelCustomerPayment` / `voidSupplierPayment` call `lock{Customer,Supplier}PaymentForUpdate` as their FIRST act. Multi-invoice loops go `ORDER BY invoice_id` for the same reason the candidate fetchers do. Pinned by `tests/unit/services/bank/confirm{Customer,Supplier}Match.test.ts`, `tests/unit/services/{paymentVoidService,supplierPaymentVoid,supplierPaymentWorkflowService}.test.ts`, `tests/unit/services/ar/customerPaymentLockOrder.test.ts`, `tests/unit/services/bank/bankAllocationUnwind.test.ts`, and — measured on real SQL — `tests/integration/k071-lock-order-deadlock.int.test.ts` and `k071-void-lock-order.int.test.ts`.
  Contention is ANSWERED, never faulted: `core/lockContention.isLockContention` classifies BOTH `55P03` (our `lock_timeout`) and `40P01`, and every settlement lock maps them to its own retryable typed refusal — `BankTransactionLockTimeoutError` (409), `PaymentLockTimeoutError`, `ReceiptRefusal`/`SupplierPaymentRefusal` ("retry in a moment"). Mapping 40P01 is the second line of defence, not a licence to stop ordering locks.
  **Do not settle a suspected cycle by argument.** "No cycle is reachable" was written into this file in round 8 about `voidSupplierPayment` and was wrong — round 9 measured `40P01 deadlock detected` on the fixture with that order restored, the void itself the victim, the route answering 400. Prove it by outcome (two interleaved pool clients) or fix the order.
- match/unmatch/exclude refuse `allocated AND matched_journal_line_id IS NOT NULL` (`BankTransactionAllocatedError` → 400). `reconciled` is deliberately excluded (its journal pre-dates the link); `allocated` with a NULL line is half-finished and allowed through. Undoing a posted allocation is `reverseReconciledTransaction`'s job.
- **Dedup is a CONTENT HASH of (date, amount, description, balance)** — no reference in it, so two genuinely separate same-day identical rows collapse (known). Do NOT add the reference: pre-2026-09-07 rows carry none and would stop matching their own statement. Known: the 2026-08-27 `parseAmount` comma fix MOVED the hash, so re-importing an SA-formatted CSV lands the corrected row beside the wrong one — undo the batch first.
- **The statement reference lives in `reference`; `bank_reference` holds a FEED'S EXTERNAL ID** (0 prod rows). So `reference` wins outright and `bank_reference` is consulted only for a reference that matched nothing. Match EXACTLY after `btrim(x, E' \t\n\r\f')` — never LIKE (`INV-1` would take `INV-10`), never bare `btrim` (strips spaces only), never `\v` (pg reads `E'\v'` as the letter). Mig 519's expression indexes must stay character-for-character identical to the query or the planner reverts to a company scan — `bankTxRefCandidateQuery` is exported UNRUN so the DB-gated test can `EXPLAIN` the service's REAL statement; the previous test planned a pasted copy and stayed green through a regression. Don't drop the column: `customer_payments` and the feed dedup key read it.
- `addBankTxAttachment`: magic-byte check → ownership read → INSERT, and **keep that order** — the attachments table has no `company_id` of its own. `listImportBatches` counts `transactionsRemaining`/`transactionsAllocated` LIVE from `bank_transactions.import_batch_id`: `bank_import_batches.transaction_count` is what the import wrote and an undo leaves it unchanged. `listAgentPostings` returns `reversalOfId` beside `reversed`.
- Open-banking Basiq/Tink/Plaid are NOT implemented (they used to INSERT invented rows, K-018): `createBankFeedConnection` refuses them, `syncBankFeed` throws `BankFeedProviderNotImplementedError`, and routes must map it to a 4xx or `withAuth` discards the `markSyncFailed` audit trail.
- `autoMatch` is not atomic (per-row); its `matched_journal_line_id NOT IN (…)` subquery IS company-scoped — unscoped, another tenant hid journal lines from this one. `completeReconciliation` requires a zero difference AND ≥1 matched transaction, reported as `completed:false` (a success, never a refusal — `start`/`autoMatch` have already written). Cancelling releases `matched` rows to `imported` and merely detaches `allocated`/`provisional`/`excluded`; it re-asserts `status='in_progress'` in the DELETE. Cancel's `dry_run` runs every guard and writes nothing, and a POSTED adjustment journal blocks the cancel — found through `gl_journal_entries.source_record_id`. Adjustments use mig 526's own column, NOT `source_document_id` (FK'd to `captured_documents` since mig 409).
- Coverage/cash: `cash.balance.v1` (ledger) is `cashBalanceService`, `cash.statement.v1` (sum of `bank_transactions.amount`) is a different question — never net them. The OTHER services answering the statement question are `bankAccountStatusService.balance` and `kpiDashboardService`; add a fifth cash answer in neither. `kpiChartsService` is the mirror of the LEFT-JOIN-ON-vs-WHERE rule below and drifts with it. `bt.amount = jl.debit - jl.credit` on all 9,097 matched prod rows, so `glOnlyMovement - statementOnlyMovement` is an EXACT identity; a non-zero `unexplainedResidual` means a `bank_opening_balance` with no journal behind it. Neither service filters `is_active` (a deactivated account still holds cash — `deactivatedWithBalance` REPORTS them, it does not exclude them); `getCashBalance` spans subtype `bank` AND `cash`; the posted/date restriction belongs in the LEFT JOIN's ON + a CASE, never a WHERE (that deletes draft-only accounts).
- `getCashBalance(companyId, asOf, { exclusive: true })` answers the OPENING balance — the closing balance of the day BEFORE `asOf`. An option, not a day the caller subtracts: JS date arithmetic on this UTC+2 server is what put 291 journals in the wrong period. `cashFlowDirectService.fetchOpeningCash` delegates here rather than keeping its own copy.
- Display columns come from the POSTED JOURNAL, never a cached label: `ALLOCATED_ACCOUNT_LATERAL` (with `AND bl.gl_account_id = bt.bank_account_id` — load-bearing, or the sibling of a user-picked line reads as the destination) and `POSTED_VAT_LATERAL` (`'standard'` asserted from the presence of a VAT-account line, NULL over zero lines). Mig 520's `allocation_rule_{id,name}` carry the rule; `allocated_entity_name` is ALWAYS the account. `allocation_batch_id` is CLEARED by allocate/split/reverse, or a batch reverse would unwind a posting it never made (mig 514/515). `recordAllocationBatchLines` THROWS unless every id was stamped — a posted journal outside the reversible set is the failure the batch id exists to prevent; `getAllocationBatchLines` LEFT-joins (returning `transactionExists`) and returns `null` for another tenant's batch so the caller renders the generic NOT_FOUND.
- Dates: build journal dates with `fmtDate` from `@/lib/neon`, never `toISOString()` — pg returns `transaction_date` at LOCAL midnight and UTC rendering dates a 00:30 SAST line to the previous day (wrong month at a period boundary). `getBankTransactions` pages on an opaque keyset cursor whose predicate must stay in lockstep with an ORDER BY ending `bt.id DESC`; a malformed cursor, a non-calendar date, a non-UUID id, or a cursor combined with a non-zero `offset` all throw `InvalidCursorError` before any query.
- Parsers: ABSA is mapped by HEADER NAME (both the current and legacy layouts) and reads SA-style "1 234,56"; `YYYYMMDD` is checked before the separator split and validated with `isRealCalendarDate`. QIF strips header LINES, not whole blocks (`!Type:Bank` shares a block with transaction #1). The Reference column is matched against exact header names and left UNSET when blank. Not every format carries one: `bankCsvParserStandard` (standard_bank/capitec/nedbank), the ABSA legacy layout and every PDF parser have none.
- VLM env: `VLLM_BASE_URL`, `VLM_MODEL`, `VLLM_API_KEY`, `VLLM_TIMEOUT`; `isVlmAvailable()` for health.

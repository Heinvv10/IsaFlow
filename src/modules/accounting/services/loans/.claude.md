# Loans service group

PRD-03 Loan Amortisation Module. Pure TS amortisation engine sits in `src/lib/amortisation/` — this directory is the DB-integrated service layer that wraps it, plus payment + period-close + compliance flows.

## Files

| File | Role |
|---|---|
| `loanService.ts` | Loan CRUD + event CRUD. `createLoan`, `listLoans(filter)`, `getLoanById`, `updateLoan`, `addLoanEvent`, `getLoanEvents`. Includes origination-fee + VAT-type fields (migration 394). |
| `loanRateCurveService.ts` | Rate curve CRUD. `listRateCurves` returns tenant curves AND system curves (`company_id IS NULL + is_system = true`). `upsertRatePoints` has an IDOR guard — verifies `company_id` ownership before writing. |
| `loanScheduleInputs.ts` | Pure row → engine-input mappers (`loanRowToInputs`, `dbEventToEngine`, `dbPointToEngine`, `mapDbRowToSchedule`), `ENGINE_VERSION` and `buildInputsHash`. No DB access — split out of `loanScheduleService.ts` at the 300-line cap. |
| `loanScheduleService.ts` | `previewSchedule` (dry-run), `getOrComputeSchedule` (SHA-256 `inputs_hash` cache in `loan_schedule_runs` / `loan_schedule_rows`), **`getPortfolioSummary`** — now uses `principal − SUM(loan_payments.principal)` for actual outstanding, not schedule projection. Keeps `totalOutstandingProjected` alongside. Weighted avg rate is weighted by remaining balance. `next_12m_interest` uses calendar window (CURRENT_DATE → +12 months). |
| `loanGlPostingService.ts` | `buildPeriodJournalInput` is a **pure** double-entry builder: non-skip = DR Interest + DR Liability, CR Bank; skip = DR Interest, CR Interest Payable; lump adds DR Liability / CR Bank. When payment < interest, principal is signed (negative → CR Liability, "interest capitalised"). `postPeriodJournals` blocks posting when `row.nca_flagged` or period is locked. |
| `loanPeriodCloseService.ts` | `closeLoanPeriod(companyId, yyyymm, userId)` — single `LEFT JOIN LATERAL` query fetches all active loans + their period-end snapshot (no N+1). Returns `skippedLoans: [{loanId, reason}]`. Post-reclass + insert into `loan_period_locks`. Re-closing throws. |
| `loanPaymentService.ts` | **`recordLoanPayment(companyId, loanId, { paymentDate, periodNumber, bankAccountId? }, userId)`** — splits principal (= opening − closing) + interest per schedule row, posts: DR current_portion · DR interest_expense (5700 fallback) · CR bank; returns `{ paymentId, journalEntryId, principal, interest, totalPaid, newOutstanding }`. UNIQUE(company_id, loan_id, period_number) for idempotency. `listLoanPayments`. |
| `loanComplianceService.ts` | NCA + IFRS 9 + IFRS 7. `checkNcaCompliance`, `determineEclStage`, `computeEclAmount`, `computeNpvImpact`, `computeRateSensitivity` (±100bp/±200bp shocks). `assessLoan` persists in `loan_compliance_assessments`. |
| `loanPostingGuards.ts` | Guards shared by the two loan paths that write to the GL. `lockLoanForUpdate` (loan row `FOR UPDATE` behind a 5s `lock_timeout`, reset to `DEFAULT` on the success path, `LoanPostLockTimeoutError` on 55P03; **throws unless it runs inside a request transaction** — an unbounded `FOR UPDATE` on a pooled connection can be neither timed out nor rolled back), `assertClosesInOrder` (takes `pg_advisory_xact_lock` on the company's closes, then refuses an earlier month after a later one), `assertFiscalPeriodResolved` (refuse a journal whose date resolves no fiscal period). |

## Multi-tenant rules
Every DB query scopes by `company_id`. `upsertRatePoints` has an explicit ownership gate. Read APIs for rate curves additionally allow system curves (`is_system = true AND company_id IS NULL`) regardless of caller.

## Engine contract
All numeric IO is `number` (2dp at output); internally the engine uses `decimal.js` (20dp, ROUND_HALF_UP). Golden-file test against `Amortisation Report AI ver.xlsx` is cent-accurate.

## Key tables
- `loans` — master. GL mappings: `gl_account_id` (long-term liab) + `interest_expense_account_id` + `interest_payable_account_id` + `bank_account_id` + `current_portion_account_id` (mig 391). `origination_fee` + `origination_fee_vat_type` (mig 394). Seed data may leave these NULL — the period-close service will skip those loans with `{reason: 'missing GL accounts'}`.
- `loan_rate_curves`, `loan_rate_points` — system curves have `company_id IS NULL` (mig 393).
- `loan_events` — append-only log: LUMP / SKIP / RESTRUCTURE / WRITEOFF.
- `loan_schedule_runs` + `loan_schedule_rows` — cached by `inputs_hash`.
- `loan_gl_postings` — every posted journal line references `journal_entry_id`.
- `loan_period_locks` — (company_id, yyyymm) one-time lock per period.
- `loan_reclass_postings` (mig 645) — what each close actually reclassified, per loan per month. `source` ('app' | 'backfill', mig 659) says which writer produced the row; migration 659's rebuild deletes only its own.
- `loan_reclass_backfill_refusals` (mig 659) — every reclass journal 659 would not reconstruct, with the reason. Operator-facing: read it after a deploy that applies 659.
- `loan_compliance_assessments` — NCA + IFRS 9 history.
- **`loan_payments`** (mig 400) — actual payment records linked to journal entries.

## Gotchas
- **`glByCode` selects `account_code`, not `code`** (fixed 2026-09-10, K-107 r8). `gl_accounts` has no `code` column, so the 5700 / 1110 fallbacks in `resolveAccounts` raised 42703 on every call — and a caught-or-not SQL error poisons the whole request transaction, so a loan merely missing `interest_expense_account_id` failed the entire request with an opaque 500. `payroll/taxDirectivePaymentService` had the byte-identical helper and the same defect.
- **`recordLoanPayment` is check-then-act on status** (registered, NOT fixed): it reads `loanRow.status !== 'active'` and SELECTs `loan_payments` for the period, then posts and INSERTs last. `idx_loan_payments_period_once` keeps the outcome safe — the loser 23505s into a 500 rather than duplicating — but the read is decorative under concurrency, and the `periodNumber`-omitted path skips the SELECT entirely.
- **Portfolio summary reflects ACTUAL balances** via `loan_payments`, not schedule projection. Both values are returned (`totalOutstanding` vs `totalOutstandingProjected`).
- **UTC date shift in consumers**: `loan_schedule_rows.date` comes back as a JS `Date` at midnight UTC. `toISOString().slice(0,10)` shifts first-of-month dates back by one day under SAST (UTC+2). Consumers must use local-date getters (`getFullYear/getMonth/getDate`) when formatting schedule dates — otherwise 2026-01-01 → 2025-12-31 (closed Dec period) and `postJournalEntry` rejects.
- **NCA blocking** runs _before_ period lock check in `postPeriodJournals` — cleaner UX.
- **`principalPaid = payment − interest`** is signed. Earlier clamped-to-zero code caused imbalanced journals when interest capitalised.
- **`inputs_hash`** is `sha256({ENGINE_VERSION, loanRowToInputs(loan), events, points}).slice(0,16)` — every engine input, so editing principal, rate, term, residual, start date, day count or the reprice/skip/lump modes invalidates the cached run. Bump `ENGINE_VERSION` on any behavioural change to `src/lib/amortisation/engine.ts`. `fetchEvents`/`fetchRatePoints` order by `(date, id)` so tie order cannot move the key.
- **`getOrComputeSchedule` reads the loan `FOR SHARE`** and must run inside a request transaction (`withAuth`). Without the lock a concurrent `updateLoan` can land between the read and the touch below, and the touch then promotes the superseded run over the one the edit produced. `previewSchedule` passes `forShare=false` — it persists nothing, so it must not block edits. The lock is held until the request commits, so the schedule rows are persisted in ONE `unnest` INSERT rather than a round trip per period (measured 39-55 ms against 773-806 ms for a 195-period schedule).
- **A cache hit touches `computed_at`.** `loanGlPostingService`, `loanComplianceService` and `loanPeriodCloseService` all pick the LATEST run by `computed_at`; without the touch, reverting a loan edit would leave the superseded run newest and post it.
- **Period close is not atomic** across loans — partial failure leaves some reclass entries posted. Lock row is inserted at the end so retry safely throws "already locked".
- **Compliance DPD counts forward from the OLDEST arrear** (K-082) — the reference instalment is the oldest non-skip schedule row dated ≤ asOf with no `loan_payments` row for its period. It used to be the NEXT row ≥ asOf, which is never in the past, so `computeDaysPastDue` returned 0 and every exposure staged 1. Lives in `loanArrearsService.resolveArrears`.
- **`loan_gl_postings` is NOT a payment record** — `postPeriodJournals` writes the CONTRACTUAL instalment journal whether or not cash arrived, dated to the schedule. Reading arrears from it makes a company that posts its period journals on time look current while the borrower pays nothing. `loan_payments` is the receipt subledger (UNIQUE on `(company_id, loan_id, period_number)`) and is the only settlement evidence `resolveArrears` consults — there is no fallback to the posting date, because that fallback reinstates the defect for exactly the loans it was meant to help. A loan with NO receipts captured therefore measures arrears from its oldest due instalment and the assessment is stamped with a `notes` line saying so.
- **The period-close reclass posts the MOVEMENT, not the balance** (K-081) — `buildReclassificationInput` (now in `loanReclassService.ts`) takes `priorStLiability` and journals `stLiability − prior`, reversing direction when the current portion falls and emitting no lines when it is unchanged. Posting the full amount every month compounded the current / non-current split.
- **`prior` comes from `loan_reclass_postings`, never from a lock or the schedule** — `closeLoanPeriod` writes the period lock unconditionally, including for loans it skipped (missing GL accounts, no schedule row, zero movement), so a lock is NOT evidence that this loan was reclassified; reading a prior off one drove the current-portion account into a debit balance that never self-corrected. Reading the latest schedule run was equally wrong: a reprice between two closes silently restated the earlier month. Migration 645 records what each close actually posted, per loan per month, and migration 659 rebuilds the backfill of that history from the reclass journals already in the GL. **659 resolves the loan by its own identity, never by rebuilding the narrative string**: 645 matched `je.description` against `'Reclassification – loan ' || COALESCE(reference, id::text) || ' for ' || yyyymm` plus the loan's CURRENT `current_portion_account_id`, and neither half is unique — `loans.reference` has no unique constraint and one current-portion account serves every loan in the company, so two loans sharing a reference each absorbed the other's journals and the next close posted a fabricated movement. 659 extracts the key from the description, refuses (loudly, per company) any key that resolves to none or more than one loan, aggregates every journal in a month before the running sum, skips a loan whose current-portion account was re-pointed, and ignores reversed entries. Every refusal is written to `loan_reclass_backfill_refusals` as well as raised as a WARNING — node-postgres discards notices unless a listener is registered, which is why `scripts/apply-migrations.ts` now registers one (review round 3, H1). Candidates are selected on a loose `LIKE 'Reclassification%loan%'`, so a description the strict parse rejects is REFUSED by name rather than dropped in silence (M3).
- **`postPeriodJournals` is idempotent** (K-083) — it takes the loan row `FOR UPDATE`, then refuses when `loan_gl_postings` already holds a row for `(company_id, loan_id, period)` with `reversal_of IS NULL AND journal_entry_id IS NOT NULL`. Migration 644 adds a btree_gist EXCLUDE constraint with the same predicate as the structural backstop; it is not a unique index because the table holds one row per journal LINE.
- **Reversing a loan journal does NOT free the period for re-posting** — a GL reversal writes `gl_journal_entries` / `gl_journal_lines` only and leaves the original `loan_gl_postings` rows with `reversal_of IS NULL`, so they keep blocking. Re-posting means deleting or re-pointing those rows first. Nothing in the repo writes `reversal_of` on this table today.
- **A loan cannot skip all twelve months with EXTEND_TERM** (K-084) — with k of the twelve months skipped the term extension converges to `termMonths * k / (12 - k)`, so k = 11 costs 11x the term and only k = 12 fails to terminate. `assertSkipScheduleRepayable` (`loanValidation.ts`) rejects k ≥ 12 and `amortise` caps `extendedPeriods` at 12x, so the two bounds accept exactly the same loans **for recurring skips** — a cap below 12x turns loans the validator accepts into 500s on every schedule recompute. `SKIP` rows in `loan_events` are per-loan data the validator never sees and skip periods too, so a loan at k = 11 plus enough SKIP events can still reach the engine cap; it throws a named error there rather than looping (review L2). ENGINE_VERSION is NOT bumped: every input the validator accepts produces a byte-identical schedule (verified over 144 term/mode/skip-count combinations against the pre-fix engine).
- **Seed data needs GL account linkage** — `gl_account_id` + `current_portion_account_id` + `interest_expense_account_id` + `interest_payable_account_id` + `bank_account_id` must all be non-null for `closeLoanPeriod` / `recordLoanPayment`. Otherwise the service silently skips.
- **Loan periods must close in ascending order** (K-081 review M2) — `fetchPriorReclass` reads the latest EARLIER record, never a later one, so closing April and then the skipped March gave March a prior of 0, posted the FULL current portion, and no later close ever unwound it. `assertClosesInOrder` refuses the out-of-order close. It is a read-then-act check with the lock INSERT several journal posts away and a PK that only stops the SAME month twice, so it first takes `pg_advisory_xact_lock(hashtextextended(company_id, 621))` — otherwise two concurrent closes of adjacent months both read an empty later-lock set and both post their full current portion (review round 3, M4). **It throws unless it runs inside a request transaction**: an advisory *xact* lock taken on a pooled connection is released the instant it is taken, so the guard would look present and serialise nothing (round 4, M1). `closeLoanPeriod` calls it BEFORE the already-locked read, so two concurrent closes of the SAME month answer under the lock instead of both re-posting the month and colliding on the `loan_period_locks` PK sixty lines later (round 4, M2).
- **Neither loan posting path may write a journal with a NULL `fiscal_period_id`** (K-081 review L6) — `createJournalEntry` falls back to NULL outside the auto-create window (10y back / 2y forward) and `postJournalEntry` guards its closed-period check behind `if (entry.fiscalPeriodId)`, so a far-future schedule row posted outside the trial balance, VAT201 and the AFS. `assertFiscalPeriodResolved` throws instead, rolling the request back.

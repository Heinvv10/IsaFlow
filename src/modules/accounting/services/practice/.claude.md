# practice/

Practice management for accounting/audit firms: time tracking, WIP → invoice, jobs + tasks, staff rate cards, client mgmt, scheduled reports. PRD-01.

## Modules
- **Time tracking + WIP**: `practiceTimeEntryTypes.ts`, `practiceTimeEntryService.ts` (CRUD + internal `validateClientCategoryWorkItem`; `listPracticeEntries` lives in `practiceTimeEntryList.ts`, re-exported; `mapEntry` in the leaf `practiceTimeEntryMap.ts`), `practiceTimeEntryWorkflow.ts` (submit/approve/reject/`markEntriesBilled`), `practiceEntryTemplateService.ts` (recurring templates), `practiceWipService.ts` (WIP aggregation → customer invoice), `wipInvoiceLines.ts` (`buildGroupedLines`, by work item / category), `wipEntryLock.ts` (`FOR UPDATE` row lock on the entries a WIP run is about to bill).
- **Clients + rates**: `practiceClientService.ts` (with optional `link_customer_id` to AR), `practiceClientFence.ts` (`assertPracticeClientInCompany`, R-073; `assertClientGroupInCompany`, R-161), `practiceClientBulkService.ts` (CSV import/export, Phase 5A), `practiceClientRateOverrideService.ts` (per-client-per-staff override, mig 395), `practiceStaffRateService.ts` (cascade resolver), `practiceCostRateService.ts`.
- **Jobs + tasks**: `practiceJobService.ts` (status `new|in_progress|review|complete|billed` + budget hrs/amt; types in `practiceJobTypes.ts`), `practiceJobBudget.ts` (pure Engagement Budget figures) + `practiceJobBudgetService.ts` (per-job budget status), `practiceJobCategoryService.ts` (Bookkeeping/Tax/Audit/AFS/VAT/Payroll/Advisory), `practiceTaskService.ts`, `practiceRecurringTaskService.ts` (`sweepRecurringTasks` cron).
- **Reporting + notifications**: `practiceReportsService.ts`, `practiceMonthlyReportService.ts`, `practiceReportRecipientsService.ts`, `practiceNotificationService.ts`.
- **Users**: `practiceUsersService.ts` (`listCompanyUsers` request-scoped via mig 716; `listCompanyUsersForSystem` for crons only).

## Caller contract
Invoked by `withAuth`-wrapped API routes in `pages/api/accounting/practice/*`. Every DB function takes `companyId` first. `sweepRecurringTasks()` runs under a cron job (loops companies internally).

## Main function signatures
- `createPracticeEntry(companyId, userId, input)` — calls `validateClientCategoryWorkItem` to ensure client/category/work_item all scope to `companyId`.
- `submitEntry / approveEntry / rejectEntry / markEntriesBilled(companyId, entryIds, invoiceId)`.
- `getWipByClient(companyId): Promise<WipRow[]>` — approved+unbilled aggregated per client.
- `generateWipInvoice(companyId, userId, { practiceClientId, timeEntryIds, invoiceDate?, taxRate?, groupBy?, dueDate?, notes? }): Promise<{ invoiceId, invoiceNumber, lineCount, subtotal, taxAmount, totalAmount }>`: creates `customer_invoices` row + items, calls `markEntriesBilled`. Requires `practice_clients.link_customer_id`.
- `resolveRate(companyId, userId, clientId, onDate): Promise<number | null>` — cascade: per-client override → staff default → `null`. Reads `COALESCE(rate_per_hour, rate)` and matches on either `staff_user_id` or `user_id`, because `practice_client_rate_overrides` carries two column pairs (mig 372 + mig 395).
- `createJob(companyId, input) / updateJob / listJobs(companyId, filters)`.
- `listJobBudgetStatuses(companyId, { practiceClientId?, jobId? }): Promise<JobBudgetRow[]>` (over first; one job = `jobId` filter) — `{ jobId, budgetAmount, consumedAmount, balance, budgetedHours, hoursUsed, percentUsed, state: 'none'|'ok'|'warning'|'over', title, jobStatus, practiceClientId, practiceClientName }`.
- `assertJobForPracticeClient(companyId, practiceClientId, jobId, { newLink }): Promise<string | null>` — the job id to store; `isJobFenceRefusal(err)` for routes.
- `sweepRecurringTasks(): Promise<RecurringSweepResult>` — cron-driven generator.

## Business rules
- Time-entry state: `draft → submitted → approved → billed`, with `rejected` branch. Billing requires approved + unbilled.
- WIP → invoice: idempotent via `entry.invoice_id` — once set, entry is excluded from WIP aggregation.
- `link_customer_id` on `practice_clients` is OPTIONAL — WIP invoice generation fails early when absent.
- WIP → invoice takes `FOR UPDATE OF te` on its eligible entries (`lockEligibleWipEntries`, 5s `lock_timeout`) and requires a request transaction; overlapping runs serialise there, and the loser finds nothing eligible. The invoice build runs in a savepoint so the billed-count guard can undo it — the route answers a caught error with a 400, which `withAuth` COMMITs. Each invoice-number attempt takes its own savepoint too: a peer's 23505 aborts the transaction, and without one the retry loop cannot execute a further statement. The retry re-reads `MAX(invoice_number)` and takes exactly the next number — never `MAX + 1 + attempt`, which would gap the VAT invoice sequence, since the re-read already reflects the peer's committed number.
- Rate cascade is deterministic; no DB writes during resolution.
- A practice client id taken from a caller goes through `assertPracticeClientInCompany(companyId, id)` BEFORE the first write (R-073). Every FK to `practice_clients` is tenant-agnostic. It throws `PracticeClientNotInCompanyError` (code `PRACTICE_CLIENT_NOT_FOUND`) and routes answer 400. An absent id passes; the read is savepointed, so a malformed id is refused rather than aborting the tx. It checks the tenant only, not `status`.
- A client group id from a caller goes through `assertClientGroupInCompany(companyId, id)` the same way (R-161): `create/updatePracticeClient` call it before the first write, and it throws `ClientGroupNotInCompanyError` (code `CLIENT_GROUP_NOT_FOUND`). `practice_clients.client_group_id` is the only FK to `practice_client_groups`, and no read joins it: the client API returns the raw id.
- **Engagement Budget** (`practice_jobs.budget_amount`, mig 850, NULL = "No budget", CHECK >= 0): consumption is EVERY time entry with that `job_id` in the same company except status `leave` — draft, submitted, approved, billed, invoiced, non-billable and written-off (`not_billable`) all count — valued at `ROUND(hours × applied_rate, 2)` per entry (not `line_total`); a NULL rate adds hours, not rand. The entry must also be the job's client's (`te.practice_client_id = pj.practice_client_id`). Client name = `COALESCE(trading_name, legal_name)`. Balance = budget − consumed. State: `none` (no budget), `over` (balance < 0), `warning` (≥ 80% used), else `ok`; computed in cents. It warns only: saving time is never blocked. Joins are `te.company_id = pj.company_id` and `pc.company_id = pj.company_id`, because `time_entries.job_id` is a tenant-agnostic FK. `updateJob` treats `budgetAmount` three-state (absent/undefined keeps, null/'' clears, number sets); anything else — negative, non-number, ≥ `MAX_BUDGET` (10^13, so cents stay exact in JS) — is `JobBudgetInvalidError` (code `JOB_BUDGET_INVALID`, 400 with its message).
- A time entry's `jobId` goes through `assertJobForPracticeClient` before the first write (create, update, duplicate): the job must be this company's AND the entry's own practice client's, else `PracticeJobNotForClientError` (code `PRACTICE_JOB_NOT_FOUND`, routes 400). Absent/null/'' = no job; a non-string or malformed id is refused (savepointed read). Update re-fences the kept job when the client changes (undefined `jobId` = unchanged); duplicate carries the source's job. A NEW link (create, duplicate, bulk, MCP, an update that changes the job) to a `complete`/`cancelled`/`billed` job is `PracticeJobClosedError` (code `PRACTICE_JOB_CLOSED`, 400); an entry keeping its job is unaffected. Bulk fill-from-template (`jobId`) and MCP `log_time_entry` (`job_id`, null = no job, dry_run too) fence once up front. Entry templates carry no job. Job ids compare case-insensitively for "new link" (an uppercase copy of the kept job is not one). Duplicating an entry whose job has since closed is refused (`PracticeJobClosedError`): a copy is new time, and closed jobs take none — deliberate (review round 2), and no UI calls `/duplicate`.
- **Migration 851:** composite FK `time_entries (job_id, company_id, practice_client_id) → practice_jobs (id, company_id, practice_client_id)` ON UPDATE RESTRICT, NOT VALID (needs UNIQUE on the three job columns). So a job whose entries are its current client's cannot move to another client: `updateJob` runs its UPDATE in a savepoint and turns that 23503 into `JobClientHasEntriesError` (code `JOB_CLIENT_HAS_ENTRIES`, 400). A job with no entries still moves. The fence reads the job without a lock, so a job moved between the read and the write reaches the FK as a 23503: create, update and duplicate run their write in a savepoint and `rethrowJobFkAsRefusal` turns that 23503 into `PracticeJobNotForClientError` (400). In bulk only a refusal (`isJobFenceRefusal`, `PracticeEntryRefusal`) is a per-date failure — reported with its message and logged at warn with the date. Every database error is re-thrown, class 22/23 included: on valid input none is reachable on this INSERT (no unique index but the pkey, hours range-checked first, 851's 23503 mapped to the fence refusal, a NUL in `taskOverride` refused by the route), so 57014, 40P01, 42703, 23502, 22P02, a lost connection, an aborted tx or a non-Error throw is a fault: the route re-throws it too, the request 500s and withAuth rolls back the dates already written. There is no per-date savepoint: refusals are JS-level or come from already-savepointed statements, so the tx stays usable for the next date. `PracticeEntryRefusal` (`practiceTimeEntryTypes.ts`, no `code`) is what create's date/hours/client/category/work-item checks and bulk's template/range checks throw.
- Monthly report cron requires `practiceReportRecipientsService` rows; silently no-ops when empty. A row is mailed only when it is active, opted into `monthly_summary`, and its email (trimmed, case-insensitive) is a member of that company in good standing (`listCompanyUsersForSystem`); any other row is skipped and counted in `recipientsSkipped` (R-168).
- Phase 5A: bulk CSV import creates+updates by `client_code` key.

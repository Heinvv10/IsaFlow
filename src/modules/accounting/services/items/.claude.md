# Items service group

Manages inventory items, fixed assets (FAR — Fixed Asset Register), item bundles, and accounting adjustments. The engine files (`inventoryService`, `assetService`, `farDepreciationService`, `farAfsService`) are pure business logic with no DB dependencies, enabling straightforward unit testing.

## Files

| File | Role |
|---|---|
| `itemService.ts` | DB CRUD for `items`. Filters: `q` (text search), `type` (physical/service), `active`, `category_id`. JOINs `item_categories` for `category_name`. |
| `inventoryService.ts` | **Pure, no DB.** `calculateWeightedAverage`, `calculateFIFO` (layer-by-layer FIFO from movement history), `validateStockAdjustment`, `validateProduct`. |
| `adjustmentService.ts` | DB service for `accounting_adjustments` (customer/supplier balance adjustments). Posts a GL journal via `createJournalEntry` + `postJournalEntry` from GL group. |
| `assetService.ts` | **Pure, no DB.** Depreciation: `straight_line`, `reducing_balance`, `sum_of_years`. SARS wear-and-tear rate table (computers 33.33%, motor vehicles 20%, etc.). `validateAsset`, `validateDisposal`. |
| `farDepreciationService.ts` | **Pure, no DB.** Dual-track engine: IAS 16 policy depreciation (`calculatePolicyDepreciation`) + SARS tax depreciation (`calculateTaxDepreciation`). `calculateDeferredTax` computes temporary difference and deferred tax asset/liability. Pro-rates first month by purchase date. |
| `farAfsService.ts` | **Pure, no DB.** Aggregates `asset_period_ledger` data into IAS 16 PPE movement note (`buildPpeMovementNote`) and deferred tax schedule (`buildDeferredTaxSchedule`). Consumed by AFS note engine. |
| `farDisposalService.ts` | DB service: records asset disposal, calculates profit/loss on disposal, posts GL entries. |
| `itemBundleService.ts` | DB CRUD for `item_bundle_lines` (parent → child item relationships). JOINs `items` for child description/price. |
| `assetRegisterService.ts` | The register as at a date (`getAssetRegister`) plus its GL reconciliation (`getAssetGlReconciliation`). An asset DISPOSED on or before `asOf` is kept out of the totals and returned separately — it is not carrying amount. The GL side is `loadAssetSectionAccounts` from `fixedAssetReconciliationQueries`; one query, two consumers, so `asset_register` and `reconcile_fixed_assets` cannot disagree about the ledger side. |
| `fixedAssetReconciliationQueries.ts` | The three queries behind the reconciliation: the asset-section GL accounts with balance/line count (`loadAssetSectionAccounts`), the journals behind them capped at 50 per account (`loadAssetSectionDocuments`), and whether any asset or the categories its assets use names a GL account (`hasRegisterLinkage`). NO `is_active` filter and NO name matching, ever. `asset_categories` has no `company_id`, so it is reached only through this company's assets. |
| `fixedAssetReconciliationService.ts` | `reconcileFixedAssets` — DECOMPOSES register-vs-GL into one item per held asset and one per asset-section account, each carrying its own amount, so the items sum to the difference. `normalBalanceViolated` flags an account whose balance sign contradicts its subtype (R8,458,079.49 of Brightsphere loan accounts). It REPORTS misclassification; it never filters on it. |
| `depreciationRunPlan.ts` | Every guard for the monthly run, nothing written: the fiscal period must exist and be open, and each asset is classified `not_in_service` / `no_purchase_price` / `below_capitalisation_threshold` / `no_useful_life` / `already_posted` or is postable. `depreciationEntryNumber` derives `DEP-<asset>-YYYY-MM` from the PERIOD. |
| `depreciationRunService.ts` | `executeDepreciationRun` (writes, guards nothing), `runDepreciation` (plan + execute — the REST route's entry point) and `previewDepreciationJournals` (the dry run's journals). A dry run is plan WITHOUT execute, so it is structurally incapable of passing where the live call refuses. |
| `index.ts` | Barrel re-export. |

## Multi-tenant rules

All DB services (`itemService`, `adjustmentService`, `farDisposalService`, `itemBundleService`) scope on `company_id`. Pure engine files have no DB access and therefore no tenant context — callers are responsible for scoping inputs.

## Key tables

- `items` — product/service master. `item_type`: physical | service.
- `item_categories` — optional grouping.
- `item_bundle_lines` — parent-child item compositions.
- `accounting_adjustments` — balance adjustment audit log.
- `assets` — fixed asset register. `status`: available | assigned | in_maintenance | disposed | written_off.
- `asset_period_ledger` — period-by-period depreciation history (consumed by `farAfsService`).

## Gotchas

- **`inventoryService` and `assetService` are pure** — they contain no `sql` calls. This is intentional. The DB persistence layer lives in `itemService` (for inventory) and future FAR DB services. Do not add DB calls to the pure engine files.
- **SARS rate table is hardcoded** in `assetService` — rates are legislated and rarely change, but the table must be updated when SARS revises wear-and-tear schedules.
- **`farDepreciationService` pro-rates the first month**: if `purchaseDate` falls mid-month, the first period's depreciation is proportional. `openingAccDep` must carry forward accumulated depreciation from prior periods — failure to pass it causes over-depreciation.
- **`farAfsService.buildPpeMovementNote`** groups by `ias16Group`. Assets not assigned a group appear under a fallback bucket. Ensure all assets have `ias16Group` set before generating AFS notes.
- **`adjustmentService` uses `getSystemAccount`** from GL's `systemAccountResolver` — it needs system accounts (`receivable`, `payable`) to be configured on the tenant's COA.

# capture/

PRD-05 autonomous capture + evidence-first ledger. Pure business logic — HTTP handlers live under `pages/api/accounting/capture/`.

## Modules
- **Ingress**: `captureInboxService.ts` (mint `cap-<32hex>@inbox.isaflow.co.za`), `inboundEmailService.ts` (Postmark webhook → `capture_events` + `captured_documents`), `imapMirrorService.ts` + `mirrorConnectionService.ts`, `whatsAppInboundService.ts` (Twilio WABA; includes bank-tx query reply hook), `whatsAppMessageDedupe.ts` (MessageSid redelivery dedupe + text-command event insert), `whatsAppTextCommandParser.ts` (pure SA expense shorthand parser), `whatsAppReplyService.ts`, `whatsAppChaseService.ts`.
- **Bank-Tx Client Query (Workstream D)**: `bankTxQueryMessage.ts` (pure compose + normalize, no DB/clock), `bankTxQueryService.ts` (create/send/list/status/settings), `bankTxQueryReplyService.ts` (find open query, attach reply media, mark replied), `twilioMediaFetch.ts` (HTTP basic-auth Twilio media download, extracted from inbound service for file-size cap).
- **Routing / query**: `captureRouterService.ts` (`routeEvent` orchestrates VLM fire-and-forget), `captureQueryService.ts` (inbox listing w/ joins).
- **Rules + auto-publish**: `supplierRulesService.ts` (per-supplier GL defaults, learning loop → `auto_publish=true` at 5 consecutive matches), `autoPublishGateService.ts` (decision ladder), `duplicateDetectionService.ts` (fingerprint + fuzzy fallback).
- **Provisional posting (Phase 5)**: `provisionalPostingService.ts` (`postProvisional` stamps `ai-provisional:v1`, `needs_evidence=true`), `evidenceAttachmentService.ts` (flips to `ai-evidenced`).
- **Attach then settle (R-127)**: `provisionalAttachSettle.ts` — `attachEvidenceAndSettleApproved`, the attach `capturePostFollowUps` and `ai-invoice-pipeline` run; when the invoice was inserted auto-`approved` and the attach succeeded, it posts it through `postSupplierInvoiceToGL` in its own savepoint so the provisional becomes its payment (`ap/provisionalInvoiceSettlement.ts`). With `postUnattached: true` (`capturePostFollowUps`, R-131, and `ai-invoice-pipeline`, R-160 — every caller) an auto-approved invoice that evidences NO provisional is posted the same way. Either posting failing withdraws the auto-approval to draft with the reason in its notes and in `settlementRefused`; the only throw is that revert failing.
- **Capture bill lines (R-131, R-160)**: `captureBillLines.ts` — `planCaptureBillLines(companyId, invoiceInput, extractedLineCount, captureAccountId, rule)` (read-only; `capture/[id]/post` and `ai-invoice-pipeline` run it BEFORE their posting claim; the pipeline passes no event account — it reads no capture event — and `getRule`'s rule) returns `{ lines }` or `{ refusal }` (→ 400). Extracted items are used, computed by `ap/supplierInvoiceTotals`, coded to the event's or the rule's account when there is one, else uncoded. With no extracted items: ONE line `As per invoice`, net = total − VAT, tax = the extracted VAT, on the event's `resolved_gl_account_id`, else the supplier coding rule's `default_gl_account_id`, else the company `default_expense` system account (Hein, 2026-09-29). Refused: no total (≤ 0), no account from any of the three (a `MissingSystemAccountError` only; any other fault throws), a line `assertSupplierInvoiceLines` refuses, or an account `billLineAccountRefusal` refuses. `insertCaptureBillLines(invoiceId, lines)` writes them on the request transaction with `createSupplierInvoice`'s columns. `createSupplierInvoice` itself is not used: it recomputes the header totals from the lines and cannot write the status, `source_document_id` or fingerprint the route decided.
- **Manual evidence attach (R-107)**: `provisionalEvidenceAttach.ts` — `attachDocumentToProvisional`, behind `POST /api/accounting/provisional/[jeId]/attach`. Locks bank line → journal → document, refuses before any write, then takes the `posted_at` claim: the provisional journal already expensed the bank line, so the slip is spent. Result is a union (`attached` / `not_found` / `refused` / `contended` → 409).
- **Matching (Phase 4/6)**: `fourWayMatchService.ts` (`recordPaymentMatch` idempotent), `supplierGraphService.ts`, `expectationEngineService.ts` (learn supplier cadence), `missingInvoiceChaseService.ts`, `alertResolutionService.ts`, `expectationCronService.ts` (daily orchestrator).
- **Supplier statement recon (Phase 7)**: `supplierStatementMatchHelper.ts`, `supplierStatementReconDb.ts`, `supplierStatementReconService.ts`; since 2026-10-17 the upload only inserts an 'extracting' row and `supplierStatementLifecycle.ts` (create / retry / delete-failed) + `supplierStatementExtraction.ts` (per-page VLM read) + `supplierStatementExtractionJob.ts` (background job, `supplierStatementMeasure.ts` measures our side) finish it. See `bank/.claude.md` Recent changes 2026-10-17.
- **Petty-cash posting**: `pettyCashJournalService.ts` — `postReceiptAsPettyCashJournal`, the
  anonymous branch of `capture/[id]/post-expense` (no employee attached). Resolves
  `gl_accounts.vat_input_denied` on the coded account and hands it to
  `buildExpenseJournalFromReceipt`, so s17(2)(a) entertainment claims are denied on a path
  that auto-posts unattended. It tags `vatType` and posts, so it — not the route — is what
  `scripts/ci/check-vat-guard-coverage.ts` governs. It runs `validateJournalEntry` on the
  built lines BEFORE its first write and throws `ReceiptDoesNotBalanceError`, which the
  route maps to a 400 — the same answer `receipt-to-journal.ts` gives, so a mis-extracted
  receipt is not reported as an internal error on either path.
- **Duplicate receipts / posted content (R-088)**: `receiptFingerprint.ts` (pure: `receiptContentKey` = `v1|vendor|YYYY-MM-DD|totalCents|vatCents-or-none`, `referencesDistinguish`), `postedContentFence.ts` (`lockPostedContent`, `findPostedContent`, `ContentSpend` = `expense | invoice | evidence`) and `receiptDuplicateGuard.ts` (`checkReceiptDuplicate`, the receipt routes' fuller check). `claimCapturedDocumentForPosting(companyId, documentId, category, content)` takes a REQUIRED `content: { spend, ...fingerprint }` and itself refuses a FILE already booked from another upload (`content_posted` / `content_busy`, `CAPTURED_DOCUMENT_REFUSAL_ERROR_CODE` → 409).
- **Audit**: `auditTrailExportService.ts`.
- **Bank-Tx Attach (Workstream G)**: `captureBankTxAttachService.ts` — tenant-preflighted link of captured doc → bank tx + ≤2MB data-URL mirror into bank_transaction_attachments, dedupe key `${documentId}_${fileName}`, mirror fail-soft link-only.

## Caller contract
Invoked by `withAuth`-wrapped API routes in `pages/api/accounting/capture/**` (and siblings like `/supplier-rules`, `/supplier-expectations`, `/provisional/**`, `/evidence/**`). Every public function takes `companyId` as first arg; not request-bound — callable from cron jobs or inline.

## Business rules
- **Evidence-first**: every JE carries `posting_agent` (`human:<uid>` | `ai:<name>:v1` | `rule:<id>` | `system:<job>` | `legacy:*`). Enforced at service write-path, not DB CHECK.
- **Auto-publish opt-in only**: company-level `chase_auto_send_enabled` + per-supplier `chase_opted_out` gate chase; supplier-rule `auto_publish` + confidence threshold gate posting.
- **Idempotency**: `expected_invoice_alerts(company, supplier, expected_by)` UNIQUE + `ON CONFLICT DO NOTHING`; `payment_matched` once-true; `ai-provisional → ai-evidenced` one-way.
- **Graceful degradation**: Twilio / Postmark / Storage return `{ sent: false, reason }` or null when env vars absent — never throw.
- Twilio webhook signature validates against `NEXT_PUBLIC_APP_URL` — must match Twilio console exactly.
- **Bank-Tx Query — fail-closed send**: No Twilio send → no `bank_tx_queries` row. The send failure `reason` is surfaced verbatim in the POST 400 response.
- **Bank-Tx Query — reply matching**: `findOpenQuery` matches by `company_id` + normalised E.164 `to_number`, status IN ('sent','replied'), 'sent' preferred (ORDER BY `status='sent' DESC, sent_at DESC`), limit 1. Resolved/cancelled queries are never resurrected — `markQueryReplied`'s WHERE guards status IN ('sent','replied').
- **Bank-Tx Query — reply text append**: a second message from the same sender appends to `reply_text` with newline; `replied_at` is set only on the first reply (COALESCE).
- **Bank-Tx Query — media size cap**: reply media ≤2MB is attached to `bank_transaction_attachments` (same surface as manual uploads); media >2MB is captured by the normal inbound pipeline but NOT attached to the query row (warn log).
- **Bank-Tx Query — ownership preflight**: `attachReplyMedia` re-verifies the bank_transaction belongs to the company before inserting, even though `query` comes from the company-scoped `findOpenQuery` (defense-in-depth, matching the manual-upload API guard).
- **Bank-Tx Query — mime re-validation**: `attachReplyMedia` re-validates the mimeType against `/^(image\/(jpeg|jpg|png|webp|tiff)|application\/pdf)$/` before building the data URL. A mimeType with parameters (e.g. `image/jpeg; charset=utf-8`) is refused with a warn log.
- **Bank-Tx Query — media dedupe**: filenames embed the Twilio MessageSid (`whatsapp_SM123_0.jpeg`). `attachReplyMedia` checks for an existing attachment with the same `file_name` before inserting and returns `true` (skip) if found — preventing duplicate attachments on Twilio webhook retries. NOTE: a retried text-only reply that creates no capture_event (not an expense command) still appends `reply_text` twice — with no event there is no MessageSid row to dedupe against.
- **Bank-Tx Query — reply_text cap**: `markQueryReplied` wraps the `reply_text` CASE expression in `LEFT(..., 10000)` to prevent unbounded growth.
- **Bank-Tx Query — Twilio host allowlist**: `fetchTwilioMedia` validates the URL hostname against `api.twilio.com`, `*.twilio.com`, and `*.twiliocdn.com` before issuing any fetch, preventing SSRF via a crafted MediaUrl in the Twilio payload.
- **Bank-Tx Query — webhook fail-open**: the inbound Twilio webhook's query-reply hook is wrapped so a DB error never 500s the webhook. A 500 would cause Twilio to retry; the retry is deduped by MessageSid (see Twilio redelivery), but the reply side effects would be re-run. The normal capture path still runs regardless.
- **Twilio redelivery (K-160, migration 700)**: `capture_events.provider_message_id` (MessageSid) + `provider_message_part` (media index, `-1` for the text-command event) under the partial unique index `uq_capture_events_provider_message`. `ingestTwilioPayload` skips parts `ingestedParts` already finds (no refetch), and inserts events `ON CONFLICT … DO NOTHING` so two deliveries in flight at once yield one event — the loser deletes its own `captured_documents` row (and, best-effort, its uploaded object) and still answers 200. A redelivery returns `parsedCommand: null` and no already-ingested ids, so the route does not acknowledge twice, and it does not call `markQueryReplied` unless it created an event. Rows written before 700 carry NULL and are not covered.
- **Bank-Tx Query — dual intent**: an expense-command text arriving from a sender with an open query BOTH creates the text-command capture event AND records the text as the query reply (intended behaviour, not a bug).
- **duplicate_fingerprint — one producer, one source per segment**: the string is `asciiLower(vat|invoice_number|amount)` and is built ONLY by `computeFingerprint` in `captureDeduplicationService.ts`, never inline in an INSERT. The VAT segment comes from `suppliers.vat_number` (`'no-vat'` when null) — never from an OCR'd `extracted.vendorVatNumber`; the amount is rendered at the column's own `NUMERIC(15,2)` scale, rounding the decimal text half away from zero as PostgreSQL does; the case fold is A–Z only, mirrored in SQL by `translate()` and NOT by `lower()`, which is collation-driven and disagrees with JS on `İ` (U+0130) and on a trailing sigma. The seven live producers (the two capture routes, `supplierInvoiceService`, `migrationApService`, `recurringTransactionService`, `sageSupplierInvoiceImportService`, migration 670) must pass the same source for each segment: the same helper with a different argument still yields a fingerprint `findDuplicate`'s exact-match step cannot find, and the bill is accrued twice. Migration 412's backfill is an eighth, historical producer, superseded by 670 on every row: its amount segment is `coalesce(total_amount::text,'0')`, which agrees with the other seven only because `total_amount` is `NOT NULL DEFAULT 0` (it would render a NULL as `0`, not `0.00`), and it folds with `lower()`. Do not treat it as agreeing by construction.
- **duplicate_fingerprint — out-of-band inserts stay NULL**: `scripts/import-sage-britech.ts`, `scripts/qa-seed/transactions.ts` and `scripts/seed-historical-data.mjs` insert `supplier_invoices` without the column. Migration 670 canonicalises the NULLs present when it runs; rows these scripts write afterwards keep a NULL fingerprint and are invisible to the exact-match step (the fuzzy step still covers them). Re-run 670 after any such import.
- **Bank-Tx Query — lifecycle**: statuses follow `sent → replied → resolved` or `sent → cancelled`. The `cancel` action is only allowed from `sent`; `resolve` is allowed from both `sent` and `replied`.

- **Posted content — what matches (R-088)**: same bytes (`raw_bytes_sha256`, set at intake by upload, email, WhatsApp and IMAP; a NULL hash never matches) is the same slip on EVERY claimer — receipt-to-journal, both post-expense branches, `capture/[id]/post`, `ai-invoice-pipeline`, manual claim lines (`claimLineSourceDocuments`) — and cannot be confirmed as a repeat. On the receipt routes only, the same `receiptContentKey` is the same slip too unless BOTH extractions read a printed `referenceNumber` and they differ; that match answers 409 `DUPLICATE_RECEIPT` with `details.canConfirm = true`, and `confirmDuplicate: true` posts it, stamping `posted_duplicate_of` + `posted_duplicate_confirmed_by`. Only rows with `posted_at` count, so a release frees the slip (`releaseCapturedDocumentPostingClaim` clears all four columns). **Evidence attach**: `provisionalEvidenceAttach` claims with `spend: 'evidence'` — no check, no stamp, because it books nothing new; but the slip IS booked, so an evidenced document counts against EVERY later posting of the same content, invoice routes included (one slip, one booking — `spend` decides the stamp only). The invoice routes used to skip it on the promise that R-127 settles the invoice, but R-127 settles only an invoice whose OWN document evidences the provisional; an invoice from a SECOND upload was approved beside the provisional and double-booked (R-088 × R-127, corrected 2026-09-27). The R-127 same-document flow is untouched: the invoice route claims its own slip, then the auto-attach evidences the provisional with it. **Every claim, the evidence attach included, takes the file's advisory lock AND refuses a file another upload has booked** (`content_posted`; evidence still stamps nothing): a manual attach of A after B was invoiced (B's auto-attach missed) would otherwise mark the provisional evidenced beside B's unsettled bill and hide it from the needs-evidence queue. Either deadlock resolution between the manual attach and a same-bytes invoice post is then safe (B victim → A waits, reads B, refused; A victim → A refused busy, B's own auto-attach evidences). The receipt key is not locked for evidence — it stamps none, so no key match could find it. **Accepted trade-off**: a slip only manually evidenced (R-107 attach) can never get an AP bill from ANY upload — its own claim is taken and every other upload is `content_posted`; the books are right (the provisional booked it once) but supplier-statement matching shows no bill (R-127 fix.md, Other limits). Serialised per fingerprint by `pg_advisory_xact_lock` (sorted, 5s `lock_timeout` → 409 `RECEIPT_POST_BUSY`, naming no document). **Lock order everywhere: document row(s) first, then fingerprints** — the routes via `captureRowLock`, `claimLineSourceDocuments` via its own `FOR UPDATE` (id order) before `lockPostedContent`; the reverse order deadlocked a claim line against a route post of one document. Every route answers a claim `content_*` refusal 409 through `CAPTURED_DOCUMENT_REFUSAL_ERROR_CODE`. Manual claim lines stamp `posted_receipt_key` too (and lock it), so a re-encoded copy is refused on a receipt route; they refuse on the FILE only (one file uploaded twice onto two lines is `duplicate_file`), never on the key, having no confirm flow. Backstop: `uq_captured_documents_posted_content` (migration 710) on posted bytes, no exemption — a confirmed repeat always has distinct bytes. The key has no unique index (the reference rule is not expressible as one). **Pre-710 postings** never recorded a key, so a re-encoded copy of one is not caught (bytes still are): `bun scripts/r088-posted-receipt-key-census.ts [--company <uuid>] [--emit-sql <file>]` is READ ONLY, reports them and the key groups already booked more than once, and writes UPDATE statements for a person to review and run — nothing backfills production automatically. **False positives (L5)**: without printed slip numbers two genuine same-vendor/day/total purchases are indistinguishable; acceptable while every caller is a person who can confirm, but an UNATTENDED receipt poster must not confirm a details match on its own. Not covered: an evidence attach of a slip whose file is already booked (R-127's territory).

## Email destination identity

New email inboxes use128 random bits (32hex). Migration616 reserves each normalized email address globally, including retired rows. Collisions in existing rows stop migration for review; no address is silently reassigned. Existing short unique addresses remain supported until an authorized rotation.

Minting uses INSERT ON CONFLICT DO NOTHING and at most5attempts, so a collision does not abort the outer withAuth transaction. Rotation failure rolls back its deactivation when called through the authenticated route. Inbound routing compares lower(address), requires exactly one active match, and rejects ambiguous legacy destinations before document/storage/event writes. Sender allow-list checks remain in place. External storage tests are contract-only; SQL routing/migration checks use real disposable PostgreSQL.

## WhatsApp destination identity

Migration617 reserves trimmed WhatsApp destinations globally, including retired rows; legacy duplicates require reviewed remediation. Migration618 adds pending company claims and nullable provider proof. Saving a number creates a 24-hour challenge, not a reservation. Only an SDK-verified callback to the exact token-bearing URL with matching To may activate it. Verification rechecks creator writer role and user/company standing after acquiring the same company lock used to replace challenges. Existing verified routing stays active during pending rotation; foreign reservations never transfer automatically.

The 32-byte URL token is stored only as SHA256; raw URL is returned once with no-store and is covered by token query redaction. Ingestion requires verified company, inbox and token hash, rechecked with destination before side effects. No address-only fallback. Existing unverified assignments require reviewed re-verification before rollout; no proof is backfilled. Proof establishes control sufficient to arrange signed provider delivery under the trusted account, not independent legal ownership. Established integrations do not depend on the original creator retaining membership; company suspension still blocks delivery. Provider sandbox acceptance remains separate from SDK fixtures.

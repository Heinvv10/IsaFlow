# Budgets module (`services/budgets/`)

Budget versions and the version-aware budget entry point (budgets programme P1, migration 947; spec `docs/plans/budgets/P1-schema-versions-spec.md`, contract `docs/plans/budgets/00-shared-contract.md`).

## Files
- `budgetVersionTypes.ts`: `BudgetVersion`, `BudgetVersionError` (code + HTTP status), `mapBudgetDbError` (BV001 → LOCKED, BV002 → STATE, 23P01 on `budget_month_amounts_one_grain` → GRAIN; anything else rethrown).
- `budgetVersionScope.ts`: `resolvePrimaryVersion`, `lockVersionForWrite`, `primaryVersionScopeAndYears` (P1's primary scope per registry year and the years a range touches, in one walk; the tracking engine's date-range entry reads it), `versionYear`, `readVersion` (the core budget reader uses it), `auditBudgetWrite`.
- `budgetVersions.ts`: list, get, create (server callers may pass `basedOn`; the POST route never does), copy, set primary, delete. `budgetVersionStatus.ts`: approve, lock, unlock.
- `budgetNotes.ts`: `setGridNote`, `carryNotes`, `normaliseNote`, `MAX_NOTE_LENGTH` (the notes header's only writer).
- `index.ts`: the barrel for P2+ code. The pre-P1 services stay in `core/budgetService.ts`, `core/budgetMonths.ts`, `core/budgetYears.ts`, `reports/budgetWindowService.ts`, `reports/budgetVarianceService.ts` (36 importers, 5 `vi.mock` paths) and are re-exported here; a later cleanup may move them behind it.

## Caller contract
- Readers use the PRIMARY version of each registry year unless a `versionId` is passed. A version contributes only months of its own year; a window walks the registry years from its first day (`primaryVersionScopeAndYears`), a month two years share counts once, in the earlier year.
- Writers lock the version FIRST (`lockVersionForWrite`: `UPDATE … SET updated_at` under `withRowLockBudget`), then write amounts. This is the upgrade-deadlock rule (the DB trigger takes `FOR SHARE`) and makes "locked" a typed 409 before any write, so the request tx is never poisoned. `gridSave` does the same (see P2 below).
- Every amount write leaves one `audit_log` row (entity `budget`, entity_id = version id). Status moves are audited by the DB trigger, never by the app.
- Every write bumps the version's `updated_at` (the pre-lock), so a status move sent with an `expectedUpdatedAt` read before an amount edit is 409 STALE: "changed since you loaded it" covers amounts too.
- The notes header (`accounting_budgets`) is per account and year, shared by every version (D4: year-scoped, no migration). Its ONLY writer is `budgetNotes.ts` (P2 follow-ups): `setGridNote` (the grid's edit: year from the viewed version, refused 409 when THAT version is locked, an active leaf revenue/expense account of the company only, trimmed ≤ 2 000 (a NUL is 400), blank clears (deletes only a `'Notes'` row it or a seed made with no legacy amounts; a legacy header keeps its row, notes NULL), one audit row `noteAction: set|cleared` (plus `alsoShownOnLocked`: the year's locked version ids) without the text when something changed (a no-op save writes nothing), the version's `updated_at` untouched: it reads the version FOR SHARE, never bumps it) and `carryNotes` (seeds). A note edited from a draft also shows on a locked version of the same year: accepted (D6), the audit row records it. Two writers of one note: last write wins (the upsert's `ON CONFLICT … WHERE gl_account_id IS NOT NULL` never raises 23505). The legacy amount columns are never written. `pages/api/accounting/budgets.ts` stays GET-only and `budgetService` read-only.
- Raw DB refusals (BV001/BV002/23P01 one_grain) that get past a service check are answered with the same contract codes by `respondBudgetVersionError` (`budgetDbRefusal`); app_user may INSERT versions only as drafts (column privileges).
- Roll-ups are computed (company total = Σ dimension rows), never stored.
- Routes answer `BudgetVersionError` through `@/lib/budgetVersionResponse` (`error.details.code` carries the contract code).

- Budget writers take `holdYearRegistry` (the SHARED form of the change-of-year-end advisory lock) before reading the registry, so a save and a year-end change, or a Settings start-month change (`gl/fiscalYearStartChange.ts` takes it exclusively), serialise. Status moves (`budgetVersionStatus.ts`) write no amounts and do not take it: a P2 change that writes amounts there must.
- A change of year end (and its undo) moves the PRIMARY budget's months into the year that now holds them (`budgetYearRehome.ts`, decision 12), including a stray month that sat outside its own year. Its preview refuses, conservatively, when a locked budget of the changed year or later, a non-primary version with months after the boundary, two primaries budgeting an account at different levels, or a non-primary 'Original' in a year with no primary is involved. Anything that still fails mid-change is a plain Error (500, full rollback): a 4xx would commit the half-applied change. Known over-refusal (to narrow in P2, when dimension budgets exist): the level clash compares any two primaries of the changed year or later, not only a moving month's source and target.

## P2 grid services (PR-B)
- `gridReadModel.ts` (+ `gridReadAccounts.ts`, `gridReadTypes.ts`): one version's grid. Accounts = active leaf revenue/expense + any account holding amounts (inactive flagged); a header (named as another account's `parent_account_id`) is a roll-up row, `ownAmounts` when it holds its own. Band totals count leaves + a header's own amounts once, never a roll-up. Token `updatedAt` = P1's UTC ISO text with microseconds (never a JS Date). A year with no version answers `version: null` WITH the accounts (the page's empty state and the wizard preview need them). Each account carries `note`: its `accounting_budgets.notes` for the version's year (one per company, account and year, shared by every version of the year; blank left out), read by `loadGridNotes`.
- `priorActuals.ts`: PY actual per account × the SAME CALENDAR month a year earlier (14-month years map right), posted only, natural sign, optional dimension. No SQL of its own: it reads through P3's `tracking/trackingActualRead.readTrackingActuals` (unfiltered, `groupBy` = the grain's level, inclusive month end), the programme's one actuals read. Parity-tested against `getMonthlyMovements` (`budget-grid-prior-actuals.int.test.ts`).
- `gridSave.ts` `saveCells`: the ONLY grid batch writer (import commit reuses it). Pure checks, then `holdYearRegistry`, then ONE savepoint: CAS on `updated_at` + not locked (the pre-lock), ownership/kind checks, DELETE nulls then upsert, one audit row. The savepoint matters: withAuth COMMITs a 4xx, so a refusal must not keep the token bump.
- Decision 18 (`gridSave`; the seeds' leaf rule): a header or inactive account takes a NEW cell only if it already holds amounts in the version. Header test: `isHeaderSql()` in `budgets/headerSql.ts` (one copy).
- Seeds lock every version row they touch FOR UPDATE in one statement ordered by (fiscal_year, id) (`lockSeedVersions`) before reading the source: never FOR SHARE then FOR UPDATE (upgrade deadlock).
- `seedSeriesCore.ts`: the PY / version-copy series rules (leaf filter, unassigned rule, includeNoActivity, months past the target), PURE and imported by the client wizard preview too: never import server-only code into it.
- `seedVersion.ts` (+ `seedSeries.ts`): wizard create; version + amounts + audit in one savepoint, amounts via PR-A `uplift` (residue on the last month). PY seed is leaf-only; a version copy carries what the source holds. `unassigned: 'company'|'drop'` keeps decision 4 at a dimension grain. Every version seed sets `based_on_version_id` = the source locked by `lockSeedVersions` (via `createVersion`'s server-only `basedOn`, or P1's `copyVersion`); PY / blank: null. A seed into another year carries the source year's notes (`carryNotes`, prior year for PY) for the seeded active leaf accounts where the target has no non-blank note, inside the savepoint (a refusal, even `setPrimary`'s after it, carries nothing); same-year seeds share the year's notes already.
- `budgetTemplateXlsx.ts` / `budgetImportParse.ts` / `budgetImportDiff.ts`: Excel round-trip. Month headers matched by TEXT, blank = not budgeted, 0 = budgeted zero, absent rows untouched; `_meta` must match the version and year. Preview writes nothing and returns save-shaped `cells` + the token. Export → import = 0 changes (invariant 3).
- Import is a 3-way diff: the template's hidden `_base` sheet holds the downloaded values; a cell changes only where file ≠ base (a colleague's later save is never reverted), and file ≠ base ≠ current is a listed conflict (`rebaseDirty`). A missing `_base` gives a preview with every change flagged `possibleRevert` (plus a warning); an altered or unsigned `_base` is 400 "download a fresh template". Limits (`BUDGET_IMPORT_LIMITS`, one `normaliseXlsxSheets` pass): 8 333 rows a sheet (MAX_IMPORT_CELLS / 12), ~21 MB unzipped, ~8.1 MiB text, shared strings ~4 MiB / 26 668 entries, styles 1 MB: tighter than `XLSX_LIMITS` on purpose (memory/CPU DoS; measurements in the code).
- XML parts are checked by `src/lib/xlsxXmlScan.ts` (one linear pass: names matched, depth ≤ 24, ≤ 100 attributes, no duplicates, no DOCTYPE) on every xlsx path, and ExcelJS is fed 64 KB pieces so it stops at its first error. Pieces are cut after the last `>` (else at a UTF-8 character start), never splitting a character. Parser failures log only `{ errorClass, position }`. The migration importer (`xlsxBufferToCsv`, `XLSX_LIMITS`): 80 MB unzipped, 50 000 × 100, styles 8 MB, shared strings 32 MB / 5 000 000 entries.
- `_meta.signature` = HMAC (key derived from `JWT_SECRET`) over version, year, grain, token and a hash of `_base`; a file without `_base` is previewed with every change `possibleRevert`.
- Saves: `amount: null` deletes only with `clear: true`; MAX_SAVE_CELLS 20 000 per request and MAX_IMPORT_CELLS 100 000 per import/seed (measured lock hold next to the constants); clears skip the revenue/expense check; writes in `gridSaveWrite.ts` update only changed cells and insert only new ones.
- Shared helpers: `gridErrors.ts` (`inputError`, `tokenSql()`, `isVersionToken`), `gridTotals.ts` (band totals for read + import), `headerSql.ts` `isHeaderSql()`. The read model reads token, status and cells in one statement.

## P5 controls (P5-1: migration 954, `remainingBudget.ts`)
- Schema (954): `budget_control_settings` (policy off|warn|block, default warn; email flag OFF), `budget_alert_thresholds`, `budget_alerts` (unique = one row per crossing), `budget_check_events` (app pools INSERT+SELECT only: no UPDATE/DELETE grant), `budget_holders`, `budget_slice_reviews`, `po_items.cc1_id/cc2_id/bu_id` (dims must be the order's company and kind, trigger), `user_notifications` (`services/notifications/`). 944 tenant policy on all; ids and stamps not app-writable (column grants). The holder slice-write trigger on `budget_month_amounts` is P5-6's, not here.
- Stamps (954, PR #1066 review): every actor stamp the app writes is the session user (`auth.uid()`) and every time stamp the clock, set by triggers, never by grants: slice-review `submitted_*`/`decided_*` come from the status move itself (a move with no session user is refused; a move back to submitted clears the previous decision and note; which moves are allowed is P5-6's), `budget_check_events.decided_by`/`decided_at`, alerts' `fired_at` (re-stamped only when a resolved alert fires again) and `resolved_at`, `created_by`/`updated_by` on settings, thresholds and holders. A check event's `document_id` must be the company's own bill or PO. A centre used by a threshold, alert, holder, slice review or PO line keeps its `cc_type`.
- `remainingFor(companyId, keys[{glAccountId, cc1Id, cc2Id, buId, month 'YYYY-MM'}], {excludeInvoiceId?, excludePoItemIds?})` → per key, input order: `{versionId, grain, slice, unassigned, budget, actual, committed, remaining}`. Pure core `remainingBudgetCore.computeRemaining` (unit-tested); the reader only gathers rows.
- Budget: primary version of the month's registry year (`primaryVersionScopeAndYears`), at the account's grain (its `dim_grain` in that version); the key's dims map onto the grain (keep the grain's dim, drop the rest). `null` = No budget: no version, no rows for the account, the unassigned slice (key lacks the grain's dim), or no row for that slice and month. A budgeted 0 is 0 (D5) — never `||`/truthiness on it.
- Actual: `readTrackingActuals`, one call per grain level, picked by (account, month, member). Equals BvA's actual for the same key (invariant 1, `budgets-p5-remaining.int.test.ts`). No grain → actual/committed at company level, budget null.
- Committed (`remainingCommitted.ts`): PO lines of approved/partially_received/received POs in the order-date month, `line_total − Σ posted net of the linked bill lines` (bills approved/paid/partially_paid, linked by `po_item_id`), floored at 0 PER LINE. The posted net is `ap/supplierInvoiceExpenseLines.buildExpenseLines` over the whole bill in the approve path's line order (gross storage scaled to the subtotal, residual on the last line), never the stored `line_total`. The core maps each PO line onto each grain once (no per-key scan). `excludeInvoiceId` counts that bill's own linked lines as billed whatever its status (its consumed part is not counted twice; the rest of the PO line stays committed). Only REST bill create writes `po_item_id`; capture/recurring/MCP bills never net a PO (census 7).
- Bounds (`remainingKeysProblem`, checked by the route as 400 and again by `remainingFor` as TrackingError 400, before any read): 1-200 keys, months `YYYY-MM` in YEAR_MIN..YEAR_MAX (1900-2200), first-to-last span ≤ MAX_REMAINING_MONTH_SPAN (12).
- Route: `POST /api/accounting/budgets/remaining` (write roles, CSRF, `budget-remaining:<userId>` 120/min).

## P5-6 budget holders (migration 955; spec §3f, decision 9a)
- FROZEN slices (r4, coordinator's ruling): a submitted/approved slice of a draft is never written by a driver recompute, whoever saves and whatever input moved (another slice's cell, a section total, a planned hire): `driverSliceGuard` filters those cells (`RecomputeOptions.guard` → `{ keep, frozen }`), the save / driver write answers `frozenDriverCells` `{ cells, rows }` (audited `frozenDriverCells`), the save bar says "N driver cells in slices under review were not recalculated"; they recalculate on the first recompute after the slice is returned. An owner's/admin's grid save opens the reviewer path only for the locked slices its OWN cells are in (`budget_slice_review_begin_slice`); a holder's recompute outside their open slices stays 409 BUDGET_SLICE_DRIVER.
- The roll and frozen slices (r4): a roll that leaves cells in locked slices does NOT advance `rolled_through_month` (those months stay in `staleMonths`), records `slice_skipped` (cells in slices under review) apart from `slice_outside_skipped` (cells outside the slices of a holder whose close set off the roll: their auto roll is confined) and `slice_skipped_slices` (rollingStatus `sliceSkipped`, `outsideSkipped`, `sliceSkippedSlices`; two pills in the rolling controls); returning the slice queues the year's roll after commit (`sliceReviewState` → `scheduleBudgetRoll`), which rolls them and advances. There is no daily roll: rolls follow period closes, Roll now, and a return, so a slice approved and staying approved keeps its months stale until the next roll after a period close (by design). The roll runs as app_user (no service-pool path); app_service can write the columns too.
- A driver-override reset (clear) in a slice under review is 409 BUDGET_SLICE_LOCKED "Return the slice first" (r5, breaker REPRO 7): the frozen slice would not refill it, leaving "No budget".
- The version gate (955) lets a caller with NO session user (the service pool, a migration) approve: by design, the server code decides; an app_user session without claims is refused.
- Other server writers (r3): the P4 roll (auto and Roll now) skips cells of a submitted/approved slice of a draft and, for a holder principal's auto roll, outside their slices (`rollableCells`; `sliceSkipped` in the outcome and audit; the daily run never fails on it); a holder's Roll now is 403; the driver routes check the driver's own row first (`ctx.sliceCheck` → 409 BUDGET_SLICE_DRIVER naming it); the year-end rehome takes the reviewer path for an owner/admin (`beginReviewForOwner`); seeds write a NEW version (no slices). `assignHolder` holds the version FOR SHARE and refuses a submitted/approved slice (409).
- Unassign (r2, `unassignHolder`, `DELETE /api/accounting/budgets/holders?id=`): owner/admin, draft only, never while the slice is submitted/approved (409); version FOR SHARE then the slice review FOR UPDATE; the last holder of an open/returned slice deletes its review (`sliceDeleted`); audited (`holderRemoved`). `SliceHolder.id` is the holder row id.
- Files: `holderSlices.ts` (PURE, client-safe: `SliceKey`, `HolderSlice`, `sliceOf`, `holderReadReason`, `sliceLabel`), `holderScope.ts` (`loadHolderScope`, `assertSliceWrites`, `beginSliceReview`), `gridHolderView.ts` (the holder's read model), `budgetHolders.ts` (`assignHolder`), `sliceReviewRead.ts` (`readSlice`, `listSlices`, `sliceHolderIds`, `sliceReviewers`), `sliceReviewState.ts` (the ONE status function `transitionSlice` + pure `nextSliceStatus`, `sliceNote`), `sliceReminders.ts` (evaluator + daily run).
- A slice = (CC1, CC2, BU), at most one set; all NULL = company level. A holder row may limit accounts (`gl_account_ids`; NULL = all). Holders are owner/admin/manager members (DB + service); only owner/admin assign, on a DRAFT version (creates the slice review 'open'; re-assigning updates accounts and, when given, the due date).
- Moves (`transitionSlice`): open|returned → submitted (a holder of that slice), submitted → approved | returned (owner/admin; return needs a note 1-2 000), approved → returned (r6: the reviewer REOPENS an approved slice, same rules, note, audit, holder notified, and the roll's re-roll; so "return the slice first" works for approved slices too). The UPDATE's WHERE is the exact status the actor read, so a return racing an approve never turns into a reopen. Draft versions only. Lock order: version FOR SHARE (bounded), then the slice UPDATE whose WHERE repeats the from-state: of two racing moves one wins, the loser is 409 BUDGET_SLICE_STATE "now <status>". One audit row per move (entity 'budget', the version; approve → 'approve', return → 'reject', submit → 'update'), notifications: submit → active owners/admins (708's `approval_company_other_members`), approve/return → the slice's holders; dedupe key per move (`budget_slice:<id>:<action>:<time>`).
- Grid save (`saveCells`, inside its savepoint, before any write): a holder's cells must be inside their slices on a draft (403 BUDGET_SLICE_FORBIDDEN naming the cell); nobody but a reviewer writes a submitted/approved slice of a draft (409 BUDGET_SLICE_LOCKED); an owner/admin save of a version with slice reviews calls `budget_slice_review_begin` (the reviewer path). Owner/admin are never limited. A non-holder manager writes as before except into a locked slice. Driver recomputes (r2): `driverSliceGuard` checks the cells a recompute is about to write (`RecomputeOptions.guard`, before any write): a holder's recompute outside their slices, or anyone's recompute into a submitted/approved slice off the reviewer path (the driver routes never take it), is 409 BUDGET_SLICE_DRIVER naming the driver row.
- HOLDER VIEW = WORK SCOPE, NOT ACCESS CONTROL (coordinator, 2026-11-03): managers can read every budget (reports, BvA, other versions, copies, the driver list), so the holder view only focuses a holder's work; never rely on it to hide figures. Grid read (`loadGridReadModel` / `loadGridCells`, `viewerId`): a holder of the version gets only their slices' cells (totals and roll-ups follow), their slice members in `dimensions`, only their accounts (+ headers) when every holder row names accounts, and `holder: { slices }`; everyone else `holder: null`. The side doors follow (r2): the Excel template (`loadBudgetTemplate(…, viewerId)`: cells, `_base`, prior actuals), the import preview (`buildImportPreview(…, viewerId)`: filtered model; a file changing any cell outside their slices is 403 BUDGET_SLICE_FORBIDDEN with no figure echoed) and prior actuals (`holderSlicesOfYear` + `priorForHolder`: a member holding slices in any version of the year sees only those slices' members, company grain only with a company-level slice).
- Version approve (`transitionVersion`): takes the version FOR NO KEY UPDATE, then reads the slices; any not 'approved' → 409 BUDGET_SLICES_PENDING (names up to 5), unless `force: true` from the OWNER with a reason 1-500 (403 for an admin, 400 without a reason) → one extra audit row `forcedApproval`, `reason`, `pendingSlices`, `slices`. API-only (no DB rule for this one). The forced audit names at most 40 slices (`capped`, then "+N more"). Self-approval is allowed: an owner or admin may approve the slices and then the version themselves; each move is audited.
- Version delete: a non-owner/admin cannot delete a version with holders or slice reviews (403; the DB refuses the cascade too).
- Migration 955 (WRITE INTEGRITY is the boundary; all SECURITY INVOKER, no app_definer_reviews row, a guard in the file refuses a definer): `budget_slice_rows_check` over the rows a statement writes (budget_month_amounts: statement-level AFTER triggers with transition tables, one check per account and slice; budget_driver_lines: the driver's OLD/NEW row) — holder outside their slices / not draft → BV004; a submitted/approved slice of a draft → BV003 unless the session is on the reviewer path (GUC list `budgets.slice_reviewer` via `budget_slice_review_begin` AND an owner/admin session, re-checked; a hand-set GUC opens nothing); budget_planned_hires by cost centre (CC1/CC2 = the centre, none = company slice); `budget_holders_rules` (owner/admin assign, manager+ holders, draft, a submitted/approved slice keeps its holders and accounts: BV003); `budget_slice_reviews_rules` (move matrix, roles, draft, a move changes nothing else: due date, slice, note only on approve/return); `budget_versions_slice_gate` (draft→approved: an owner/admin session, every slice approved unless the owner's `budget_version_force_begin`; BV006 → 409 BUDGET_SLICES_PENDING; no session user under app_user is refused, server processes pass). ## Business rules (decisions 1-4, 11-14)
- Approve and lock: owner or admin. Unlock: owner only, reason 1-500 chars (DB requires a non-blank reason, 23514). Owner-only is app-enforced (decision 11).
- Set primary: owner or admin, but owner only when the year's current primary is locked (moving reports off a locked budget is an unlock in effect; Hein, 2026-10-27).
- Approved-but-unlocked stays editable; locked is immutable in the DB (`budget_month_amounts_refuse_locked`, ENABLE ALWAYS).
- One grain per account per version (exclusion `budget_month_amounts_one_grain`), and at most one dimension per amount (`budget_month_amounts_one_dimension`).
- Delete: not primary, not locked; an approved version needs owner/admin; a draft any writer.
- Migration 947 converted existing budgets to APPROVED primary Originals. A year's first version now comes from the wizard (`seedVersion`) or the version routes.

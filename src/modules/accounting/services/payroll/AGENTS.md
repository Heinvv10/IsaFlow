# payroll/

South African payroll: PAYE, UIF, SDL, ETI + run lifecycle, leave, termination/IRP5 prep, tax directives, UIF declarations. Pure engines have no DB; DB services are all company-scoped.

## Modules
- **Pure engines (no DB)**: `payrollTypes.ts`, `taxTables.ts` (TAX_2025/2026/2027; `getTaxYearConfig` THROWS `UnsupportedTaxYearError` for any other year; SA tax year ends Feb → March N ⇒ tax year N+1), `payeEngine.ts` (annual→rebates→medical credits→monthly), `payeAnnualPayment.ts` (annual payments, `payeTreatment`), `uifEngine.ts` (1%+1%, capped at ceiling), `sdlEngine.ts` (1% leviable, after the s11F retirement deduction; exempt <= R500 000 annual remuneration), `etiEngine.ts` + `etiTables.ts` (18–29, non-UIF-excluded, ≤24m employed; formula chosen by pay period), `payrollCalculator.ts` (`calculatePayrollLine` orchestrator), `validationEngine.ts`, `irp5ValidationEngine.ts`, `payrollJournalSplitBuilder.ts`, `payrollLabourComparison.ts` (the approval gate's labour comparison).
- **Run lifecycle**: `payrollRunService.ts` (CRUD + `calculatePayrollRun` populates lines), `payrollRunPeriodInputs.ts` (the review grid's once-off amounts, recalculated in the request; a #1117 writer: company lock, no write at all while the run's journal is in force (400, reverse it first), refuseAssignmentWrite on insert, inserts name `supersede_inferred = FALSE`, audited as `run_input` / `run_input_remove` (a removal is action 'delete' with the employee in metadata, which payrollRunRecalcGate reads); it reads what the run pays through the run's own reader, `payrollRunPeriodInputsRead.ts`; a cell save holds the company lock ~0.12-0.16 s on a 20-employee run (two whole-run calculations)), `payrollRunLock.ts` (period lock), `payRunApprovalControl.ts` (always-on R-035 clearance for the exact plan hash), `sdlLeviabilityService.ts` (SDL threshold basis), `payrollApprovalService.ts` (`approvePayrollRun` → approved + posts JE), `payrollJournalPostingService.ts` (`postPayrollRunJournal` / `reversePayrollRunJournal`), `payrollBatchService.ts`, `payrollBulkEmployeeService.ts`.
- **Employees + history**: `payrollEmployeeOnboarding.ts` (`createEmployeeWithPay`, POST /api/payroll/employees: judges every field and the salary component before the first write, then the employee and the recurring component in the request transaction; `EmployeeOnboardingRefused` = 400, raised only before the first write; `salary.amountCents` is integer cents, the column is rands, and `salary.amount` is refused; the salary component must be active, a taxable periodic earning), `employeeFieldRules.ts` (the tax and ID rules and `MAX_SALARY_CENTS`, DB-free so the form shares them; `irp5ValidationEngine` re-exports the validators), `payrollEmployeeService.ts`, `payrollEmployeeComponentService.ts`, `payrollEmployeeHistoryService.ts`, `payrollBankDetailsService.ts`, `payrollComponentService.ts`, `payPackageService.ts`, `payScaleService.ts`, `sarsCodesService.ts`.

- **Statutory**: `uifDeclarationService.ts` (UI-19 + `markUifDeclarationPaid`: DR 2150 / CR bank), `taxDirectiveService.ts`, `taxDirectivePaymentService.ts` (`applyTaxDirective`: DR labour, split and CC1-tagged as a pay run / CR 2140 / CR bank), `easyFileExportService.ts` (e@syFile EMP501 CSV).
- **Loans / costing**: `payrollLoanService.ts`, `payrollLoanReversal.ts` (undoes a run's own loan payments, tombstoning each on `payroll_loan_payment_reversals`), `payrollRunLoanApplication.ts` (`applyRunLoans` — reverse-then-re-apply in one locked transaction; refuses a run whose `journal_entry_id` is still set, in BOTH directions), `payrollCostAllocationService.ts`, `costCentreGlMappingService.ts`, `costCentreRunSummary.ts` (`costCentreSummaryForRun`: a run rolled up by cost centre, split by allocation; the master itself is `core/costCentreService`), `cashPayRegisterService.ts`.

## Caller contract
Invoked by `withCompany`-wrapped API routes in `pages/api/accounting/payroll/*`. Every DB function takes `companyId` first. Pure engines accept plain typed inputs and return plain results.

## Main function signatures
- `createPayrollRun(companyId, input) / getPayrollRun(companyId, id) / calculatePayrollRun(runId, companyId, preparedBy?)`.
- `setRunPeriodAmount(companyId, runId, employeeId, componentId, amount, expectedAmount)` / `getRunInputs(companyId, runId)` (`PUT|GET /api/payroll/runs/[id]/inputs`) — `assertNotImpersonating` first. The row key is (employee, component, `is_recurring = false`, the run month's first and last day); the one row on it is edited whoever wrote it, 0 deletes. Rows are selected by the window the run pays (`getEmployeeComponents`' date): any once-off it pays that is not exactly on the key, or more than one, is `conflict: true` on read and 409 on write, because typing beside it would pay twice. `expectedAmount` is what the cell held: a mismatch is 409. Company lock, header lock, the row lock (bounded), every refusal (`PayrollRunInputRefusedError`), then `calculatePayrollRun`, the write and `calculatePayrollRun` again in one savepoint; a line this edit leaves further below nil than the first calculation did refuses inside it, so all of it is undone, and anything else thrown after the write is a 500 that rolls it back. `inputs.recurring` is what the run pays every month on each editable component. `isEditableRunComponent`: taxable earnings 3601/3606/3607; non-taxable deductions on `EDITABLE_LOCAL_DEDUCTION_CODES` only (company-local, never a four-digit SARS code or LOAN). No seeded catalogue has such a deduction, so the grid has no deduction column by default; the seed's Salary Advance is coded 3907, and any 39xx in a run's breakdown trips `lump_sum_without_directive`. A local code fails IRP5 readiness at year end (`IRP5_UNKNOWN_CODE`).
- `assertPayRunApproved(companyId, runId, expectedPlanHash?)` — mandatory reusable guard for every post/finalise path, including future payslip release, EFT export and `paid` transitions. It requires an approved R-035 request for the exact plan hash; only migration-951 historical approved/paid runs are grandfathered.
- `approvePayrollRun(companyId, runId, userId)` — status `draft|calculated → approved`, posts JE, links `payroll_run_headers.journal_entry_id`. Every refusal (not found, status, any journal-plan blocker via `judgePayrollApproval`) is thrown BEFORE the status write as `PayrollApprovalRefusedError` (its own module, `payrollApprovalRefusal.ts`); callers answer only that as a 4xx and rethrow the rest, so a post-write failure rolls back (K-079). Returns the plan's `advisories`.
- `judgePayrollApproval(companyId, runId)` (`payrollApprovalGate.ts`) — THE approval gate, used by `approvePayrollRun`, `previewPayrollApproval` (`GET /api/payroll/runs/[id]/journal-plan`, and the MCP dry run): status gate (`approvalStatusRefusal`, `payrollApprovalRefusal.ts`) → for a run linking a journal, by what its reversal chain leaves in the ledger (round 5, below): in force → figures must match (`recalculated_after_posting`, or `net_pay_target_changed` when net pay moved between the bank and the clearing account); out → replaced (with the `net_pay_target_replaced` advisory when its net-pay account differs from the reversed journal's; the dating moved to `payrollReplacementDating.ts`); unclear → `posted_journal_not_live` → else plan blockers except `run_not_approved`. Returns `{ plan, posted, replaces, blocker, planHash }`. `approvePayrollRun(…, { expectedPlanHash })` locks the header `FOR UPDATE`, then refuses a different hash with `PayrollApprovalConflictError` (route: 409) before any write.
- `postPayrollRunJournal(companyId, runId, userId)` — DR 5200 Labour = gross + (total_uif÷2) + sdl − etiUsed (split by cost centre: account by mapping, `cc1_id` = the centre); CR 2140 PAYE = paye − etiUsed; CR 2150 UIF (employee+employer combined); CR 2160 SDL; CR net pay (`payrollJournalBank#resolveNetPayTarget`, resolved once in the plan): the account holding the company's BANK system role (not the code 1110; no active holder is the `missing_bank_account` blocker, never a 1110 fallback), or, when Default Accounts' `payroll_net_pay` names one, that clearing liability (e.g. 2170) with the bank role not consulted (below); zero lines dropped. `etiUsed = max(0, min(eti, paye))` (see Business rules).
- `calculatePayrollLine(input): PayrollLineResult` — pure orchestrator.
- `markUifDeclarationPaid(companyId, declarationId, userId)` — idempotent (returns existing row when already paid).
- `applyTaxDirective(companyId, directiveId, input)` — one payment per directive.
- `computeExpectedAccrual(input): number`, `computeCarryOver(balance, maxCarryOver)` — pure leave helpers.
- `parseExternalPayslipCsv(csv): ExternalCsvParseResult` — pure; header aliases (VIP/Sage), comma/semicolon, SA amount formats; integer cents out.
- `compareParallelRun(isaflowLines, externalRows, opts?): ParallelRunComparisonReport` — pure; employee-number matching is trim/case/zero-pad-insensitive (numeric only); `uifTotal` compares vs ee+er sum; only components present in the external data are compared.
- `getParallelRunReport(companyId, importId, runId?)` — resolves the run by the import's period when runId omitted; `run`/`comparison` null when no run exists.

## Business rules
- **Pay-run approval (R-035, 2026-10-31).** Every existing and future company has a fixed, immutable `All pay runs` manager rule and enforcement row; there is no off switch or threshold. The last calculator is `prepared_by` and an approval request snapshots that author, so another eligible company member authorises it; R-035's audited sole-eligible requester exception remains. Every recalculation/reopen rotates `approval_revision`, changing `planHash` even when cents are identical. `approvePayrollRun` checks clearance for its locked hash before its first write; `postPayrollRunJournal` repeats the reusable guard. Reopen needs its existing >=5-character reason and clears the digest cache. Migration 951 grandfathers only historical approved/paid rows.
- **ETI in the journal (K-079, Hein 2026-09-26; carry since wave 5 ET).** ETI offsets PAYE payable and is presented net of labour cost. The journal books the MONTH's ETI used from the ETI ledger (`etiCarry.ts` / `etiCarryRead.etiMonthForRun`): this run's ETI plus any brought forward from earlier months of the reconciliation period (ETI Act s9(1)), against the month's whole PAYE, stand-alone directive PAYE included; so the month's net 2140 (this run's PAYE − etiUsed, plus each directive journal's PAYE) equals `emp201Service`'s `payePayable`. When the ETI used exceeds the run's PAYE the 2140 line is a debit. ETI beyond the month's PAYE is carried (advisory `eti_beyond_paye`), and the EMP201 claims the August/February excess as a refund (s10). Before K-079 the labour debit fell by ETI while 2140 carried full PAYE, so every ETI run was unbalanced and could not post. The ETI formula is SARS' two-table schedule in `etiTables.ts` (law since Act 3 of 2026; see Recent changes).
- **Payroll journal plan = what the GL will accept (K-079).**
  - The balance check is exact to the cent. The cost-centre labour split ties to the labour debit
    (residual on the largest share), but only the rounding residual (half a cent per line). A
    bigger gap means the lines disagree with the header, and it is refused as `unbalanced`. ETI
    comes off the cost of the employees whose run lines carry it.
  - The GL poster's refusals are plan blockers (`nothing_to_post`, `negative_amount`,
    `closed_period`, `inactive_target_account`).
  - The deactivated-account check covers cost-centre labour accounts, resolved by id. It is not
    an advisory: `postJournalEntry` refuses deactivated accounts.
  - `approvePayrollRun` refuses every blocker before its status write. withAuth COMMITs a 4xx, so
    a refusal after the write stranded runs `approved` with no journal.
  - A run that already carries its journal (reopen keeps `journal_entry_id`) is refused by none of
    them, because re-approval posts nothing and returns that journal.
- Run state: `draft → calculated → approved → paid`. Re-approve is allowed when `status=approved` but journal unposted (2026-04-24 fix).
- JE posting: do NOT include `runId` inside `sourceDocumentId` (2026-04-24 fix — FK is to `documents`).
- Leave accrual INSERTs supply `company_id` for RLS (2026-04-24 fix); EXCLUDED out of scope in RETURNING clause (same-day fix).
- Employee active-check uses `payroll_employees.status`, NOT `is_active` column (2026-04-24 fix).
- **Run population is by end date, not status (audit 2026-10-18 P4).** `calculatePayrollRun` reads `listPayrollRunEmployees(companyId, period)`: every employee whose `end_date` falls in the run's month, whatever their status; active or terminated employees whose `end_date` is after the month (a run recalculated after they left); active employees with no `end_date`. `updatePayrollEmployee` still sets `terminated` on an end date of today or earlier; that no longer hides the leaver's final pay, leave pay-out and notice pay. Nobody whose `start_date` is after the month. Loan instalments are taken only from the run's employees (`RunLoanInput.employeeIds`). Termination pay-outs already paid in another run are not paid again (`payrollTerminationPaidCheck.ts`: `findPaidTerminationRun`, warning `TERMINATION_ALREADY_PAID`), and the approval gate refuses a run still carrying them (`termination_already_paid`, `findTerminationsPaidElsewhere`). "Paid" = approved or paid, or reopened with a linked journal whose chain is not `out` (a reversed journal stays linked, so the link alone is not enough; a linked journal the company cannot read counts as paid). `approvePayrollRun` takes a company-scoped advisory lock (`lockCompanyPayrollApprovals`) before the header lock so two such approvals cannot both pass; a second approver waits up to 5s, then gets the retryable lock-timeout 503. The posted-journal loan guard (`readRunLoanWork`, live and dry run) counts only the run's employees' instalments. `listPayrollEmployees` (active only; `{ includeTerminated }` adds leavers, for the directive form) is the employee list, not the run. Tests: `tests/integration/p4-leaver-in-final-run.int.test.ts`, `p4-leaver-run-edges.int.test.ts`, `p4-termination-approval-gate.int.test.ts`.
- **Employee bank details (wave 3 K1, migration 952).** `payroll_bank_details`: one active row per employee (partial unique index), a change deactivates that row and inserts the next. `setEmployeeBankDetails` takes the output of `parseBankDetailsInput` (all refusals before the first write), locks the employee `FOR UPDATE` (after the approval lock, see below), and only then decides first entry (owner / admin / manager) vs change (owner / admin, `CHANGE_REQUIRES_ADMIN`): any row, active or not, makes it a change. A manager's first entry is refused (`FIRST_ENTRY_REQUIRES_ADMIN`, 403, nothing written) for an employee who has been in any of this company's runs that was ever approved, posted or paid, in any period (Hein's ruling on D1, 2026-11-02): status approved / paid, `approved_at`, `reopened_at` or a non-empty `approval_history`, or a linked `journal_entry_id`; for a reopened run, whose lines may have changed, also anyone in `approved_taxed_employees` or employed in its period (so nothing taxable and a NULL set fail closed). Decided after the change rule. A caller who is not owner / admin first takes the company payroll-approval lock (`payrollApprovalLockScope`, the key approve / calculate / reopen use; an owner / admin is never refused by the first-entry rule, so takes none), then the employee row; so an approval cannot commit between the verdict and the insert. Both waits share one 5s deadline (503 `RowLockTimeoutError`: "Payroll for this company" for the approval lock, "This employee" for the row). The employee lock alone serialises bank-details writes for the employee. It is the service's rule only (RLS could state it but would not bind a forger of owner claims). Outside it: `tax_directive_payments` (pay outside a run) and an employee re-created as a new record. Bank name and holder take letters, digits, spaces and `. , ' ’ & ( ) / -`, starting with a letter or digit (422). The same details sent again write nothing, decided after the role check so a manager's PUT cannot confirm a guessed number; nor can `/api/payroll/duplicates`, which gives a manager no bank-account groups. `account_number` is full for owner / admin, else `…1234` (GET, PUT, history). For anyone but owner / admin, GET and PUT also mask `branchCode` to its last two digits (`…55`) and `accountHolder` to its first letter (`K…`; a value of two characters or fewer shows as `••`). `bankName` is not masked. This reduces, not prevents, matching two employees to one account: bank name + last two digits can give a bank's universal branch code, and last four + bank + type + initial can still match. The history masks the same three the same way for every role (`SENSITIVE_FIELDS` and `FIELD_MASKS` in `entityChangeMasking.ts`, MCP included); owner / admin see them in full only through the audited reveal (`entity-changes-reveal`, own session). `/api/payroll/duplicates` returns bank-account groups to owner / admin only, in full in their own session and masked to `…1234` in Login-as and token sessions; `findDuplicates` queries bank details only when called with `includeBankAccounts` (or `fullBankAccounts`) true, so omitting the option returns none. A full read (GET, duplicates) writes an `export` row in `audit_log` in the same transaction (`payrollBankReadAudit.ts`); its `revealed` names the fields shown in full: `account_number,branch_code,account_holder` for GET (from `SENSITIVE_FIELDS`), `account_number` for duplicates. The route's request log also masks `branchCode` and `accountHolder` (`maskBodyKeys`). Request bodies are logged only as scrubbed JSON objects, and query strings get the same key checks (`loggableRequestBody`, `loggableUrl` in `sanitizeRequestBody.ts`). The route refuses Login-as and tokens on GET too; MCP has no bank-details tool (census). No request role holds DELETE; rows go with the employee (FK cascade) or by `migration_admin` (the seed). RLS: owner / admin / manager read and insert, owner / admin update, and `is_active` is the only updatable column, so a stored number cannot be rewritten. `platform_admin` holds nothing and `app_service` has no mirror (915's exclusion list): a new reader must run in a request transaction. The history keeps the number in full (a reveal needs it), so 952 also puts `entity_changes` on 915's exclusion list: `app_service` has no mirror on it and a claimless service-pool session reads no row of it, whatever role it switches to mid-query (a per-row check failed there: a mirror's `USING (true)` is fixed at plan time). Every reader of the history (the routes, MCP, audit snapshots and comparisons through `runAuditTx`) switches to `app_user` with the caller's claims first and reads through `entity_changes_read`; a new service-pool reader must do the same. This closes accidental unscoped reads, not injected SQL: a claimless service session reads `company_users`, so injected SQL can forge each owner's claims in turn and read every company's history. No verification gate yet: it ships with the salary bank file (decision 6). Tests: `tests/integration/k1-*.int.test.ts`.

- **PAYE by SARS source code (audit 2026-10-18 P3).** `payeTreatment` (`payeAnnualPayment.ts`): `3605` = annual payment, taxed by the SARS annual-payment method (G21 2027 p. 32–33: tax(annual equivalent + payment) − tax(annual equivalent), rebates/credits once, whole difference this month); `39xx` = lump sum, never taxed by the tables — only the PAYE on its directive (`EmployeeComponent.directive`), else `LUMP_SUM_WITHOUT_DIRECTIVE` and nil PAYE; anything else periodic (cumulative since G4, below). `PayrollLineResult.payeSplit` = regular / annualPayment / directive; `paye.monthlyPaye` is their sum; `taxableIncome` excludes lump sums. ETI base unchanged (whole gross). **Severance is paid in the run at its directive's figures** (`payrollSeveranceDirective.ts`, `payrollRunTermination.ts`): none approved → left out, `SEVERANCE_AWAITING_DIRECTIVE`; the first later run pays the leaver the severance line alone (`listSeveranceOnlyRunEmployees`: no salary, loans, UIF or SDL); directive ≠ calculated → paid at the directive, `SEVERANCE_DIRECTIVE_MISMATCH`; paid elsewhere → `SEVERANCE_PAID_BY_DIRECTIVE`. The run claims the directive AT APPROVAL in its one `tax_directive_payments` row (`payroll_run_id`, migration 901, no journal of its own; `payrollRunDirectiveClaim.ts`), so calculate/recalculate never consumes it, a reopened run keeps its claim, re-approval refreshes or releases it, and the stand-alone `applyTaxDirective` answers 409. Gate blockers `severance_directive_unavailable` (directive paid elsewhere, cancelled, or edited since calculation) and `lump_sum_without_directive` (a taxable 39xx component with no directive: no PAYE was deducted, and para 9(3) requires the directive before payment). The claim is taken after approval's last refusal. A claim is released only by approving its run again without the line (e.g. reopen → reverse the journal → directive cancelled → recalculate → approve); a run reopened and never re-approved keeps it, and nothing deletes a run. A leaver from an earlier period whose approved directive is not paid — unpayable figures (`SEVERANCE_DIRECTIVE_UNPAYABLE`), or severance already paid by hand as a 3901 in a run that has paid (`findHandMadeLumpSumPaid`, P4's `runHasPaid`) — has no line, so the reason is a non-blocking approval-preview advisory `severance_directive_not_paid` (`unpaidLeaverDirectiveNotes`), repeated on every run until the directive is corrected or paid, plus a `log.warn`. The repetition is deliberate (Hein 2026-10-22, G6 won't-fix): do not suppress it. Codes are classified after `normaliseSarsCode` (ASCII space/tab/CR/LF only), the same rule in JS and SQL. The severance-only line takes no ETI (`notEmployedInPeriod`: ETI is apportioned by hours employed, ETI guide Issue 5 §5.3). e@syFile also splits 3605 out of 3601 (`listRunAnnualPayments`). Lock order: approval lock → header → journal chain → directive rows (FOR SHARE) → payment row. Calculation takes no directive row; it only deletes stand-alone payment rows whose journal chain is undone (`releaseReversedStandalonePayment`) and holds nothing an approval needs after that. IRP5 data `lumpSums` and e@syFile 3901/4115 + 3230–3233 (`payrollLumpSumFiling.ts`); 3601 excludes them. Tests: `tests/integration/p3-*.int.test.ts`, `tests/unit/services/payroll/payrollCalculatorAnnualPayment.test.ts`.
- SDL leviability is an EMPLOYER test, not a per-line one: section 4(b) exempts total remuneration <= R500 000 over twelve months. `estimateAnnualRemuneration` bases it on the company's own trailing twelve periods (the eleven `calculated|approved|paid` runs before this one plus this run) using REMUNERATION — each run's `total_gross` (cash) plus its lines' breakdown items flagged `isNonCash` (the 3801 loan benefit), this run's `PayrollLineResult.remuneration` alike — divided by ELAPSED CALENDAR MONTHS since the company's first run, capped at 12, and by 1 when the window holds no prior run at all — so a seasonal employer's unpaid months count as zero, a company younger than a year extrapolates, and a dormant company resuming payroll is not spread over twelve months it did not pay; the 1% is then charged per line on `sdlLeviable` only. `sdlLeviable` is CUMULATIVE over the tax year's LIABLE months (`sdlLeviableCumulative.ts`; SDL Act s3(3), the leviable amount since TLAA 2017 (s3(4) is the exclusions; migration 957's comment still says s3(4)); SDL-GEN-01-G01 Rev 5 s6): to date = clamp(liable SDL-applicable pay to date − liable s11F deduction to date, 0, that pay); a line takes the rise over what earlier liable lines carried (floored at nil, cent-rounded; `sdl` is charged on that rounded figure, as `applySdlToLines` recomputes it). The deduction is PAYE 4c's own signed `retirementDeduction` from `calculateCumulativePaye` (4001/4003/4006, s11F: 27.5% and `retirementDeductionCap`), so SDL and PAYE take the same figure and there is no second cap or constant. A deduction larger than a month's liable pay waits for later liable pay, a reversal takes back only what liable pay absorbed (never above the year's liable pay), and a reversal-only or non-SDL-only line levies nothing. EXACT STORED STATE (migration 957, additive, nullable: `payroll_run_lines.sdl_applicable`, `sdl_leviable`, `sdl_exempt`): the writer (`replaceRunLines`, the only writer of the table) stores the line's SDL-applicable pay (`PayrollLineResult.sdlApplicable`), the leviable amount it carried, and whether the run was SDL-exempt (s4(b); `applySdlToLines` sets `sdlExempt` from `isSdlExempt`, the same test `calculateSDL` uses). `loadPayeYearToDate` sums ONLY the liable lines (`payrollSdlYearToDate.ts`: `PayeYearToDate.sdlApplicable` / `sdlLeviable` / `sdlRetirementDeduction`); an exempt run's pay, deduction and leviable amount stay out, so exempt months cannot be mistaken for liable ones (no heuristics). Breakdown items also carry `isSdlApplicable` (an earning flagged is_sdl_applicable, as costed). LINES BEFORE 957 (columns NULL, costed on gross) are read as costed: pay rebuilt from the breakdown (flag, else TODAY's catalogue: a later `is_sdl_applicable` toggle changes how those lines are read; `synthetic:termination` leave/notice pay by id; a deleted component counts nothing), exempt when the stored `sdl` is nil although that pay would have carried a levy of a cent or more (exact for them: no deduction reduced SDL then), leviable amount = that pay, and NONE of its deduction (Hein: no credit): the new rule starts with the first run after deploy and each EMP201 period stays right for its own month, so that month's leviable amount is its own pay less its own deduction. A later reversal of a legacy-month contribution is capped at the liable pay. REMAINING LIMITS: (1) a deduction larger than ALL the year's liable SDL pay, or recovered when no later liable month has any, is an over-levy that is not refunded or carried into the next tax year; (2) PAYE records one cumulative deduction, not whose contribution a reversal undoes: a reversal in a liable month of a contribution made in an exempt month counts against the liable months' deduction (an over-levy, never an under-levy). (3) A contribution capped by s11F in an exempt (or legacy) month has its catch-up recorded by PAYE on the next liable line, and SDL credits it there: an UNDER-levy, the only under-levy direction left (accepted by Hein; pinned by the "KNOWN LIMIT (3)" tests: R3 000 pay / R5 000 RA in an exempt month, then R60 000 liable: R558.25 against R600). A non-finite figure throws, and so does a year to date with earlier lines but no `sdlApplicable` / `sdlLeviable` / `sdlRetirementDeduction` (a hand-built one would silently over-levy; the loader always sets them). Every other taxable deduction (union 4018, medical 4005, garnishees) reduces neither SDL nor PAYE (calc version 4); donations 4030 only as `s18aDonation` allows. Like PAYE, it depends on which earlier months are approved when the month is calculated. The threshold stays on gross remuneration (`sdlLeviabilityService`: the header stores only total_gross). Tests: `sdlLeviableAfterDeductions.test.ts`. Never gate on the leviable subset — one component flagged `is_sdl_applicable = false` would exempt the whole employer.

- **Deductions and tax above pay (`DEDUCTIONS_EXCEED_PAY`).** `calculatePayrollLine` floors net at nil, as it always did, and reports the raw net (`ValidationResult.rawNet`); it changes no figure. - **Cumulative (run-to-date) PAYE (PAYE 4a follow-ups G4) — a business decision, not a SARS prescription (Hein 2026-10-22).** SARS prescribes per-period tables for a full-year employee; G21 2027 p. 8's annual-equivalent formula is for a tax period shorter than a year, and G01 p. 5 accepts programs that "render the same results" — this does not when pay changes (it spreads the change, so can under-deduct that month; employer's risk, accepted). `payeCumulative.ts`: AE = periodic taxable to date × 12 ÷ periods with periodic pay; liability to date = tax(AE) × n/12 + [tax(AE + all annual payments to date) − tax(AE)]; PAYE now = liability − table PAYE already deducted, floored at nil and carried (no in-year refund); the annual-payment part = tax(AE + earlier + this) − tax(AE + earlier) (earlier 3605s stay in the base; G21 p. 32–33). Rebates/credits pro-rated by n/12. Unchanged pay (and any first period) = the ×12 result. A period with neither periodic pay nor an annual payment (severance-only line) deducts nil from the tables. Year-to-date: `payrollYearToDate.loadPayeYearToDate` — the employee's lines on approved/paid runs of the same tax year BEFORE this period (a reopened run, the run itself and later periods are out), directive PAYE excluded; each line stores `periodic_taxable`/`annual_taxable` (mig 913), a line from before 913 is split from its breakdown (taxable 3605 items). A month's PAYE depends on which earlier months are approved when it is calculated; the next month trues it up. A run calculated while LATER months of its tax year are approved (back-fill, or a reopened earlier month) is not refused: its taxed lines carry `PAYE_LATER_PERIODS_APPROVED` (`laterPeriodsWarnings`), since those later months missed it and, if February is among them, nothing trues it up. And a run is refused at approval exactly when its PAYE missed an earlier month, or a later month missed it and, for an employee both pay from the tables (periodic/annual taxable > 0), its line lacks that warning for that month (read off the lines per employee and month, as `laterPeriodsWarnings` writes it: jsonb containment on the warning's `periods` (YYYY-MM), never the message; a warning without `periods`, from #786 dev/test lines, reads as none: refused until recalculated) (`paye_year_to_date_stale`, `payrollYearToDateGate.judgeYearToDate` in the gate, under the company approval lock): recalculate it. Also refused (remedy: the LATER month — reopen it, approve this run, recalculate and approve it): a later month calculated from an EARLIER version of this run (this run approved then, per `approval_history`, its lines rewritten since) that pays someone from the tables whom an earlier approved version taxed (`approved_taxed_employees` UUID[], mig 925: the union over every closed approval, written by `reopenPayrollRun`; NULL with a history = reopened before the column, unknown, conservative, kept NULL) and this run no longer pays from the tables; the union is conservative for someone taxed only in a version that month did not read. A PAID later month is not refused for (it cannot be reopened): named limit (f), with an advisory. The remedy reverses the later month's journal only if its figures change (approval says so). Named limits: (b) the gate ignores how PAYE was computed — a run calculated before cumulative PAYE (lines without `periodic_taxable`) is judged like any other (refused if an earlier month was approved after it; otherwise approved with its ×12 PAYE, which the next month trues up, not February); (a) a NULL `approved_at` (pre-718) counts as approved all along, and a run that missed one is pre-913 too; (c) once the warning names a later month, the gate passes even if that month read this run's EARLIER figures for an employee still taxed here; (d) only approved months are judged: a month reopened and left (or cancelled) is in no pair until approved again; (e) callers with no outer transaction; (f) a PAID later month (legacy rows) keeps this run's old figures, said in the non-blocking preview advisory `paye_paid_later_month_stale`. The one-sentence rule and its completeness argument head `judgeYearToDateStale` (tests: `p4fu-r2-brk-employee-set`, `p4fu-r2-older-version`, `p4fu-r2-brk2-older-version`). "Missed" = the other month, as it now stands (lines no newer), was not approved when this one was calculated (first line's `created_at`); "approved at t" = current `approved_at` ≤ t, or t inside an approval a reopen ended (`approval_history` tstzmultirange, `[approved_at, reopened_at)`, mig 925; `reopenPayrollRun` writes it and `reopened_at` from one `clock_timestamp()`). The whole history, not the last reopen: two reopens leave a gap before the last one (p4fu-r2-exact-gate case 1). Runs reopened before 925 have no history → conservative refusal. All compared times are `clock_timestamp()`. Approve, calculate AND reopen take `lockCompanyPayrollApprovals` before their header lock, so nothing changes declarability between a calculation's year-to-date read and its first line; approvals, reopens and other calculations of the company wait (5 s bound). Kept company-wide, not per tax year (R2): 200-employee calculation p50 147–184 ms, max 233 ms at load ~38 (2026-10-23). Lock order: top of `payrollRunLock.ts`. ETI, UIF, SDL untouched. One rule for contributions, `payrollRetirementRecord.loadRetirementRecord`, feeds both the year to date and the certificate: a post-948 line's marked items; a pre-948 line's 4001/4003/4006 deduction items (today's components, named limit), with its taxable-flagged ones added back to periodic pay (the old calculator deducted them uncapped). **Paid outside payroll** (`payroll_components.paid_outside_payroll`, mig 948; a "private RA" the employee pays the fund directly): counted for the deduction and the certificate, but not in net pay, total deductions or the 2175 line (the journal's 2175 is the residual gross − PAYE − UIF − net, so nothing else changes); the breakdown item carries `paidOutsidePayroll: true`. Only a deduction coded 4001/4003/4006 (`retirementFundCodes.ts`, the one TS list): a non-boolean flag is a 400; CHECK `payroll_components_paid_outside_payroll_check` (code trimmed as `normaliseSarsCode`) and `POST /api/payroll/components` 400 (`paidOutsidePayrollRefusal`). Privately paid medical aid (4005, same shape) is NOT supported. Certificate: 4001/4003/4006 = the year's contributions per code, cents dropped, none when nil (`easyFileRetirementFields`, `payrollRetirementRecord`; BRS V25.3.0 p. 101-102). **Not supported (PAYE 4b):** employer contributions (3817/3825/3828 benefit + deemed contribution, 4472/4473/4475; 4474 is employer MEDICAL): an `employer_contribution` component is left out with error `EMPLOYER_CONTRIBUTION_NOT_SUPPORTED`; an earning coded 3817/3825/3828 warns `EMPLOYER_FUND_BENEFIT_NOT_DEEMED`. - **Date of birth 3080 (2026-10-25).** Every certificate is nature A with a 13-digit RSA ID, and BRS V25.3.0 p. 26 makes 3080 mandatory, CCYYMMDD, correlated with 3060 and not after today. `buildEmployeeRecord` emits it after 3060 from `birthDate3080` (`easyFileMedicalFields.ts`): the payroll date of birth, which must BE the ID's date (YYMMDD; it gives the century) and not in the future, else the export is refused naming both dates (replaces round 2's 65-only `assertBirthCorrelates`: every age the export uses reads the payroll date, so it must be the one filed). With none on file, the ID's date; refused when that reads as under 15 at the year's end (ambiguous century: enter the date of birth). An ID whose first six digits are no date is refused. **Behaviour change:** exports with a payroll date of birth that disagrees with the ID, or an ID that carries no date, used to succeed and are now refused. `birthFromIdNumber` takes the latest century on or before today (was: 2026-12-01 for a 1926 birth). The route turns pg's 'YYYY-MM-DD' into a local day (`localDay`; `new Date()` read it as UTC midnight). `validateCertificateTaxFields` checks 3080 for 3020 A/B/C/M/N/R and refuses it on D-H (`birthDateRules`).

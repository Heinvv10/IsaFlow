# customer-invoices/ (list and form components)

## Purpose
Sage-style filters for `pages/accounting/customer-invoices/index.tsx`: status, search, customer, invoice-date period, aging chips. Mirrors `../supplier-invoices/` (FilterBar + URL-state hook).

## Caller contract
- The URL is the state: `?status=&q=&customer=&from=&to=&aging=&page=`. `?filter=<status>` (dashboard widgets) is still read. `listQuery.ts` is the only place that maps URL ↔ filters ↔ API params (`client_id`, `from_date`, `to_date`); the list and the CSV export both take `arFiltersToApiParams`.
- Hydration is lenient (a bad value in a hand-edited URL is dropped); the API is strict (400).
- Links in: `../ViewAllInvoicesLink.tsx` (aging panels) builds `?customer=<id>`.

## Form components (new and edit pages)
- `InvoiceHeaderFields` (client, VAT, currency, job, exchange rate, four dates), `InvoiceNotesCard`, `InvoiceSummaryCard`, `InvoiceLineItemsTable`: both `new.tsx` and `edit/[invoiceId].tsx` render them; the page owns the form state.
- Dates are the kit's `DateField`. A refused date reaches the page as null, so `useInvoiceDateValidity` records the reason and `invoiceDateProblem` blocks submit on it, and on due-before-invoice (a later edit of the invoice date can break an accepted due date). Never submit on the form value alone.
- The request bodies are unchanged by the kit: `tests/unit/components/invoiceFormKit.test.tsx` pins them.
- `useContactDefaults` (new page only) fills Due date, the line discount and the VAT mode from the picked customer. A default is never written over what the user touched (a Due edit, even refused, cleared or still being typed; a VAT mode or rate edit; what a scan filled), follows the invoice date until edited, and comes back out when the customer changes to one without it. A line's discount follows the customer while `discountFromDefault` holds, priced or not; `editedLine` drops the flag (not while the customer is being read), and the flag never reaches the API. Save is disabled while the customer is being read. The edit page does not use it: a stored invoice's figures are the invoice.
- `useDueDateFollowsTerms` (edit page): while the user has not touched Due date, a draft whose `due_date_source` is `terms` shows the date the customer's terms give for a changed invoice date or customer (and the stored date again when both are back), so the autosaved body is what the server re-dates to (`shared/draftDueDate`). A hand-set, document or legacy date never follows. `sendDue` says whether a save names the due date at all (the user touched it, or the hook recalculated it): otherwise `invoicePutBody(..., { omitDueDate })` leaves it out and the server keeps its own, so a page that is out of date cannot put back a date that moved since it loaded (Re-apply, another tab) and record it as set by hand. Named limit: to keep the old terms date after changing the invoice date, save, then change the due date.
- `useCustomerLookup` is the single-customer GET behind both pages. The edit page reads its customer on load only to warn, and refills nothing; its Save waits only for a customer changed there. The lookup gives up after 15 s. `vatTypeWarning` shows on both pages when the customer's VAT type conflicts with the effective rate or is one nobody knows; the user's choice stands.
- `taxMode.ts`: "Amounts are" (excl / incl / none) never reaches the API; it is a rate and a price by the time it is sent. `effectiveTaxRate` for every total and body, `storedUnitPrice` for every sent price. Switching mode converts the shown prices (`linesForModeChange`: grossed up into inclusive, back out of it), so it never reprices at the same rate: an untouched line saves as it was. A rate changed while inclusive holds the gross and moves the ex-VAT price; a rate below 0 converts nothing. An inclusive total can land off what was typed (spec decision 2): `InvoiceSummaryCard`'s `typedTotal` shows both, and the stored total is the invoice. The edit page loads in `exclusive`, or `none` for a stored rate of 0 (it prices the same, and leaving it seeds the standard rate).
- Autosave (`useInvoiceAutosave`): the new page keeps `{form, lines, taxMode}` in localStorage (`src/lib/invoiceDrafts.ts`, per company and user) until create, never a server draft (create is wallet-metered); sign-out and a company switch clear every draft. The edit page PUTs `invoicePutBody` (the Save button's body) 1.5 s after a change, only when it differs from the server's (an edit PUT can stamp the editor as an approval author), never during a VAT rate edit or while `autosaveProblem` holds, one PUT at a time; a refusal stops it until the next change. Build every body from ONE render's form, lines and mode. Every autosave PUT that moves the approval digest makes the editor an author of the content (R-035 PR4), with no Save click: so they cannot decide its approval request (gl/approvalAuthors.ts).
- A save sent as the edit page leaves (Back, a link, another invoice in place) is registered in `src/lib/pendingInvoiceSaves.ts`; the invoice page and the edit page wait for it (5 s at most) before reading the invoice. "Leave without them" cancels only the change not yet sent: a PUT already out finishes and stays tracked, and the question says so.
- The shown digest (`ar/invoicePdfModel.ts`: the hash of the model the PDF renders, with the approval digest): the GET returns `shown_digest`, the create and each PUT reply `shownDigest`. Approve sends the total, currency, rate and `expectedContentDigest` (the route answers 409 `INVOICE_APPROVE_VIEW_INCOMPLETE` to any `expected*` without the digest); each draft PUT sends `expectedDraftDigest` (the draft digest: the invoice row and its lines only, what the PUT's lock covers; GET `draft_digest`, replies `draftDigest`), added as it is sent (`useServerInvoiceAutosave`, per invoice, never in the compared body). A mismatch is 409 `STALE_VIEW`, nothing written; the edit page reloads in place with the server's sentence.
- WIP lines (`useWipLines`): a time-entry line is badged; removing it asks, holds autosave and Approve & email until Save Changes; the PUT names its entry in `releaseTimeEntryIds` (added as it is sent). Every line always carries `timeEntryId` (null when unlinked): a WIP invoice refuses a body without it (409 `INVOICE_WIP_CLIENT_STALE`) and a linked line left unlinked unnamed (400 `INVOICE_WIP_LINK_REFUSED`).
- Back / Forward with a change autosave is holding ask (`useInvoiceAutosave`); Stay returns with the Navigation API (`navigation.traverseTo` to this page's entry key). No Navigation API: not asked. The PDF preview's iframe is keyed by its document, so a refresh adds no history entry.
- `useApproveAndEmail`: save, approve, then open `InvoiceEmailModal`. Send stays the user's click on `/api/accounting/invoice-email`; a refused approval keeps the draft and is never retried. Tests mock `apiFetch`: dev SMTP is live.

## Main signatures
- `hydrateARFilters(query)`, `arFiltersToQuery(f)`, `arFiltersToApiParams(f)` — `listQuery.ts`.
- `useCustomerInvoiceListState()` — re-hydrates whenever the URL changes under it (back/forward), writes with a shallow `router.replace` only when the query changes.
- `ARFilterBar`, `CustomerTypeahead`, `CustomerInvoiceTable`, `InvoiceDrawerBody`.

## Business rules
- The customer's NAME is never read from the URL: a URL label could name a different customer than the id it filters. It comes from the typeahead pick or the loaded rows' `client_name`, keyed by id.
- The typeahead searches only once something is typed — `/api/accounting/customers` without `?q=` returns the whole directory.
- A month is a UI convenience (`../invoicePeriod.ts`): it becomes an inclusive from/to pair; never `toISOString()` a date here.

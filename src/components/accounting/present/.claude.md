# present/

Presentation mode: a report pack paged on a boardroom screen.

## No nav entry, and how it is actually reached

`pages/accounting/reports/present/[pack].tsx` has no entry in
`accountingNavConfig.ts`, by design: it needs a pack type AND a date range,
so a nav item with no query params would open a page that immediately
reports "Unknown pack".

It is entered from the **Present control in the statement page header** —
`reportControls/PresentLink.tsx`, on `income-statement.tsx` and
`balance-sheet.tsx`, which carries the period the reader is already looking
at into `?from=&to=` (the balance sheet has no period start of its own, so
it passes the same year-to-date window its account drill-down uses). Same
tab: presentation mode is full screen, and a new tab would leave the
presenter's own window behind the projected one.

The **packs page carries the entry too**, as of WS2's integration merge:
`report-packs.tsx` mounts the same `PresentLink` in its header, beside the
PDF, PowerPoint and Share controls. It is the only mount that names a pack —
`pack={selectedType}` — because it is the only page that is itself about a
pack, and the deck route serves all three types. The two statement pages
have no pack to name and keep the `management` default.

## No app chrome

`pages/accounting/reports/present/[pack].tsx` does not use `AppLayout`. The
sidebar, header and tenant switcher are what this route removes; adding the
layout back defeats it.

## One slide in the DOM

`PresentDeck` renders only the current slide. Paging holds at both ends
rather than wrapping — a presenter who over-clicks at the end should see the
last slide, not the cover.

Keys: right / down / PageDown / space / enter advance; left / up / PageUp /
backspace go back; Home and End jump; Escape exits.

## Files
- `reportControls/PresentLink.tsx` (sibling directory) — the entry control
  and `presentHref`. The pack it opens defaults to `management`, the pack
  whose sections this deck has renderers for; an optional `pack` prop names
  another, which only the packs page passes.
- `presentSlides.ts` — `buildSlides`, `clampSlide`. Unknown section types are
  dropped, never paged to as a blank slide.
- `PresentDeck.tsx` — the shell and the keyboard map.
- `PresentSlide.tsx` — section kind → component. Maps, never computes.
  Every slide that shows a sentence instead of a figure goes through
  `SlideNote`, which carries the section title: a presenter paging onto a bare
  grey line cannot tell which section of the pack it is, and the room reads it
  as a rendering fault.
  The trends slide titles each panel `code · name`, taking the name from the
  income statement the deck already fetched and keeping the bare code when no
  line names that account. It also passes an explicit `height` so the grid
  fills the slide instead of sizing itself to the panel count.
  The income-statement slide is the one exception: it fetches
  `reports-income-statement` and maps it with `toIncomeStatementRows` rather
  than reading the pack section, because the pack's income-statement section
  carries band totals with no `accountCode` and the trend/budget comparators
  need one. Its `budgetedCount` prop mirrors
  `useStatementComparators`'s guard via `hasBudgetData` — the budget
  comparator is applied only when a real budget was captured, never against
  an implicit budget of zero. `[pack].tsx` fetches it from
  `reports-budget-comparator`'s `budgetedCount` alongside `lines`.
  Three states, never two. `trendsLoading` / `budgetLoading` /
  `incomeLoading` mean the request is IN FLIGHT, `trendsFailed` /
  `budgetFailed` mean it rejected, and neither of those is "no data was
  captured". The deck is rendered as soon as the PACK fetch resolves, which
  is before any of the three behind it have landed — so without the loading
  flags the income slide claimed "could not be loaded" and the trends slide
  "no presentation renderer yet" about requests that were still running.
  `[pack].tsx` sets all three flags before the pack fetch, clears each one
  as its `Promise.allSettled` result is read, and clears all three if the
  pack fetch itself throws (the comparator fetches never started).
- `[pack].tsx` renders an explicit "Unknown pack" error (via the same error
  state as a pack-fetch failure) once `router.isReady`, rather than spinning
  forever on an unrecognised `pack` type or a missing `from`/`to` range.

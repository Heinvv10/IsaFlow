# lib/auth/

## Purpose
Request authentication and the per-request transaction. `withAuth` (cookie session), `runBearerRequest` in `bearerPipeline.ts` (PAT / OAuth; behind `withBearerOrCookieAuth` and `withBearerAuth`) and `withExtensionToken` (bank-feed extension) each authenticate, open one transaction as `app_user` with the RLS GUCs, run the handler inside it, then COMMIT or ROLLBACK and release. They and `withPlatformAdmin` (admin routes, platform_admin pool) are the four that also defer the response flush. `withInviteToken` and `publicRouteTx` (`src/lib`) own transactions too, but flush as the handler writes. `withPlatformAdmin` rolls back on a 5xx answer (as `withAuth`), on `criticalAuditFailed` and on `rollbackOnly`, and every rolled-back mutating admin request leaves one `admin_request_failed` row (`adminFailureAudit.ts`).

## Caller contract
- Compose a route as `withAuth(withErrorHandler(handler))`: `withErrorHandler` goes INSIDE the wrapper, so a caught error is answered 500 and the wrapper sees the status and rolls back. If the handler had already flushed its headers, `withErrorHandler` cannot send a 500. While the response has not ended (always so under the three wrappers, whose `end` is buffered) it sets `statusCode = 500` anyway, so the wrapper rolls back, and aborts the response. A response that already ended through the real `end` is left alone.
- A status of 500 or more rolls back; anything lower COMMITs, so a 4xx sent after a write commits that write. Throw (or answer 500) after a write, never 4xx.
- Background work goes through `runAfterCommit`; the wrapper starts it only after COMMIT.

## Main signatures
- `withAuth(handler)`, `withBearerOrCookieAuth(handler)`, `withBearerAuth(handler)`, `withExtensionToken(handler)`: `NextApiHandler`
- `runBearerRequest(req, res, rawToken, handler, opts?)` (`bearerPipeline.ts`)
- `deferEnd(res): DeferredEnd`, `answerThrow(req, res, deferred, err, ctx)`, `answerCommitFailed(res, deferred)`, `answerInstead(res, deferred, status, payload)` and `reportFinalizeFailure(req, res, err, ctx)` (`deferredEnd.ts`)
- `rollbackFailed(client, source): Promise<boolean>` and `rollbackError(client, source): Promise<Error | null>` (`src/lib/rollbackFailed.ts`)
- **`AUTH_POOL_MAX` (R-182)** sizes four pools: `authPool`, `withExtensionToken`, `bearerPipeline` and the platform-admin app pool, read through `authPoolMax()` (`src/lib/limits/poolLimits.ts`, default 10 since R-188 (was 20), honoured 2-100). The floor is 2: a PDF render holds one connection and the browser re-enters the API for a second from the same pools. It is a floor, not a safe size, since a pool of 2 can still be taken by a concurrent request. Anything else gives `min(10, ceil(Number(text)))` when `Number(text)` is finite and above 0, else 10, never below 2 (so `10.0`, `+10` and `1e1` mean the default and give 10, `15.0` and `20.0` give 10, not their own size, and `1`, `1.0`, `0.5` and `+1` all give 2), with one warning that never carries the text. The cap is per variable: the default is 40 connections per process (80 until R-188) and 100 would be 400, so with `max_connections` 100 shared with dev, CI and Supabase, set it no higher than the default. A plain whole number above the default (`15`, `20`) is still honoured as given. Rollback: write it as plain `20` (`20.0` gives 10) and restart. Post-deploy signal: `auth pool saturated: an acquire had to queue` (warn, at most once per 10 s per pool, with waitingCount/totalCount/idleCount/max; since R-196 only when the waiters outnumber the idle clients plus the connections the pool may still open) and `auth pool acquire failed` (error), from `poolTelemetry.ts`. Per-process total of every pool at the defaults: 77 plus 2 per in-flight verify-email request and 1 per impersonation write (was 117). Never read a pool size with `Number(process.env...)`.
- **`PLATFORM_ADMIN_POOL_MAX` (R-182)** sizes the platform-admin pool in `withPlatformAdmin.pools.ts` (`getPlatformAdminPool`), read through `poolSizeFromEnv('PLATFORM_ADMIN_POOL_MAX', 10)`: default 10, honoured 1-100, floor 1. Anything else gives `min(10, ceil(Number(text)))` when `Number(text)` is finite and above 0, else 10, with one warning (the same rule as above). It is a separate pool from the four `AUTH_POOL_MAX` pools, so it adds its own 10 connections per process.

## Business rules
- **The response flushes after the transaction ends.** Each wrapper swaps `res.end` for a buffer (`deferEnd`), finalises, then replays the one buffered `end` through the real one (`replayEnd`). Otherwise a client that refetches right after a 200 can read the database before COMMIT. A failed COMMIT turns the buffered 2xx into 500 `COMMIT_FAILED`; if the headers were already flushed, the response is aborted instead, so the client never reads a complete 2xx for a write that did not land.
- **Nothing after COMMIT may reach the wrapper's catch.** `replayEnd` never throws: if the real `end` refuses the buffered body, it logs and aborts the response. The catch would otherwise ROLLBACK a committed write and tell the client it failed, inviting a duplicate retry.
- **A throw inside the request transaction is answered by the wrapper, never rethrown (R-159).** A throw before it (token validation, the pool `connect()`) still propagates; nothing is buffered yet, so it cannot hang. On a throw the wrapper rolls back, puts the real `end` back and answers with `respondToUnhandledError`, the same responder `withErrorHandler` uses: 503 for a lock timeout, 403 for a refused Login-as session, otherwise 500 `INTERNAL_SERVER_ERROR`. It also logs and reports to Sentry with the tenant. It used to rethrow with the buffer still in place, so any later 500 was swallowed and the client hung. `invitations/revoke/[id].ts`, which has no `withErrorHandler`, hung on every throw. The real `end` goes back before anything else, and an error whose message cannot be read or a failing Sentry capture cannot stop the answer. If the headers were already sent, the response is aborted, not closed.
- **A transaction owner that cannot roll back destroys its connection (R-176).** Roll back with `rollbackFailed(client, source)` (`src/lib/rollbackFailed.ts`), keep its result, and call `client.release(result)`: pg-pool destroys a client released with `true`. A bare `release()` after a failed ROLLBACK pools a live connection still inside its transaction, and the next request's COMMIT lands the failed request's writes. A ROLLBACK that succeeds keeps the connection, including after a failed COMMIT. `rollbackFailed` never throws, logs the failure, waits at most 5 s (no answer counts as a failure), and sends Postgres a cancel request, because destroying a socket does not stop its statement. The bound covers the ROLLBACK only: `BEGIN` and `COMMIT` are unbounded, as they were before. Use it for every ROLLBACK, early returns included, never a bare `client.query('ROLLBACK')`. Put `BEGIN` inside the `try` whose `catch` rolls back, and roll back in the function that releases. An owner that can roll back twice keeps the first failure (`failed || unusable`): a cancel is already on its way to that backend. The 5 s bound is a constant; tests shorten it with `setRollbackBoundForTests`, which throws unless `NODE_ENV` is `test`. Every owner in `src/` and `pages/` does this, and every one in `scripts/` except `apply-migrations.ts` and `migrations/resolve-checksum-conflicts.ts` (the ROLLBACK sits in a helper and the release in `main`) and `ap-backfill-supplier-payments.ts` (two ROLLBACK paths the census cannot tell apart, in a script no test can drive); each ends its pool with the run (R-176 fix.md). `tests/unit/lib/rollbackCensus.test.ts` fails on any other statement that ends a transaction (`ROLLBACK`, `ABORT`, with `WORK`, `TRANSACTION` or `AND [NO] CHAIN`) sent through `.query(`, dedicated `pg.Client` owners included, and on an unreadable query text in a file that owns a transaction, and `tests/unit/lib/releaseCensus.test.ts` fails on a release that is bare, or whose argument is not the outcome of a ROLLBACK on that same client, unless it is pinned there with its reason.
- **A long-lived pool has an `error` listener (R-176).** pg-pool re-emits a pooled or removed client's error on the pool, and with no listener that is an uncaught exception. Every pool in this directory has one, and so does every pool in the server, per-request ones included. `tests/unit/lib/poolErrorListenerCensus.test.ts` fails on a pool whose own name has no `.on('error', …)` in the same function; a pool built and ended within one script run is pinned there instead, because ending that run on a pool error is the wanted outcome.
- **The answer the caller is owed stands whenever nothing is meant to commit, whatever the ROLLBACK did (R-176).** That is an early 403 or 429, a handler's own 5xx, and the 500 after a failed critical audit write: a failed ROLLBACK destroys the connection, and the transaction goes with it. A failed COMMIT, or a <5xx answer on a request marked `rollbackOnly` (`src/lib/als.ts`, set by `lib/apiJournalDate`), replaces the buffered answer with 500 `COMMIT_FAILED` through `answerCommitFailed` (`deferredEnd.ts`); withPlatformAdmin's audit failure answers 500 `AUDIT_WRITE_FAILED` through `answerInstead`. **A replaced answer, and a handler's own 5xx replayed over a ROLLBACK, drops the `Set-Cookie` and `Location` the route set** (`answerInstead`, `answerThrow`, `replayEnd(…, rolledBack)`), so a rolled-back request (an impersonation, say) never puts a session in the browser. Both failures are reported through `reportFinalizeFailure`, under `transaction finalize failed after handler responded`, with the path and never the query string.
- **An auth-provider outage is not a verdict on the token (D9).** GoTrue calls on the session path (`verifyToken`'s `GET /user`, `refresh`, `signIn`) and every MFA call (`mfaFetch` in `gotrue-mfa.ts`) go through `callAuthUpstream` (`authUpstream.ts`): bounded at 5 s (`AUTH_UPSTREAM_TIMEOUT_MS`, body included), and a network error, timeout, 5xx, 408 or 429 throws `AuthUpstreamUnavailableError`. Every caller answers that with `respondIfAuthUnavailable`: 503 `AUTH_UNAVAILABLE` + `Retry-After: 5`, cookies untouched, handler never run (`withAuth`, `withUserAuth`, `withPlatformAdmin`, `/api/auth/refresh`, `/api/auth/login` without counting a lockout failure, `change-password` and `change-email` (never "Current password is incorrect"), `invitations/[token]/accept` (an outage at step 2, the GoTrue password set for a new invitee, or step 3, `signIn`, is 503, never SIGN_IN_REQUIRED or a 500; `adminUpdateUser` and `logout` are bounded and classified too; so `change-password` and `change-email` answer an outage at the update 503, `do-reset-password` hands its consumed link back (`releasePasswordResetToken`, never an expired or superseded one) so a retry with the same link finishes the reset and the revocation, and `verify-email` answers 503 CONFIRMATION_INCOMPLETE at all three confirmation calls, where reopening the link completes it). An outage on a PASSWORD update leaves its outcome unknown (GoTrue may have saved it and lost the reply), so both password routes fail safe: they still try the revocation with the new password, which signs in only if the change landed: change-password then completes normally (200, fresh cookies); on GoTrue's definite `invalid_credentials` (`GoTrueSignInError.credentialsRejected`) it answers 503 telling the user to try the current password, then the new one and sign out of all devices (the update may still land); on any other probe failure it answers 503 `PASSWORD_CHANGE_UNCONFIRMED`. Neither promises that nothing changed, and do-reset-password completes (200, link stays spent) or hands the link back with a 503, and every 2FA route: `2fa-enroll`, `-status`, `-confirm`, `-disable`, `-challenge` (no lockout charge) and admin `reset-2fa`, which answers 503 instead of a partial success; a retry skips factors already removed). `requireAuth` (App Router) answers 503 and `getUserFromRequest` rethrows; `/oauth/authorize` rethrows instead of redirecting to `/login`. Any other non-OK reply (401/403 included) stays a rejection: 401 and cookies cleared. Either way the request is refused. The client half: `apiFetch` does not bounce to `/login` when the refresh is unavailable (it answers 503), and `AuthContext` keeps the user (see `src/contexts/.claude.md`). `/api/auth/login`'s `listFactors` failure keeps its own 503 `MFA_CHECK_UNAVAILABLE`. **An outage spends no attempt budget:** routes that charge a limiter before calling GoTrue (invitation accept, the per-factor 2FA limits on challenge/confirm/disable, login's per-email limit) keep charging first and hand the units back through `respondToAuthOutage` only when the outcome is a classified outage, because nothing was judged, so no guess was spent and none is given back; genuine failures stay counted. The per-IP `withRateLimit` wrappers are never refunded; invitation accept has one too (`invite-accept-by-ip`, 20 per 15 min), because its per-token charge is refunded on an outage and nothing else bounded one link holder's GoTrue calls. Tests: `tests/unit/auth/authUpstreamOutage.test.ts`, `authUpstreamRoutes.test.ts`, `authUpstreamReauth.test.ts`, `authUpstreamMfa.test.ts`, `authUpstreamBudget.test.ts`, `authUpstreamAdminUpdate.test.ts`, `verifyEmailOutage.test.ts`, `tests/integration/d9-password-reset-release.int.test.ts`, `tests/unit/components/authOutageClient.test.tsx`, `authUnavailableScreen.test.tsx`.
- `res.end` is swapped only in `deferredEnd.ts`. A new wrapper that defers the flush must call `deferEnd` inside a `try` whose `catch` calls `answerThrow` and throws nothing, and must be added to `WRAPPERS` in `tests/unit/lib/auth/deferredEndCensus.test.ts`, which pins the callers to that list and enforces the other two rules.

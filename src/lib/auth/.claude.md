# lib/auth/

## Purpose
Request authentication and the per-request transaction. `withAuth` (cookie session), `runBearerRequest` in `bearerPipeline.ts` (PAT / OAuth; behind `withBearerOrCookieAuth` and `withBearerAuth`) and `withExtensionToken` (bank-feed extension) each authenticate, open one transaction as `app_user` with the RLS GUCs, run the handler inside it, then COMMIT or ROLLBACK and release. They are the three that also defer the response flush. `withInviteToken`, `withPlatformAdmin` and `publicRouteTx` (`src/lib`) own transactions too, but flush as the handler writes.

## Caller contract
- Compose a route as `withAuth(withErrorHandler(handler))`: `withErrorHandler` goes INSIDE the wrapper, so a caught error is answered 500 and the wrapper sees the status and rolls back. If the handler had already flushed its headers, `withErrorHandler` cannot send a 500. While the response has not ended (always so under the three wrappers, whose `end` is buffered) it sets `statusCode = 500` anyway, so the wrapper rolls back, and aborts the response. A response that already ended through the real `end` is left alone.
- A status of 500 or more rolls back; anything lower COMMITs, so a 4xx sent after a write commits that write. Throw (or answer 500) after a write, never 4xx.
- Background work goes through `runAfterCommit`; the wrapper starts it only after COMMIT.

## Main signatures
- `withAuth(handler)`, `withBearerOrCookieAuth(handler)`, `withBearerAuth(handler)`, `withExtensionToken(handler)`: `NextApiHandler`
- `runBearerRequest(req, res, rawToken, handler, opts?)` (`bearerPipeline.ts`)
- `deferEnd(res): DeferredEnd`, `answerThrow(req, res, deferred, err, ctx)`, `answerCommitFailed(res, deferred)` and `reportFinalizeFailure(req, res, err, ctx)` (`deferredEnd.ts`)
- `rollbackFailed(client, source): Promise<boolean>` and `rollbackError(client, source): Promise<Error | null>` (`src/lib/rollbackFailed.ts`)

## Business rules
- **The response flushes after the transaction ends.** Each wrapper swaps `res.end` for a buffer (`deferEnd`), finalises, then replays the one buffered `end` through the real one (`replayEnd`). Otherwise a client that refetches right after a 200 can read the database before COMMIT. A failed COMMIT turns the buffered 2xx into 500 `COMMIT_FAILED`; if the headers were already flushed, the response is aborted instead, so the client never reads a complete 2xx for a write that did not land.
- **Nothing after COMMIT may reach the wrapper's catch.** `replayEnd` never throws: if the real `end` refuses the buffered body, it logs and aborts the response. The catch would otherwise ROLLBACK a committed write and tell the client it failed, inviting a duplicate retry.
- **A throw inside the request transaction is answered by the wrapper, never rethrown (R-159).** A throw before it (token validation, the pool `connect()`) still propagates; nothing is buffered yet, so it cannot hang. On a throw the wrapper rolls back, puts the real `end` back and answers with `respondToUnhandledError`, the same responder `withErrorHandler` uses: 503 for a lock timeout, 403 for a refused Login-as session, otherwise 500 `INTERNAL_SERVER_ERROR`. It also logs and reports to Sentry with the tenant. It used to rethrow with the buffer still in place, so any later 500 was swallowed and the client hung. `invitations/revoke/[id].ts`, which has no `withErrorHandler`, hung on every throw. The real `end` goes back before anything else, and an error whose message cannot be read or a failing Sentry capture cannot stop the answer. If the headers were already sent, the response is aborted, not closed.
- **A transaction owner that cannot roll back destroys its connection (R-176).** Roll back with `rollbackFailed(client, source)` (`src/lib/rollbackFailed.ts`), keep its result, and call `client.release(result)`: pg-pool destroys a client released with `true`. A bare `release()` after a failed ROLLBACK pools a live connection still inside its transaction, and the next request's COMMIT lands the failed request's writes. A ROLLBACK that succeeds keeps the connection, including after a failed COMMIT. `rollbackFailed` never throws, logs the failure, waits at most 5 s (no answer counts as a failure), and sends Postgres a cancel request, because destroying a socket does not stop its statement. The bound covers the ROLLBACK only: `BEGIN` and `COMMIT` are unbounded, as they were before. Use it for every ROLLBACK, early returns included, never a bare `client.query('ROLLBACK')`. Put `BEGIN` inside the `try` whose `catch` rolls back, and roll back in the function that releases. An owner that can roll back twice keeps the first failure (`failed || unusable`): a cancel is already on its way to that backend. The 5 s bound is a constant; tests shorten it with `setRollbackBoundForTests`, which throws unless `NODE_ENV` is `test`. Every owner in `src/` and `pages/` does this, and every one in `scripts/` except `apply-migrations.ts` and `migrations/resolve-checksum-conflicts.ts` (the ROLLBACK sits in a helper and the release in `main`) and `ap-backfill-supplier-payments.ts` (two ROLLBACK paths the census cannot tell apart, in a script no test can drive); each ends its pool with the run (R-176 fix.md). `tests/unit/lib/rollbackCensus.test.ts` fails on any other statement that ends a transaction (`ROLLBACK`, `ABORT`, with `WORK`, `TRANSACTION` or `AND [NO] CHAIN`) sent through `.query(`, dedicated `pg.Client` owners included, and on an unreadable query text in a file that owns a transaction, and `tests/unit/lib/releaseCensus.test.ts` fails on a release that is bare, or whose argument is not the outcome of a ROLLBACK on that same client, unless it is pinned there with its reason.
- **A long-lived pool has an `error` listener (R-176).** pg-pool re-emits a pooled or removed client's error on the pool, and with no listener that is an uncaught exception. Every pool in this directory has one, and so does every pool in the server, per-request ones included. `tests/unit/lib/poolErrorListenerCensus.test.ts` fails on a pool whose own name has no `.on('error', …)` in the same function; a pool built and ended within one script run is pinned there instead, because ending that run on a pool error is the wanted outcome.
- **The answer the caller is owed stands whenever nothing is meant to commit, whatever the ROLLBACK did (R-176).** That is an early 403 or 429, a handler's own 5xx, and the 500 after a failed critical audit write: a failed ROLLBACK destroys the connection, and the transaction goes with it. Only a failed COMMIT replaces the buffered answer, with 500 `COMMIT_FAILED` through `answerCommitFailed` (`deferredEnd.ts`). Both failures are reported through `reportFinalizeFailure`, under `transaction finalize failed after handler responded`, with the path and never the query string.
- **An auth-provider outage is not a verdict on the token (D9).** GoTrue calls on the session path (`verifyToken`'s `GET /user`, `refresh`, `signIn`) and every MFA call (`mfaFetch` in `gotrue-mfa.ts`) go through `callAuthUpstream` (`authUpstream.ts`): bounded at 5 s (`AUTH_UPSTREAM_TIMEOUT_MS`, body included), and a network error, timeout, 5xx, 408 or 429 throws `AuthUpstreamUnavailableError`. Every caller answers that with `respondIfAuthUnavailable`: 503 `AUTH_UNAVAILABLE` + `Retry-After: 5`, cookies untouched, handler never run (`withAuth`, `withUserAuth`, `withPlatformAdmin`, `/api/auth/refresh`, `/api/auth/login` without counting a lockout failure, `change-password` and `change-email` (never "Current password is incorrect"), `invitations/[token]/accept` (never SIGN_IN_REQUIRED or a 500), and every 2FA route: `2fa-enroll`, `-status`, `-confirm`, `-disable`, `-challenge` (no lockout charge) and admin `reset-2fa`, which answers 503 instead of a partial success; a retry skips factors already removed). `requireAuth` (App Router) answers 503 and `getUserFromRequest` rethrows; `/oauth/authorize` rethrows instead of redirecting to `/login`. Any other non-OK reply (401/403 included) stays a rejection: 401 and cookies cleared. Either way the request is refused. The client half: `apiFetch` does not bounce to `/login` when the refresh is unavailable (it answers 503), and `AuthContext` keeps the user (see `src/contexts/.claude.md`). `/api/auth/login`'s `listFactors` failure keeps its own 503 `MFA_CHECK_UNAVAILABLE`. Tests: `tests/unit/auth/authUpstreamOutage.test.ts`, `authUpstreamRoutes.test.ts`, `authUpstreamReauth.test.ts`, `authUpstreamMfa.test.ts`, `tests/unit/components/authOutageClient.test.tsx`, `authUnavailableScreen.test.tsx`.
- `res.end` is swapped only in `deferredEnd.ts`. A new wrapper that defers the flush must call `deferEnd` inside a `try` whose `catch` calls `answerThrow` and throws nothing, and must be added to `WRAPPERS` in `tests/unit/lib/auth/deferredEndCensus.test.ts`, which pins the callers to that list and enforces the other two rules.

## Recent changes
- 2026-10-02 (D9 round 2): change-password, change-email and invitation accept answer an outage 503; the MFA calls are bounded and classified too.
- 2026-10-02 (D9): a GoTrue outage (5xx, network error, timeout) is answered 503 + `Retry-After` and no longer clears the cookies; the session-path GoTrue calls are bounded at 5 s. On 2026-10-02 01:08–01:25 UTC Postgres ran out of connection slots, GoTrue `/user` returned 500, and every AAL1 request was answered 401 with its cookies cleared.
- 2026-10-01 (R-176): every transaction owner (but the three scripts named above) rolls back through `rollbackFailed` (bounded at 5 s, cancels the backend) and releases with its result, so a connection left inside its transaction is destroyed, not pooled. An early 403/429 or a handler 5xx whose ROLLBACK fails keeps its answer; the COMMIT-failed answer moved into `answerCommitFailed` and the report into `reportFinalizeFailure`. The pools here all have an `error` listener. The `res.end` census also catches `Reflect.defineProperty`, and a release census proves every released value is a ROLLBACK outcome.
- 2026-09-30 (R-159): the buffered flush moved into `deferredEnd.ts`; the three wrappers answer a throw instead of rethrowing it, never let a replay failure after COMMIT reach their catch, and abort (not complete) a response whose headers were flushed before a failure.

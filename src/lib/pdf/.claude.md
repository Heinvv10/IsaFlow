# lib/pdf/

## Purpose
Renders one authenticated app page to PDF bytes by photographing the page a user would see. The figures in a PDF are therefore COPIED from the rendered page, never re-derived — a document and the screen behind it cannot disagree on a number.

## Caller contract
`renderPagePdf(options)` is called from API routes (`pages/api/accounting/packs/[id]/pdf.ts`). It mints the print token itself; the token never leaves the process.

**`APP_URL` is required and is NOT `NEXT_PUBLIC_APP_URL`.** The public one is a build-time value baked into the browser bundle — the address the CLIENT uses. This one is read at request time to build the URL the RENDERER navigates to, so it must be reachable from the renderer: `host.docker.internal:3200` locally, the real hostname in production. Falling back to the public value would produce a render that fails inside the container with a network error instead of a clear refusal here, which is why `renderPagePdf` throws `APP_URL is not set` rather than defaulting. Documented in `.env.example`; pinned by `tests/unit/lib/pdf/renderPagePdf.test.ts`. The PPTX route needs none of this — it assembles the deck in-process and launches no browser.

## Main signatures
- `renderPagePdf({ companyId, userId, path, query?, apiPaths?, landscape? }): Promise<Buffer>`
- `withRenderSlot(handler): NextApiHandler` (`withRenderSlot.ts`) — the OUTER route wrapper
- `acquireRenderSlot<T>(fn): Promise<T>` / `RenderCapacityError` / `RenderQueueFullError` / `renderQueueBound()` (`renderSemaphore.ts`)
- `mintPrintToken(companyId, userId, paths, ttlSeconds = 120)`, `verifyPrintToken(token, requestPath)`, `verifyPrintTokenSignature(token)` (`printAuth.ts`)
- `isPrintRender(router)`, `PRINT_RENDER_PATH` (`printRenderQuery.ts`)
- `chooseTransportName(env)` (`selectTransport.ts`), `buildGotenbergFields(request, env?)`

## Business rules
- **Print token contract**: HMAC-SHA256 over `company|user|paths|exp`, bound to an EXACT set of API pathnames matched with `===` (never a prefix) and to the company. 120-second TTL. It is **replay-bounded by the TTL only** — there is no nonce and no revocation, so a captured token is usable for its remaining lifetime; accepted, because every bound path is a read-only GET and the token is minted per render, server-side, and travels only to the renderer. All three signed fields reject `|` and `\n` on both mint and verify: without that `sign` is not injective and one signature validates a different tenant's payload. **A token also has exactly one valid SPELLING** — lowercase 64-character hex signature, unpadded base64url payload that round-trips. Node's decoders accept uppercase hex, standard base64, `=` padding and non-round-tripping trailing bits, each of which is a different string carrying the same authority; with no nonce and no revocation, string identity is the only handle anything upstream has on a token.
- **A print token authorises `GET` and nothing else.** It binds a path SET, not a verb, so without this a captured token would become a write credential the day a bound route grew a write method — and the token has no nonce and no revocation, only its 120-second TTL. `authenticatePrintToken` refuses a non-GET before it checks the signature, without clearing cookies (a render may still be in flight on the same cookie).
- `withAuth` accepts the token ONLY through `authenticatePrintToken` (`src/lib/auth/withAuthPrint.ts`), which calls `verifyPrintToken`. Never re-implement the path check at a call site: the inline copy is how the tested function ended up with no production caller. The whole branch is disabled unless `PRINT_TOKEN_SECRET` is set and at least 32 characters.
- A genuine token presented on an unbound path 401s **without clearing cookies**; only a forged/expired one clears. Clearing wiped the render's own credentials mid-render.
- **Gotenberg cookies go in the `cookies` form field, never `extraHttpHeaders`** — that header attaches to every resource the page loads, including cross-origin ones, and would leak the print token off-domain. Residual, accepted: Gotenberg's cookie object requires `domain` and offers no host-only/`url` form, so a bare hostname is the tightest scope available and matches subdomains. The container's `--chromium-allow-list` is what contains it — Chromium can only navigate to the app host.
- **The container MUST run with `--chromium-allow-list` pinned to the app host, and `--api-timeout` above the client's 55s.** Neither can be asserted from this repo: the flags are on the `docker run` line (there is no compose file, no systemd unit and no env-check hook in `scripts/deploy.sh`), and Gotenberg's `/health` and `/version` report neither flags nor configuration, so a health-check cannot verify it either. What the code does instead is refuse to be quiet about it — `selectTransport.ts` logs a warning on every boot that selects this transport until `GOTENBERG_ALLOW_LIST_VERIFIED=true` records that an operator has checked the running container. The flag asserts nothing; it is a signed-off assumption, and it is deliberately not honoured by default.
- **The client timeout is STRICTLY under the container's.** `GOTENBERG_TIMEOUT_MS` is 55s against a 60s `--api-timeout`: equal was a race — whichever clock reached 60 first won, so one slow render surfaced as a Gotenberg 5xx and the next as a client `AbortError`, and only the server's answer says what went wrong. Raise `--api-timeout` before raising this, in that order.
- **In production, an absent or blank `GOTENBERG_URL` THROWS.** It is not a silent fallback to Playwright; that path is reachable only by setting `PDF_TRANSPORT=playwright` deliberately.
- **Concurrency is bounded process-wide** (`renderSemaphore.ts`, default 3 via `PDF_MAX_CONCURRENT_RENDERS`, clamped to a quarter of `AUTH_POOL_MAX`, so 2 at the default pool of 10 since R-188). Each render holds a `withAuth` pool connection AND the browser re-enters the API for the report, so unbounded renders exhaust `AUTH_POOL_MAX` and stall every tenant. Excess waits `PDF_RENDER_QUEUE_TIMEOUT_MS` (default 10s), then the route answers 503. The PPTX route is NOT gated: it launches no browser and makes no inbound call.
- **The slot is taken OUTSIDE `withAuth`** — `withRenderSlot(withAuth(withErrorHandler(handler)))`, never inside the handler. withAuth takes a pool connection and opens a transaction before the handler runs, so a request queueing for a slot inside was already holding both: twenty-five parallel exports from one viewer (inside the per-company export rate limit) took every connection, and the renders' own inbound fetch for the report then had none. The queue consumed the pool the bound exists to protect.
- **The wait queue is bounded too**, at `2 ×` the concurrency bound. Past that a request is refused IMMEDIATELY with the same retryable 503 — no wait, no DB touched — because a third layer of waiters could not be served inside the wait bound anyway. `withRenderSlot`'s precheck is deliberately the cheapest thing that costs no I/O: an `sb-access-token` cookie must be PRESENT, else the request goes straight to withAuth and 401s without spending a slot. Presence is not validity; the queue bound is what caps a junk-cookie flood.
- **RESIDUAL, accepted: an admitted render still runs inside withAuth's open transaction** (`withAuth.ts` BEGIN → COMMIT), for up to the 30s print-ready gate plus transport overhead. Bounded at three concurrent, that is at worst three connections idle in transaction — the pool carries it, and the alternative (committing before the render) would mean the render's own inbound fetch could not see this request's GUCs. What was NOT acceptable, and is fixed, is an unbounded number of *waiters* holding one each.
- **Both env knobs are CLAMPED to ceilings derived from `src/lib/limits/poolLimits.ts`, never restated there.** The queue wait caps at the pool's `connectionTimeoutMillis` minus a 2s margin — a request waiting for a slot already holds a connection, and a refusal arriving after the pool has failed the next caller refuses work that has already died. Concurrency caps at a quarter of `AUTH_POOL_MAX`, because a render takes at least two connections and the pool must stay usable for other tenants. An over-large value is clamped and logged once, never honoured. Change a pool constant and both bounds move with it.
- The pool constants both this directory and `lib/auth` read live in `src/lib/limits/poolLimits.ts`. They were in `lib/auth/`, which made the two directories mutually dependent — `lib/auth` imports `lib/pdf` for `withAuth`'s print fallback, and `lib/pdf` imported `lib/auth` for two numbers. The neutral directory breaks the cycle without moving behaviour.
- **The provider gate is scoped to the pack page**, not global on `?print=1`. `print` is not a reserved parameter, and a global gate would strip an unrelated page's auth and company context with no error. `_app.tsx` gates `AuthProvider`, `CompanyProvider` and the analytics tracker on it: `/api/auth/me` CLEARS the cookie carrying the print token, `/api/accounting/companies` 401s into a redirect to `/login`, and the tracker would record a synthetic pageview for every export.
- The PAGE adds `print-mode` to `<html>` and drops `.dark`, not the renderer — Gotenberg cannot execute a script on our behalf.
- One Chromium is reused for the process; the per-render isolation is the CONTEXT.
- **`PRINT_ERROR_ATTRIBUTE_PREFIX` (`data-print-error`, `printErrorAttribute.ts`) names the print page's "I will never be ready" signals — ONE ATTRIBUTE PER PRODUCER** (`data-print-error-fonts`, `data-print-error-pages`; set by `markPrintError(producer, reason)` in `components/accounting/packs/usePrintMode.ts`, value `<producer>: <reason>`, cleared only by that producer's `clearPrintError`). The Playwright transport waits (one `waitForFunction`) for ready OR any prefixed attribute and takes what that predicate OBSERVED in the same instant: any error attribute — even an empty-valued one, even beside the ready marker, even if withdrawn a moment later — fails the render at once with every reason; nothing is re-read after the wait. Under Gotenberg the same failure is a 400 in seconds with no PDF: the `waitForExpression` THROWS on any prefixed attribute (measured against `gotenberg/gotenberg:8`: `400 … returned an exception` in ~0.2 s; a forced refusal through the route answered 422 in 3.3 s where the old form waited out the 55 s client timeout). `failOnConsoleExceptions` is deliberately NOT used — it would fail every healthy pack on any unrelated uncaught exception. `markPrintError` also raises an uncaught error (`reportError`, or a macrotask throw), but that is for visibility (logs, Sentry) and the Playwright transport; it no longer gates Gotenberg. Gotenberg writes only the standard Info keys, so `gotenbergTransport` adds the custom `IsaFlow…` keys itself (`capabilities.metadata` is `best-effort`).
- **Page margins come only from `PDF_MARGIN_MM`** (`pdfTransport.ts`), passed by both transports; neither sets `preferCSSPageSize`, so a CSS `@page` margin is ignored. The tenant logo never reaches the browser as a URL: the pack fetches it server-side (`services/packs/packBrandForRender.ts`) and embeds a `data:` URI.
- **The footer typeface loads only via the data-URI resource-cache route.** Chromium's header/footer template inherits no stylesheet and fetches nothing, so a normal `@font-face` there does not load. `buildFooterHtml` (`printFurniture.ts`) emits `packFooterFaceCss(...)` byte-identical to what `usePrintMode` injects into the main document; never write the face a second way.

## Recent changes
- 2026-10-03 (R-188): the `AUTH_POOL_MAX` default fell from 20 to 10. The render ceiling is `floor(pool/4)`, so at the default it is 2 (was 5) and the default of 3 renders is clamped to 2 with a one-time warning; set `PDF_MAX_CONCURRENT_RENDERS=2` to silence it, or raise `AUTH_POOL_MAX` to 12+ for 3.
- 2026-10-02 (R-182): `AUTH_POOL_MAX` is validated (`poolSizeFromEnv`, floor 2). An unusable value (NaN, 0, negative, Infinity) now gives a pool of 10 and a render ceiling of 2 (it was 3: the semaphore's own NaN guard); a numeric refused spelling such as `15.0` gives its own size, and a value of 1 is raised to 2 so a render's re-entry can get a second connection (the ceiling stays 1), and `10.0` still means the default 10 (R-188 moved the default from 20, so `20.0` now gives 10).
- 2026-09-07 (task 20c): **`capabilities.metadata` is `'guaranteed' | 'best-effort'`, not a boolean.** `writePdfInfoDictionary` returns the file unchanged for any PDF whose cross-reference section it does not recognise, so a `true` on the Playwright transport told a call site gating PDF/A that the metadata was certainly there. Gotenberg's renderer takes the Info dictionary as a form field and is `guaranteed`; Playwright post-processes and is `best-effort`. The writer now returns `{ pdf, written }` rather than a buffer and a `log.warn`. `PdfMetadata` gained `custom` — non-standard Info keys (`IsaFlowPack`, `IsaFlowPeriod`, `IsaFlowStatus`…), written through `pdfName` escaping, because `pdfinfo` reports `Custom Metadata: no` for a dictionary of standard keys however well populated, and that literal line was the acceptance check. Both transports write them.
- 2026-09-07 (task 20b): `pdfInfoDictionary.ts` added — `page.pdf()` exposes no metadata option, so the Playwright transport appends the Info dictionary as a PDF incremental update instead of logging that it dropped what the call site asked for. `playwrightTransport.capabilities.metadata` stopped saying `false` (see task 20c above for what it says now). It returns the input unchanged for any file it does not fully understand (a cross-reference stream cannot take a classic xref section appended to it).
- 2026-09-06: `withAuth` routed through `verifyPrintToken`; separators banned in all three signed fields; render semaphore added; Chromium reused; print gate scoped to the pack page.
- 2026-09-06 (PR review): the render slot moved OUTSIDE `withAuth` and the wait queue gained a bound; pool constants moved to `src/lib/limits/`.

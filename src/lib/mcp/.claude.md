# src/lib/mcp — MCP server core

## Purpose

Tenant-scoped MCP (Model Context Protocol) server internals: tool registry,
audit/idempotency, types. Exposed to clients via `pages/api/mcp/index.ts`
(Bearer-only JSON-RPC transport, dark behind the `mcp_connector` flag).

## Caller contract

- Transport builds `McpToolContext` from the authenticated request ONLY
  (`withBearerAuth`). **companyId/userId never come from tool args** — no tool
  accepts a company identifier. Cross-tenant probes must return the same
  generic "Not found" text as a genuine miss.
- All tool handlers call existing `src/modules/accounting/services/*`
  functions — tools NEVER write SQL.
- `McpRegistry.call()` fence order (tests prove handler-never-ran):
  resolve → scope → `write:post` → idempotency-key presence (write tools) →
  replay lookup → handler → audit. Rejections audit as `'rejected'`.
- Handler errors surface as a GENERIC message (no stack/SQL); audited `'error'`.

## Main signatures

```typescript
// types.ts
interface McpToolContext { userId; companyId; scopes; tokenJti; oauthAppId }
interface McpTool { name; description; inputSchema; scope: string | null;
                    write: boolean; requiresPost?: boolean; handler(args, ctx) }
// registry.ts
class McpRegistry { register(tool); getManifest(); listTools(); call(name, args, ctx) }
// audit.ts — persists to mcp_tool_calls (mig 507, tenant RLS, append-only)
recordToolCall({ ctx, tool, argsHash, idempotencyKey, status, result, durationMs })
findIdempotentReplay(companyId, tool, key): Promise<McpToolResult | null>
hashArgs(args): string   // sha256 of key-sorted canonical JSON
```

## Business rules

- Write tools REQUIRE `args.idempotency_key`; replays return the stored
  result without re-running the handler. **Only a SUCCESS THAT WROTE is stored
  under the key.** A handler refusal (`isError`) is audited `'rejected'` with a
  NULL key and no stored result — most refusals are state-dependent ("Not found" for a
  row that had not committed, "Transaction already allocated"), so the identical
  call becomes correct once the state is fixed, and a refusal wrote nothing that
  a re-run could duplicate. Stored under the key it would replay forever: the
  partial unique index has no status column and `recordToolCall` does
  `ON CONFLICT DO NOTHING`, so the row occupies the key permanently. A success
  that wrote nothing (a dry run) frees the key the same way, via
  `result.wroteNothing` — otherwise the real call, which carries the same intent
  and the same natural key, is served the preview forever.
- **A freed key makes the write-vs-refuse rule load-bearing, not stylistic.**
  Because a refusal no longer consumes the key, a handler that WRITES and then
  returns a `toolError` gets re-run by the agent's retry and writes a SECOND
  time — the savepoint only rolls back on a throw, so the first write survives
  too. So: only PRE-write validation may return `toolError`; once a service that
  can write has been called, every failure RETHROWS. Where the service raises
  its own refusals after it has begun writing (`reverseReconciledTransaction`
  posts the contra journal, then resets the row; `allocateTransaction` posts the
  entry, then updates the row), the tool answers those refusals from a READ
  first — `getBankTransactionStatus`, `getJournalEntryById` — so the precise
  message survives without a catch. `registry.test.ts` pins the registry half:
  a write-then-refuse handler runs twice on one key. Known bound: two CONCURRENT calls
  with the same key can both pass the replay lookup — the partial unique
  index on (company_id, tool, idempotency_key) makes the second audit INSERT
  fail (logged), but the handler will have run twice. Sequential replays are
  fully idempotent.
- Posting tools (`requiresPost`) additionally need the `write:post` scope —
  default-off, explicit user opt-in at consent/PAT-mint (Hein decision,
  2026-07-18 — do not re-open).
- **Ownership is the tool handler's job.** Any id an agent supplies that
  becomes a foreign key (`account_id`, `customer_id`, `entity_id`,
  `contra_account_id`, `bank_account_id`) must be checked against
  `ctx.companyId` BEFORE the service call — `accountsBelongToCompany` /
  `customerBelongsToCompany` / `supplierBelongsToCompany` /
  `bankGlAccountBelongsToCompany`. The services do not re-check the tenant and
  there is no composite `(id, company_id)` FK, so nothing downstream stops a
  cross-tenant write. Refuse with the shared `NOT_FOUND` constant: a distinct
  "belongs to another company" reply is an existence oracle.
- **Every posting path stamps `mcp:<tool>:v1`.** `createJournalEntry` and the
  services that wrap it fall back to `defaultHumanMeta(userId)` when no meta
  is passed, which labels agent work as `human:<userId>` and hides it from
  `list_agent_postings` (filters `posting_agent LIKE 'mcp:%'`). Drafts count —
  `post_journal` does not restamp. Service-side the stamp travels as an
  optional last-positional `opts?: { postingAgent?: string }` so non-MCP
  callers keep human attribution.
- **PAYG metering lives in `flowMetering.ts`, applied by `registry.call()`.**
  `TOOL_FLOW_OPERATIONS` must name EVERY registered tool — `null` for free, and
  a missing entry is a bug, not a default (a drift test fails the build).
  **Writes only** — a write costs what the equivalent `withFlowMeter` endpoint
  costs; every read is free. Full UI parity was the first cut and was reversed
  on evidence: 10-Flow reports at the endpoint's 120/min drain 1,200 Flows/min,
  exhausting a month's budget in under three minutes and 402-ing the human UI
  that shares the wallet. Corrections (`reverse_bank_allocation`,
  `undo_bank_import`) and review (`list_agent_postings`) are free — pricing the
  controls the safety model depends on would discourage using them.
  Three rules are load-bearing: the debit runs AFTER the replay check (else a
  retry bills twice); OUTSIDE the savepoint (inside it, a write-tool throw rolls
  the debit back AND the explicit refund fires, crediting twice); and the
  insufficient-Flows rejection is audited with a NULL idempotency key — the
  partial unique index has no status column and `recordToolCall` does
  `ON CONFLICT DO NOTHING`, so a rejected row carrying the key would block the
  later `'ok'` row forever and every retry would re-run the handler.
  A handler may return `billable: false` to refund a success that did no work
  (all-duplicate resend); `registry.call()` strips the flag before responding.
- Tests live in `tests/unit/mcp/` (vitest includes only `tests/unit/**`).

- **Bulk write tools are ALL-OR-NOTHING and must RETHROW mid-write.**
  `registry.call()` gives a write tool exactly ONE savepoint; a handler must not
  open its own. Because the savepoint rolls back only on a THROW, any failure
  after the first service write has to propagate — `catch → toolError` returns
  normally, the savepoint RELEASES and the transport's HTTP 200 COMMITs the
  lines already posted. Only PRE-write refusals may return `toolError`; they run
  before the first write, so there is nothing to unwind and the agent gets an
  actionable message with the offending line index.
- **A refusal is about the REQUEST; a skip is about the DATA.** That is the line
  the two shapes fall on. Shape, size, duplicate lines and cross-tenant
  ownership are faults in what the caller sent — it has to change the request,
  so they refuse the batch, and ownership answers at BATCH level so naming a
  line never becomes an existence oracle. Anything the data says about one row —
  already allocated, excluded, not importable, the reference matches no row, the
  reference matches several — is a skip, and must not cost the other 499 lines.
- **A batch skips what it cannot post; it does not fail on it.** PRD-11 §4.
  `bulk_allocate_bank_transactions` reads the CURRENT state of every resolved
  row in ONE company-scoped query (`findBankTransactionAllocationStates`)
  before it writes anything, and splits the batch: postable is
  `status='imported'` AND `matched_journal_line_id IS NULL`; everything else is
  `skipped` with `{index, transaction_id, reason}` — `already allocated`,
  `excluded`, `already allocated (excluded)` (in the ledger AND marked out of
  it — both facts, because either alone hides the other), or
  `not importable: <status>`. Both columns, never `status`
  alone: an allocated row carries the journal line the reverse tool navigates
  by, and a fixture that sets only the status passes while production fails.
  A line whose selector never resolved is skipped the same way, with
  `transaction_id: null` because there is no id to report: an unrecognised
  `bank_reference` and an ambiguous one both carry their reason (the ambiguous
  one lists its candidates, so the agent can re-issue naming one). A resolved id
  that is not in the company at all is likewise a skip, reported with the id the
  caller sent. A batch with nothing left to post returns a toolError and opens NO
  batch row — that guard, not per-line fatality, is what stops a wholly wrong
  list reading as a silent `posted: 0`.
- **A per-line failure inside a batch must not surface as GENERIC_FAILURE.**
  Anything `allocateTransaction` still throws after the pre-check is rethrown
  as `BulkAllocationLineError(index, transactionId, detail)`, and
  `registry.call()` renders that as
  `<tool> line <i> (<txid>): <detail> — batch rolled back, nothing posted`.
  Everything else on that path is unchanged (savepoint rollback, refund, audit
  `'error'` with a NULL key). The exception is narrow on purpose: index and id
  are the agent's own input, so naming them leaks nothing — and the DETAIL is
  sanitised before it gets there (`safeLineDetail`), because this is the one
  hole through which the "no SQL in a tool result" rule could be smuggled back
  out. Anything carrying a SQLSTATE (or reading like a driver message) is
  reduced to `database error <code>`; service-written messages pass through,
  capped at 200 chars. A row that is LOCKED by another request
  (`BANK_TX_LOCK_TIMEOUT`, 5s) is write-free like the race, so it is a skip
  (`locked by another request — retry`), not a batch failure. A row that becomes
  allocated BETWEEN the pre-check and its post is not a failure at all — the
  service's own guard fires after its `FOR UPDATE`, nothing was written, and it
  is counted as a skip so the batch carries on. That is why the posting loop
  opens a savepoint PER LINE (`bulk_alloc_line_<i>`, ≤31 chars): without one a
  service throw leaves the request transaction aborted and the batch cannot
  continue past a fault it is entitled to skip.
- **Savepoint names are capped at 31 characters.** `withSavepoint` validates
  `^[a-zA-Z_][a-zA-Z0-9_]{0,30}$` and THROWS otherwise, so
  `registry.savepointNameFor()` truncates `mcp_<tool>`; `mcp_bulk_allocate_bank_transactions`
  is 35 and would have failed every call before the handler ran, surfacing only
  as GENERIC_FAILURE. `registrySavepointName.test.ts` asserts the truncated
  names stay distinct — a collision would let a nested call release another
  tool's savepoint.


## Recent changes

- 2026-08-29: **a reversal's date is now a PARAMETER, and the tools say what it is.** The date a contra carries was decided entirely inside `reverseJournalEntry` — original entry date when that period is open, today when closed — as an internal local variable. No surface accepted it and no tool description mentioned it, so an agent correcting a closed month could not find out which period its correction would land in except by posting one. `reverse_bank_allocation` and `reverse_bank_allocation_batch` now take `reversal_date` (shared `REVERSAL_DATE_PROPERTY` in `allocationSchema.ts`, so both read identically), `POST /api/accounting/journal-entries-action` takes `reversal_date`, and every description states the DEFAULT as well as the override — offering the override while leaving the default unstated answers the wrong half of the question. Validation lives in ONE place, `reverseJournalEntry`, which is the only code that knows the entry being reversed: the value must be a real YYYY-MM-DD day (it reaches a DATE column, where a malformed value raises 22P02 and surfaces as a generic failure) and must not PRECEDE that entry (a correction dated before the thing it corrects is nonsense in every period-bounded report). Whether the TARGET period is open is deliberately NOT re-checked — `createJournalEntry` derives the fiscal period from the date and `postJournalEntry` raises `ClosedFiscalPeriodError`, so a second check could only drift from the one that governs the write. All ten existing callers pass no date and are unchanged.
- 2026-08-28: **an unresolved line is SKIPPED too — not-found and ambiguous join already-allocated.** The batch still refused whole when any line's selector did not resolve: an unknown `bank_reference`, one carried by more than one transaction, or a `transaction_id` naming no row in this company. One bad line in a 500-line statement batch posted nothing and could only be located by bisecting — the same failure PRD-11 §4 had already fixed one step later in the pipeline. `tools/bulkAllocationPrepare.ts` now returns `{resolved, skipped}` instead of refusing on `resolveTxSelectors` errors, and `partitionAllocationLines` returns a plain `Partitioned` (its missing-row case became a skip), so `SkippedLine.transaction_id` is `string | null` — null for a selector that never resolved. The handler merges both skip sets and sorts by the agent's own line index, so a caller never has to know which stage refused which line. What stays fatal: malformed lines, oversize batches, duplicate lines and cross-tenant ownership — faults in the REQUEST, with ownership still answered at batch level. `nothingToPostText` is now the only guard against a wholly wrong list reading as success, and it is reached in every all-skipped case because `postable.length === 0` is checked once, after the merge. `writeBankBulkAllocate.ts` was split at the same time — `reverse_bank_allocation_batch` moved to `tools/writeBankReverseBatch.ts` — to stay inside the 300-line cap.
- 2026-08-28: **an already-allocated line is SKIPPED, not a batch failure** (PRD-11 §4, production blocker). A pilot batch of 124 verified lines contained one transaction the books already carried; `dry_run` reported it as a normal postable line, the live call threw from inside `allocateTransaction`, and `registry.call()` rendered that as "The operation failed. Please try again or contact support." with no line index — the batch was bisected by hand. Two fixes, on opposite sides of the write boundary. PRE-WRITE: `tools/bulkAllocationSkip.ts` reads every resolved row's `status` and `matched_journal_line_id` in ONE company-scoped query (`findBankTransactionAllocationStates`) and partitions the batch, so `dry_run` and the live call agree; skipped lines carry `{index, transaction_id, reason}` and the batch posts the rest. `line_count` and `bank_allocation_batch_lines` cover the POSTED lines only — the batch is opened after the postings now, so its count describes what exists — and a batch with zero postable lines refuses (`nothing to post: all N lines skipped …`) rather than leaving an id that reverses nothing. Both columns are read, never `status` alone: the journal line is what the reverse tool navigates by, and a fixture that sets only the status is how #261 got through. POST-WRITE: `tools/bulkAllocationPost.ts` wraps each line in its own savepoint (`bulk_alloc_line_<i>`) and either counts a lost race as a skip — `allocateTransaction` re-reads the settled status under its own `FOR UPDATE`, so nothing was written — or rethrows a genuine fault as `BulkAllocationLineError`, which `registry.ts` renders WITH the line index instead of GENERIC_FAILURE. The all-or-nothing property is unchanged: a real fault still throws, and the registry's savepoint still unwinds the whole batch.
- 2026-08-28: **selector resolution moved to `tools/txSelectorResolve.ts` and became batched** (review follow-up to the entry below). `resolveTxSelectors(selectors, companyId)` resolves a whole bulk call with ONE lookup per distinct `bank_account_id` scope — `prepareAllocationLines` used to `await resolveTxId` per line, so 500 by-reference lines meant 500 sequential lookups inside a request that already holds every row's lock. Lines scoped to DIFFERENT bank accounts still get separate queries: merging them would resolve a reference against an account the caller deliberately excluded. `pickTxSelector` / `resolveTxId` / `TxSelector` moved with it and are re-exported from `allocationLine.ts`, so the "single and bulk go through exactly these functions" rule is unchanged. The ambiguity reply now names the COLUMN as well as the value (`… (2026-03-01, -1234.56, bank_reference "FEED-77")`): with `reference` preferred over `bank_reference`, candidates are all one or all the other, and which one it was tells a human whether they are looking at a statement reference or a feed's external id. **`reverse_bank_allocation` now runs `badUuidArg` before resolving** — `transaction_id` reaches pg as `$n::UUID` in the status read and `bank_account_id` in the lookup, so a malformed one raised 22P02 from inside the handler; every other allocation path was guarded by `parseAllocationLine`, which this one never calls. Guard order is selector-first, cast-second, matching `parseAllocationLine`'s documented contract.
- 2026-08-28: **the statement reference resolves against EITHER reference column, and compact rows finally carry it.** Production had 9,824 `bank_transactions` rows with `reference` set and ZERO with `bank_reference`, so `findBankTransactionsByReference`'s `btrim(bank_reference) = $ref` answered NOT_FOUND for every reference the MCP pilot could read off a statement — `allocate_bank_transaction` / `bulk_allocate_bank_transactions` / `reverse_bank_allocation` all refused rows that allocated fine by `transaction_id`. The WHERE is now `(btrim(reference) = $ref OR btrim(bank_reference) = $ref)` in both branches, and the lookup reports `matchedReference` (which stored value matched) so the ambiguity reply can show it: two candidates can now collide through DIFFERENT columns and ids alone would not say why. The ≤25-candidate cap, the blank-ref guard and the exact-match rule are unchanged. `list_bank_transactions` `fields="compact"` had the mirror bug — it mapped `tx.bankReference ?? null` and so answered `bank_reference: null` on every production row while `fields="full"` showed the value under `reference`; it now falls back (`bankReference ?? reference ?? null`), keeping `bankReference` first because that is the feed's stable external id. Tool descriptions say both things out loud: compact `bank_reference` is the statement reference from either column, and a `limit` above 100 is ACCEPTED and silently clamped rather than refused.
- 2026-08-28: `list_gl_accounts` (18 read tools) — the chart of accounts in one
  call, on `search_gl`'s `read:reports` scope and free like every other read.
  Pilot agents were resolving codes to UUIDs one at a time through `search_gl`'s
  `meta.accountId`, which forces a date range and returns ledger lines nobody
  wanted; the description says "resolve account codes to UUIDs in one call
  before allocate/journal tools" because the description is all an agent reads
  before choosing. It reuses `getChartOfAccounts(companyId, includeInactive)`
  verbatim (the same cached service the COA page uses) and filters
  `account_type` / `search` in memory — a second SQL path over `gl_accounts`
  would be a tenant-scoping surface for no gain. Rows are mapped DOWN to
  `{id, account_code, account_name, account_type, account_subtype, is_active,
  parent_account_id}`: `normal_balance`, `level`, `is_system_account` and
  `has_transactions` are ours. An unknown `account_type` is REFUSED against the
  real `GL_ACCOUNT_TYPES` enum (now a runtime const in `gl.types.ts`) before any
  query — filtering to an empty list would read to an agent as "this company has
  no expense accounts", a wrong answer dressed as a right one. No pagination:
  `limit` defaults to 200 and clamps at 500, and `total` is the pre-limit match
  count so a truncated list is visible rather than assumed complete. `search` is
  compared as TEXT in JS, so it takes no cast guard.

- 2026-08-27: **every tool argument that lands in a SQL cast is guarded before the
  service call** — `guardCastableArgs` / `guardUuidList` in `toolHelpers.ts`, applied
  across all 12 tool files. An id becomes `$n::UUID` and a date `$n::DATE`, so 'abc' is a
  22P02 and '2026-02-31' a 22008; a READ tool has NO savepoint, so that aborts the whole
  request transaction and the registry's own refund and audit writes then fail with 25P02
  (500, Flow debit unrefunded). WRITE tools have a savepoint and survive, but the reply
  degrades to a generic failure naming no argument — and for `allocate_bank_transaction`
  the error fires from the OWNERSHIP lookups, where an agent cannot tell a typo from a
  refusal. `format: date` in a JSON Schema is advisory and enforces nothing. Guards use
  `isRealCalendarDate`, NOT `isValidDate` — Date.parse rolls '2026-02-31' forward to 3
  March, and JS's year 0 does not exist in Postgres. TEXT-compared arguments
  (`account_code`, `bank_reference`, `search`, `status`) stay free-form by design. New
  tool arguments that reach a cast must be added to the tool's guard spec and to
  `tests/unit/mcp/toolArgCastGuards.test.ts`, which fails if any guard is removed.

- 2026-08-27: PRD-11 §4 follow-ups from the adversarial review —

  still carries that journal; anything re-allocated or already reversed is

- 2026-08-27: PRD-11 §4 — `bulk_allocate_bank_transactions` (≤500 lines,

- 2026-08-27: `list_bank_transactions` gained `cursor` + `fields` (PRD-11 §3). The reply is

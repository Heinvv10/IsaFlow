# src/lib/mcp — MCP server core

## Purpose

Tenant-scoped MCP (Model Context Protocol) server internals: tool registry,
audit/idempotency, types. Exposed to clients via `pages/api/mcp/index.ts`
(Bearer-only JSON-RPC transport, dark behind the `mcp_connector` flag).

## Caller contract

- Transport builds `McpToolContext` from the authenticated request ONLY
  (`withBearerAuth`). **companyId/userId never come from tool args** — no tool
  accepts a company identifier. Cross-tenant probes must return the same
  generic "Not found" text as a genuine miss.
- All tool handlers call existing `src/modules/accounting/services/*`
  functions — tools NEVER write SQL.
- `McpRegistry.call()` fence order (tests prove handler-never-ran):
  resolve → scope → `write:post` → idempotency-key presence (write tools) →
  replay lookup → handler → audit. Rejections audit as `'rejected'`.
- Handler errors surface as a GENERIC message (no stack/SQL); audited `'error'`.

## Main signatures

```typescript
// types.ts
interface McpToolContext { userId; companyId; scopes; tokenJti; oauthAppId }
interface McpTool { name; description; inputSchema; scope: string | null;
                    write: boolean; requiresPost?: boolean; handler(args, ctx) }
// registry.ts
class McpRegistry { register(tool); getManifest(); listTools(); call(name, args, ctx) }
// audit.ts — persists to mcp_tool_calls (mig 507, tenant RLS, append-only)
recordToolCall({ ctx, tool, argsHash, idempotencyKey, status, result, durationMs })
findIdempotentReplay(companyId, tool, key): Promise<McpToolResult | null>
hashArgs(args): string   // sha256 of key-sorted canonical JSON
```

## Business rules

- Write tools REQUIRE `args.idempotency_key`; replays return the stored
  result without re-running the handler. **Only a SUCCESS THAT WROTE is stored
  under the key.** A handler refusal (`isError`) is audited `'rejected'` with a
  NULL key and no stored result — most refusals are state-dependent ("Not found" for a
  row that had not committed, "Transaction already allocated"), so the identical
  call becomes correct once the state is fixed, and a refusal wrote nothing that
  a re-run could duplicate. Stored under the key it would replay forever: the
  partial unique index has no status column and `recordToolCall` does
  `ON CONFLICT DO NOTHING`, so the row occupies the key permanently. A success
  that wrote nothing (a dry run) frees the key the same way, via
  `result.wroteNothing` — otherwise the real call, which carries the same intent
  and the same natural key, is served the preview forever.
- **A freed key makes the write-vs-refuse rule load-bearing, not stylistic.**
  Because a refusal no longer consumes the key, a handler that WRITES and then
  returns a `toolError` gets re-run by the agent's retry and writes a SECOND
  time — the savepoint only rolls back on a throw, so the first write survives
  too. So: only PRE-write validation may return `toolError`; once a service that
  can write has been called, every failure RETHROWS. Where the service raises
  its own refusals after it has begun writing (`reverseReconciledTransaction`
  posts the contra journal, then resets the row; `allocateTransaction` posts the
  entry, then updates the row), the tool answers those refusals from a READ
  first — `getBankTransactionStatus`, `getJournalEntryById` — so the precise
  message survives without a catch. `registry.test.ts` pins the registry half:
  a write-then-refuse handler runs twice on one key. Known bound: two CONCURRENT calls
  with the same key can both pass the replay lookup — the partial unique
  index on (company_id, tool, idempotency_key) makes the second audit INSERT
  fail (logged), but the handler will have run twice. Sequential replays are
  fully idempotent.
- Posting tools (`requiresPost`) additionally need the `write:post` scope —
  default-off, explicit user opt-in at consent/PAT-mint (Hein decision,
  2026-07-18 — do not re-open).
- **Ownership is the tool handler's job.** Any id an agent supplies that
  becomes a foreign key (`account_id`, `customer_id`, `entity_id`,
  `contra_account_id`, `bank_account_id`) must be checked against
  `ctx.companyId` BEFORE the service call — `accountsBelongToCompany` /
  `customerBelongsToCompany` / `supplierBelongsToCompany` /
  `bankGlAccountBelongsToCompany`. The services do not re-check the tenant and
  there is no composite `(id, company_id)` FK, so nothing downstream stops a
  cross-tenant write. Refuse with the shared `NOT_FOUND` constant: a distinct
  "belongs to another company" reply is an existence oracle.
- **Every posting path stamps `mcp:<tool>:v1` AND records the actor.** Use
  `mcpPostingOpts(ctx, toolName)` from `mcpActor.ts` — never assemble the
  fields by hand. It returns `{ postingAgent, actorType: 'agent',
  actorTokenJti }`, which is both the legacy stamp and the migration-530
  columns, and is assignable straight to `JournalEntryMeta`. Service-side the
  shape is `PostingActorOpts` (`gl/journalEntryMeta.ts`), an optional
  last-positional argument on every stamping service, so non-MCP callers pass
  nothing and both actor columns stay NULL.
  `createJournalEntry` still falls back to `defaultHumanMeta(userId)` when no
  meta is passed, which labels agent work as `human:<userId>` and hides it from
  `list_agent_postings` (filters `posting_agent LIKE 'mcp:%'`). Drafts count —
  `post_journal` does not restamp.
  **`defaultHumanMeta` deliberately sets NO `actor_type`.** It is the fallback
  path: writing `human` there would turn "nobody said" into a recorded claim
  that a person typed the entry, and `audit_trail` could no longer flag it as
  an inference. NULL is resolved at read time by `resolveLegacyActorType` and
  reported as `provenance: 'derived'` with the caveat. So after W5 an AGENT
  posting is provable and a HUMAN one still is not — which is the honest state
  of the ledger, not an omission.
  Document tables carry the actor too (`create_credit_note`,
  `create_draft_invoice`, `create_supplier_invoice`): a draft posts no journal,
  so until approval the document row is the only trace of who raised it.
- **PAYG metering lives in `flowMetering.ts`, applied by `registry.call()`.**
  `TOOL_FLOW_OPERATIONS` must name EVERY registered tool — `null` for free, and
  a missing entry is a bug, not a default (a drift test fails the build).
  **Writes only** — a write costs what the equivalent `withFlowMeter` endpoint
  costs; every read is free. Full UI parity was the first cut and was reversed
  on evidence: 10-Flow reports at the endpoint's 120/min drain 1,200 Flows/min,
  exhausting a month's budget in under three minutes and 402-ing the human UI
  that shares the wallet. Corrections (`reverse_bank_allocation`,
  `undo_bank_import`) and review (`list_agent_postings`, `audit_trail`,
  `list_documents`, `get_document`, `list_unsupported_transactions`) are free —
  pricing the controls the safety model depends on would discourage using them.
  Three rules are load-bearing: the debit runs AFTER the replay check (else a
  retry bills twice); OUTSIDE the savepoint (inside it, a write-tool throw rolls
  the debit back AND the explicit refund fires, crediting twice); and the
  insufficient-Flows rejection is audited with a NULL idempotency key — the
  partial unique index has no status column and `recordToolCall` does
  `ON CONFLICT DO NOTHING`, so a rejected row carrying the key would block the
  later `'ok'` row forever and every retry would re-run the handler.
  A handler may return `billable: false` to refund a success that did no work
  (all-duplicate resend); `registry.call()` strips the flag before responding.
- Tests live in `tests/unit/mcp/` (vitest includes only `tests/unit/**`).

- **Bulk write tools are ALL-OR-NOTHING and must RETHROW mid-write.**
  `registry.call()` gives a write tool exactly ONE savepoint; a handler must not
  open its own. Because the savepoint rolls back only on a THROW, any failure
  after the first service write has to propagate — `catch → toolError` returns
  normally, the savepoint RELEASES and the transport's HTTP 200 COMMITs the
  lines already posted. Only PRE-write refusals may return `toolError`; they run
  before the first write, so there is nothing to unwind and the agent gets an
  actionable message with the offending line index.
- **A refusal is about the REQUEST; a skip is about the DATA.** That is the line
  the two shapes fall on. Shape, size, duplicate lines and cross-tenant
  ownership are faults in what the caller sent — it has to change the request,
  so they refuse the batch, and ownership answers at BATCH level so naming a
  line never becomes an existence oracle. Anything the data says about one row —
  already allocated, excluded, not importable, the reference matches no row, the
  reference matches several — is a skip, and must not cost the other 499 lines.
- **A batch skips what it cannot post; it does not fail on it.** PRD-11 §4.
  `bulk_allocate_bank_transactions` reads the CURRENT state of every resolved
  row in ONE company-scoped query (`findBankTransactionAllocationStates`)
  before it writes anything, and splits the batch: postable is
  `status='imported'` AND `matched_journal_line_id IS NULL`; everything else is
  `skipped` with `{index, transaction_id, reason}` — `already allocated`,
  `excluded`, `already allocated (excluded)` (in the ledger AND marked out of
  it — both facts, because either alone hides the other), or
  `not importable: <status>`. Both columns, never `status`
  alone: an allocated row carries the journal line the reverse tool navigates
  by, and a fixture that sets only the status passes while production fails.
  A line whose selector never resolved is skipped the same way, with
  `transaction_id: null` because there is no id to report: an unrecognised
  `bank_reference` and an ambiguous one both carry their reason (the ambiguous
  one lists its candidates, so the agent can re-issue naming one). A resolved id
  that is not in the company at all is likewise a skip, reported with the id the
  caller sent. A batch with nothing left to post returns a toolError and opens NO
  batch row — that guard, not per-line fatality, is what stops a wholly wrong
  list reading as a silent `posted: 0`.
- **A per-line failure inside a batch must not surface as GENERIC_FAILURE.**
  Anything `allocateTransaction` still throws after the pre-check is rethrown
  as `BulkAllocationLineError(index, transactionId, detail)`, and
  `registry.call()` renders that as
  `<tool> line <i> (<txid>): <detail> — batch rolled back, nothing posted`.
  Everything else on that path is unchanged (savepoint rollback, refund, audit
  `'error'` with a NULL key). The exception is narrow on purpose: index and id
  are the agent's own input, so naming them leaks nothing — and the DETAIL is
  sanitised before it gets there (`safeLineDetail`), because this is the one
  hole through which the "no SQL in a tool result" rule could be smuggled back
  out. Anything carrying a SQLSTATE (or reading like a driver message) is
  reduced to `database error <code>`; service-written messages pass through,
  capped at 200 chars. A row that is LOCKED by another request
  (`BANK_TX_LOCK_TIMEOUT`, 5s) is write-free like the race, so it is a skip
  (`locked by another request — retry`), not a batch failure. A row that becomes
  allocated BETWEEN the pre-check and its post is not a failure at all — the
  service's own guard fires after its `FOR UPDATE`, nothing was written, and it
  is counted as a skip so the batch carries on. That is why the posting loop
  opens a savepoint PER LINE (`bulk_alloc_line_<i>`, ≤31 chars): without one a
  service throw leaves the request transaction aborted and the batch cannot
  continue past a fault it is entitled to skip.
- **Savepoint names are capped at 31 characters.** `withSavepoint` validates
  `^[a-zA-Z_][a-zA-Z0-9_]{0,30}$` and THROWS otherwise, so
  `registry.savepointNameFor()` truncates `mcp_<tool>`; `mcp_bulk_allocate_bank_transactions`
  is 35 and would have failed every call before the handler ran, surfacing only
  as GENERIC_FAILURE. `registrySavepointName.test.ts` asserts the truncated
  names stay distinct — a collision would let a nested call release another
  tool's savepoint.


## Recent changes

- 2026-09-03: **The fourth attribution axis: `acting_company_id` (migration 581, all four document tables, uuid, no FK, no backfill).** The company the actor was operating FROM — the practice, on a client engagement. **A NULL is UNKNOWN, never "same company"**, and `audit_trail` reports it as three states, not two: `acting_company_known: false` and `cross_company: null`. Collapsing "not recorded" to "not cross-company" is the same lie as reporting a derived human as a recorded one. `posted_from_outside_this_company` is the client auditor's first question and is a filter of its own; it requires a RECORDED firm that differs, so rows with no recorded firm can never satisfy it and it under-reports while the write side is unbuilt. **Nothing writes the column yet** — that needs a token to carry a firm binding, which is the multi-company amendment, not this workstream. Two review fixes shipped with it: the `excludedRows` query now carries the caller's NON-actor filters (it carried none, so "manual journals with no attribution" returned the whole company), and `excludedTotal` is counted separately from the 200-row sample and handed to `buildEnvelope`, which checks `rowsTotal + excludedTotal === universeTotal` — the true identity — and sets `truncatedExcludedRows` itself — a 201st unattributed row used to vanish from every figure with nothing flagged, the completeness defect this programme exists to fix reappearing inside the completeness block. `universeTotal` is withheld only on a SELECTION — an actor, token or firm filter. A CAPPED SAMPLE IS NOT ONE: withholding it there was a local workaround for the envelope checking `excludedRows.LENGTH`, absorbed into the contract on master (`480617f5`) so every report capping a sample does not invent the workaround differently. The principle, now in CONTRACTS.md: a fault whose cause is paging is arithmetically true and tells the reader the wrong thing, and a reader who learns the signal fires for benign reasons stops seeing the real ones.

- 2026-09-03: **`audit_trail` carries three of the four attribution axes.** The auditor's line is "JE-0412 posted to <company>, by an agent, acting for <user> of <firm>, via token pat-42". Whose books is `company_id`, stated once on the response rather than on every row, because scope comes from the token and a page is never mixed. Which human is TWO people: `user_id`/`user_name` (created_by, who raised it) and `posted_by_user_id`/`posted_by_user_name` (posted_by, who committed it). They are joined by two SEPARATE outer joins on `users`, cast on the uuid side — `users.id` is `character varying(255)` while both columns are `uuid`. On production `posted_by` is set on 14,126 of 15,647 journals with five distinct values against created_by's eight, and **not one journal in any company has a poster different from its creator** — no segregation of duties anywhere, which is a finding the trail can now state. Agent-or-human and which token is `actor_type` / `actor_token_jti`. **Which firm the actor was acting for is NOT yet answerable**: `acting_company_id` does not exist in the schema. When it lands, NULL must be reported as UNKNOWN, never as "same company" — the same discipline as `actor_type`, and inferring it would be worse than admitting the gap.

- 2026-09-03: **Governance (W5): `audit_trail`, `list_documents`, `get_document`, `list_unsupported_transactions`** (67 tools — 36 read + 31 write), plus the actor propagation that is the actual fix. `audit_trail` supersedes `list_agent_postings`, which stays registered (it is on the wire) but is structurally narrow: `posting_agent LIKE 'mcp:%'` finds only what was ALREADY provable. On production Brightsphere that is 2,287 of 4,949 journals; the other 2,589 carry `human:<userId>` from `createJournalEntry`'s fallback and prove nothing. Every `audit_trail` row therefore carries `actor_provenance` (`recorded` | `derived`) and, on a derived one, `actor_caveat` — an inference presented as a fact is worse than an admitted gap, because a reader cannot tell which rows to check by hand. The `attribution` block totals recorded vs derived across the whole filtered range, which is the number that says how much of the ledger can be relied on. `universeTotal` is withheld when an `actor_type` / `token_jti` filter is applied: that result is a selection, not a census, and asserting completeness would manufacture a false fault. Postings with NEITHER column set go to `excludedRows` as `unattributed_posting` rather than into the human bucket. Documents: there are TWO stores and they are not interchangeable — `bank_transaction_attachments` (what `attach_document` writes; fenced by the parent bank transaction) and `procurement_documents` + `document_links` (fenced by `verifyEntityOwnership`, which must run BEFORE the read). Neither carries `company_id`, so there is no company-wide listing of the entity store and `list_documents` says so. All three tables hold **0 rows in production**, so `list_unsupported_transactions` currently reports every material transaction as unsupported — that is the correct answer, not a bug. Its "supporting document" means a file on the BANK TRANSACTION; evidence filed against the related invoice is a different store and is not linked.

Reads: `list_practice_clients`, `list_job_categories`, `list_work_items`, `list_time_entries`. Writes: `create_job_category`, `create_work_item`, `log_time_entry`, `submit_time_entries`. All free — the app meters neither the taxonomy nor time capture, and none posts to the ledger; pricing `create_work_item` would toll the remedy for the state that blocks time entry outright. Four things worth not re-deriving. (1) **A time entry REQUIRES a work item, and work items are never seeded** — `seedDefaultCategories` seeds categories only, so a live practice sits on N categories and zero work items and every entry is refused; production had Brightsphere on 9/0 and Dotbiz on 1/0. `list_work_items` is how an agent finds that state, `create_work_item` is the fix. (2) **`origin` is forced to `'assisted'` and never read from args** — it is the only thing separating agent-booked hours from typed ones, and the rate is resolved server-side with no `rate`/`applied_rate`/`line_total` argument existing to be supplied. (3) **Both time tools scope to `ctx.userId`.** `createPracticeEntry` already took a userId; `submitPracticeEntries` was company-scoped only, so any caller could push a colleague's drafts into approval — it now takes an optional `userId` and the tool passes it (**the REST route at `pages/api/accounting/practice/time-entries/submit.ts` still does not, and that gap is open**). `submit_time_entries` resolves ids through `getEntryStatusesByIds` (O(ids)), NOT by listing the user's entries — `listPracticeEntries` had no LIMIT at all and would have pulled a whole timesheet per call; it now takes optional limit/offset, absent binding to NULL, which Postgres reads as LIMIT ALL / OFFSET 0 so existing callers are unchanged. (4) **`entry_date` has a floor of the first day of the PREVIOUS calendar month**, overridable with `allow_backdating: true`, and the guard runs before the dry-run branch. This does NOT protect the invoice — `getWipByClient` only picks up `approved` rows and nothing an agent can call reaches `approved` (the draft→submitted→approved path needs a human; `markEntriesBilled` permanently excludes billed rows). It protects REPORTING: every figure in `practiceReportsService` windows on `te.entry_date`, so a row merely EXISTING in `draft` already restates a closed month's utilisation and recovery with no approval anywhere in the loop, and rates are date-effective so the entry silently carries that period's rate. A rolling day count was the wrong shape — 90 days on 2 September still admits early July while on 1 March it would refuse an ordinary January catch-up; periods are what the downstream code keys on, so the bound is a period. (5) **`hours` is NUMERIC(6,2) and `line_total` used to be derived in JS from the PRE-rounding value** at all three write sites, so the two columns could describe different entries: `hours: 0.004` stored as `0.00` while carrying a `line_total` of `0.004 * rate` — zero hours on the timesheet, a real charge on the invoice — and `1.999` stored as `2.00` while billing 1999. `roundHours`/`lineTotalFor` in `practiceTimeEntryTypes.ts` round to the column scale first and derive everything from that; the range check moved onto the rounded value so a sub-0.005 entry is refused rather than stored as nothing. This was reachable from the UI too (the form's `step="0.25"` is client-side only), so it was a pre-existing defect the connector merely made agent-reachable. (6) **Migration 527 puts unique indexes on `(company_id, lower(btrim(name)))` and `(company_id, category_id, lower(btrim(name)))`.** The duplicate-name pre-checks in both setup tools are read-then-write and lose under concurrency; the index is what actually holds, and a 23505 is mapped back to the duplicate refusal. A foreign `category_id` returns the shared `NOT_FOUND`, never a distinct message.
- 2026-09-02: **`list_bank_reconciliations` + `cancel_bank_reconciliation`** (50 tools — 26 read + 24 write). The UI grew a Cancel Reconciliation action for in-progress sessions; the pair mirrors it. Cancel DELETES the session and releases its transactions: rows the session MATCHED go back to `imported` with `matched_journal_line_id` cleared, while `allocated`/`provisional`/`excluded` rows keep their status and their journal and are only detached — a matched row's link is reconciliation work, an allocated row's is a posted journal, and undoing the second would orphan GL entries. Completing a reconciliation is deliberately NOT exposed: it is a sign-off a person makes on a balanced screen. The `status = 'in_progress'` filter is re-asserted in the DELETE so a concurrent complete refuses instead of being silently discarded, and a `reconciled` row under an in-progress header refuses too (it is only reachable through completion, so finding one means the data is inconsistent and releasing it would strand a terminal row). Posted adjustment journals REFUSE the cancel — deleting the session under them would leave posted journals pointing at nothing. They are found through `gl_journal_entries.source_record_id` (migration 526): `createAdjustmentEntry` used to write the reconciliation id into `source_document_id`, which has FK'd to `captured_documents` since migration 409, so every adjustment threw on insert and that path was dead until the same change moved it over. Free, like every other correction, and `dry_run` runs every guard and reports the counts without writing.

- 2026-09-02: **Credit notes over MCP — `list_credit_notes`, `get_credit_note`, `create_credit_note`, `approve_credit_note`, `cancel_credit_note`** (63 tools — 32 read + 31 write). The connector could raise invoices and bills but never correct one: the only route left was a hand-built journal, which moves the GL and not the subledger, so `aged_debtors` / `aged_creditors` keep showing the uncredited balance forever. Three things worth not re-deriving. (1) **`createCreditNote` interpolated `Number(input.supplierId)` into a UUID column** — `credit_notes.supplier_id` has referenced `suppliers(id)` as a UUID since migration 202, so every real supplier turned into NaN and Postgres refused the INSERT with `invalid input syntax for type uuid: "NaN"`. Supplier credit notes had therefore never been creatable through any caller; the 37 rows in the dev database are one day of seed data, all carrying `supplier_id` NULL and so attributable to no supplier at all. Fixed at the service, pinned by an interpolated-value assertion in `creditNoteService.test.ts` rather than a rendered string, so the coercion cannot come back unnoticed. (2) **Approving a LINKED note is not just a ledger write** — `approveCreditNote` also adds the note total to the linked invoice's `amount_paid` and lands the note in `applied`, not `approved`. One `approve_credit_note` call can therefore reduce a customer's outstanding balance, which is why it takes `write:post` and why the reply carries `applied_to_invoice_id`: an agent reading `approved` vs `applied` as cosmetic would go looking for a second apply step and double-credit the invoice. (3) **`validateCreditNoteLinks` (new `creditNoteLinkService`) checks the counterparty, not only the tenant.** Every id the tool accepts is a bare foreign key with no `(id, company_id)` constraint and the service re-reads none of them, so a note naming customer A but linked to customer B's invoice would silently pay down B's debt with A's credit. (4) **approve and cancel take a `FOR UPDATE` row lock** (`creditNoteLock.ts`, mirroring `bankTxLock.ts`). Both read `status`, refuse on the wrong one, then post and rewrite the row — a check-then-act window, and a fresh idempotency key defeats the registry's replay guard, so an agent retrying an apparently-hung call is exactly the caller that trips it. Without the lock two concurrent approvals of one draft each post a journal and each add the total to the linked invoice's `amount_paid`. The end-to-end "fire two at once" test is NOT the proof — it passes just as happily with the lock removed, because the interleaving is timing-dependent; `creditNoteLock.test.ts` pins the contract deterministically instead (a second transaction blocks, times out as `CreditNoteLockTimeoutError`, an unrelated note never blocks, and the helper refuses to run outside a request transaction where `FOR UPDATE` would release immediately). (5) **the tenant + counterparty fence lives in `createCreditNote`, not in the tool.** It started in the tool only, which left `POST /api/accounting/credit-notes` — which passes its request body straight through — able to create a note pointing at another company's customer. The tool still pre-checks so it can answer with a specific message before any write instead of a generic failure, but the service is the fence. The four `LEFT JOIN`s in `getCreditNotes` / `getCreditNoteById` are scoped `AND x.company_id = cn.company_id` for the same reason. (6) **`applied_amount` (mig 529) is what cancel reverses, never `total_amount`.** `applyCreditNoteToInvoice` credits `min(total, outstanding)`, so a note worth more than the invoice owes is only partly consumed — while cancel used to un-credit the face value, erasing real cash receipts: an invoice of 1000 with 950 paid absorbs 50 of a 115 note, and un-crediting 115 left it showing 115 outstanding against a true 50, with `GREATEST(0, …)` silently absorbing the difference. The un-apply now refuses (`AND amount_paid >= X`, zero rows → throw) rather than flooring, because flooring hides exactly the corruption worth hearing about. Note the still-open asymmetry this did NOT change: approve's auto-apply adds the full total with no cap, so a linked note larger than the invoice's outstanding balance over-applies it. (7) **every credit_notes write path takes the lock, in the same order.** `applyCreditNoteToInvoice` was missed by the first pass, so one approved note applied concurrently to two invoices was consumed twice; locking note-then-invoice everywhere also removes the deadlock a concurrent MCP cancel and UI apply would otherwise hit. The lock RESTORES `lock_timeout` on its success path only — putting that in a `finally` made the reset run on the aborted transaction after a timeout and replace `CreditNoteLockTimeoutError` with an opaque 25P02. (8) **the read tools carry `read:invoices`, and the OAuth consent screen says so.** The copy fix initially landed only in `PAT_SCOPE_META`; the screen an MCP connector actually shows still promised "create and edit invoices" while the grant could reduce receivables — `consentScopeCopy.test.ts` now fails on that drift. (9) **`create_credit_note` refuses an identical open draft.** The registry replays only on the SAME idempotency key and a timed-out agent retries with a fresh one, so nothing else stopped a second draft; harmless until both are approved, and then it is two journals against one invoice. The dedupe compares the four nullable link columns with `IS NOT DISTINCT FROM` — plain `=` finds no SUPPLIER duplicate at all, because `client_id = NULL` is never true. It lives in the tool, not the service: the REST route backs a form where a person can see their own drafts, and refusing there would obstruct a legitimate duplicate. All five tools are free: the app meters neither credit-note route, and a credit note IS a correction — the same rule that keeps `reverse_bank_allocation` free. `apply_credit_note` is deliberately NOT exposed: `applyCreditNoteToInvoice` hard-refuses supplier notes, so the tool would be an AR-only surface wearing a symmetric name.

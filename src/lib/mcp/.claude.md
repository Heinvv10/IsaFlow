# src/lib/mcp — MCP server core

## Purpose

Tenant-scoped MCP (Model Context Protocol) server internals: tool registry,
audit/idempotency, types. Exposed to clients via `pages/api/mcp/index.ts`
(Bearer-only JSON-RPC transport, dark behind the `mcp_connector` flag).

## Caller contract

- Transport builds `McpToolContext` from the authenticated request ONLY
  (`withBearerAuth`). **companyId/userId never come from tool args** — no tool
  accepts a company identifier. Cross-tenant probes must return the same
  generic "Not found" text as a genuine miss.
- All tool handlers call existing `src/modules/accounting/services/*`
  functions — tools NEVER write SQL.
- `McpRegistry.call()` fence order (tests prove handler-never-ran):
  resolve → scope → `write:post` → idempotency-key presence (write tools) →
  replay lookup → handler → audit. Rejections audit as `'rejected'`.
- Handler errors surface as a GENERIC message (no stack/SQL); audited `'error'`.

## Main signatures

```typescript
// types.ts
interface McpToolContext { userId; companyId; scopes; tokenJti; oauthAppId }

// audit.ts — persists to mcp_tool_calls (mig 507, tenant RLS, append-only)

findIdempotentReplay(companyId, tool, key): Promise<McpToolResult | null>
hashArgs(args): string   // sha256 of key-sorted canonical JSON
```

## Business rules

- Write tools REQUIRE `args.idempotency_key`; replays return the stored
  result without re-running the handler. **Only a SUCCESS THAT WROTE is stored
  under the key.** A handler refusal (`isError`) is audited `'rejected'` with a
  NULL key and no stored result — most refusals are state-dependent ("Not found" for a
  row that had not committed, "Transaction already allocated"), so the identical
  call becomes correct once the state is fixed, and a refusal wrote nothing that
  a re-run could duplicate. Stored under the key it would replay forever: the
  partial unique index has no status column and `recordToolCall` does
  `ON CONFLICT DO NOTHING`, so the row occupies the key permanently. A success
  that wrote nothing (a dry run) frees the key the same way, via
  `result.wroteNothing` — otherwise the real call, which carries the same intent
  and the same natural key, is served the preview forever.
- **A freed key makes the write-vs-refuse rule load-bearing, not stylistic.**
  Because a refusal no longer consumes the key, a handler that WRITES and then
  returns a `toolError` gets re-run by the agent's retry and writes a SECOND
  time — the savepoint only rolls back on a throw, so the first write survives
  too. So: only PRE-write validation may return `toolError`; once a service that
  can write has been called, every failure RETHROWS. Where the service raises
  its own refusals after it has begun writing (`reverseReconciledTransaction`
  posts the contra journal, then resets the row; `allocateTransaction` posts the
  entry, then updates the row), the tool answers those refusals from a READ
  first — `getBankTransactionStatus`, `getJournalEntryById` — so the precise
  message survives without a catch. `registry.test.ts` pins the registry half:
  a write-then-refuse handler runs twice on one key. Known bound: two CONCURRENT calls
  with the same key can both pass the replay lookup — the partial unique
  index on (company_id, tool, idempotency_key) makes the second audit INSERT
  fail (logged), but the handler will have run twice. Sequential replays are
  fully idempotent.
- Posting tools (`requiresPost`) additionally need the `write:post` scope —
  default-off, explicit user opt-in at consent/PAT-mint (Hein decision,
  2026-07-18 — do not re-open).
- **Ownership is the tool handler's job.** Any id an agent supplies that
  becomes a foreign key (`account_id`, `customer_id`, `entity_id`,
  `contra_account_id`, `bank_account_id`) must be checked against
  `ctx.companyId` BEFORE the service call — `accountsBelongToCompany` /
  `customerBelongsToCompany` / `supplierBelongsToCompany` /
  `bankGlAccountBelongsToCompany`. The services do not re-check the tenant and
  there is no composite `(id, company_id)` FK, so nothing downstream stops a
  cross-tenant write. Refuse with the shared `NOT_FOUND` constant: a distinct
  "belongs to another company" reply is an existence oracle.
- **Every posting path stamps `mcp:<tool>:v1` AND records the actor.** Use
  `mcpPostingOpts(ctx, toolName)` from `mcpActor.ts` — never assemble the
  fields by hand. It returns `{ postingAgent, actorType: 'agent',
  actorTokenJti }`, which is both the legacy stamp and the migration-530
  columns, and is assignable straight to `JournalEntryMeta`. Service-side the
  shape is `PostingActorOpts` (`gl/journalEntryMeta.ts`), an optional
  last-positional argument on every stamping service, so non-MCP callers pass
  nothing and both actor columns stay NULL.
  `createJournalEntry` still falls back to `defaultHumanMeta(userId)` when no
  meta is passed, which labels agent work as `human:<userId>` and hides it from
  `list_agent_postings` (filters `posting_agent LIKE 'mcp:%'`). Drafts count —
  `post_journal` does not restamp.
  **`defaultHumanMeta` deliberately sets NO `actor_type`.** It is the fallback
  path: writing `human` there would turn "nobody said" into a recorded claim
  that a person typed the entry, and `audit_trail` could no longer flag it as
  an inference. NULL is resolved at read time by `resolveLegacyActorType` and
  reported as `provenance: 'derived'` with the caveat. So after W5 an AGENT
  posting is provable and a HUMAN one still is not — which is the honest state
  of the ledger, not an omission.
  Document tables carry the actor too (`create_credit_note`,
  `create_draft_invoice`, `create_supplier_invoice`): a draft posts no journal,
  so until approval the document row is the only trace of who raised it.
- **PAYG metering lives in `flowMetering.ts`, applied by `registry.call()`.**
  `TOOL_FLOW_OPERATIONS` must name EVERY registered tool — `null` for free, and
  a missing entry is a bug, not a default (a drift test fails the build).
  **Writes only** — a write costs what the equivalent `withFlowMeter` endpoint
  costs; every read is free. Full UI parity was the first cut and was reversed
  on evidence: 10-Flow reports at the endpoint's 120/min drain 1,200 Flows/min,
  exhausting a month's budget in under three minutes and 402-ing the human UI
  that shares the wallet. Corrections (`reverse_bank_allocation`,
  `undo_bank_import`) and review (`list_agent_postings`, `audit_trail`,
  `list_documents`, `get_document`, `list_unsupported_transactions`) are free —
  pricing the controls the safety model depends on would discourage using them.
  Three rules are load-bearing: the debit runs AFTER the replay check (else a
  retry bills twice); OUTSIDE the savepoint (inside it, a write-tool throw rolls
  the debit back AND the explicit refund fires, crediting twice); and the
  insufficient-Flows rejection is audited with a NULL idempotency key — the
  partial unique index has no status column and `recordToolCall` does
  `ON CONFLICT DO NOTHING`, so a rejected row carrying the key would block the
  later `'ok'` row forever and every retry would re-run the handler.
  A handler may return `billable: false` to refund a success that did no work
  (all-duplicate resend); `registry.call()` strips the flag before responding.
- Tests live in `tests/unit/mcp/` (vitest includes only `tests/unit/**`).

- **Bulk write tools are ALL-OR-NOTHING and must RETHROW mid-write.**
  `registry.call()` gives a write tool exactly ONE savepoint; a handler must not
  open its own. Because the savepoint rolls back only on a THROW, any failure
  after the first service write has to propagate — `catch → toolError` returns
  normally, the savepoint RELEASES and the transport's HTTP 200 COMMITs the
  lines already posted. Only PRE-write refusals may return `toolError`; they run
  before the first write, so there is nothing to unwind and the agent gets an
  actionable message with the offending line index.
- **A refusal is about the REQUEST; a skip is about the DATA.** That is the line
  the two shapes fall on. Shape, size, duplicate lines and cross-tenant
  ownership are faults in what the caller sent — it has to change the request,
  so they refuse the batch, and ownership answers at BATCH level so naming a
  line never becomes an existence oracle. Anything the data says about one row —
  already allocated, excluded, not importable, the reference matches no row, the
  reference matches several — is a skip, and must not cost the other 499 lines.
- **A batch skips what it cannot post; it does not fail on it.** PRD-11 §4.
  `bulk_allocate_bank_transactions` reads the CURRENT state of every resolved
  row in ONE company-scoped query (`findBankTransactionAllocationStates`)
  before it writes anything, and splits the batch: postable is
  `status='imported'` AND `matched_journal_line_id IS NULL`; everything else is
  `skipped` with `{index, transaction_id, reason}` — `already allocated`,
  `excluded`, `already allocated (excluded)` (in the ledger AND marked out of
  it — both facts, because either alone hides the other), or
  `not importable: <status>`. Both columns, never `status`
  alone: an allocated row carries the journal line the reverse tool navigates
  by, and a fixture that sets only the status passes while production fails.
  A line whose selector never resolved is skipped the same way, with
  `transaction_id: null` because there is no id to report: an unrecognised
  `bank_reference` and an ambiguous one both carry their reason (the ambiguous
  one lists its candidates, so the agent can re-issue naming one). A resolved id
  that is not in the company at all is likewise a skip, reported with the id the
  caller sent. A batch with nothing left to post returns a toolError and opens NO
  batch row — that guard, not per-line fatality, is what stops a wholly wrong
  list reading as a silent `posted: 0`.
- **A per-line failure inside a batch must not surface as GENERIC_FAILURE.**
  Anything `allocateTransaction` still throws after the pre-check is rethrown
  as `BulkAllocationLineError(index, transactionId, detail)`, and
  `registry.call()` renders that as
  `<tool> line <i> (<txid>): <detail> — batch rolled back, nothing posted`.
  Everything else on that path is unchanged (savepoint rollback, refund, audit
  `'error'` with a NULL key). The exception is narrow on purpose: index and id
  are the agent's own input, so naming them leaks nothing — and the DETAIL is
  sanitised before it gets there (`safeLineDetail`), because this is the one
  hole through which the "no SQL in a tool result" rule could be smuggled back
  out. Anything carrying a SQLSTATE (or reading like a driver message) is
  reduced to `database error <code>`; service-written messages pass through,
  capped at 200 chars. A row that is LOCKED by another request
  (`BANK_TX_LOCK_TIMEOUT`, 5s) is write-free like the race, so it is a skip
  (`locked by another request — retry`), not a batch failure. A row that becomes
  allocated BETWEEN the pre-check and its post is not a failure at all — the
  service's own guard fires after its `FOR UPDATE`, nothing was written, and it
  is counted as a skip so the batch carries on. That is why the posting loop
  opens a savepoint PER LINE (`bulk_alloc_line_<i>`, ≤31 chars): without one a
  service throw leaves the request transaction aborted and the batch cannot
  continue past a fault it is entitled to skip.
- **Savepoint names are capped at 31 characters.** `withSavepoint` validates
  `^[a-zA-Z_][a-zA-Z0-9_]{0,30}$` and THROWS otherwise, so
  `registry.savepointNameFor()` truncates `mcp_<tool>`; `mcp_bulk_allocate_bank_transactions`
  is 35 and would have failed every call before the handler ran, surfacing only
  as GENERIC_FAILURE. `registrySavepointName.test.ts` asserts the truncated
  names stay distinct — a collision would let a nested call release another
  tool's savepoint.


## Recent changes

- 2026-09-05: **Nine tools so payroll can be run end-to-end through the connector.** The surface had `create_pay_run` and `post_payroll_journal` and nothing in between: the two steps that make a run real — creating the employees and COSTING the run — were reachable only through the browser, so an agent rebuilding a company's books stalled at the first pay run. Writes: `create_employee`, `update_employee`, `assign_employee_component`, `end_employee_component`, `calculate_pay_run`, `approve_pay_run`. Reads: `get_employee`, `list_payroll_components`, `list_employee_components`. **The trap the design turns on: `calculatePayrollRun` reads earnings from `getEmployeeComponents`, not from any field on the employee — so a run over component-less employees costs cleanly to R0 without erroring, which looks like success.** `create_employee` and `calculate_pay_run` both say so in their replies rather than letting an agent approve an empty month. `approve_pay_run` is `requiresPost` because `approvePayrollRun` approves AND posts the journal in one call — it is not a status flip; `calculate_pay_run` is not, because costing writes only run lines. Costing is deliberately re-runnable (it rebuilds lines from the CURRENT employees and components, which is how a wrong salary is corrected) and returns `PayrollRunLockedError` as a refusal while rethrowing everything else, since a returned error RELEASES the registry's savepoint and frees the idempotency key for a retry that would recompute or re-post. `id_number` (13 digits) and `tax_number` (10 digits) are shape-checked before the write because both reach EMP201 and IRP5, where a malformed one is rejected months later by someone who cannot tell which employee it came from. - 2026-09-05: **Four tools for reloading a subledger, and a cents guard that was rejecting real money.** (1) `apply_receipt_to_invoice` and `settle_by_contra` refused valid amounts: the guard was `Math.round(amount * 100) !== amount * 100`, and `282543.34 * 100` is `28254334.000000004` in IEEE-754, so a real R282,543.34 receipt came back as "more than two decimal places". `hasWholeCents` (`tools/toolHelpers.ts`) compares the two-decimal rendering back to the number instead, which is exact at every magnitude a `NUMERIC(15,2)` holds — a fixed epsilon on `amount * 100` is not, because past 1e13 the spacing between doubles already exceeds a cent. - 2026-09-02: **AP is writable and readable** — `create_supplier_invoice` + `approve_supplier_invoice` (write), `list_supplier_invoices` + `get_supplier_invoice` (read). - 2026-08-29: **a reversal's date is now a PARAMETER, and the tools say what it is.** The date a contra carries was decided entirely inside `reverseJournalEntry` — original entry date when that period is open, today when closed — as an internal local variable. No surface accepted it and no tool description mentioned it, so an agent correcting a closed month could not find out which period its correction would land in except by posting one. `reverse_bank_allocation` and `reverse_bank_allocation_batch` now take `reversal_date` (shared `REVERSAL_DATE_PROPERTY` in `allocationSchema.ts`, so both read identically), `POST /api/accounting/journal-entries-action` takes `reversal_date`, and every description states the DEFAULT as well as the override — offering the override while leaving the default unstated answers the wrong half of the question. Validation lives in ONE place, `reverseJournalEntry`, which is the only code that knows the entry being reversed: the value must be a real YYYY-MM-DD day (it reaches a DATE column, where a malformed value raises 22P02 and surfaces as a generic failure) and must not PRECEDE that entry (a correction dated before the thing it corrects is nonsense in every period-bounded report). The target date's fiscal period must also EXIST and be open, checked in the same place. That third guard was initially left to `postJournalEntry` on the reasoning that a second check could only drift — and an adversarial review proved the reasoning wrong: `postJournalEntry` guards its closed-period check behind `if (entry.fiscalPeriodId)`, and `createJournalEntry` leaves that column NULL when NO `fiscal_periods` row covers the date. A date in a fiscal year nobody has created (`9999-12-31`, or a typo'd year) therefore skipped the check and POSTED with `fiscal_period_id` NULL — permanently outside the trial balance, the VAT201 and the AFS. The NULL-period hole is older than this parameter and reachable from any `createJournalEntry` caller, but this parameter is what made an arbitrary date remotely selectable, so it is closed on that path. `no_period` and `closed` get different messages because the remedies differ (create the fiscal year vs re-open the period). All ten existing callers pass no date and are unchanged.
- 2026-08-28: **an unresolved line is SKIPPED too — not-found and ambiguous join already-allocated.** The batch still refused whole when any line's selector did not resolve: an unknown `bank_reference`, one carried by more than one transaction, or a `transaction_id` naming no row in this company. What stays fatal: malformed lines, oversize batches, duplicate lines and cross-tenant ownership — faults in the REQUEST, with ownership still answered at batch level. `nothingToPostText` is now the only guard against a wholly wrong list reading as success, and it is reached in every all-skipped case because `postable.length === 0` is checked once, after the merge. `writeBankBulkAllocate.ts` was split at the same time — `reverse_bank_allocation_batch` moved to `tools/writeBankReverseBatch.ts` — to stay inside the 300-line cap.

# Historical email addresses and migration rollout

No production query, rotation, migration or data repair has run. historical-impact.sql is a scoped read-only inventory. The normalized-address registry is global by necessity; it reports only rows inside the approved company scope and a collision boolean. Short addresses alone do not prove an attack; collisions alone do not prove which historical email was misattributed.

Before deployment, run the migration collision preflight in the authorized environment. Migration616 intentionally refuses any duplicate normalized email address, including retired rows. Do not select one tenant as the winner or delete provenance rows to force the gate green. Resolve each collision with affected owners: quarantine the ambiguous destination, establish new unique addresses, preserve original inbox/event/document identifiers and address history, and prepare a reviewed migration/repair that preserves the old address as globally reserved. Such a historical schema/data repair is not part of this code patch and needs separate authorization.

For unique legacy short addresses, plan owner-approved rotation and sender updates. Automatic mass rotation would break invoice delivery and is not authorized. For historical documents/events attached to collided addresses, review sender/recipient metadata, storage hashes and source documents before proposing any tenant reassignment. Never move financial records based on a guessed winner. Prepare exact-ID, repeat-safe changes plus an immutable rollback snapshot and verify original/destination tenant views after an authorized repair.

The code can reject ambiguous active destinations before migration succeeds. New address uniqueness depends on applying616; generation entropy alone is not a uniqueness proof. Rollback should retain the reservation index where possible; reverting the routing guard or dropping the index reopens the defect. Existing short-address and historical attribution work remain explicit dependencies.

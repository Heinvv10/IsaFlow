# K-025 — once-off payroll batches no longer recur
**Trigger.** `postBatch` copied the batch line's `effective_to` verbatim. Neither the API schema nor the batch UI ever supplies one, and `getEmployeeComponents` filters on the date window only and ignores `is_recurring`, so a once-off batch wrote an open-ended assignment that `calculatePayrollRun` paid again every period, indefinitely.
**Rule.** A once-off row closes at the end of the LINE's own `effective_from` month. That is the rule `assignComponentToEmployee` already applied, so all three writers to `payroll_employee_components` now agree and share one helper, the pure `endOfMonthIso(year, month)` from `leaveAccrualService`. Recurring rows stay open-ended and an explicit `effective_to` always wins.
**Why not the batch period end** (first attempt, corrected after review): it bounds only the tail. A line backdated to 2025-01-10 on a March batch pays January, February and March. A line dated after the period end clamps to a single day the run never evaluates, so it posts successfully and is never paid at all. The line's own month pays each of those exactly once.
**Files.** `payrollBatchService.ts` (`closeOnceOffAt`, applied in the `component_values` and `reimbursive_travel` arms). `payrollEmployeeComponentService.ts` (its private `endOfMonthIso` derived the month end with local-time accessors and rendered it with `toISOString()`, so in SAST a once-off assignment closed on the 30th of a 31-day month — now the shared UTC helper). `payPackageService.ts` (its INSERT named no `effective_to` at all, so a package row flagged once-off produced the same open-ended assignment). `tests/unit/services/payroll/payrollBatchService.test.ts` (two `postBatch` mock rows omitted the NOT NULL `period_year`/`period_month`, plus an assertion on the bound `effective_to`).
**Tests.** `tests/integration/k025-once-off-batch-recurs.int.test.ts` — 17 tests, real Postgres, real service calls: closed at month end; paid in its own period; not the next; not a year later; recurring unchanged and still paying; explicit `effective_to` kept; both travel rows (3702/3703) closed; backdated line paid once in January only; forward-dated line paid once in June and never otherwise; second tenant unaffected and cross-tenant reads empty; pay-package once-off closed while its recurring sibling stays open; re-applying a package in the same month pays the once-off once, and in a later month pays it once per apply; a row closed the day before an apply survives untouched; a future-dated row is voided rather than paid alongside; R-006 still reproduces. Unit: 3 assertions on the bound `effective_to` across the three writers. Mutation check in `green.log`.
**Pay-package supersede (found re-reviewing the previous commit).** `applyPackageToEmployee` end-dated only rows matching `effective_to IS NULL`. Once a once-off row is inserted already closed, that predicate stepped over it, so re-applying a package in the same month — the obvious way a user corrects a mistyped effective date — left two overlapping windows and paid the once-off component twice (R10 000 against a package defining R5 000). The predicate is now `effective_to IS NULL OR effective_to >= effectiveFrom`, so the apply supersedes every assignment it overlaps. Re-applying in a LATER month still leaves the earlier once-off row intact, because it closed inside its own month.
**Supersede boundaries.** A row that closed the day before the apply is left untouched; a row still open on the apply date is shortened. A row starting on or AFTER the apply date is not shortened but voided — the new `effective_to` lands before its own `effective_from`, an empty window the reader never selects. That is the idiom this table already used for open-ended rows and there is no payment effect, so it is kept rather than deleting rows, but it is now logged: `applyPackageToEmployee` warns and names the voided rows. Consequence worth knowing before someone rediscovers it as a bug: a future-dated assignment is cancelled by an earlier apply of the same package. Before the supersede predicate was widened a CLOSED future row survived, so this is a deliberate behaviour change, matching what an open-ended future row already got.
**Migration/rollback.** None. Revert the commits.
**R-006 (not fixed; confirmed still reproducing).** The batch UI defaults a line's `effectiveFrom` to the LAST day of the batch period while `calculatePayrollRun` evaluates before month end, so the line is skipped in its own period. Before this fix it leaked into every later period; now it is never paid. The final test pins that.
**Correction to the first commit's wording.** `f54247a9`'s message and the validation doc say the run evaluates at "day 28". `payrollRunService.ts:130` builds `new Date(year, month - 1, 28)` in LOCAL time and `payrollComponentService.ts:34` renders it with `toISOString()`, so the date actually queried is **day 27 in SAST** and day 28 only on a UTC or western server. Nothing in this fix depends on it — a once-off row is open for its whole month either way — but R-006 will be worked from these documents.
**Historical impact.** Every once-off batch posted before this change left an open-ended row. Read-only, NOT run against production. There is no `source_batch_id` on `payroll_employee_components`, so rows are attributed through `payroll_batch_lines`; this is still an upper bound where one employee has several batches on one component at the same `effective_from`. Verified on the fixture DB inside a rolled-back transaction: two damaged rows worth R3 000 report as 2 rows / R3 000, where a `component_id`-only join reported 4 rows / R6 000.
```sql
SELECT pb.company_id, pb.id AS batch_id, pb.description, pb.period_year, pb.period_month,
       COUNT(DISTINCT pec.id) AS open_ended_rows, SUM(pec.amount) AS amount_per_period
FROM payroll_batches pb
JOIN payroll_batch_lines pbl ON pbl.batch_id = pb.id
JOIN payroll_employee_components pec
  ON pec.employee_id = pbl.employee_id
 AND pec.component_id = pb.component_id
 AND pec.effective_from = pbl.effective_from
JOIN payroll_employees pe ON pe.id = pec.employee_id AND pe.company_id = pb.company_id
WHERE pb.status = 'posted' AND pb.is_recurring = false
  AND pb.batch_type = 'component_values'
  AND pec.is_recurring = false AND pec.effective_to IS NULL
GROUP BY 1,2,3,4,5 ORDER BY amount_per_period DESC;
```
Two damaged populations are NOT covered by that query and need their own sweep before any correction is scoped: `reimbursive_travel` batches, whose rows carry the company's 3702/3703 component ids rather than the batch's own `component_id`; and `applyPackageToEmployee` rows, which have no batch to attribute to at all (`pec.is_recurring = false AND pec.effective_to IS NULL` with no matching batch line finds them).
Closing any of these rows changes PAYE/UIF/SDL already declared on an EMP201 — an accounting decision, not a code change. Both commits change new writes only.
**Limits.** `getEmployeeComponents` still ignores `is_recurring`; adding that filter would retroactively unpay every existing open-ended once-off row, which is the same declared-payroll decision. `payrollBatchService.ts` is 585 lines against the repo's 300-line rule — pre-existing, not split here. `tests/**` is outside `tsconfig`, so the integration file is neither type-checked nor lintable in CI — structural, not introduced here.

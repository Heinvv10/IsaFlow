## PLAUSIBLE (not proven)

- **FNB PDF sign (potentially HIGH).** `utils/bankPdfParserFnb.ts:28,119-121` reads amounts with `AMOUNT_PATTERN = /[-]?\d…\.\d{2}/`, which cannot capture a `Cr`/`Dr` suffix. Sign therefore depends on a leading minus. If FNB PDFs mark credits `…Cr` and leave debits unsigned (my recollection of the layout), every debit imports as a deposit. There is no FNB fixture in `test-docs/bank-statements/`. The only tests are synthetic one-liners. No balance-delta cross-check exists (ABSA has one).
- **Trailing-minus amounts.** `utils/bankPdfParserUtils.ts:83-113` `parseAmount("1 234.56-")` returns +1234.56. The trailing minus is ignored and only ABSA Investment handles it. That affects any PDF parser layout that prints debits with a trailing minus.
- **European decimal format.** `utils/bankCsvParserUtils.ts:62-74` `parseAmount("1.234,56")` returns 1.23456. `utils/bankQifParser.ts` `parseQifAmount("1234,56")` returns 123456. Both would only bite on a dot-thousands or comma-decimal export.
- **FNB CSV is positional.** It is detected by header *names* in any order but parsed positionally (`bankCsvParserFnb.ts`: date, description, amount, balance, reference). An FNB export ordered `Date,Amount,Balance,Description,Reference` would read Balance as Amount.
- **Relink amount mismatch.** `bank/bankTransferLinkService.ts` `relinkTransferCounterparts` matches the new line's amount against the *source* line, not against `jl_mine`. A split journal paying R3k of R10k to bank B, plus an unrelated +R10k on B within two days, links that deposit to the R3k leg.
- **K-149.** The `bank_transactions` write is still skipped when no bank leg is found (`bankAllocationService.ts:453`). I found no reachable path that produces it.
- **Customer-receipt write is a savepoint, not atomic with the journal.** `bankAllocationService.ts:452-480`: the inner `withTransaction` is only a savepoint relative to the journal posted at :416-419. If `insertCustomerBankReceipt` fails with a non-contention DB error, the bank-line UPDATE rolls back and the route's blanket catch answers 400. `withAuth` then commits the posted journal, the line stays `imported` and can be allocated again. No concrete trigger found. A related shape: `bank-transactions-action` answers 400 for any refusal raised after the journal posted (R-060).
- **Batch reversal checks the journal id unlocked.** `writeBankReverseBatch.ts`. A reverse-then-reallocate in between could reverse the new journal. The window is narrow.
- **Cross-tenant created_by fallback.** `bankAllocationService.ts:436-442`, the customer-receipt `created_by` fallback, picks an arbitrary user from any tenant when `userId` isn't a UUID. Every current caller passes a UUID.
- **LLM confidence never clamped.** `aiCategorizationService.ts:104`. `persistLlmResult` can rewrite suggestion columns on already-allocated rows (labels only).
- **Two sessions on one account.** `completeReconciliation` requires GL balance = statement balance. Month-end unpresented payments or uncleared deposits in the GL therefore cannot complete without an adjustment journal that books a fake movement. This may be a deliberate design choice (balance-based rather than item-based reconciliation).

# Security, tenancy and API audit (2026-10-18)

Area: security-tenancy-api. Code audited at `origin/master` 6ee5e9108 (detached worktree). This was a read-only audit. The only database access was read-only catalog SELECTs on `isaflow_dev`. There was no prod database access. Server config was read from `/etc/nginx` and `journalctl`, read-only.

Counts: CRITICAL 0 · HIGH 3 · MEDIUM 5 · LOW 5. Separately, 2 known findings are still open and 6 items are only plausible.

I found no cross-tenant read or write, and no unauthenticated auth bypass. The HIGH findings are all role bypasses inside a tenant: a lower-privileged member of company X can do things in company X that their role is meant to forbid.

## PLAUSIBLE (not proven)

1. **Rate-limit IP key under Cloudflare.** `getClientIp` (`src/lib/rateLimit.ts:25-43`) keys on the *last* `X-Forwarded-For` entry. The site config `/etc/nginx/sites-enabled/isaflow-combined` uses `$proxy_add_x_forwarded_for`, and every app request in the nginx access log arrives from `127.0.0.1` (cloudflared). If IsaFlow traffic goes cloudflared → nginx → :3101, every client shares one key, `127.0.0.1`. The login limit (20/15 min), forgot-password, portal-auth and so on would then be global: one attacker could lock everyone out, and the per-IP brute-force limit would mean nothing. I could not see the remotely-managed tunnel ingress, and no IsaFlow requests appeared in this nginx log, so I could not confirm the path. To check, log `getClientIp` once in prod.
2. **The RLS policy is membership-wide, not active-company.** `tenant_isolation` USING is `company_id IN (SELECT company_id FROM company_users WHERE user_id = auth.uid())`. Any handler or MCP service read that forgets `company_id` would therefore return rows from the user's *other* companies. For an OAuth token consented for company A, that is a consent-scope leak into company B. My scan of `src/lib/mcp` SQL found no unscoped statement, and the sampled tools pass `ctx.companyId`, so this is latent.
3. **Signum webhook** (`pages/api/webhooks/signum.ts`). It verifies the HMAC but has no timestamp or nonce. A replayed `document.declined` sent after a document was signed resets `signum_document_id` only when the status is not `signed_off`. The impact is low, and I did not confirm Signum's retry semantics.
4. **`extension-ingest` (`withExtensionToken`).** I did not check whether the extension token path rechecks company standing, which is the S-06 class.
5. **`authenticatePortalUser`** (`src/modules/accounting/services/ar/portalService.ts:77-91`). It does not check the customer's company standing, so a suspended company's AR portal users can still log in.
6. **Flow bundle and subscription settle on `charge.success`** (`src/modules/billing/services/paystackEventHandlers.ts:180-213`). It does not compare `event.data.amount` to `amount_cents`, while the invoice path does. The amount is set server-side at initialisation, so I found no way to exploit it.

## Coverage

What I covered:
- **Auth wrappers.** I enumerated all 802 `pages/api` routes for a wrapper on the default export. The 70 routes without a standard wrapper are public-by-design or self-authenticating:
  - cron routes (13, all fail-closed with a timing-safe compare)
  - webhooks (Paystack HMAC-SHA512, Signum HMAC, Twilio `validateRequest`, Postmark and dunning secrets — all fail-closed and timing-safe)
  - the AR and AFS portals and portal invoice/pixel/pdf (64-hex tokens)
  - OAuth metadata, register and token
  - auth login/register/reset (rate-limited)
  - invite (GET public with masked email; POST `withUserAuth` with an email match)
  - payment-link (public GET by a 256-bit token, POST `withWriteAccess`)
  - health and landing-stats (S-12)
  - `withAdmin` routes (super_admin plus host gate)
- **Membership and company switching.** I read `withAuth`, `bearerPipeline` and `withUserAuth`. Membership and company standing are checked on every request under `app_user`, and the transaction commits before the response is sent. `switch-company` checks membership plus the company being live. OAuth consent checks membership for the target company.
- **Role gates.** I ran a census of mutating `withAuth` routes without a write or role gate, which led to S-03 and S-05. I also covered MCP scopes, `write:post` and the role fence (S-01), PAT and OAuth scope grants, company-users (S-04), invitations, bureau linking and the payroll route census (all per-employee GETs are gated or names-only).
- **IDOR.**
  - `tsc --noUnusedLocals --noUnusedParameters` found no unused `companyId`.
  - An AST-less scan of every `sql` template that touches the 70 non-RLS tables without `company_id` found that all 16 writes and every read are parent-verified.
  - All 235 tables with a `company_id` column have RLS (isaflow_dev).
- **SECURITY DEFINER functions.** All 31 pin `search_path` with `pg_temp` last. I read the `create_company_with_owner` and `company_member_directory` bodies.
- **NL-query.** It requires SELECT only, has a keyword denylist, a table allowlist and AST tenant-scope guard (no OR, FK-reachability from a seed), runs under `app_user` RLS with a 5s timeout, and needs write access.
- **Uploads.** Every formidable use has `maxFileSize` and `filter`. Storage paths are generated server-side, and there are no writes under `public/`.
- **Other checks.** I also checked SSRF (Twilio host allowlist, `safeFetch`), `dangerouslySetInnerHTML` (only typed SVG sinks), `sql.unsafe` sites (constants and whitelisted ORDER BY), secret-bearing columns (no SELECT * returned to clients for netcash, IMAP or bank-feed tokens), and the OAuth code exchange (atomic single-use, PKCE S256, `redirect_uri` match, refresh rotation with reuse revocation).
- **Billing.** I checked the webhook idempotency and transaction, the K-items listed above, and auto-topup (K-200 is latent: `payment_method_token` is never written).

What I did NOT cover:
- I did not do a per-route IDOR read-through of all ~650 `withAuth` handlers. I relied on RLS plus the scans above.
- I did not inspect each of the ~115 MCP tools' service functions individually; I scanned and sampled them.
- I did not cover `/api/admin/*` business logic beyond the wrapper (K-099/K-100/K-209/K-274 are known).
- I did not check the GoTrue MFA flows beyond K-001's fix, the Chrome extension pairing, or Sage-sync browser sessions.
- I made no live HTTP requests, so all triggers above come from reading the code.

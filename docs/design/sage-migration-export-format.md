# Sage migration: assumed export format and field mapping

Phase D of `docs/design/items-inventory-po-mcp.md`. Code: `src/modules/accounting/services/sage-migration/`, runner
`scripts/sage-migration/run.ts`. **The shapes below are ASSUMED from the Sage Business Cloud Accounting (South Africa,
API v2 "Sage One") documentation; no real export has been seen.** The synthetic fixture
`tests/fixtures/sage-export/sage-export.json` is the executable form of this page. Anything the real export does differently is
a parser change, not a data change: a row the parser cannot read is refused with its reasons, never guessed.

## File

One JSON object with `Items` and/or `PurchaseOrders` and NO other key (a misspelt or re-cased container, `Purchase_Orders`, `items`, is refused by name; a file with neither is refused). `Items` and `PurchaseOrders` each hold the rows as an array, as one Sage list page
(`{"$totalResults", "$startIndex", "$itemsPerPage", "$resources": [...]}`) or as an array of pages.
A page whose `$totalResults` is not the number of rows read across ALL pages (above is a partial export, below one that is not what it says; page 1 of a whole export holds fewer, so the total is never compared with one page's rows), that carries a `$`-key outside `$resources`, `$totalResults`, `$startIndex`, `$itemsPerPage`, `$next`, `$back` (a re-cased `$Next` or `$TotalResults` is refused, never ignored), that is the LAST page (or the only one) and has a `$next` link (Sage keeps `$next` on every page but the last), whose `$totalResults` / `$startIndex` is not a whole number, that starts anywhere but where the rows before it end (a first page with `$startIndex` above 0), or a first page with a `$back` link, is a partial export and the file is refused (later pages of an array of pages may carry `$startIndex` and `$back`). An ARRAY of pages must show it is one whole chain: every page but the last carries `$next`; every page carries `$totalResults` or `$startIndex`; a page that is not the last holds its `$itemsPerPage` rows (when given, a whole number); a `$next` link naming a position (`$skip`, `skip`, `$startIndex`, `startIndex` in its query) names where the rows read so far end. So is a container holding a ROW that is an array or carries a page marker (`$resources`, `$next`, `$totalResults`, `$startIndex`, `$back`, in any case): a nested page, whose rows would otherwise vanish into one bad row. Fields not listed below are ignored, but a field listed below spelled any other way (keys compared normalised: NFKC, lower case, letters and digits only, so `ItemID`, `lineType`, `category`, `taxTypeIdSales`, `LineType ` with a space, `Line_Type`, a dotted I or a zero-width character; inside `Category` too) refuses the row: it is never read as if the field were absent. Money is a JSON number.

## Purchase order (`PurchaseOrders`)

| Sage field | Rule | IsaFlow |
|---|---|---|
| `ID` | required | `external_ref` (`sage`) |
| `DocumentNumber` | required, unique in the file | `po_number`, `external_document_number` |
| `Date`, `DeliveryDate` | `YYYY-MM-DD` or an ISO date-time; Date required. A date-time with a Z or an offset is converted to the Johannesburg (UTC+2) date: `2026-03-04T22:00:00Z` is 2026-03-05; with no zone it is taken as written | `order_date`, `delivery_date` |
| `Status` | Pending, Overdue, Invoiced, Cancelled (any case) | open, open, billed (= closed), cancelled; any other is refused. How Pending/Overdue go in is the one constant `OPEN_SAGE_PO_IMPORTED_AS` (`sagePoStatus.ts`; `draft` is the alternative) |
| `Currency`, `CurrencyId`, `ExchangeRate` and any field with "currency" or "exchange" in its name | none, or ZAR / rate 1. Anything else is refused as `foreign_currency` (a `CurrencyId` passes only beside a field saying ZAR: its ids are Sage's) | |
| `Reference`, `Comments` | optional | `reference`; `notes` = "Sage status: X" + comments |
| `SupplierId`, `SupplierName` | `SupplierId` required | `supplier_id`: found by Sage reference on the supplier, else by exact name; unresolved or ambiguous refuses the PO |
| `Exclusive`, `Tax`, `Total` | required, whole cents, Exclusive + Tax = Total | `expected_totals` (checked by the tool to the cent) |
| `PdfFile` | optional file name of the PO's PDF | listed in the report; **not uploaded by the runner** |
| `Lines[]` | at least one | `lines` |
| `Lines[].Description`, `Quantity` (> 0, 2 dp), `UnitPriceExclusive` | required | `description`, `quantity`, `unit_price` |
| `Lines[].TaxPercentage` / `TaxTypeId` | one of them; both must agree. The rate is the one that applied on the PO date: standard 14% before 2018-04-01, 15% from then; a percentage is that rate or 0, any other is refused | `tax_rate` |
| `Lines[].Exclusive`, `Tax` | optional, whole cents | `line_total`, `tax_amount` |
| `Lines[].Total` | optional, whole cents; with `Tax`, it is `Exclusive + Tax`; without `Tax`, it is `Exclusive` + the tax the PO tool computes at the line rate (its own `lineCents`) | checked only |
| `Lines[].Tax` / `Total` WITHOUT `Exclusive` | refused: the tool would book the line at quantity x price, dropping Sage's figure (round 13, B13-1) | never |
| `Lines[].UnitPriceInclusive` | optional; when given it must be `UnitPriceExclusive` at the line rate, to 1 cent either way (8.70 ex VAT is 10.005 incl: a source rounds it either way; round 15, R15-M1); with no line `Tax`, also what the tool books: net + tax = cents(Quantity x UnitPriceInclusive) (round 14, B14-1) | checked only |
| `Inclusive` (the PO) | optional, true or false (anything else refused). When true (a VAT-inclusive Sage document) every line must give its own `Exclusive` and `Tax`: the PO tool takes a line's tax the exclusive way, round(net x rate), where Sage takes it out of the gross, which can be a cent off each way while the header totals still agree (B14-1). Refused rather than sent as the tool's own `inclusive: true`: that rule is not proven to be Sage's | checked only |
| `SubTotal`, `AmountDue` (the PO) | optional, whole cents; `SubTotal` must be `Exclusive`; `AmountDue` must be `Total` on an OPEN PO (Pending / Overdue; anything else is a PO with payments or credits against it: `po_money_field_unsupported`); on an Invoiced or Cancelled PO it is not checked (it may show 0 due) | checked only |
| a discount: any key holding `disc`, `markdown`, `allowance`, `percentoff` or `rebate` (so `Discount`, `DiscountPercentage`, `DiscountAmount`, `Disc%`, `TradeRebate`), on a line, the PO or an item, any spelling (keys are compared by `fieldKey`, which drops case, separators and accents: `Discöunt` is `discount`) | 0, absent or blank (also `0%`, `0,00`, `-0.00`): ignored. Anything else refuses the row: `po_discount_unsupported` (the PO) or `item_discount_unsupported` (the item), naming the field and value; a key only NAMED like a discount (`Disc%`, `Discontinued`) is worded "a field named like a discount (<key>) is not read". A discount is not imported, and dropped it would book the undiscounted figures | never |
| any other key on a PO or a line that looks like money (`amount`, `price`, `total`, `surcharge`, `charge` in its name) and is not a field above | 0, absent or blank: ignored; anything else refuses the PO (`po_money_field_unsupported`; the reason says to add the field, with its check, to the reviewed list in `sageMoneyFields.ts` if the real export carries it) | never |
| `Lines[].ItemId` (alias `SelectionId`) | optional; must be an item in the file | `item_code` on the line (links `po_items.item_id`), see below |
| `Lines[].LineType` | optional; **ASSUMED, unconfirmed against a real export**: Sage One API v2 `PurchaseOrderLine.LineType`, 0 = item line, 1 = account line. Absent, null or 0: an item line, as above (`""` is not: it is refused like any other value). 1: the PO is refused (`po_account_line_unsupported`, naming the account id): its SelectionId is a ledger ACCOUNT and Sage numbers entity types separately, so it can equal an item's id. Any other value: refused (`po_line_type_unknown`). A line that is not known to be an item is never linked to one | the line is read, never linked, when refused |

**Item links.** `bulk_create_purchase_orders` takes `item_code` on a line and refuses the WHOLE batch for an unknown, inactive or other-company
item, so the plan sends `item_code` only for an item it knows is active and sent in this run, or already present, owned by Sage and active
(then BY ITS ID: a code stored with whitespace is trimmed by the PO tool and could resolve to another item, or to none, which fails the whole batch; item codes are compared trimmed throughout the plan). Any other line goes WITHOUT `item_code`, keeps " [item CODE]" in its description (the Sage
code stays readable) and is counted in the report as "line not linked: item inactive" or "item refused"; one such line cannot cost its
batch. A linked line has no suffix. An item the export does not contain still refuses the PO (`line_item_unknown`). A PO found already
there is never changed, so re-running a file imported before the links existed (or while the item was inactive) lists each new link as a
difference (`lines[i].item_id`) rather than adding it. The report's line count is therefore MEASURED in the books after a live run, for the
POs that run created (a dry run reports what the plan would link, labelled planned); POs already there are listed as such and add nothing.
Lines not linked are informational: they never change the exit code or block `--live`, because the Sage item code stays readable in the
description and nothing is lost (an inactive item named on an old PO is common in Sage, and making every such run exit 1 would only teach
people to pass the allow flags without reading).

## Refusals

A row is refused with a code and every reason:
- Row and file shape: `invalid_row`, `duplicate_id`, `duplicate_code`, `duplicate_number`, `category_description_conflict`,
  `category_name_collision`, `unknown_status`, `foreign_currency`, `invalid_text` (a NUL byte or a lone surrogate in a text field: item
  Code / Description / category, PO DocumentNumber / Reference / Comments / supplier name / line description).
- PO lines and items: `line_item_unknown` (a line names an item the export does not contain), `line_item_refused` (a line names an item
  that is refused AND has no readable Code to name it by; a refused item WITH a readable code does not refuse the PO, its line goes
  unlinked), `line_description_too_long` (an UNLINKED line's description with its " [item CODE]" passes 500: nothing is cut),
  `po_account_line_unsupported` / `po_line_type_unknown` (a line whose `LineType` is 1 = account, or not 0 / 1: never linked to an item; the mapping is assumed),
  `po_discount_unsupported` / `po_money_field_unsupported` (a discount, or another money field this import does not read, that is not zero); an item: `item_discount_unsupported`.
- Suppliers: `supplier_unresolved`, `supplier_ambiguous` (also when a name search hits its 1000-row cap), `supplier_ref_conflict` (the
  supplier of that name already carries another Sage reference), `supplier_collapsed` (two Sage suppliers resolve to one IsaFlow
  supplier), `supplier_inactive`.
- What the company already holds: `code_held_by_existing_item` (an item the migration did not import, or another Sage item, holds the
  code: the migration only ever updates an item it owns), `ref_code_conflict`, `item_deleted`, `item_has_stock_movements` (an owned item
  with stock movements would change type or tracking), `category_name_in_use` (an IsaFlow category the migration did not import holds the
  name, case-insensitively; it is never renamed or adopted) with its items `category_refused`, `po_number_taken` (another PO carries the
  number), `accountless_under_block_policy`, `po_ref_ambiguous` (the Sage PO reference is carried by more than one IsaFlow PO: none is picked), `booked_supplier_deleted` (a booked PO whose Sage supplier no longer resolves and whose booked supplier is deleted: the PO tool cannot replay it).
- The tools' own validators: `tool_refuses` (the item or PO tool's own validator).
A refused row is reported and not sent; the rest of the file goes on. A batch a tool refuses as a whole (a budget
block, a race) fails the dry run, so nothing is written; its whole message is in the report file, the console shows its start.

## Running it (local databases only)

```
DATABASE_URL=postgresql://postgres@127.0.0.1:<port>/isaflow_test bun --no-env-file scripts/sage-migration/run.ts \
  --company <uuid> --user <uuid> --file export.json [--live] [--report report.json] [--skip-budget-check] [--po-gl-account <uuid>] [--allow-refusals] [--allow-differences] [--run-tag <text>] \
  [--expect-items 383] [--expect-pos 757] [--expect-po-total 80950000.00]
```

Without `--live` it is a dry run and writes nothing. `--live` is NOT started when the dry run shows what the person did not allow: `--expect-*` figures that miss what would be sent, rows refused without `--allow-refusals`, differences without `--allow-differences` (status `live_blocked`, exit 1, nothing written). `--po-gl-account` must name an active, non-header expense account of the company (checked before the dry run). With `--live` (which needs `--expect-items` and `--expect-pos`, 0 if none, so a file that lost a container cannot pass unnoticed) it dry-runs first and goes live only if the dry run is clean. Every batch (category, item and PO) is keyed by the state of the existing rows it touches, so a re-run is a fresh call that finds them unchanged or already there (it writes nothing): a stored answer is only ever replayed for rows that are absent, never one true of an earlier state. If the rows of an earlier run were deleted since, a replayed batch is reported "replayed, rows absent" and fails, and `--run-tag <text>` imports afresh under new keys.
The runner refuses unless `DATABASE_URL` is a local throwaway database (`localGuard.ts`): host 127.0.0.1 or localhost, an
explicit port that is not the IsaFlow Supabase stack's (7770-7776), no query parameters but `sslmode`, and a database named
`isaflow_schema_fixture`, `isaflow_test` or `isaflow_sagemig_*`; `SERVICE_DATABASE_URL`, `PLATFORM_ADMIN_DATABASE_URL` and
`MIGRATION_ADMIN_DATABASE_URL` are held to the same rule when set. `--no-env-file` keeps bun from loading a `.env.local`.
Exit 0 = a clean dry run, or a live run that booked everything it sent; `--expect-*` figures must match what was sent (dry) or
booked (live); no row refused unless `--allow-refusals`; and no PO already in IsaFlow with other figures than Sage, and no owned item
that Sage's values would change, unless `--allow-differences` (a PO found already there is never changed: one Sage has since invoiced
stays as imported until a person closes it). 1 = anything else; 2 = refused start (nothing written to the books). The dry run is the live run in a rolled-back
transaction: categories, items and POs are all written live inside it, so each PO batch's budget check sees the batches before it.
`--po-gl-account` puts one expense account on every PO line so the budget check judges the lines. `--skip-budget-check` lists the POs
the check would have blocked.

A re-run sets the items and categories the migration owns back to the values it SENDS: **edits made to those fields in IsaFlow after the import
are overwritten** (the report lists each owned item and category that would change, with the fields, and the summary says so). Limit: the
tools never clear a field (a field left out keeps its value), so a value Sage has since DROPPED (a price emptied, a category removed) stays
in IsaFlow, and is not listed: the migration cannot see what it does not send.

Budget policy: a PO line with no GL account is "No budget" and is not judged, EXCEPT under the company's `block` policy, where the PO
tool refuses a whole batch for any approved (open) PO with an account-less line. The plan reads the policy and refuses each such PO
itself (`accountless_under_block_policy`), naming the remedies: `--skip-budget-check` (owner or admin), `--po-gl-account <uuid>`, or
importing open POs as drafts (`OPEN_SAGE_PO_IMPORTED_AS`). Other codes: `supplier_collapsed` (two Sage suppliers that resolve by name
to one IsaFlow supplier are both refused).

## Named limits

- **The snapshot race.** What the company already holds (item codes, PO numbers, supplier references) is read once, before the dry
  run, and the plan refuses rows against it. A writer that adds a clashing row between that read and the live batch can still make a
  tool refuse a batch. The dry run reports such a refusal and writes nothing; a live batch that hits it is reported failed with the
  tool's whole message, nothing of it written, and running again resumes.
- **Pages.** An array of pages is refused unless it shows it is one chain (`$next` on every page but the last, `$totalResults` or
  `$startIndex` on every page, full pages but the last, `$next` positions that match): a missing middle or last page is then told.
  What remains: a container of plain rows, or a single page without `$totalResults`, says nothing beyond itself, so a file cut short
  there reads as a whole, smaller export; and the chain checks trust the markers Sage wrote. `--expect-items` and `--expect-pos`
  (required with `--live`) stay the last guard: the dry run's counts must match them.
- **The PO tool's own rounding of a line with no Exclusive.** A line that gives only Quantity and UnitPriceExclusive is booked at
  cents(Quantity x UnitPriceExclusive): 3 x 33.333 is booked at R100.00 (99.999 rounded), whatever Sage's own line figure was. The
  header totals are checked to the cent (`expected_totals`), so a PO whose lines Sage rounds otherwise is refused by the tool; one
  whose header agrees is booked at the tool's rounding. Giving the line's `Exclusive` removes the question.
- **Money fields fail closed by their name.** A PO or line key whose name holds a money word and is not a field read refuses the PO
  when it is not zero, also when it is not money at all (a `ChargeCode` of "X"); a discount word inside a key refuses it as a discount
  also when it is not one (an item's `Discontinued: true`); and only discounts are checked on an item (its `PriceInclusive` and other
  unread price fields are not read and not checked). A key in look-alike letters (a Cyrillic і in `Dіscount`) is not folded to its Latin
  word and goes unseen too. A money field with no money word in its name (`Rounding`, `Afslag`) is not seen.
  The export is fixed, or the reader taught the field, never guessed.
- **A field spelled another way fails closed, also when it is harmless.** The normalised key check refuses the whole row for any key
  that is a field this import reads in another spelling, including ones that would mean the same (`Id`, `SupplierID`,
  `quantityonhand`): such a row is refused, never guessed, and the export is fixed or the reader taught the spelling.
- **Other causes that can still fail a PO batch as a whole:** a PO that is really over budget under `block` (the dry run reports it
  and nothing is written), and a supplier merged into another or deleted after the snapshot (the tool refuses the batch).
- **`--po-gl-account` posts every PO line to that one account.** It is opt-in; the default is no account, and a line with none is
  "No budget" (not judged; under `block` an approved one is refused, see above). With the flag the budget check, and so what a PO commits, is only as right as that one choice: a line
  that Sage would have coded elsewhere is judged against this account's budget.
- **The ownership window.** The dry run's item outcomes are checked against the snapshot (an item that came back `updated` for a Sage id
  the migration did not own, or `created` for one it did, fails the dry run naming the row), which closes the gap between the snapshot
  and the dry run. A writer that adds an item with an export code between the dry run and a live batch can still be overwritten by
  that batch: the tool matches by code. External systems of items and categories are compared exactly (case-sensitive `sage`), as
  those tools do; PO and supplier lookups are case-insensitive, as theirs are.
- **A booked PO whose Sage supplier no longer resolves** (renamed, merged, deactivated or deleted in IsaFlow; suppliers are matched by Sage reference, else by name) is NOT refused on a re-run: it is sent (the tool replays it) under the supplier it is booked to, and listed in `differences.purchaseOrders` as `supplier_id: Sage supplier N "name" not found in IsaFlow (...); PO is booked to <name> (<id>)`, so a real supplier move is never hidden. If the booked supplier is DELETED the tool answers Not found for the whole batch, so that PO is refused (`booked_supplier_deleted`) with the remedy (restore the supplier, or give it the Sage reference). A Sage PO reference carried by more than one IsaFlow PO (nothing makes it unique) refuses the PO (`po_ref_ambiguous`, naming the numbers). A tool answer that succeeds but is not a JSON object fails the batch.
- **Supplier carried by two live suppliers.** `find_by_external_ref` answers the first live match and lists the others; two live IsaFlow suppliers on one Sage reference refuse every PO naming it (`supplier_ambiguous`, naming both ids), never a guess.
- **A line's link follows the state the items phase leaves.** A sent item counts as active when SAGE says it is active (the item batch sets it active again, whatever IsaFlow held), so its lines are linked by code; inactive in Sage too, they go unlinked and the book's link is a listed difference. An owned item NOT sent keeps its IsaFlow state. The stored link of an owned item is looked up by its Sage reference (a rename in IsaFlow changes nothing).
- **A lost run lock stops the next batch.** The lock is asked before EVERY batch (the connection's own error flag, and one `SELECT 1` bounded by 10 s), before the live phase and between phases. A dropped connection that reports itself stops the run before the next batch; a half-open one is noticed within the timeout, so at most one batch can be in flight beyond the loss. `unlock` is bounded the same way (a dead connection cannot hang the end of the run: the connection is destroyed).
- **`--expect-po-total` before a live run** is compared with the PROJECTED booked total (the booked total of a PO already there, which an allowed difference keeps, plus the sent totals of new ones), so a run the gate lets through does not then miss its own figure (`MISMATCH purchaseOrderTotalCents: expected X, projected Y`). `--expect-items` / `--expect-pos` stay what is SENT.
- **Open question for the real export: the VAT-inclusive flag.** `Inclusive` absent is read as false (an exclusive PO). If the real
  export has no such flag, names it otherwise (`IsInclusive`), or puts it on the line, an inclusive PO's line with no Tax and no
  UnitPriceInclusive is booked the exclusive way, which can be a cent off Sage's per line (B14-1). To be confirmed beside LineType.
- **Open question for the real export: PO line types.** The assumed format has an OPTIONAL `Lines[].LineType` (0 = item, 1 = account: an assumption taken from Sage One API v2, to be confirmed against the real export; the export may name it differently or not carry it at all). With it, an account line is refused with its account id (`po_account_line_unsupported`) and any other type is refused (`po_line_type_unknown`): a non-item line is never linked to an item. WITHOUT it a line cannot be told from an item line, so a ledger-account line reads as an item whose id the export may not contain (`line_item_unknown`, the reason says so) or, worse, equals one (then it would be linked: the reason a real export's line-type field must be found before this runs on real data).
- **Open question for the real export: page metadata.** The page rules are the assumed Sage list page; they fail CLOSED where the real
  export may differ, and must be checked against one: a 1-based `$startIndex` (SData counts from 1) is refused (the first page must
  start at 0); SData page metadata such as `$url`, `$links` or `$title`, and any other `$`-key outside the known set, refuses the file
  as an unknown page key; an array of pages without `$next` on every page but the last is refused (see Named limits). If the real export
  carries any of these, the reader is taught it once confirmed, never by ignoring the key. A relative `$next` (`/items?$skip=100`) is
  read against a placeholder base; a `$next` naming a page number (`page=2`) instead of a row position is not checked.
- **Open question for the real export: its money fields.** The money-word scan refuses a PO for any unread money-like field that is
  not zero, so a real export carrying, say, `TotalInclusive` on every PO would refuse them all. That is deliberate (no override flag):
  the refusal names the field, and the FIRST real export decides the reviewed list. Each field it carries is added, with the check
  that makes it safe, to `sageMoneyFields.ts` / the parsers' `PO_FIELDS` / `LINE_FIELDS` / `sageLineMoney.ts` (as `UnitPriceInclusive`,
  `SubTotal` and `AmountDue` were: read and checked, refused only when they disagree), never dropped. Two of those checks need the real
  export too: what `AmountDue` means on an Invoiced or Cancelled PO (not checked there today), and whether Sage's `UnitPriceInclusive`
  is rounded from the untruncated unit price (then it can be a cent off cents(UnitPriceExclusive x (1 + rate)) and the PO is refused:
  fail closed until confirmed).
- **Open question for the real export: Sage's "none" ids.** An `ItemId` / `SelectionId` of 0 (or "0") or "" (or blanks), a `TaxTypeId` / `TaxTypeIdSales` / `TaxTypeIdPurchases` of 0 or "", and a `Category` that is `{}` or has `ID` 0 or "" or an empty (or blank) `Description` may mean "none" in a real Sage export. This import does NOT guess: such a row is refused (fail closed), the reason says "id 0 / empty: unknown whether Sage means none", and a person decides (an absent or null field is simply absent). Only those fields carry that reason: a row's own `ID` 0 or a `SupplierId` 0 is a plain bad id ("must be a Sage numeric id (0 is not one)"); a negative id is refused everywhere ("(negative)": a -1 SupplierId would otherwise fall to the by-name lookup). If the real export uses 0 or "" for "none", the readers must be taught it (as null) once that is confirmed.
- **A container that mixes pages and plain rows** (`[{ "$resources": [...] }, { ...row }]`) is a shape error for the whole file: the page would otherwise be read as one bad row, its rows dropped and its partial-export markers never checked.
- **After a live run** the summary says an owned item or category `was updated to Sage's values (an IsaFlow edit of these fields was overwritten)` only when the live batch that carried it is ok (checked against the books); its phase not run: `would be updated ... (not written: the items phase did not run)`; its batch rolled back (refused, or its request failed): `would be updated ... (not in the books: item batch N failed)`; its batch was answered from a STORED answer (the registry says so, `ctx.onIdempotentReplay`): `would be updated ... (not in the books: item batch N was answered from a stored answer, nothing written)`; its batch COMMITTED and then failed the check because another writer changed or removed rows of it (`changedAfterCommit`): the rows the check named (`changedRows`) `was updated to Sage's values, then changed in the books since (check)`, the others `was updated to Sage's values (another row of its batch changed since: check)`; the live answer leaves it as it was: `not updated by the live run (item batch N answered unchanged for it)`. **The rule** (round 12): every was / may have been / would be / nothing-written claim comes from the LIVE tool answer of the batch that carried the row (`sageRowWording.ts`); the dry run's answer only finds the batch of a live batch with no answer; the books check only adds "then changed". An unconfirmed COMMIT never reaches the summary: it stops the run (below). Before a live run, `would be`.
- **Duplicates behind an invalid row.** An ID, Code (item) or DocumentNumber (PO) that another row carries, valid or not, refuses every VALID row that uses it (`duplicate_id` / `duplicate_code` / `duplicate_number`, the reason says another row with it is invalid); the invalid row keeps its own `invalid_row`. A row whose ID or Code is unreadable makes no claim on any.
- **What a re-run compares of a PO already in the books.** The PO tool compares number, date, total, status and item links only. The plan keeps, for every PO it sends, the COMPLETE row set the tool would write (its own parse of the element: a line's stored unit price is net / quantity to 6 decimals, so a discount line, a 3-decimal price or a repeating price is not a false difference), and the runner compares it column by column with the same columns read from the books before the run: `purchase_orders` po_number, supplier_id, order_date, expected_delivery_date, status, subtotal, tax_amount, total, reference, external_system, external_ref, external_document_number; each line, by position, description (without its own exact " [item CODE]" suffix), quantity, unit_price, tax_rate, line_total, tax_amount, item_id (the link the plan would send: the item's id, null when unlinked) and sort_order; and the line count. Any difference is listed under `differences.purchaseOrders` (so it counts in the exit code and the live gate like the tool's own), keyed by the number the books hold, once (a fact the tool already reported is not repeated). Nothing is rewritten. **The column lists are the contract** (`sagePoContent.ts`): every column of both tables is compared or EXCLUDED with a reason (ids, who/when, goods received and invoiced since, the company scope, and the IsaFlow-owned coding of a line: gl_account_id, cc1_id, cc2_id, bu_id, which Sage has no field for, so a line a person codes in IsaFlow never blocks a re-run), and `tests/integration/sage-migration-po-columns.int.test.ts` fails when a table has a column in neither list, or when the PO tool's own INSERT writes one that is. Named limits: zero-rated versus exempt (both 0%) is neither stored nor detected (the tool stores the rate only); `notes` is excluded (people edit it, and the importer writes the Sage status text into it, which `status` covers), so a change of the Sage Comments is not detected.
- **"Already booked" is decided by the Sage reference**, as the tool replays: a booked PO renumbered in Sage (or two whose numbers were swapped) is not refused for its number, supplier or the policy; the number is a difference. `--allow-differences` and `allSentBooked` agree (by reference).
- **One Sage supplier id under several names.** Every distinct name the export gives it is searched and what they find is pooled: one IsaFlow supplier is the answer, two or more refuse all its POs (`supplier_ambiguous`), whichever row comes first.
- **A stop lists only what it can stand behind.** A batch that wrote nothing (its rows were all there) stays `answered ok, nothing new written` when one of its rows is changed or removed after its COMMIT, with what changed named; "What the batch wrote was written" only for one that wrote, and "the next phase" only where there is one (round 14, B14-2). The batches it calls committed are checked against the books first: a batch the registry answered from a stored answer whose rows are gone is listed as `replayed: rows absent, nothing written (use --run-tag ...)` (a batch the tool RAN whose rows another writer removed since is `committed (then changed or removed in the books by another writer: ...)`, never "nothing written"), and an ok batch that WROTE NOTHING (its rows were all there already and the tool answered unchanged / `written: false`, or a PO batch that answered `created: 0` without raising the counter: one that re-created a deleted PO is `committed`) as `answered ok, nothing new written`; the category and item batches are checked against what they sent too, as between the phases (`settleCommitted`); an unconfirmed batch the tool REFUSED says `the tool refused this batch (<reason>); its COMMIT was not confirmed`, never "may have been updated"; an item batch the tool UPDATED (an allowed difference, put back to Sage's values) is `committed`. A PO batch is never rewritten, so a PO batch of rows already there is listed as answered ok. Under each committed batch the stop names the owned items / categories it put back to Sage's values (`was updated to Sage's values (an IsaFlow edit of these fields was overwritten): item FIB-0002 (description)`): once they are, the dry run the message recommends no longer shows them. Under a `commit unconfirmed` batch it names what that batch may have updated, from its LIVE answer (`CommitUnconfirmedError` carries it; with none, "what it may have updated is not known (no live answer): check the books", never the dry run's), and every batch that failed before the stop is listed `failed, nothing written: <batch>: <reason>`: true because a refused batch's tool undoes its own partial write (pinned: `sage-migration-tool-savepoints.int.test.ts`) and a success that is not JSON throws inside its request, which rolls back. A stopped CLI run writes a stop report (`status: stopped`, the message, the batches) to the `--report` it created.
- **A live run needs its counts, in the runner too.** `runSageMigration` throws on `live` without `expect.items` and `expect.purchaseOrders` (the CLI needs `--expect-items` / `--expect-pos`); `liveWithoutCounts: true` is the explicit opt-out for a caller that checks the counts another way (the CLI never sets it: a unit test runs `run.ts` with `--live` and both counts against a mocked runner and reads the options back). In the summary a phase that never started (an earlier one failed) reads `not run`, not `0 batches`; every live phase's batches are checked against the books whether a sibling failed or not; a COMMIT is bounded (120 s) and a timeout is `commitUnconfirmed`, which STOPS the run at that batch, in any phase (the next batch would be checked, its budget among it, against books that may not hold it yet); a dry run prints `booked n/a, difference n/a` for the PO total and its JSON report has `bookedTotalCents` and `differenceCents` null.
- **Pool.** The run lock holds one connection for the whole run and the tool sessions need others, so a pool of fewer than 2 connections is refused at the start. The lock session also sets `idle_session_timeout` to 0 for itself (reset on unlock) and is pinged every 15 s.
- **Exit codes.** 0 = ok; 1 = not ok (blocked, refusals or differences not allowed, figures off); 2 = refused or failed to START: nothing written to the books (bad arguments, not a local database, an export that does not parse, another run holds the lock); 3 = the run finished but `--report` could not be written (the summary is printed before the report is written); 4 = the run STOPPED after its live phase started: on an error (a lost connection, a lost run lock), at a live batch whose COMMIT did not answer (listed `commit unconfirmed`; a COMMIT the server answered with an ERROR, a cancel or a deferred constraint, was rolled back: `failed, nothing written`, "the server refused the COMMIT (SQLSTATE: ...)", B28-2; only the server's own ErrorResponse counts, never a client errno, a FATAL or 40003, R29-5), on SIGINT / SIGTERM / SIGHUP, or on an uncaught error: batches may be committed, the message and the stop report list them, and a re-run resumes; also 4 when the run's own summary fails after a live run (`the live run committed; the summary failed: check the books`). **Signals and abnormal ends** (rounds 17-18): the first SIGINT / SIGTERM / SIGHUP is asked before every batch, dry and live, and before the live phase starts (in the live phase after the lock's round trip), never after the last batch (a finished run keeps its reconciliation; a signal that came after the run's last stop check is said last, after the report write, "SIGTERM came after the run's last stop check: the run finished (exit N)", and the run keeps its own exit code): the run stops there, before its next batch, through the usual stop: in the dry run or before the live phase exit 2, nothing written; after, exit 4, the stop report lists what was committed, checked against the books (when the books cannot be read after the stop, the message and the stop report's `booksNotRechecked` say the list is as the run recorded it, not re-checked). A second signal, an uncaught error or an unhandled rejection ends the run AT ONCE through one path (`terminate` in run.ts): its stop report is built from what the runner reported so far (`MigrationOptions.onProgress`, kept in `scripts/sage-migration/runState.ts`): the batches recorded, by outcome, and a batch in flight listed `commit unconfirmed`, said to be not re-checked against the books; exit 4 once the live phase started, else 2 ("nothing was written to the books"). After the run's own report is written an end at once changes neither the report nor the exit code. A stdout or stderr whose reader went away (`| head`, a dead `tee`: EPIPE) is no longer written and never ends the run; the run's report is in `--report`. A stop report that cannot be written (a full disk) is replaced once, through the same descriptor, by `{"status": "stop_report_not_written", "exitCode", "why"}`; the exit code is unchanged. A connection lost in the middle of a live batch is no crash: the run's own session listens to the client's errors. **The rule (round 22):** a loss seen BEFORE the batch's COMMIT was sent means no COMMIT was sent (pg marks such a client not queryable) and the server rolled the batch back, so the batch is `failed, nothing written` with "the connection was lost before its COMMIT was sent (...); nothing of it was written", whatever the tool answered, and the run stops there (exit 4: the live phase had started). Only a loss during or after the COMMIT is `commit unconfirmed`; it keeps the live answer: an ok one, or a refusal ("the tool refused this batch (...); its COMMIT was not confirmed: the connection was lost (...)"). A loss is a backend terminated by the server (57P01-03), pg's own "Connection terminated" (no code), or the client's error event; an 08006 or a "terminating connection" message raised by the books' own SQL on a live connection is an unconfirmed COMMIT with its raw reason. The stop message never words a live batch from the dry run's answer: an unconfirmed batch with no live answer says "what it may have updated is not known (no live answer): check the books". A connection lost in a request that commits nothing (the dry run, which WRITES and rolls back, the plan, a read; a loss first seen at its own ROLLBACK too) is `the connection to the database was lost (...) in a request that commits nothing (the dry run, which writes and rolls back, the plan or a read of the books): the server rolled it back, so nothing of it was written` (it names that request only): before the live phase a refused start (exit 2), never a dry-run batch blamed. A ROLLBACK of the plan or a read that fails for another reason (it did not answer) costs only its connection, and what the request read stands. The dry run's ROLLBACK must be confirmed: one that fails or does not answer for another reason means its writes and locks may still be held by its backend (whose pid is said, with `SELECT pg_terminate_backend(pid)`); a run that would go live refuses (exit 2, "... so the live run was not started"), while a preview, a failed dry run or a blocked one keeps its result and exit code with a `WARNING:` line saying so (B24-1); a dry run that ended on its own error says the same after that error (R24-5). **No wait of the migration is unbounded or silent** (rounds 25-26): every connection the CLI opens (the run lock's included) has TCP keepalive, a client `query_timeout` (75 s) and a `connectionTimeoutMillis` (15 s, `sagePoolConfig`), and each request sets `statement_timeout` (60 s) above its `lock_timeout` (10 s); the COMMIT bound (70 s) sits between the statement and the query timeouts, so it is the one that fires on a COMMIT. A connect that cannot be had sent nothing: before the live phase a refused start ("no connection to the database could be had (...): nothing was sent"), in a live batch a failed batch, nothing written. Once a request's connection is lost every later query of it fails at once. A read timeout in the dry run whose ROLLBACK is then not confirmed says its writes may still be held (its pid, the remedy), never "the server rolled it back", and then that nothing was written to the books and the live run was not started. A live batch lost by a read timeout is failed, nothing written, and says its backend may still hold the request's locks and the batch's key (its pid, R27-8). A cancel (57014) is told by its SQLSTATE, never by the server's message (which the server translates, B27-2): one that had run for the statement_timeout is "a statement ran past the migration's 60 s statement_timeout", one cancelled sooner (another session's `pg_cancel_backend`) is "a statement was cancelled after N s, before the migration's 60 s statement_timeout"; the session's own cancel (sent when its ROLLBACK does not answer) is neither. A stall (57014, 55P03) stops the run where it happened, as a lock wait does, whatever statement raised it: the tool's, the registry's own bookkeeping, the key lock, BEGIN or the membership query (R27-1): the live run stops (exit 4), the dry run stops at that batch. Every holder is named with its pid, application, state, transaction age and idle age, the blocker found by walking pg_blocking_pids to the root holder (a UNION on pid, so each backend is looked at once; never a waiter queued ahead of the run). Ending it is offered only for a migration transaction left open: THIS company's migration application_name (`isaflow-sage-migration:<company id>`, set on the CLI's pool; any client can set it, so it is not enough alone; another company's run never matches it, B29-3), idle in a transaction ("aborted" included) in two samples at least 2 s apart with its state unchanged, in a transaction that began before this run took its run lock; it then says its client MAY be gone (R28-4, B28-3). Any other session idle in a transaction is left to whoever owns it ("check with whoever owns it before ending it": an application's request looks just like that between two statements); one at work is waited for; one that is itself waiting on a lock is said to be waiting, never "at work", and a cycle through the run's own request is named as a deadlock the server breaks (B28-5; no deadlock_timeout value is promised: each session has its own). The server's ending of an idle transaction is said only from the holder's own role / database default (pg_db_role_setting), as a default: a session's own SET cannot be seen (R28-2, B28-4). The CLI says its stop message, its summary and its closing line before it ends the pool, and ends it bounded (5 s): a pool that does not close is said, and the process exits with the run's code. Every line the CLI says goes through one console (`scripts/sage-migration/runConsole.ts`): written with `fs.writeSync` as far as the pipe takes it, the rest queued and retried on a timer (the event loop keeps running), and every exit waits for it, so no exit drops what a lagging reader has not taken yet (B27-1). Each stream has its own budget of 30 s with NO progress (a clock deadline, reset by every byte taken; one shared queue and budget when 2>&1), so a stalled stdout never costs stderr its time (R28-1); a stream past it, or one whose reader went away (EPIPE), is given up, the rest of its output dropped, and that is said on the other stream when that is a different file, with where the report is; the exit code is never changed by it. **Ending is one act (R29-1):** the moment an end is decided (a second signal, an uncaught error, an unhandled rejection, or the run's own stop), the run is marked ended, before anything waits: no further batch is sent, the run's sessions refuse to start a request (nothing is sent), and the run's own code says, writes and decides nothing more after an end at once; the batch in flight then can only settle (finished or lost, by the usual rules): a crash waits for it, at most the query timeout + 5 s (80 s; each request of the batch is bounded, the batch as a whole is not, so past that it stays commit unconfirmed) and whatever the console's reader does, then says it and writes it into the report ("the batch in flight when the run ended, ... then committed; no batch followed it: the report says so"), or says it did not settle and stays commit unconfirmed, a settle after that neither said nor written (R30-1, L4). A rewrite that fails leaves the first stop report: the report is written at offset 0 and only then truncated to its new length, so a write refused before its first byte changes nothing, and one refused part-way is followed by the first report written back; each line says what became of the report and what the file holds (the first stop report, one written in its place when the first was itself never written, the "running" placeholder or the small note), never what is about to be tried (R30-4, B31-2, B32-1; a disk that fails in the middle of a write can still leave a mix of the two bodies, said as such: named limit). A body written whole whose truncate fails while the file grew counts as written (the file is exactly that body); one that shrank leaves the old tail, so it is a failed write. A first signal during that wait says what it waits for and how long, and that a second one ends it (B31-3); a second signal ends the process at once, the batch in flight listed commit unconfirmed (B30-2). The exit is asked for once: a later ask (the run's own stop after an end at once, the pool's timeout, a stray error) keeps the first exit code and waits the same wait, so it never cuts the stop message (R29-2); the wait has a ceiling of 120 s in all, a run that ends by itself too (R29-4, R30-3), armed once from the first ask, so an error after a natural end waits only what is left of it; past it only the streams that still have bytes queued are given up, and the cut is said on the other stream (R30-2), or, both stalled, in one notice on stderr, best effort only: its reader is stalled too, so that pipe is usually full and the notice is refused; --report holds the run then (L2, B32-2); with 2>&1 none at all. Every such notice (a stream given up or closed, the ceiling, a second signal's cut) says only where --report is, never what it holds. What it holds is said ONCE, as the console's final word, at every end (a natural end, an exit after the console drained, the ceiling, a second signal): computed after the file's last write, one non-blocking try per stream until one takes it: the live streams first (stderr, else stdout; one whose lane has nothing queued first), then those given up for a stall (a stalled pipe, 2>&1 too, still takes a short line; on a line of its own), never one that failed (EPIPE, ENOSPC); silent only when every try was refused (B35-1, R35-5). A line about a report write (the rewrite's "kept", "written back", "the report says so") says what that write did, after it, and the rewrite is the file's last write (R35-1): "--report <path> holds the run's report" only when it holds one whole, else what it holds (the "running" placeholder, the note, or "may hold a torn or partial body now (a failing disk)", which a failed fsync also says: the file is not trusted then, a named limit) and "no report of this run was written: check the books" (round 34: B33-1, B34-1). The worst case from a crash to the exit is 80 s + 120 s. A first signal while the exit waits says the run has already stopped (B29-4); only a second signal ends the process at once, with the exit code already decided, and says on the other stream how much was cut when it can (B28-1). After a finished run a second signal also exits at once (R29-9). The CLI puts fd 1 / fd 2's O_NONBLOCK back as it found them, and process.stdout / stderr.write back, when it exits or ends by itself (B29-2: a wrapper's later writers on the same pipe no longer meet EAGAIN); it sets O_NONBLOCK again before every write to a pipe, the one-try notices of the exit (a second signal's cut, the ceiling's) included, so neither a second signal nor the ceiling can wait in write(2) on a pipe another program made blocking, and it puts back only a flag still as it set it, last, after any line about a restore that failed, each restore on its own both at an exit and at a natural end, never changing the exit code (B30-1, B31-1, B32-3, B33-2). Named limits: two programs sharing one pipe change one flag between them, so the pipe may be left non-blocking after both; a CLI killed by SIGKILL or by a signal other than INT / TERM / HUP never puts it back; a foreign 'exit' listener that throws before the CLI's skips it (B30-1, B30-3, B30-4): give each run its own pipe, or --report; while it runs, the logger's writes keep node's contract (encoding, Buffers, a null chunk refused, the callback only once the chunk is written, `false` then 'drain', R29-3, R29-8). The CLI touches stdout / stderr at its start (bun then makes fd 1 / 2 non-blocking, which the bound needs) and reads the flags back; a pipe still blocking is said. Named limit (R29-7, B29-5): bun leaves a terminal in blocking mode, so on a tty a paused terminal (Ctrl-S, a stalled ssh) holds the run until it reads again; nothing is said of it on every run: give --report and redirect, or run it under tmux. **Give `--report` on a large run:** a pipe holds little (8 KiB on velo), the committed list of an exit-4 stop goes to stderr only, and a reader paused for 30 s cuts it; `--report` always holds all of it. Waits are counted only while a query (or the connect) is in flight; a half-open socket then surfaces as "Query read timeout", which counts as a lost connection (before the COMMIT: the batch failed, nothing written; at it: commit unconfirmed). A request (the run lock's connect included, R27-6) with no answer for 5 s is said on stderr every 5 s, with the backend that blocks it (pg_blocking_pids). A lock timeout (55P03) stops the dry run at the FIRST batch that met it, naming that batch, the holder's pid and the remedy (a --live run refuses its start, exit 2; a preview is `dry_run_failed`, exit 1); in the live phase a lock timeout or a held key stops the run there (exit 4, nothing of that batch written, no further batch sent). The remedy is worded by phase: a dry key can only be held by a dry transaction (end it); a live one by a live transaction that has not ended: one idle in its transaction when looked up had not received a COMMIT then (R28-3: a snapshot; check the books); one at work may be committing (do not end it); an unconfirmed COMMIT is never claimed (R27-8). A holder lookup that fails is logged and said "could not be read" (R27-7). A run refused by the run lock names the holder's pid (a dead run's connection is ended with pg_terminate_backend); a run whose run lock could not be taken (its try-lock timed out or failed) says so, that nothing was written, and the pid of its own connection, which may hold the lock until the server drops it (B28-6); a run whose run lock release was not confirmed says so with that connection's pid. **No lock wait of a migration request is unbounded** (B24-2): each request sets `lock_timeout` (10 s), and a write tool's idempotency key is taken without waiting before the tool runs: a key another session holds (typically a previous run's dry transaction left open) fails at once with "another session holds this batch's lock (likely a previous run's dry transaction, backend pid N: ...); wait or terminate it, then re-run" (before the live phase: exit 2). A replayed batch whose COMMIT is unconfirmed stays in `nothingWritten` (a replay writes no rows either way), its line saying the COMMIT was not confirmed. A signal after the run returned says the run had finished. Named limit (B29-3): the registry's batch key lock is `hashtext(text)`, 32 bits, shared by every tenant's idempotent MCP write, so two different keys can share a lock: the advice then names "a different key with the same 32-bit hash" and never offers to end another company's session; moving the registry to a 64-bit or two-key lock is left out (it changes the lock every deployed caller takes, so old and new code would no longer exclude each other during a deploy). Named limit (R23-4): "a loss seen before the COMMIT" means seen by the client; a backend that dies with no ErrorResponse (SIGKILL, a postmaster crash) and whose FIN arrives in a later read than the request's final answer leaves the loss unseen, so the COMMIT is written into the dying socket and the batch is `commit unconfirmed` (the safe direction: never "nothing written" for a COMMIT that may have been sent); if the tool's failed answer was itself that loss, it is then worded "the tool refused this batch (...)". A dry run whose ROLLBACK fails or does not answer for any reason other than a lost connection is a refused start (exit 2): "the dry run's ROLLBACK was not confirmed (...); its writes may still be held, so the live run was not started" (R23-5; the plan and the plain reads keep what they read). Named limits: SIGHUP is handled like SIGTERM, so `nohup` does not keep a live run going after a hangup (it stops before its next batch, exit 4): run it under tmux, screen or systemd-run; an exit-4 summary goes to stderr only, so with stderr closed and no `--report` the committed list reaches nobody: give `--report`; SIGKILL cannot be handled (the file keeps `running` with the pid); a first signal stops a run hung in one database wait only once that wait ends (send a second, or `timeout -k`); an export `--file` that blocks while it is read (a FIFO, a stalled mount) is read before any handler can act (the signals are queued until it is read). **`--report`** (round 16 rule, round 17 decision): it must name a path that does NOT exist. The run first checks every argument and reads the export (nothing needs the database); a refusal there writes nothing anywhere and says `(nothing written; --report <path> was not created by this run)` (an export that cannot be read or parsed is such a refusal: `--file <path> cannot be used: ...`). Then, before its first database step, it creates the path exclusively (`open 'wx'`) holding `{"status": "running", ...}`; a path that exists (the export, an earlier run's report, another tool's file, a running run's report, a symlink) is refused: exit 2, nothing written anywhere, "pick a new path or delete the old file". A placeholder that cannot be written (a full disk) removes the file it created. The run keeps that descriptor open and writes every report ONLY through it (truncate, write at offset 0, fsync): no temp file, no rename, no lookup of the path again, so it can only ever write the inode it created; if the path is moved, replaced or linked meanwhile, the run writes its own (moved or unlinked) file and never another one. So the report file exists exactly when the start got past the pure checks, and every exit after that leaves a report in it (a stop report of a refusal or a stop, the run's own report at the end). A final write that fails is said on stderr, the exit 0 becomes 3 (a 1 or a 4 stays), and the run tries once more through the same descriptor with `{"status": "report_not_written", "exitCode", "why"}`; a pool that fails to close changes neither. Named limit: a kill in the middle of a write can leave a partial (invalid JSON) file of the run's OWN inode. Also: `--report` given twice with different paths, `--report=` with no path, a value starting with `--`, and `--report` naming a `--file` are refused. A stop report lists its batches by outcome: `committed` (wrote), `nothingWritten`, `commitUnconfirmed` (a refused one among them, `toolRefused`), `failed`.
- **Flows.** Every registry tool the runner calls (`list_suppliers`, `find_by_external_ref`, `upsert_item_category`, `bulk_upsert_items`, `bulk_create_purchase_orders`) is free in `flowMetering` (`null` operation), so a dry run and a live run cost a PAYG company 0 Flows and a wallet that runs out cannot stop a run mid-way (a test asserts the wallet is unchanged). If a tool were ever metered, the debit is refunded when the call fails or its request rolls back (the dry run), but a committed batch keeps its charge.
- **Batches follow IsaFlow's state.** Every batch's idempotency key (category, item and PO: one shared salt, `stateSalt`) is salted with a hash of the state of the existing rows it touches (for a PO: the fields the PO tool compares, its line items and updated_at), so
  once a person has changed an owned item in IsaFlow the batch is not replayed from the stored answer of the run that wrote it (that would
  write nothing and leave the item as the person left it, while the dry run said it would be put back). With no owned row (a first run, or
  rows deleted) the key is the plain one, so a failed batch still resumes under its key. After the items phase the books are also checked
  against what was sent (code, active flag, type, tracking); on a mismatch the PO phase is not started. The report's differences list
  combines the dry run's findings with the live run's.
- **One run per company.** A session advisory lock is held on its own connection for the whole run, dry runs included. A second run for the
  same company is refused at its start ("another Sage migration is running for this company", exit 2) and writes nothing; other companies
  are not held up. A PO this migration already booked is never refused on a re-run for a supplier deactivated, or a budget policy turned to block, since (`supplier_inactive` and `accountless_under_block_policy` are for new POs; the tool replays the booked one), so `--expect-pos` still counts it. The lock goes with its connection if the process dies. The connection is watched: an error on it is recorded (it does not kill the process), and the run checks it before the live phase and between phases; if it is gone the run stops with "the run lock is lost" (exit 4, committed batches listed), because another run could now start.

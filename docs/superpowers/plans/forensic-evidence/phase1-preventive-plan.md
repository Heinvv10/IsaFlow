# Phase 0 preventive-control report

Baseline: `f57f71a75aa0c8ff2a0202c4b2c65d20f0de510e`. Programme: `c76b9706:docs/superpowers/plans/2026-09-09-mcp-forensic-controls.md`.

Read-only static review. Every source file in `source/` was materialized using `git show <baseline>:<path>`; it is an immutable baseline copy, not a shared-working-tree read. No tests, CI, build, database, external payment call, branch change, or repository mutation was performed. Findings below are code-confirmed where described; runtime exploitability and migrated schema behavior remain to be proved. A historical audit memory quick pass was used only to select evidence discipline, not as current findings.

## Priority findings

1. **Confirmed P0 control absence:** `services/gl/approvalService.ts:112,178,230` has no executing financial caller. Repository-wide references to `checkApproval`, `requestApproval`, `decideRequest` occur only in that service and `pages/api/accounting/approval-requests.ts`. It is currently an advisory standalone approval list. `decideRequest` checks pending status only: no requester separation, configured role, live approver membership, operation/version/expiry/consumption. Request API accepts caller-supplied rule, document ID/type and amount. Rule editing and decision API both use ordinary `withWriteAccess`, allowing manager writes.
2. **Confirmed P0 release bypass:** `pages/api/accounting/netcash/submit.ts` has authentication/CSRF but no write-role gate. Raw `payments` bypass document/beneficiary lookup entirely; batch mode reads current supplier banking and no batch approval status. `submitEftBatch` runs before submission insert; there is no durable release intent/idempotency/recovery boundary. Missing credentials return labelled mock success in `ap/netcashService.ts`; do not mistake that for external confirmation. Batch query selects `sp.amount` although batch service writes `total_amount`; schema behavior is a separate candidate requiring migration proof, not relied on to excuse the raw-array bypass.
3. **Confirmed P0 beneficiary bypass:** `core/supplierWriteService.ts:112,183` creates/updates banking through ordinary contact APIs/MCP. `core/migrationContactService.ts:147,162` independently creates/overwrites banking. `pages/api/accounting/supplier-merge.ts:63` reassigns existing payments to a target supplier, changing the future bank lookup without editing any banking column. `core/duplicateMergeService.ts` also requires merge-parent review. Guarding just the supplier editor misses old prepared batches and supplier identity reassignment.
4. **Confirmed P1 stale authority:** bearer pipeline refreshes company membership/account standing but sets `authedReq.scopes = ctx.scopes`; MCP context omits companyRole and registry enforces scopes and `write:post` only. PAT/OAuth grant revocation is checked per token lookup; role downgrade still does not attenuate an existing write scope. `withWriteAccess` is role-only; `permissionService.checkPermission` is separate and accepts caller-supplied role, immediately grants owner/admin, and ignores account-range/restrictions in enforcement. Existing connection grants are not current effective permissions.
5. **Confirmed P1 alternate posting fences:** adding approval only to `postJournalEntry` is insufficient. Direct posted writes exist in `pages/api/accounting/bank-transfers.ts:78`, `gl/assetDepreciationPosting.ts:113`, `gl/yearEndCloseService.ts:229`, and `admin/services/sageMigrationCommitService.ts:179`; AR historical import is also explicitly exempted from period guard. The first three directly insert status posted. These need shared authorization/approval/version/event execution, including deliberate historical import authority.
6. **Confirmed P1 payroll execution separation absent:** `payrollApprovalService.ts` accepts actor and changes status then posts; `payrollJournalPostingService.ts` builds a plan and uses an existing journal marker as idempotency but no independent operation approval. `writePayrollRun.ts` and `writePayroll.ts` expose both paths. Employee base salary/component/package/batch/bulk changes can invalidate a previously calculated/approved run without any shared operation-version contract.
7. **Confirmed P1 lock control gap:** `fiscalPeriodService.ts:141,172,188,207` changes close/lock/reopen/year state without shared approval and without locking the read-check-write sequence. `core/companyService.ts:123` modifies lockdown enable/date. `postJournalEntry` checks the linked fiscal period when non-null, with no period row lock or VAT/company-lockdown check. `vatPeriodLockService` stores filed-period records; it expressly does not impose a database-wide posting fence. `fiscalPeriodCloseService` readiness composition is MCP-specific; existing UI close is advisory. Do not silently convert readiness warnings into blanket blockers; mandatory authorization/approval is shared, existing attended advisory semantics can remain explicit.
8. **Confirmed transaction integration hazard:** cookie and bearer wrappers commit on HTTP <500. Several payment/action routes catch errors and return 400. New controls must run before effects or throw within service-owned savepoint; a refusal envelope after partial writes cannot be assumed to roll back. MCP registry rolls back thrown handler failures, but `isError` results are not themselves a rollback signal.

## Proposed shared interfaces for root to freeze

Paths below are proposed new paths; root owns their allocation and integration. Do not independently add migrations or modify registry/contracts.

- `src/lib/controls/contracts.ts`: `ControlPrincipal { companyId; personId; userId; channel: cookie|pat|oauth|job; connectionId?; oauthAppId?; delegatedByPersonId?; operationId; requestId }`. Built only from authenticated ALS/request or durable delegated job; never tool arguments. `personId` initially authenticated users.id; if multiple account identities can represent one person, server identity-link registry is required to prevent cross-account evasion. Token IDs never define person separation. Preserve user IDs as text, not blanket UUID cast.
- `src/lib/controls/operation.ts`: `OperationRef { kind; entityId; expectedVersion? }`, `MaterialOperation { companyId; kind; entityId; entityVersion; digest; amountMinor: string; currency; beneficiaries: Array<{ supplierId; beneficiaryVersion; fingerprint }>; policyVersion; accountingDate; relatedEntityVersions }`. Decimal amounts derive from persisted lines, checked safe integer/decimal cents, never request amount/reference. Canonical digest uses ordered keys/lines, explicit currency and account IDs, not descriptions alone. Payroll binds calculated run lines plus employee/component/package input versions.
- `src/lib/controls/permissions.ts`: `resolveEffectivePermissions(tx, principal)` and `assertEffectivePermission(tx, principal, operationPermission)`. Intersect current active membership/role capability ceiling, current explicit permission policy and granted bearer scopes; explicit deny/restrictions apply, cookie has no bearer attenuation, job has durable delegated scope. Do not let a stale explicit grant rescue viewer downgrade. Freeze compatibility for current owner/admin override deliberately, not accidentally. Approver role predicate uses current configured role rule and active account at decision AND execution.
- `src/lib/controls/approval.ts`: `inspectRequirements(tx, principal, operationRef)`; `requestOperationApproval(tx, principal, ref)` derives and persists immutable snapshot; `decideOperationApproval(tx, humanPrincipal, requestId, decision, evidenceRefs?)`; `executeControlledOperation(tx, principal, ref, approvalId?, execute)` reloads locked state, checks live permissions for requester/executor and approver, role/separation, policy/version/digest/expiry, aggregate threshold, consumes approval atomically with effect and change event. Services throw typed safe errors. Preview never reserves/consumes or creates hidden work. Approval cannot be replayed to another endpoint; stable operation kind joins alternative transports.
- `src/lib/controls/changeEvents.ts`: `recordCommittedChange(tx, {principal, entity, beforeVersion, afterVersion, protectedBefore, protectedAfter, operationId, provenance})`. Minimal Phase 1 event writer is prerequisite; outer rollback leaves no committed event. Protected bank/payroll payloads use narrow projection/encryption/redaction, not plaintext audit copies. Separate failed-attempt design belongs to root/Phase 2.
- `services/ap/beneficiaryVersionService.ts`: `getActiveVerifiedBeneficiary(tx, companyId, supplierId)` returns internal payment-use details and immutable version; `assertBeneficiaryBinding(tx, paymentIntent)` checks holds and version equality at prepare AND dispatch. Public projection returns mask/status only. Reject changed/missing snapshot on legacy prepared payments with `BENEFICIARY_REVALIDATION_REQUIRED`.
- `services/ap/paymentReleaseService.ts`: materialize immutable authorized intent and outbox payload in same transaction as approval consumption; dispatch only that payload with stable provider idempotency reference. A provider lacking guaranteed idempotency cannot be retried blindly after uncertain outcome: persist unknown, query/reconcile before further send. No external request inside rollback-dependent financial effect transaction.

Concurrency semantics: lock deterministic tenant+policy aggregation bucket(s), entity rows in sorted order, approval row, beneficiary versions and relevant period rows; use consistent ordering to avoid deadlock. Atomic compare-and-set approved/unconsumed/version checks with `RETURNING` must affect exactly one row. Consumption rolled back with failed effect. Live permission revocation linearizes against locked membership/grant/policy rows; state changed before that lock is observed, change racing after cannot overtake committed authorization. Aggregate limits use persisted committed/reserved intent amounts per configured tenant/beneficiary/currency/time bucket; do not sum just current batch or JS request amounts. Cancellation/rejection terminal for that request; new request has new ID/version. Expiry checked on database clock at execution, UTC instant independent of accounting date.

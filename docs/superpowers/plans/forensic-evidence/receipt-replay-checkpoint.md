# Shared receipt replay checkpoint

`replayKnownOperationEffect<T>(ctx, ref, effectId): Promise<T>` requires a valid context, canonical operation reference, current domain write permission and current write:post when monetary. It reads only the exact company/entity/operation/effect association. Originating approvals are located by operation ID or consumed-effect linkage; multiple associations, non-consumed status or mismatched consumed effect refuse. Approved receipts re-enter executeControlledOperation using the stored approval ID with a callback that always throws, so current original-requester grant and approver/decision authority are checked before the kernel's existing-effect branch returns. No synthetic context, approval or new effect is generated. No-approval receipts require current authority and exact immutable effect association.

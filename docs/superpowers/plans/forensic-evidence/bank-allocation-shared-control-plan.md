## Concrete immutable payload proposal for migration 638

Root reserves 638. Proposed versioned discriminated JSON body: common `{version:1,bankTransactionId,kind,description,sourceMode,ruleId?,ruleFingerprint?,lines}` plus server-derived metadata columns company/requester/grant/date/currency/amount/source fingerprint. Never accept company, actor, bank amount, original source fingerprints or arbitrary journal IDs from the request. `sourceMode` is attended/rule/gate, bound to actual principal and current persisted rule/delegation.

- account: exactly one line `{accountId,grossAmount,vatCode,cc1Id?,cc2Id?,buId?}`. Bank signed amount derives direction; grossAmount positive exact decimal string equals absolute bank amount.
- split: 1–100 ordered lines with same account shape, all positive exact cents, exact total equals absolute bank amount; reject duplicates with conflicting dimensions or unsupported VAT representation rather than silently merge.
- customer: `{customerId,applications:[{invoiceId,amount}]}` with 0–100 unique owned invoice IDs, exact positive cents, all same party/currency, applied sum <= bank receipt amount; zero applications is explicitly unapplied. Preparation fixes the selected auto-allocation result, never reruns FIFO dynamically during execution.
- supplier: analogous supplierId/applications for money out; bind verified beneficiary and target live posted invoices. No fresh external bank transfer is performed: this is accounting for imported cash, with party approval and receipt evidence retained.

All money canonical decimal strings; at most two fractional digits and explicit bounded precision (proposed18integer+2fraction digits subject to actual DB numeric limits), using Decimal precision80 for sums. Reject unsupported FX; currency derives owned bank metadata and ledger, agrees with every target. No JavaScript Number in material/effect arithmetic. Material includes exact source statement link/metadata and current bank row, account/period/company guard state, line classifications, target documents/active generated JEs and relevant observed versions. Reversal gets separate immutable `{version:1,originalIntentId,bankTransactionId,reversalDate,reason}`; exact original financial receipt is server-resolved and retained.

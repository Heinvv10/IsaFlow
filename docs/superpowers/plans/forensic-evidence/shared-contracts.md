Baseline f57f71a7. All programme requirements remain mandatory. Root owns these contracts and migrations.

## Trust and execution boundary
Authenticated person is users.id, not token ID. Company is authenticated context only; company assertions cannot select a tenant. Authoritative membership/account standing and role/grant intersection are checked in the executing transaction. A job must carry a persisted authorized operation identity and recheck it; no missing-context bypass. UI, REST, MCP and imports converge on the same services. Financial control enforcement must also cover direct SQL paths identified by the preventive matrix. No feature flag may disable mandatory controls on an alternative ingress. Existing MCP connector flag continues to govern exposure only.

An operation approval binds company, operation kind, entity ID, material version, server-derived exact decimal amount/currency, beneficiary identity/version/fingerprint, policy ID/version, requester person, expiry. Caller-provided financial facts are never authoritative. Lock authoritative parent and policy/approval rows before comparing and consuming. Reject/cancel are terminal decisions; material edit makes old approval stale; approval consumed once in same transaction as effect. Aggregate policy exposure is serialized by company/policy/beneficiary/window to resist splitting and races. Idempotent replay returns prior effect after current access check, never consumes twice. Record the execution identity and original operation version for retry correlation.

Beneficiary proposal never overwrites approved supplier banking. Proposed details are encrypted/restricted; independent authenticated verifier must link authorized evidence. Maintenance is separate explicit opt-in scope write:beneficiaries, with human role permission ceiling. A hold prevents payment preparation/release during pending verification. Prepared payment binds beneficiary version; changed version requires re-preparation/re-approval. Existing initial bank data is legacy/unverified, never fabricated verified evidence. Ordinary contact edits remain compatible.

## Durable history and jobs
Attempt admission uses own bounded connection (pool2, connect2s/query3s), tenant GUCs and no secret payload; admission fails closed before high-risk execution. Admission survives rollback. Final success must be reconciled with committed effect, never inferred from handler return. Separate immutable financial effect/idempotency records preserve retries independently of audit retention. External release consumes approval when committing immutable authorized outbox intent; dispatch rechecks actor/approver authority, holds and beneficiary versions before calling provider. A prior intent authorization is not a second consumable approval. Provider uncertainty stays unknown, with no blind retry unless provider proves idempotency; financial settlement requires observed confirmation.  Retain legacy dedup keys before disabling old lookup; no destructive history migration.

Snapshot/export/check workloads enqueue jobs. Claim transaction uses row lock + lease; retries have stable job id and no duplicate artifact. Repeatable-read starts before any source read; materialize canonical population and checks. Store canonical-data hash separately from artifact bytes hash. Export receipt HMAC key is separate from DB; DB+key administrator is outside trust boundary. Missing source bytes remain listed. GET/status never runs work.

Exception identity persists across runs; remediation requires fresh passing check and evidence, high-risk verifier differs from remediator/owner. Accepted risk is separate visible state with reason/expiry, never remediated. Recurrence reopens with immutable occurrence history.

## Concrete failing-test scenarios and limits
- Canonical fingerprint identical across key order and Date/string representation; changes on any material tenant/amount/beneficiary/policy field; reject nonfinite numbers and unsupported values rather than hash collisions.
- Generic event redaction excludes nested token/account/salary secrets; roundtrip real SQL change+event commit, injected rollback leaves neither.
- Current role downgraded before execute strips writes despite token grant; deactivated/missing/wrong-tenant principal rejected. Person U1 token2 cannot approve U1 token1 request.
- Approval edited amount/beneficiary/version/currency/policy, expired/rejected/cancelled/consumed cases refuse; U2 valid approval executes once under two simultaneous clients.
- Invocation error/success/replay has three attempts, one effect. Audit prune does not permit second effect; admission failure performs no financial mutation.
- Snapshot population501 entries/1002 lines and detector121 findings exceed pages20; counts/totals exact. Local representative performance gate: 10,000 source rows, page<=100, page p95<=2s and enqueue/status<=1s, job batch<=1000, configurable job timeout120s, failed lease recovered in <=2 lease periods. Record observed values; do not waive limits silently.

- Paths in this document are canonical; worker proposals under src/lib/controls map to services/controls. Pure principal/binding/check types in contracts.ts, permissions in src/lib/auth/effectivePermissions.ts, approval facade in services/controls/operationApprovalService.ts with implementation split by materializer/requests/execution.
- Operation vocabulary includes supplier_invoice.approve/post/cancel; supplier_payment.process/void; supplier_payment_batch.process; payment_release.dispatch; payroll_run.approve/post/reopen; payroll_compensation.change; journal.post/reverse; fiscal_period.close/lock/reopen; year.close; company_lockdown.change; vat_period.lock; beneficiary.propose/verify/activate; historical_import.post. Parent operations carry an internal transaction-bound capability for generated child journals, unavailable to user arguments; one approval authorizes its bound full multi-effect operation. Authorization alone is not a second approval consumption.
- Existing configured approval rules remain authoritative after validation/versioning; independent approval is mandatory for beneficiary activation, payment release, sensitive payroll changes and relaxing period/lockdown controls. Other financial execution evaluates matching configured rules with aggregate thresholds. Missing/unsupported rule semantics fail closed. Policy changes are themselves audited/versioned and require current owner/admin; they cannot silently invalidate a pending request into unrestricted execution.
- New-tool scope proposals in new-tools-contract-proposals.json are accepted, with domain current-permission checks additionally required even for scope-null approval_requirements. New scopes: read:approvals, write:approvals, write:beneficiaries, read:access, read:audit, write:audit, write:controls, read:payroll-sensitive. Sensitive payroll reveal requires read:payroll plus read:payroll-sensitive and current explicit permission. write:beneficiaries, write:approvals, write:audit, write:controls and read:payroll-sensitive require explicit consent; ordinary old tokens gain no implicit grants.
- Existing owner/admin broad defaults remain for ordinary accounting actions; current explicit denies apply in forensic controls. Viewer is a hard read-only role ceiling even if a custom write grant survives downgrade. Manager may do ordinary writes, but approval/release/beneficiary/sensitive payroll access needs explicit capability; configured approver role must also match current membership.
- Existing schema-compatible numeric coercions/clamped pagination remain accepted through a named per-tool compatibility table. Unsupported dry_run is rejected before dispatch. Unknown authority fields (approver_id, verified, role, tenant selectors) never become permissions. Preserve company_id as assertion-only on writes.
- Canonical data retention is immutable to app_user; privileged DB+receipt-key administrators remain outside tamper-protection promise. Failure/recovery and missing historical source coverage must be explicit in every assurance result.

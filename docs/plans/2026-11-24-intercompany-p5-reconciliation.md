## (a) What it does
A signed-in member of company S with an intercompany write role (`intercompany_user_can_write(S)`: owner / admin / manager), S having the flag, opens **Settings > Intercompany > Loan reconciliation**, picks one of S's connections and sees, for that connection, in one consistent read **as of the statement** (T = the statement's Africa/Johannesburg date, `(statement_timestamp() AT TIME ZONE 'Africa/Johannesburg')::date`; there is NO user-chosen as-of date in v1, (k).2; history is P5b):
1. **Loan balances both sides** (section (d) identity I1/I2): S's loan account balance at T, the partner X's loan account balance at T (only when `partner_state = 'ok'`, (k).1/(k).3; else "withheld: <reason>"), the difference, and the difference split into named components with counts, plus the **Unexplained** amount ((k).4). Each component lists its messages.
2. **Accepted, then undone** (the orchestrator's items 1 and 2 are ONE list with a state column): accepted allocation messages where (a) the payer's side no longer stands (voided / unapplied / journal reversed / allocation changed: possible from pre-gate history, from the #1855 window, or by `migration_admin` edits) while the receiver's clearing receipt stands = `payer_undone`; (b) the receiver's clearing receipt is cancelled / its journal chain is even while the payer's side stands = `receiver_undone` (#1833, the reverse); (c) both = `both_undone` (nets to zero; listed, not counted as an exception).
3. **Needs attention** (allocation messages): `unsent` (S as payer: a processed / reconciled payment applied to a bill that holds an ACTIVE link on this loan connection, with no `allocation` message for that `payment_allocations` row: flag was off, no session, a link confirmed later, pre-cut-over; P5 shows S's own facts (payment date, pair cut-over, payment status) and never infers which); `unlinked_partner_bill` (S as payer: a bill of the side's `supplier_id` dated on or after the pair cut-over, paid, holding no link: P4-B "Decided questions"); `pending_too_long` (pending or failed, older than 7 days); `failed` (with the stored generic `error` sentence, which both parties already read); `not_live` (pending / failed / dismissed but the payer side no longer stands: `allocation_gone` / `payment_not_posted` / `journal_reversed` / `changed` / `bill_gone`); `not_through_loan` (the payer's journal made no credit to the payer side's loan account: bank-paid; P4-D refuses it as `cash_not_through_loan`); `rejected` / `dismissed` while the payer's loan credit stands. Also listed here ((k).7, (k).8): `withdrawn`, `anomaly`, `loan_account_changed`, `timing` / `payer_timing`.
4. **Mismatches** (a column on the rows above plus their own list): `amount` (payload amount differs from the allocation row now; or a payer journal's loan credit differs from the sum of the messages standing on it: batch / partial funding, #1833 bullet 2), `currency` (payload currency not ZAR), `date` (payment date before the pair cut-over; one side's journal dated after T while the other's counts: `timing` / `payer_timing`, (k).7), `partner_document` (S as payer: the receiver's invoice named by the message is `gone` / `not_open` / `currency`, coarse word only).

S may be payer on some messages and receiver on others of the same connection (both directions are reported; `direction` = `out` when S sent it, `in` when S received it).

## (d) Consistency identities (exact to the cent). (k).4 and (k).6-(k).9 bind this section.
Notation for connection C, T = the statement's date ((k).2), session S, partner X. All balances debit minus credit, posted, entry_date <= T. A mirrored pair nets to zero (P4-D/E force the two loan accounts to opposite types). For a message m: amount a_m = round(payload.amount, 2); `out` = S pays; sgn = −1 for `out`, +1 for `in`. Per message: pc = payer_counts, lc = payer_loan_credit, rc = receiver_counts (b3).
- **I0 (row census, (k).7).** Every allocation message on C visible to S falls in exactly ONE bucket of the precedence table in (k).7, zero-amount buckets included; count of rows = count of messages. Asserted in the service; a gap is a 500 in tests, an "Unexplained (count)" line in production.
- **I1 (own ledger split).** `own_balance = own_attributed + own_other` (and the same for X). Asserted inside b4 (all three from the same lines; A_Y is a DISTINCT set). Mutation: count a member twice, red.
- **Message contribution (one formula for every bucket).** contrib_m = sgn × a_m × ([pc ∧ lc] − [rc]): the payer's loan credit stands and the receiver's loan debit does not, or the reverse. The bucket only names it; the amount never depends on the bucket, so no (status × pc × rc × lc) cell can fall through.
- **Residuals.** expected_S = Σ over S's payer messages (−a_m × [pc ∧ lc]) + Σ over S's received messages (+a_m × [rc]); residual_S = own_attributed − expected_S. residual_X likewise from `partner_balance − partner_other`. Non-zero = the journals differ from their messages (batch or part-funded journal: `payer_journal_differs`; a reversal dated before its root; #1833's reclass).
- **Unexplained (the headline, (k).4).** U = own_other + partner_other + residual_S + residual_X.
- **I2 (code assertion, not the badge).** D = own_balance + partner_balance = Σ contrib_m + U. Given I1 and the definitions this is arithmetic, so it fails only on a code defect (a lost row, a double count, a sign); a failure is a 500 in tests and, in production, logged without figures and shown as an "Unexplained (count)" line. **Badge:** "Reconciles" ONLY when D = Σ contrib_m to the cent AND U = 0; else "Unexplained R |U|" with its four parts listed.
- I3 (credit vs debit per direction) is dropped as a separate identity: it is I2 restricted to one direction and kept only as a unit test of the arithmetic.
**Worked example** (S = payer on all; T = today, 30 Nov; S's opening loan balance credit R50 000 posted by hand; X's matching opening debit R50 000 by hand):
m1 R10 000 accepted, both stand (matched); m2 R2 500 pending, S cleared (in_flight); m3 R1 200 accepted, X cancelled its receipt (receiver_undone); m4 R800 accepted, S's payment voided before the undo gate existed (payer_undone); m6 R300 bank-paid, pending (not_through_loan).
own_attributed = −(10 000 + 2 500 + 1 200) = −13 700 (m4's chain nets 0, m6 has no loan line); own_other = −50 000; own_balance = −63 700 (I1 ✓). Partner: attributed = 10 000 (m1) + 800 (m4) = 10 800 (m3's chain nets 0); other = +50 000; partner_balance = 60 800.
D = −63 700 + 60 800 = −2 900. Σ contrib = −2 500 (m2) −1 200 (m3) +800 (m4) = −2 900. U = −50 000 + 50 000 + 0 + 0 = 0: **Reconciles**.
Variant 1: X posted its opening as R49 000. partner_other = 49 000, D = −3 900, Σ contrib still −2 900, U = −1 000: **"Unexplained R1 000"** (other postings: S −50 000, partner +49 000). Variant 2: a batch journal crediting R5 000 for two pending messages of R2 000 each: residual_S = −1 000, U = −1 000, `payer_journal_differs` on both rows, no "Reconciles".

## (f) Performance, indexes, locks, snapshot consistency
- **One snapshot.** withAuth's transaction is READ COMMITTED and already started (GUCs), so REPEATABLE READ cannot be set. Instead the whole response (summary, components, the section page and its total) is ONE SQL statement: CTEs call b4 once and b3 once (`FROM public.intercompany_loan_recon_messages(...)`), join S's own message and document rows, aggregate, and window-page the section (`ORDER BY created_at, id`). In PostgreSQL a STABLE function runs on the calling statement's snapshot, so the partner's figures, the message states and S's own rows are all as of the same instant; b5 HALTS the migration if b0-b4 or any callee is not STABLE ((k).10). Separate requests (another tab or page) are separate snapshots: each response carries `readAt` = `statement_timestamp()` (NOT `now()`, which is withAuth's transaction start) and the page shows it ((k).11).
- **States vs figures.** T is today, so figures and states differ only for journals dated after today (a future-dated payment or reversal): figures and the buckets use chain length as at T; the list's state words (`payer_state`, `receiver_state`, `partner_document`) describe now. The page says "as at <T>".
- **Locks.** None: no FOR SHARE, no advisory key (the 1027 cap keys are not taken: a report must never make an accept or an undo wait), no lock_timeout change, and no call of `intercompany_in_one_group` (it is VOLATILE and takes `intercompany_lock_companies` locks: (k).10). The service tightens `statement_timeout` to 15 s, tighten-only, with the inline `set_config('statement_timeout', ..., true) ... WHERE setting = 0 OR setting > 15000` pattern of `budgets/budgetAlertCron.ts:56` / `sliceReminders.ts:87` (there is no shared helper), and maps 57014 to 503 "The report took too long; try again".
- **Indexes (no new one expected).** Messages: `idx_intercompany_messages_connection`; the `unsent` anti-join: the unique constraint `intercompany_messages_once`. Loan lines: `idx_gl_jl_account` (one account per company; never a scan of `gl_journal_lines`). Chains: `ix_gl_je_reversal_of_lookup (company_id, reversal_of_id)` plus `ux_gl_je_reversal_of`; each chain walked ONCE ((k).11). Payments / receipts / invoices by primary key; `payment_allocations` by `idx_pa_invoice` / pk. Cost is O(messages × chain depth) like 1027's cap scan (#1833 bullet 4, not re-reported). The builder EXPLAINs the statement on a dev copy (with stale stats, the plan-shape gotcha) and adds an index only if a seq scan of `gl_journal_lines` / `gl_journal_entries` appears. Hard cap: > 5 000 allocation messages on one connection is refused 422 "too many to reconcile in one view" (no partial answer that would look reconciled).

## (j) Ways the report could be wrong or leak, and how each is prevented
1. **Existence oracle on connection ids.** Any uuid that is not S's loan connection gives the same 404 body and b3/b4 zero rows; tested with C, a random id and a cash connection.
2. **Wrong perspective for a user of both companies.** No company id parameter anywhere; b3/b4 read `app.current_company_id()` and require membership; tested.
3. **Partner facts without consent or after the relationship ended.** b0 gates BOTH b4's figures and b3's partner-fact columns ((k).1): X has the flag (override else is_global, fail closed), the connection is active and group, both share a current group, X's loan account is usable and serves only this connection; tested per condition.
4. **Snapshot skew between the two companies' reads** (an accept commits between reading X's balance and reading the message states, so a cleared message looks in-flight AND counted). One statement, STABLE functions only, callees included (migration halts otherwise), `readAt` shown; tested with a hook.
5. **Double counting a journal** (a batch journal named by several messages; a receipt in two chains; a loan account shared by two connections). A_Y is a DISTINCT set of b1 members; I1 asserted; `own_loan_shared` flags S's own account and the card says S's figures include S's other connections; a shared PARTNER account withholds the partner ((k).3); mutation removes DISTINCT.
6. **Reversal chains read wrongly** (O ← R ← R2 stands again; a forged non-negating "reversal"). b1 is the 1019 walk (negation test included), consistency-tested against `chain_eff`; a forged reversal is not a member, so it lands in `other`, so in U, and is visible, never silently netted.
7. **The partner's loan account carries other postings** (interest, manual transfers). They are inside `partner_balance` / `partner_other` by design, so inside U (never "Reconciles" while non-zero): the accepted disclosure, (b4) and (k).2; the settings page's loan-account help text gains one sentence saying the partner's reconciliation reads this account's balance.
8. **Payload text treated as fact.** Payload numbers / references are display text from the sender (as in C); identities use `payload.amount` only where the guard enforced it (accepted clearings, target_ok: two lines = amount) and the payer's GL otherwise; the residual catches any difference. Partner ids in the payload are never rendered as links; S's own documents are looked up under `company_id = S`.
9. **As-of vs now confusion.** Only journals dated after today can differ; buckets use chain length AS AT T, state words are NOW, the page labels both; mutation uses "now" and goes red.
10. **Status filter drift with the trial balance.** Balances use `getPostedAccountBalance`'s exact predicate (`je.status = 'posted'`, company on line and entry) plus `entry_date <= T`; a test compares `own_balance` with the trial balance for today.
11. **A report that writes or blocks.** No locks, no advisory keys, no writes, no VOLATILE callee; tested by counts, `pg_locks` and a concurrent `FOR UPDATE`; definers registered as 'nothing'. Verified: withAuth writes nothing for this route (it matches no `AUTO_RATE_LIMIT` bucket, so no counter; `settleQuotaCharges` only refunds charges a handler registered: none), and `hasFeature` is one SELECT inside `loanClearingEnabled`'s savepoint.
12. **Silent truncation that looks reconciled.** Totals come from the full set in the same statement on every page, pagination only cuts the list; over 5 000 messages refuses rather than answering partly; a statement timeout is a 503, never an empty report.
13. **Rounding.** All money 2 dp before summing, identities in integer cents in the service; a sub-cent payload is a mismatch, not dust.
14. **Error text leaks.** Logs carry SQLSTATE only (the `loanClearingGate.ts` pattern); the API answers fixed sentences.

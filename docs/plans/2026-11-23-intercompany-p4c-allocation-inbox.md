# Intercompany P4-C: the receiver's allocation inbox (read + liveness, no posting), 2026-11-23

Parent: docs/plans/2026-11-17-intercompany-mirror-posting.md (P4). Stacked on P4-B (#1787, migration 1025). C lets the RECEIVER (issuer I) see "payment allocations" the payer P sent, and ask the database whether each is still true. **No ledger write, no draft, no clearing, no change to any document.** D (receiver clearing via `settleDocumentByContra`) is the only slice that acts on a message.

Binding rulings (orchestrator, 22:27): drafts only and never approval; `bankAllocationService` unchanged; mismatch is state on the message, no new ledger object; reversals out (#1772); a pre-cutover paired invoice or locked VAT period is REFUSED with the reason on the message (D).

## (a) Liveness definer (the #1788 M1 prerequisite)
`intercompany_allocation_message_live(p_message uuid) RETURNS TABLE(live boolean, reason text)`: SECURITY DEFINER, owner migration_admin, `search_path = pg_catalog, public, pg_temp`, REVOKE ALL FROM PUBLIC, GRANT EXECUTE to app_user only, registered in 930 `app_definer_reviews` AFTER create and owner change; tighten-only lock timeout like 1019/1025.
Caller must be the RECEIVER: session company = `to_company_id` (else one row `(false,'not_found')`, same answer for a missing, foreign or non-allocation message: no existence oracle), `auth.uid()` present. Read role only (membership), not a write role: it reads and writes nothing.
Reasons, cheapest first, first failure wins: `not_found`; `not_pending` (status not pending/failed: a handled message is not re-judged); `allocation_gone` (no `payment_allocations` row with `source_doc_id`); `changed` (the row's payment, bill or amount differs from the payload, text through `intercompany_clean_text`, money 2 dp); `payment_not_posted` (payment not processed/reconciled, deleted, or voided); `journal_reversed` (`intercompany_journal_chain_length(source_journal_entry_id, from_company)` even or NULL, or the payment's standing journal is no longer the one recorded); `bill_gone` (bill deleted or no longer the payload's bill); `link_gone` (link not active, or other side not the receiver's `issuerDocument` customer_invoice, or connection not active/loan). `ok` = `(true,'ok')`.
Dedupe: unapply then re-apply makes a NEW allocation row id and a new message; the old message answers `allocation_gone` (stale), so only one is ever live. Bank unwind plus re-allocation, void, `reverseBatch`: same (`allocation_gone`, `payment_not_posted`, `journal_reversed`). Two live messages for one payment+bill+journal are impossible because the allocation row is UNIQUE(payment_id, invoice_id) (round 1: the `duplicate` answer this once had was unreachable and is gone).
Reads P's rows FOR SHARE? No: a read of a settled fact needs no lock; D re-calls it under its own locks. C documents that the answer is advisory and D must re-check inside its transaction.

## (b) Receiver service and API (read only)
`allocationInbox.ts`: `listAllocationInbox(companyId, filter, limit, offset)` and `loadAllocationDetail`. Each item: message id, status, sender name and payment number/date/method/reference (text from payload, display only, never an identity), amount, currency, `payerDocumentNumber`, `cashLegIsLoanAccount`, the receiver's OWN issuer invoice looked up by `issuerDocument.id` under `company_id` (number, open amount, status, currency; null if gone), `live` + `liveReason` (one definer call per item, per-id savepoint, a failure shows `liveReason:'check_failed'` never throws), and a derived `mismatch` (read-only, not stored): `amount_exceeds_open` (amount > open amount), `currency` (not ZAR or differs from the invoice), `invoice_gone`, `pre_cutover_invoice` (invoice date before the connection cutover), or null. Malformed payload: listed with `blocker`, never a figure (`parseMirrorPayload` gains the `allocation` kind: strict, unknown keys ignored, money finite and positive, ids uuid).
API (GET only; both `withAuth(withErrorHandler)`): `pages/api/accounting/intercompany/allocations.ts` (`?filter=open|handled&limit&offset`) and `.../allocations/[id].ts` (detail). `inbox-count` stays invoice/credit_note only (the Bills badge counts things a person must act on; an allocation is not yet actionable): a separate `allocationCount` is returned by the allocations list.
Actions in C: reject and dismiss reuse the existing guarded status transitions (a person may reject an allocation with a reason, or dismiss it); NO accept route. `loadInboxRow` and the invoice routes keep their `kind IN ('invoice','credit_note')` filter, so accept/auto-accept stay unreachable for allocations (tested). The messages guard already lets the receiver set `accepted` by direct UPDATE on an allocation (#1788); C does not change that: D owns the transition and closes it (D's migration makes the guard require the clearing journal). C's test pins the current behaviour so D's change is deliberate.

## (g) Review round 1 (2026-11-23): supersedes the sections above where they differ
- Order: after `not_pending` the definer judges the RELATIONSHIP before any payer row (payment, bill, journal, allocation): the message's connection active and loan, and the payload's link active on it joining the payload's bill to the receiver's `issuerDocument` customer invoice, else `link_gone` (a dead relationship says nothing more specific); then the cut-over: no cut-over, or the payload's payment date before it, is `before_cutover` (one answer for both; nothing is mirrored before a cut-over the pair has set). Then `allocation_gone`, `changed`, `payment_not_posted`, `journal_reversed`, `bill_gone`, `ok`.
- No `duplicate` (unreachable: the allocation row is UNIQUE(payment, bill) and the message key names it). No lock setting in the definer: the service bounds the page's lock wait ONCE (tighten-only 2 s, restored after the checks, outside every savepoint), asks only for pending / failed rows (handled rows are `not_pending` without a call), and after the first failed call marks the rest of the page `check_failed` without asking (one wait per page at most).
- Mismatch, first that applies: `invoice_gone` (missing, deleted, cancelled), `invoice_not_open` (draft, pending approval, paid: `openAmount` null), `currency`, `pre_cutover_payment`, `pre_cutover_invoice`, `amount_exceeds_open`.
- Restore: a dismissed allocation comes back to pending (`POST allocations/[id]/restore`, the guard's dismissed -> pending, needs the connection active); Dismiss is confirmed first. Reject on a revoked connection is a 409.
- The list's `total` and `allocationCount` come from their own count (a page past the end still says how many). Buttons are named by their payment; the table has a caption; the invoice list's empty state does not say nothing is waiting while payments are listed.

## (h) Review round 2 (2026-11-23)
- Only a check that runs out of time (SQLSTATE 55P03, 57014) stops the page; any other failure is that row's `check_failed` alone. The lock setting is put back after the checks whatever they answered (no try / finally: the per-row call never throws).
- Open invoice statuses are the shared `AR_OPEN_STATUSES` (same set as before).
- UI: every button, dialog and notice names its row by payment and this company's invoice ("payment SP-1 on INV-900"; the payer's bill when the invoice is gone; "(1 of 2)" for a repeated pair, e.g. a stale and a live message of one payment). The reject dialog says the rejection is final and the reason is recorded on the message (nothing shows the payer a rejected allocation yet). Foreign amounts carry their currency code. A mismatch shows on a stale row too (a pre-cut-over payment's only beside a reason other than `before_cutover`). A failed reload keeps the list and any open dialog under an alert; a 409 reloads the list; busy is per row; a filter switch clears an old error; the payment count is kept while a list loads.
- Not in this round: one definer call per open row and the 100-row page (filed separately, L3).

# Agent workflow: Git, merges, deploys

Long-form procedure moved verbatim from `CLAUDE.md`. The prohibitions themselves stay in `CLAUDE.md`.

- **Git**: No `--no-verify`, no force-push to `master`, no amending published commits. Stage by explicit path — never `git add -A` (parallel sessions leave untracked files in the tree). **No `git stash`** — `push`, `pop`, `list`-then-`apply`, none of it: `refs/stash` is shared across every worktree, and `stash push -- <path>` creates NO entry when that path is already clean, so a paired bare `pop` silently takes whatever another session left at `stash@{0}` instead. Commit to your own branch instead — a WIP commit is cheap, reversible, and scoped to your worktree. Prefix every Bash call with an explicit `cd` to your worktree; a drifted cwd is what turns a worktree-local mistake into a cross-session one. **When reading a committed state, read it with `git show <sha>:<path>`, not from disk.** Seven worktrees are active as a matter of course and an author can commit and resume editing between your first command and your next one — on a shared worktree a clean `git status` is a fact about one instant, not a state that holds for a round; checking it once at the start of a review or a run proves nothing about the reads that follow it. This binds reviewers especially: score a named commit, not a working tree, and if you need the working tree, say so explicitly in the finding. Same hazard as the `stash` rule above, and why `git show` is the only safe read — a reviewer cannot stash the author's work to get a clean one, and should not want to.

- **Merges go through the merge queue** (Hein, 2026-10-17): master's branch protection is strict as of 2026-10-15 (`gh api repos/Heinvv10/IsaFlow/branches/master/protection`: both checks required, `strict: true`, `enforce_admins: true`). Before then it 403'd and #496 merged with Type Check FAILED. Strict means every merge turns the other open PRs BEHIND. With one self-hosted runner and Golden Paths' single pending slot (a newer pending run cancels an older one), updating several PRs at once only cancels runs. So one worker merges serially and agents only queue:
  - `mq-isa add <N>` queues a PR; `mq-isa status` shows what is in flight; `mq-isa log` lists recent events; `mq-isa remove <N>` takes a PR out of the queue (a PR already in flight finishes its run and can still merge). `add` checks nothing; the worker judges each queued PR when its turn comes. A draft, a PR stacked on another branch, or one GitHub is still computing waits. A conflicting PR, or one whose own head has failed required checks, is ejected with a comment. Queue a PR once its own CI is green or still running.
  - The worker (`systemctl --user status merge-queue-isaflow`; source `/home/hein/Workspace/merge-queue`; config `~/.config/merge-queue/isaflow.json`) updates the next PR from master, waits for `Type Check, Lint & Test` and `Golden Paths E2E (blocking)` on that exact head, then merges with the head pinned. If the base moved, GitHub refuses the merge and the worker starts that PR again (update, then test). Never merge on a check from an earlier head (R-052).
  - A **cancelled** required check (usually Golden Paths bumped out of its pending slot, but any required check counts) is re-run with `gh run rerun --failed` once its run has finished, at most twice per head. A third cancel, or a real failure, ejects the PR with a comment.
  - Batching (`maxBatch: 2`): two PRs already green on their own heads are tested together in one `merge-queue/batch-*` PR, which is one CI run for two PRs. The queue has only one run in flight either way, so batching cannot bump its own Golden Paths. A red batch is split.
  - After a merge, PRs stacked on the merged branch are retargeted to master. The worker never queues them, so `mq-isa add` a stacked PR too: it waits while its base is not master, then goes through.
  - `~/.claude/hooks/critical-guard.py` denies `gh pr merge` and `PUT …/pulls/<N>/merge` for this repo.
  - **Fallback, Hein only, from his own shell** (agents are denied `gh pr merge`; worker down or an emergency): update only the next PR (`gh api -X PUT repos/Heinvv10/IsaFlow/pulls/<N>/update-branch -f expected_head_sha=<sha>`) and wait for both checks on that exact head. `gh pr checks <N>` must show every check `pass` (a `cancelled` Golden Paths is not a pass; re-run it). Then run `gh pr merge <N> --merge --match-head-commit <full 40-char sha>`.

- **Deploys**: `bash scripts/deploy.sh` runs `bun run ci` (lint and migration naming included; `SKIP_CI=1` skips it), and first runs `scripts/check-migration-parity.ts --apply-dev` (dev vs prod vs repo; applies pending migrations to dev only, prod read-only; not skippable by `SKIP_CI`). Tradeoff: the gate updates dev *before* CI, so if CI then fails, dev can end ahead of master. A dev outage blocks every deploy; rollback uses `/home/velo/isaflow-rollback` (`scripts/rollback-deploy.sh`), not `deploy.sh`. The gate's real-database suite (`tests/integration/migration-parity-gate.int.test.ts`) needs `PARITY_TEST_PG_URL` + `PARITY_TEST_PG_DISPOSABLE=1` on a throwaway Postgres; `bun run ci`'s integration step provides both (two empty throwaway clusters it starts; on GitHub, or locally with `CI_INTEGRATION=1`), and the file header says how to run it alone. Note that deploy.sh's local `bun run ci` does not run the integration step. The script itself has **no** clock or approval check (corrected 2026-10-12: earlier text claimed a business-hours block and a lint ratchet that do not exist). The business-hours ban and Hein's per-deploy approval are rules you must follow; nothing enforces them.

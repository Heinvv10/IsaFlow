# SDL leviable amount after para 2(4) deductions — result

Commits: `223b926d1` (SDL deduction after para 2(4)), s11F cap commit, `5358dab00` (donation 4030 allowlist) on `isa/sdl-leviable-after-rfd` (not pushed, no PR).

## Found
- The reported problem is real. `calculatePayrollLine` (`payrollCalculator.ts`) added every SDL-applicable earning to `sdlLeviable` and charged 1% on it. Meanwhile PAYE subtracted `taxableDeductions` (deduction components flagged `isTaxable`) from taxable income. A pension/provident/RA deduction flagged taxable therefore lowered PAYE but not SDL, so SDL was over-charged by 1% of the deduction.
- What the PAYE path counts as "para 2(4)" is any deduction component with `isTaxable = true`, uncapped. It is applied against periodic pay first, then annual payments, and never against lump sums.
- These are **not modelled for PAYE** anywhere in the code:
  - **s11F cap:** there is no 27.5% / R430 000 logic.
  - **Employer retirement contributions** (fringe benefit plus deemed employee contribution): the calculator ignores `employer_contribution` components, and since 2026-10-25 the API refuses to create them.
  - **s18A donations through payroll.**
- `sdlEngine.ts` (1% plus the threshold) and `sdlLeviabilityService.ts` (the threshold estimate) were correct for whatever base they were given. The defect was the base.

## Changed (commit 2 — s11F cap for SDL)

A Codex review found that the original fix still over-charged SDL when retirement contributions exceeded the s11F limit: SDL should deduct at most min(27.5% × remuneration, annualCap/12), not the full contribution.

Files changed:

- **`taxTables.ts`**: Added `s11fAnnualCapRands: number` to `TaxYearConfig`. Values: 2025 = R350 000 (unverified for 2025 — no SARS source fetched in this PR), 2026 = R350 000 (source: PAYE-GEN-01-G20 Rev 1 s7.3.1), 2027 = R430 000 (source: PAYE-GEN-01-G21 Rev 1 s7.3.1).

- **`retirementDeductionCap.ts`** (new): Pure helper `cappedRetirementDeduction(contributions, remuneration, periodsPerYear, taxYear)`. Returns `min(contributions, min(27.5% × remuneration, annualCap / periodsPerYear))`.

- **`payrollCalculator.ts`**:
  - Tracks `taxableRetirementDeductions` (SARS codes 4001/4003/4006 + `isTaxable`) separately from other taxable deductions.
  - Builds `para24DeductionsForSdl = min(sdlRetirementAllowable + otherTaxableDeductions, fourthScheduleRemuneration)`.
  - PAYE continues using the uncapped `para24Deductions` until PR #891.
  - Comment explains the temporary divergence.

### Why only retirement codes are capped, not all taxable deductions

Section 11F applies specifically to "contributions to a retirement fund." Other taxable deductions (e.g. union fees) are para 2(4) deductions in full. The code identifies retirement deductions by SARS codes 4001 (pension), 4003 (provident) and 4006 (RA) — the same codes used by EasyFile and the BRS. Only those are subject to the 27.5% / annual-cap limit.

### PAYE divergence note

PAYE still deducts the full contribution (uncapped). For contributions above the s11F limit, PAYE income is lower than SDL leviable. This is a temporary discrepancy until PR #891 adds the same cap to PAYE. Both bases floor at zero via the `max(0, ...)` wrappers.

## Threshold decision
The R500 000 estimate stays on **gross** pay. The reasons:
- The run header stores only `total_gross`. Measuring the trailing 11 periods after deductions would need a new stored column, which means a migration.
- Mixing an after-deduction current month with gross history would skew the estimate.
- Gross is always ≥ the leviable amount, so any error is towards levying.

**Open for Hein:** the SDL guide's registration test uses "total leviable amount". On that reading, an employer whose gross is just over R500k but whose leviable amount is ≤ R500k would be exempt, yet is still levied here. If you want that fixed, it is a follow-up: store a per-run leviable total (migration), then switch the estimate. It is the same proxy as before (no company-level "registered for SDL" flag).

## Changed (commit 3 — 5358dab00: donation allowlist)

A second Codex review found that `otherTaxableDeductions` (all non-retirement taxable deductions) passed through uncapped to SDL, violating para 2(4)(f). Example: R30 000 salary + R10 000 donation produced SDL R200; allowable donation = R1 500 (5%), so SDL should be R285.

Files changed:

- **`payrollCalculator.ts`**:
  - Added `taxableDonationDeductions` accumulator (code 4030 + isTaxable).
  - Replaced `otherTaxableDeductions` with an explicit allowlist:
    - Retirement (4001/4003/4006): capped by s11F as before.
    - Donations (4030): capped at 5% of (remuneration − capped retirement) per para 2(4)(f).
    - All other taxable deductions (union fees, medical 4005, garnishees, loans): excluded from SDL entirely.
  - Limitation noted in comment: s18A receipt not tracked in payroll.
  - PAYE now diverges from SDL for non-allowlisted taxable deductions (union fees etc.) in addition to the prior s11F divergence. Both documented in the comment.

### PAYE divergence (updated)

PAYE continues to deduct all `taxableDeductions` (all codes) uncapped until PR #891. SDL and PAYE bases now diverge for:
- Retirement contributions above the s11F cap.
- Non-allowlisted taxable deductions (union fees, etc.): reduce PAYE but NOT SDL.
- Donations above the 5% cap: full amount reduces PAYE; capped for SDL.

## Changed (commit 4 — minor cleanup + docs fix)

A third Codex review found two issues:

**Minor (fixed):**

- **`payrollCalculator.ts`**: Removed unused `para24Deductions` variable (was declared at the old line 121 for PAYE documentation purposes, never read after the SDL explicit-allowlist refactor in commit 2/3).
- **`.claude.md` + regenerated `AGENTS.md`**: The SDL leviability rule still said `para24Deductions` / "one figure for both: no s11F cap" — contradicting the implementation. Updated to reference `para24DeductionsForSdl` and the explicit allowlist (retirement s11F capped + donations 5% capped), with the cumulative-cap limitation noted.

**Major (not implemented — inputs missing):**

The Codex finding: the per-period s11F cap resets each month without considering unused year-to-date allowance. For an employee with no earlier contributions, a large February RA contribution within the annual 27.5% limit still sees SDL > 0 because only 1/12 of the annual cap is allowed per period.

**Why not implemented:** A cumulative cap requires "SDL retirement deductions allowed in earlier periods of the same tax year." This is NOT stored on `payroll_run_lines` and is NOT in `PayeYearToDate`. The `loadPayeYearToDate` query returns only PAYE-relevant fields (`periodic_taxable`, `annual_taxable`, `table_paye`, `medical_credit`, `additional_medical_credit`, `medical_scheme_fees`). There is no `sdl_retirement_allowed` column.

**What is needed to implement it:**

1. A migration adding `sdl_retirement_allowed NUMERIC(12,2)` (or similar) to `payroll_run_lines`, populated by `calculatePayrollRun`.
2. `PayeYearToDate` extended with `sdlRetirementAllowed: number` (or a separate `SdlYearToDate` type).
3. `loadPayeYearToDate` (or a new `loadSdlYearToDate`) querying that column.
4. `cappedRetirementDeduction` or a new function accepting `ytdRemuneration` + `ytdAllowed` and returning `max(0, min(capOnYtdRemuneration, annualCap × periodsElapsed / periodsInYear) - ytdAllowed, thisContribution)`.

This work belongs to PR #891 (which already extends the input types for PAYE) or a follow-up migration. Until then the per-period cap (annualCap/12) is a conservative approximation: it under-allows for a month with a large contribution but no earlier contributions, and over-allows for a month with contributions that pushed past the annual limit. The `.claude.md` and AGENTS.md now document this limitation.

## Historical data / migration
- **Migration:** none.
- **Stored values:** SDL is stored per line (`payroll_run_lines.sdl`) and per header (`total_sdl`). EMP201, EMP501/IRP5, journals, the parallel-run report and payslip verification all read those stored values. The only caller of the calculator is `calculatePayrollRun`, so approved and paid runs are untouched.
- **Caveat:** a run that is calculated, recalculated or reopened after this deploy gets the new figure. That is a new calculation, but a reopened historical month would then differ from what was declared on its EMP201.
- No queries were changed, so RLS and tenant scoping are unaffected.

## Risks / unverified
- The SDL deduction follows the `isTaxable` flag on deduction components. The seed script marks Provident (4001) and RA (4006) `is_taxable: false`; for tenants configured that way, neither PAYE nor SDL deducts them, and this fix changes nothing for them.
- Going the other way: new components default to `is_taxable = true`, so a non-retirement deduction (e.g. union fees) left at the default is deducted for PAYE (a pre-existing PAYE defect) and now for SDL too. I did not check the real tenants' component flags.
- The s11F cap and employer-contribution fringe benefits are missing for PAYE as well. For SDL, an employer contribution within the cap nets to nil (added as remuneration, deducted as deemed contribution), so ignoring both is consistent. Above the cap, both PAYE and SDL under-charge.
- SDL Act s3(4) and s4(b): the amended text was not verified.
- No blind `/review` has been run on this commit yet (required before a PR).

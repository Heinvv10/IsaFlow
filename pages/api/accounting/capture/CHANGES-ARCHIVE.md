## Recent changes
- 2026-10-21 (audit 2026-10-18 S-06): the `upload.ts` API-key path (Bearer or `X-Api-Key`) acts with the key creator's CURRENT company role (`ctx.role`, no longer a hard-coded `'manager'`) and answers 401 'Invalid or revoked API key' once the key's company is suspended or deleted, or its creator is no longer an owner/admin/manager there or is suspended. The key is checked again after the multipart body is read and before the first write (401, nothing written, if it lost standing meanwhile), and the request acts with the re-checked role. **Deploy impact:** such keys 401 from deploy and the owner re-issues them; legacy keys with no `created_by` keep working as manager (warned on each use) while the company is live. A fixture key needs a `created_by` that is a current owner/admin/manager, or NULL (see `tests/integration/r075-route-event-after-commit.int.test.ts`).
- 2026-10-03 (D11 round 3): `evidenceAttachmentService` (the auto-attach `capture/[id]/post` and `ai-invoice-pipeline` run) now re-throws a deadlock victim too, reversing the round-2 note below: the post committed a bill with its own journal beside an unevidenced provisional (slip booked twice). `r107-auto-attach-savepoint` / `r088-evidence-attach-check` re-expressed: the attach rolls back alone, the transaction stays usable, the request rolls back (503), a retry works. Test: `tests/integration/d11-r3-attach-deadlock.int.test.ts`.
- 2026-10-03 (D11 round 2): `capture/[id]/post` and `ai-invoice-pipeline` reach `attachEvidenceAndSettleApproved`, whose `provisional_settle` savepoint now re-throws ALL contention (`isHeldRowError`: also a raw 40P01 / 55P03, `CAPTURE_EVENT_LOCKED`, a held refusal). It used to treat a deadlock victim as a refusal: the bill was withdrawn to draft, the slip claimed and the route answered 200. Tests: `tests/unit/services/capture/provisionalAttachSettleContention.test.ts`, `tests/integration/d11-r2-pipeline-deadlock.int.test.ts`.
- 2026-10-03 (D11): `[id]/post.ts` and `[id]/post-expense.ts` answer a held capture event or document (`CaptureRowLockTimeoutError`) 503 + Retry-After through `respondIfLockTimeout`, as `receipt-to-journal`, `ai-invoice-pipeline` and `document-capture-action` now do (all four were 409 or 400), and `[id]/discard.ts` answers a held event (`CaptureEventLockedError`, was 409) the same way. The R-088 content fence's `content_busy` (a fingerprint lock a peer holds past the 5s wait: `claimCapturedDocumentForPosting`'s refusal, `checkReceiptDuplicate`'s `kind:'busy'`, `ClaimSourceDocumentError('busy')` on the expense-claims routes) is a held lock too: 503 + Retry-After via `capturePostingClaim.respondCapturedDocumentRefusal` / `respondRowHeld`; `content_posted` and `already_posted` are state refusals and keep 409 / 400. Nothing is written before those locks, and the 503 rolls back. The status REFUSALS (`CAPTURED_DOCUMENT_REFUSAL_ERROR_CODE`) stay 409. Tests: `tests/unit/api/d11HeldRowDocumentRoutes.test.ts`, `tests/unit/api/d11HeldRowCaptureFenceRoutes.test.ts`, `tests/integration/d11-held-row-routes.int.test.ts`.
- 2026-09-29 (R-131): `[id]/post` writes `supplier_invoice_items` (it wrote none, so an auto-approved bill sat `approved` with no journal and could not post one). New 400s, both before the claim: "The document has no total to bill…" and "…no expense account to put its total on…" (only when the event, the supplier rule and the company `default_expense` all give none). An auto-approved bill now carries its journal; when that journal cannot post (closed fiscal period, filed VAT period, missing `payable` account) the bill is answered and left as a draft with `provisionalAttach.settlementRefused` and a note — the response `invoice.status` is `draft`, `approvalRoute` `manual_review`.
- 2026-09-26 (R-088 round 2): `[id]/post.ts` claims with `{ spend: 'invoice' }`; the claim refuses a slip whose FILE is already booked from another upload (a receipt journal, an invoice, a claim line) and the route answers it 409 via `CAPTURED_DOCUMENT_REFUSAL_ERROR_CODE`, before any write. The inbox (`pages/accounting/capture/inbox.tsx`) already toasts `error.message` on any non-OK answer, and a same-file match has no override, so there is no confirm flow to add. `[id]/post-expense.ts`: a same-file match is final even with `confirmDuplicate`; `details.canConfirm` says which 409s can be confirmed; a busy fingerprint answers `details.code = 'RECEIPT_POST_BUSY'`.
- 2026-09-26 (R-088): `[id]/post-expense.ts` runs `checkReceiptDuplicate` once, before either branch writes, and answers 409 (`details.code = 'DUPLICATE_RECEIPT'`, `details.earlierDocumentId`, `details.matchedOn` `'file' | 'details'`) when the same slip was already posted from another upload; body `confirmDuplicate: true` posts a genuine repeat. `receipt-to-journal.ts` does the same. No `.tsx` calls either route today, so there is no UI override flow to add; a caller that adds one must resend with `confirmDuplicate` on that 409 code only (the route also answers 409 for lock contention).

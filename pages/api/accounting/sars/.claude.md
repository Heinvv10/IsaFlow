# sars/ (SARS tax compliance)

SARS return preparation + eFiling submissions tracking + compliance calendar. VAT201, EMP201, EMP501 bi-annual, IRP6 provisional. All handlers at same depth (no subdirs).

## Endpoints
- `GET /api/accounting/sars/sars-compliance` — DB-backed calendar (`?year=YYYY`); returns `{ events }`; delegates to `getComplianceCalendarWithDB`
- `GET /api/accounting/sars/compliance-calendar` — pure calendar (no DB); `?year=YYYY`; returns `{ year, deadlines, total }`
- `GET|POST /api/accounting/sars/sars-submissions` — list / mark-submitted `{ id, action: 'mark_submitted', reference, overrideReason? }`. For a VAT201 submission, refuses with getVatExceptions' blocking exceptions UNLESS the caller is owner/admin and supplies `overrideReason` — recorded in `vat_gate_overrides` (migration 704, `reports/vatGateOverrideService`), never consulted by the ISV `efiling-submit` gate below. No MCP equivalent (this route has no MCP tool at all today)
- `GET|POST /api/accounting/sars/sars-vat201` — GET `?from=&to=` build; POST `{ periodStart, periodEnd }` save draft. Both answer from `getVat201Return` (vat201Return.ts) = `getLedgerVAT201` (journal-derived) + `sarsFields` (the SARS VAT201 form), `warnings` (classification calls to confirm) and `filability` (fields 1, 1A, 2, 2A, 3, 4, 4A, 5-20; `vat201SarsFields.ts`); the invoice-derived `generateVAT201` is the exceptions recon's input only
- `GET|POST /api/accounting/sars/sars-emp201` — monthly PAYE/UIF/SDL; same query shape as VAT201
- `POST /api/accounting/sars/emp201-book-eti` `{ month: 'YYYY-MM' }` — "Book ETI for this month" (wave 5 ET round 4): `etiRebook.bookEtiForMonthLocked` posts the run-less month's `ETI-YYYY-MM` journal as the EMP201 declares it; idempotent; answers `{ month, status, journalEntryId, entryDate, used, refund }` (what it booked); write roles + CSRF; a held payroll approval lock is the retryable 503. MCP equivalent: `book_eti_for_month`
- `GET /api/accounting/sars/returns/[form]/versions?periodStart=&periodEnd=` and `POST /api/accounting/sars/returns/[form]/{finalise,file,amend}` (`form` = `vat201` | `emp201`; the only subdirectory here) — wave 5 L1a/L1b, `services/returns/.claude.md`. `file` `{ versionId, reference, overrideReason? }` runs the VAT gate and markSubmitted in one savepoint with the version's move to filed; `amend` `{ versionId, reason }` is owner/admin only with a mandatory reason and refuses Login-as; a blank reference or reason is 400. Finalise runs the same exceptions gate as `POST /vat-period-locks` (VAT201), or refuses 409 unless every pay run of the period is R-035 final (EMP201); both `no-store`, refusals before the first write, one savepoint
- `GET|POST /api/accounting/sars/irp6` — provisional tax (1st/2nd/top-up)
- `GET /api/accounting/sars/emp501` — bi-annual employer recon summary
- `GET /api/accounting/sars/vat-exceptions` — `?from=&to=`; pre-filing VAT exceptions (uncoded GL VAT lines, invoice tax-code issues, invoice↔GL mismatches, VAT201-vs-GL-control recon); informational for the panel, **but the eFiling submit path re-runs it as a HARD gate**
- `GET /api/accounting/sars/efiling-status` — redacted `{ configured, baseUrlHost, channel }`; drives whether the "Submit to SARS" surface appears. Never returns credentials (Phase 4)
- `POST /api/accounting/sars/efiling-submit` — `{ submissionId, action?: 'submit'|'poll' }`; files a VAT201 via the ISV channel (or polls status). DARK unless `SARS_EFILING_ENABLED=true` + creds; server re-checks the exceptions gate and REFUSES when not clean/degraded (Phase 4), and additionally refuses a material 15% variance (0.5% of the tax declared, floor R1 — NOT `rateCheck.ties`, whose R1 absolute bar no real book clears), a negative supply value, an input breakdown contradicting field 10, or figures drifted from the reviewed draft (`draftDrift`)

## Auth
All routes: `withAuth(withErrorHandler(withWriteAccess(handler)))`.
- CSRF applied only on mutating routes that import `withCsrf`: `sars-submissions`, `sars-vat201`, `sars-emp201`, `irp6`, `efiling-submit`
- Read-only routes (`sars-compliance`, `compliance-calendar`, `emp501`, `vat-exceptions`, `efiling-status`) omit CSRF. `efiling-status` is `withAuth(withErrorHandler(handler))` only (no write access needed to read a redacted config flag)

## Business rules
- **Two calendar endpoints intentionally coexist** — `sars-compliance` is DB/tenant-customised, `compliance-calendar` is pure math. Don't merge
- **Route naming is inconsistent** — some have `sars-` prefix, others don't (`irp6`, `emp501`). URLs are public API; don't rename without client migration
- SARS credentials encrypted — `sarsEfilingService` decrypts via `@/lib/encryption`. Never log decrypted value from a route
- POST `sars-submissions` is destructive when not sandboxed — check `SARS_EFILING_ENV=sandbox` in dev/staging
- `emp501` depends on payroll runs being posted for every month of the recon period (builds via `buildEMP501Summary` over `EMP501MonthlyData`)

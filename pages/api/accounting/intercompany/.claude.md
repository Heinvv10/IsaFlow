# pages/api/accounting/intercompany/

Routes of the intercompany connections (P1) and the pre-cut-over pairing (P3). All are `withAuth(withErrorHandler(...))`; the mutating ones add `withCsrf(withWriteAccess(...))`. Logic lives in `src/modules/accounting/services/intercompany/` (see its `.claude.md`).

## Routes
- `connections` — GET list (each connection with the pair `settings`, `canEditSettings`, the session company's OWN side and checklist); POST `{ partnerCompanyId }` creates a GROUP connection (or re-activates a revoked one).
- `connections/[id]` — PUT the session company's OWN side `{ customerId?, supplierId?, loanAccountId?, defaultExpenseAccountId?, autoAccept? }`; DELETE revokes (either party).
- `connections/[id]/settings` — PUT the pair's agreement `{ settlementMode?, cutoverDate?, interestRatePct? }`; needs a write role in BOTH companies.
- `connections/[id]/pairing` — GET `?direction=ar|ap` the pairing screen's data (suggestions, exceptions, pairings, loan difference; the partner's side only as number / date / total / open amount); POST `{ direction, pairs: [{ mineId, theirsId }] }` records the pairs (all or none, at most 200; only pairs the screen suggests: anything else is a 409). The link routes act on manual invoice pairings only (a mirror or credit-note link is a 404). `connections/[id]/pairing/links/[linkId]` — PUT confirms the partner's proposal, DELETE unlinks. Nothing here posts.
- `group-candidates` — GET group companies the session company could connect to. `side-options` — GET the session company's customers, suppliers and postable accounts for the side form.

## Rules
- Input types are checked first (400, never a 500 from a `::UUID` or `::DATE` cast): unknown keys, non-UUID ids and out-of-range values are refused by `connectionValidation.ts`.
- Refusals are `ConnectionRefusal` (400 / 403 / 404 / 409), answered by `respondIfRefusal`; a connection that is not the session company's is a 404.
- A viewer is refused (403) on every mutating method by `withWriteAccess`; `tests/unit/security/viewerMutationRoutes.test.ts` lists them.

## P2 routes: the inbox (messages other companies sent THIS company)
- `inbox` — GET `?filter=open|handled&limit&offset`: `{ items, total, openCount }` (`open` = pending + failed, `handled` = accepted, rejected, dismissed, withdrawn; an item has `sourceCancelled`). `inbox-count` — GET `{ openCount, enabled }` for the Bills "Intercompany" tab badge (`enabled` = this company has any intercompany connection).
- `inbox/[id]` — GET one message with its lines, the account each will use (last used for that description, else the side default), the supplier, any duplicate and the blockers. `inbox/[id]/accept` — POST `{ lineAccounts?: { "<line index>": accountId }, accountId? }` creates the DRAFT supplier invoice / credit note, answers `{ messageId, targetDocType, targetDocId, linkId, pdfCopied }`. `inbox/[id]/reject` — POST `{ reason }` (required). `inbox/[id]/dismiss`, `inbox/[id]/restore` — POST.
- A message that is not the session company's (its own outgoing one, another company's) is a 404; an unreadable id is a 400. A refusal (handled, dismissed, duplicate, no supplier, foreign currency, connection not active, an account that cannot be used) is a `ConnectionRefusal` (400 / 409) written BEFORE or rolled back WITH its savepoint: nothing is left behind. The mutating routes are `withCsrf(withWriteAccess(...))` (a viewer is a 403).
- The cron route `pages/api/cron/intercompany-auto-accept.ts` is outside `withAuth` (X-Cron-Secret); see the service's `.claude.md`.

## P4-C routes: payments from the group (allocation messages THIS company receives), read only
- Dark flag `intercompany_loan_clearing` (migration 1028, off for every company by default; `loanClearingGate.ts`): `allocations` and `allocations/[id]` also answer `loanClearingEnabled` for the session company (off: the detail's `preview` is null and the UI shows no Accept); `allocations/[id]/accept` answers 403 "Clearing intercompany payments against the loan account is not enabled for this company." before reading the body when it is off. Reject / dismiss / restore are not gated.
- `allocations` — GET `?filter=open|handled&limit&offset`: `{ items, total, allocationCount }`; each item carries the payload facts, this company's own issuer invoice (or null), `live` / `liveReason` (the database's advisory answer for a pending / failed one, `not_pending` for a handled one, `check_failed` if it could not be asked) and the derived `mismatch`. `allocations/[id]` — GET `{ item, allocationId, linkId, linkOrigin, cutoverDate }`.
- `allocations/[id]/reject` — POST `{ reason }` (required; 409 on a revoked connection); `allocations/[id]/dismiss` — POST; `allocations/[id]/restore` — POST (a dismissed one back to pending; 409 if not dismissed or the connection is not active). All `withCsrf(withWriteAccess(...))` and act on an allocation message of the session company only (another company's, or an invoice message, is a 404). There is NO accept route: clearing is P4-D. `inbox`, `inbox-count` and `inbox/[id]/*` never reach an allocation.

## P4-E route: the PAYER clears a linked bill against the loan (posts; DARK behind `intercompany_loan_clearing`)
- `loan-clearings` — `withAuth(withErrorHandler(withCsrf(withWriteAccess(...))))`. The flag off for the session company: 403 with a plain sentence before the query or the body is read. GET `?billId=<uuid>`: the preview (both legs, the bill's open amount, the partner, `receiverReady` = the partner can clear something now, `blocked` = the sentence the POST would answer for a good date); read only, no row lock, and for a member with the intercompany WRITE role only (403 `no_write_role` otherwise: withWriteAccess lets every GET through, so the service asks). POST `{ billId, amount, postingDate, expected: { loanAccountId, linkId, amount, openAmount, payableAccountId } }`: ONE contra settlement (DR Accounts Payable / CR the loan account) and its allocation message, 200 `{ cleared, billId, paymentId, paymentNumber, journalEntryId, messageId }`. A refusal is a 4xx with a plain sentence, always before any write (404 the bill, 403 the person, 400 the date or the body, 409 the books, a stale preview or the partner not ready); anything after the posting is a 5xx (the request rolls back). Logic: `payerLoanClearService.ts` / `payerLoanClearPreview.ts` (see the service's `.claude.md`, P4-E).

## P5 routes: the loan reconciliation (READ ONLY; DARK behind `intercompany_loan_clearing`)
- `loan-reconciliation` — GET `{ connections }`: the session company's loan connections and those carrying an allocation message. `loan-reconciliation/[connectionId]` — GET `?section=undone|attention|mismatch&limit&offset` (limit 1-200, default 50): `{ connectionId, partnerName, asOf, readAt, summary, section: { key, items, total, limit, offset } }`, the whole summary and the total from the same one statement on every page.
- `withAuth(withErrorHandler(handler))`, GET only (405). Order: 403 for a Login-as session or one without a session id, the flag off, no intercompany write role (before anything else is read); 400 for a connection that is no UUID, a bad section / page, or ANY `asOf` parameter; 404 (one body) for a connection that is not the session company's loan connection; 422 over 5 000 messages; 503 when the 15 s bound runs out. Refusals are `ReconRefusal`, answered by `respondIfReconRefusal`. Nothing is written.

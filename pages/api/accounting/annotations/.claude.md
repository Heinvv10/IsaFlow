# annotations/ (internal row notes)

## Endpoints
- `GET  /api/accounting/annotations?rowIds=&from=&to=` — notes on the rows the caller rendered, for exactly that period.
- `POST /api/accounting/annotations` — add a note to one row.
- `POST /api/accounting/annotations/[id]/resolve` — mark one note settled.

## Caller contract
`withAuth(withErrorHandler(withCsrf(withWriteAccess(handler))))`. Company AND author both come from the session — a body field claiming a different author is ignored, not honoured.

**INTERNAL ONLY.** There is no unauthenticated counterpart, and the share page never calls these routes. Annotations are colleagues' working notes and must never reach a share link; `sharedPackService.ts` does not query `report_annotations` and `SharedPackProps` has no field one could travel in. If you are adding a share-side reader for these rows, stop — see `tests/unit/services/annotations/annotationsNeverShared.test.ts`.

## Business rules
- `rowIds` is capped at `MAX_ROW_IDS` (500) and dates must be real calendar dates — the ISO pattern alone accepts `2026-02-31`, so the guard round-trips through `Date`. Same shape as `parseSharePackParams`.
- Row ids are opaque adapter strings (`acc:4000`, `total:grossProfit`) and are parameterised into the query, so a length bound is the only guard they need.
- A body longer than `MAX_BODY_CHARS` (4000) is truncated, not rejected.
- Create and resolve are rate limited per company AND per user: `checkReportRateLimit` supplies the company, `annotationRateLimitKey(action, userId)` the user, so one colleague cannot spend a teammate's capacity.
- Resolve answers 404 for a cross-company id, an unknown id and an already-resolved note alike. `[id]` is guarded by `isUuidParam` (`@/lib/validation`).

# Netcash API routes

Integration with the Netcash payment gateway for EFT batch submissions. Reads company-stored `netcash_service_key` / `netcash_payouts_key` credentials, submits payment batches, persists a submission record to `netcash_submissions`, and polls for status updates. Delegates to `services/ap/netcashService.ts`.

## Endpoints

| Method + path | Handler | Purpose |
|---|---|---|
| `POST /api/accounting/netcash/submit` | `submit.ts` | Submit an EFT batch. Body: `{ batchPaymentId? }` OR `{ payments: NetcashPayment[] }`. Batch mode is idempotent (AP-01, see below). Records submission regardless of outcome. |
| `GET /api/accounting/netcash/status?submissionId=` | `status.ts` | Poll Netcash for submission status. Updates `netcash_submissions` row on non-terminal states. Short-circuits if already `completed` or `failed`, and never polls an `unknown` row (no Netcash reference). |
| `GET /api/accounting/netcash/submissions?status=&limit=&offset=` | `submissions.ts` | List submission history for the company. Default limit 50, max 200. |
| `POST /api/accounting/netcash/test-connection` | `test-connection.ts` | Test a service key against the Netcash API. Body: `{ serviceKey }`. Returns `{ valid, mock? }`. |

## Auth

All routes: `withAuth(withErrorHandler(handler))` — no CSRF wrapper. Mutation endpoints (POST) rely on session auth only.

**Note:** `submit.ts` and `test-connection.ts` are state-mutating POSTs without CSRF middleware — flag for security review if CSRF protection is needed for these payment operations.

## Response contract

All routes use `apiResponse.success` / `.badRequest` / `.notFound`. `submit.ts` returns `{ submissionId, batchReference, recordCount, totalAmountCents, mock? }`. `status.ts` returns `{ submissionId, status, detail, polled, mock? }`. Clients MUST unwrap `json.data`.

## Business rules / gotchas

- `netcash_enabled` must be `true` on the company row — `submit.ts` returns 400 if not enabled.
- `submit.ts` accepts either a `batchPaymentId` (loads payments from `supplier_payment_batches`) or a raw `payments[]` array — not both simultaneously.
- Amounts in `NetcashPayment.amount` are in **cents** (rands × 100).
- `status.ts` maps Netcash status strings to internal enum values (`completed | failed | processing | submitted`) via a keyword-match function — no strict string equality.
- A submission record is always written, even on failure, so audit trail is complete.
- **Batch submit is idempotent (AP-01, migration 898).** With `batchPaymentId`, a claim row (`status='pending'`, `batch_id`) is inserted BEFORE the send with `ON CONFLICT (company_id, batch_id) WHERE batch_id IS NOT NULL AND status <> 'failed' DO NOTHING`; no row back = 409 naming the holding submission. The partial UNIQUE index admits one non-`failed` row per batch, so a concurrent request blocks on it until the first ends. After the send the row becomes `submitted`, `failed` (Netcash DEFINITELY rejected: 4xx JSON answer, not 408 — retry allowed) or `unknown` (timeout/abort, network error, unparseable 2xx, 5xx — batch stays claimed, answered 409). `netcashService.submitEftBatch` carries this as `outcome: 'accepted' | 'rejected' | 'unknown'`.
- **Every failure after the claim MUST answer 4xx**: withAuth rolls back a >=500, which would erase the claim of a batch that may already be paid. Residual risk: a DB error on the post-send UPDATE, a failed COMMIT or a process crash between the send and the COMMIT loses the claim (the claim lives in the request transaction). The raw `payments[]` mode names no batch and is NOT claimed — it can still be double-sent.
- An `unknown` row is resolved by hand today (check Netcash, then set the row `failed` to allow a resend, or `submitted`); there is no endpoint or UI for it yet.
- Test-connection uses the same service key validation path as live submissions.

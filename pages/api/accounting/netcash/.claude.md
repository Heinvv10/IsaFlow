# Netcash API routes

Integration with the Netcash payment gateway for EFT batch submissions. Reads company-stored `netcash_service_key` / `netcash_payouts_key` credentials, submits payment batches, persists a submission record to `netcash_submissions`, and polls for status updates. Delegates to `services/ap/netcashService.ts`.

## Endpoints

| Method + path | Handler | Purpose |
|---|---|---|
| `POST /api/accounting/netcash/submit` | `submit.ts` | Submit an approved supplier payment batch. Body: `{ batchPaymentId }`. Idempotent (AP-01, see below). A raw `{ payments: [...] }` list is refused 400. Records the submission regardless of outcome. |
| `GET /api/accounting/netcash/status?submissionId=` | `status.ts` | Poll Netcash for submission status. Moves a live row between submitted/processing/completed and keeps the answer as a display hint. Short-circuits if already `completed` or `failed`, and never polls a `pending`/`unknown` row (no Netcash reference). |
| `GET /api/accounting/netcash/submissions?status=&limit=&offset=` | `submissions.ts` | List submission history for the company. Default limit 50, max 200. |
| `POST /api/accounting/netcash/resolve` | `resolve.ts` | Record what an operator found at Netcash for a `pending`/`unknown`/`submitted`/`processing` row. Body: `{ submissionId, outcome: 'failed' \| 'submitted', note }`. Owner/admin only. "Resolve" per row on `pages/accounting/netcash/index.tsx`. |
| `POST /api/accounting/eft-file-release` | `../eft-file-release.ts` | `POST`: say a generated bank file was not used so the batch may go to Netcash. Body: `{ batchId, reason }`. Owner/admin only. `GET ?batchId=`: the newest unreleased file (`{ bankFile }`), any member. |
| `POST /api/accounting/netcash/test-connection` | `test-connection.ts` | Test a service key against the Netcash API. Body: `{ serviceKey }`. Returns `{ valid, mock? }`. |

## Auth

`submit.ts` and `resolve.ts`: `withAuth(withErrorHandler(withCsrf(withWriteAccess(handler, { allowedRoles: ['owner', 'admin'] }))))` - sending money, or releasing a claim that can let a batch be paid again, is owner/admin only (as are eft-generate and eft-file-release). `test-connection.ts`: `withAuth(withErrorHandler(withCsrf(handler)))`. `status.ts` and `submissions.ts` are GET-only: `withAuth(withErrorHandler(handler))`; `status.ts` calls `assertNotImpersonating()` first (a poll calls Netcash and writes the row).

## Response contract

All routes use `apiResponse.success` / `.badRequest` / `.notFound`. `submit.ts` returns `{ submissionId, batchReference, recordCount, totalAmountCents, mock? }` (409 `BATCH_ALREADY_SUBMITTED` / `NETCASH_OUTCOME_UNKNOWN` with `submissionId`). `status.ts` returns `{ submissionId, status, detail, polled, mock? }`. Clients MUST unwrap `json.data`.

## Business rules / gotchas

- `netcash_enabled` must be `true` on the company row — `submit.ts` returns 400 if not enabled.
- `submit.ts` takes a `batchPaymentId` only (payments are loaded from the batch's `supplier_payments`). A raw `payments[]` list is refused 400: it names no batch, so nothing could approve, claim or make it idempotent, and nothing in production sent one (AP-01). Do not re-add it without a claim key.
- Amounts in `NetcashPayment.amount` are in **cents** (rands × 100).
- `status.ts` maps Netcash's free-text status by its LEADING word, never a substring anywhere: failure words (`unsuccessful`, `failed`, `rejected`, `error`, ...) are checked before success (so "Unsuccessful" is not `completed`); a completion word with a failure word anywhere ("Completed with errors") is ambiguous; `submitted` -> submitted; anything else ("Processing - 0 errors", "Accepted, no rejections", "Not successful") -> `processing`.
- Once a batch is claimed, its submission record is always written, even on failure (`failed` / `unknown`), so the audit trail is complete. A request refused before the claim (no credentials, a malformed payee, a bank file, a held batch) writes none.
- **Batch submit is idempotent (AP-01, migration 898).** With `batchPaymentId`, a claim row (`status='pending'`, `batch_id`) is COMMITTED in its own transaction BEFORE the send (`services/ap/netcashSubmissionClaim.ts`: own pooled connection, `app_user`, the caller's claims and company GUC) with `ON CONFLICT (company_id, batch_id) WHERE batch_id IS NOT NULL AND status <> 'failed' DO NOTHING`; no row back = 409 naming the holding submission. The partial UNIQUE index admits one non-`failed` row per batch. After the send the row is settled in another committed transaction to `submitted`, `failed` (Netcash DEFINITELY rejected: a 400 or 422 JSON answer only - 401/403/404/409/429 and the rest are `unknown`; retry allowed after `failed`) or `unknown` (timeout/abort, network error, unparseable 2xx, 5xx - answered 409). `netcashService.submitEftBatch` carries this as `outcome: 'accepted' | 'rejected' | 'unknown'`.
- **Payees are validated before the claim** (`services/ap/netcashPayeeValidation.ts`): digits only, account 1-11 digits, branch exactly 6 digits; 400 naming the payment (`Payment N: ...`), nothing claimed or sent.
- **The batch row is read `FOR SHARE` first** (then the gate's payee `FOR SHARE`, the order processBatch uses), so a `cancelBatch` waits for the submit's transaction instead of committing between the status check and the send. The claim/settle connections only take `FOR KEY SHARE` on the batch (the `batch_id` FK), which neither `FOR SHARE` nor a waiting cancel conflicts with: they cannot deadlock against the request tx. Do NOT strengthen that read to `FOR UPDATE` (the claim would wait on it).
- **The claim must never ride the request transaction**: withAuth rolls that back on any >=500, a crash or a timeout, and the claim of a batch that may already be paid would go with it. A claim left `pending` (process died between send and settle, or the settle failed -> 500) blocks resubmission exactly like `unknown`.
- **Operator resolves a row that holds its batch** after checking Netcash, with `POST /api/accounting/netcash/resolve` (owner/admin, also a "Resolve" control per row on `pages/accounting/netcash/index.tsx`). `pending`/`unknown` -> `failed` (Netcash never got the batch - it may be sent again) or `submitted` (it did); `submitted`/`processing` -> `failed` only (Netcash rejected it or never processed it) - the form warns that freeing an accepted batch pays it twice if Netcash has it, and shows the last poll's answer as context. **The operator's note is the only evidence: a poll is never consulted** (round 9 - a gate on the poll freed batches on "Processing - 0 errors"). `completed`/`failed` rows are never resolved (409). A note is required; compare-and-set on the status read (409 if a settle or a poll moved the row in between, e.g. Netcash answered `completed`); a `pending` row younger than `SEND_WINDOW_MS` (`services/ap/netcashTimeouts.ts`: the 30 s send timeout + 90 s margin = 2 min) is refused 409 `IN_FLIGHT` - its send may still be running; an `unknown` row is resolvable at any age; audit-logged as an `update` of `netcash_submission` and recorded in `netcash_response.resolved`. `status.ts` does not poll `pending`/`unknown` rows (their `batch_reference` is our own batch number, not Netcash's), and the submissions page shows a note instead of the poll button and merchant link.
- Test-connection uses the same service key validation path as live submissions.
- **Credentials are required** (K-132): `submit.ts` answers 400 when either the service key or the payouts key is empty, before the batch is read or claimed, and `submitEftBatch` itself refuses (no mock success). The mock answers remain only in `getSubmissionStatus` and `testConnection`.
- **The settle is compare-and-set on `pending`** (`settleClaim`): if the claim is no longer pending (an operator resolved it past the window while the send was still running), Netcash's answer is NOT applied - it is kept on the row as `netcash_response.lateSendResult`, the request answers 409 `CLAIM_RESOLVED_DURING_SEND`, and an error is logged. Operator: check Netcash for that batch before anything else; the override can have let a second send through.
- **The whole send is bounded** (`netcashService.fetchJsonWithTimeout`): the 30 s timer stays armed until the response BODY has been read, so a stalled body cannot hold a send past `SEND_WINDOW_MS`; a body that times out is an `unknown` outcome (never `rejected`).
- **Keys are trimmed** before the empty check (a whitespace-only key is no key).
- **A poll never frees a batch and is never evidence; only write-access roles poll, never from a Login-as session** (a read-only member is shown the stored status: a poll calls Netcash and writes the row). A poll that maps to `failed` leaves the row's status as it is, logs an error and answers `needsAttention: true`. The answer is a display hint only: `netcash_response.latestPoll` (`{ status, detail, at }`, `at` = when Netcash answered) and, while it reads as a failure, `pollFailure` (the page's note). It is MERGED into `netcash_response` (`- 'pollFailure' || hint`), never rewritten from the poll's read, so `lateSendResult` / `resolved` / a key written meanwhile survive. The UPDATE is compare-and-set on the status read (a settle, a resolution or another poll's move is never overwritten) AND on the stored `latestPoll.at` being older than this answer: of two overlapping polls, the one Netcash answered later wins even if it writes first (timed by this host's clock; 0 rows = no-op, `polled: false`, current status returned). An operator then checks Netcash and resolves the row (see above).
- **A batch Netcash may hold is not undone**: `cancelBatch` and the batch reversal refuse (400, naming the submission) while a non-`failed` submission exists (`services/ap/netcashBatchGuard.ts`). Lock order: batch row (`FOR NO KEY UPDATE` / `FOR UPDATE`) -> submission row `FOR SHARE` -> members; netcash/submit holds the batch row `FOR SHARE` for its whole request, so a cancel waits for a submit in flight and then finds its claim.
- **One channel per batch.** `eft-generate` refuses (409 `BATCH_SENT_TO_NETCASH`, naming the submission) a batch with a non-`failed` Netcash submission (`netcashBatchGuard.liveNetcashSubmission`, a plain read after the lock below). It takes the batch row `FOR NO KEY UPDATE` (held to the end of the request), which conflicts with netcash/submit's `FOR SHARE` (held from its status check across its send): a file request waits for a submit in flight and then sees its claim, and a submit waits for a file in progress. Both routes are owner/admin only, call `assertNotImpersonating()` first, and take UUID ids (400 otherwise); `eft-generate` accepts only own keys of its bank table (`Object.hasOwn`).
- **Lock census of the batch row**: approve/process/reverse/supplier-bank-change (`lockBatchesPayingSupplier`) `FOR UPDATE`; eft-generate, eft-file-release and cancelBatch `FOR NO KEY UPDATE`; netcash/submit `FOR SHARE`; the claim/settle connections only `FOR KEY SHARE` (the `batch_id` FK, the only FK to the table), which none of these conflict with except `FOR UPDATE` - and a `FOR UPDATE` holder cannot coexist with a claim, since a claim is only made by a submit already holding `FOR SHARE`. `updateSupplier` takes the supplier row, then the batch `FOR UPDATE`; submit and eft-generate take the batch, then the payees `FOR SHARE`: a cycle Postgres detects (40P01) and aborts one side of BEFORE anything is sent or served (the claim and the file come after the payee lock). `cancelBatch`'s guard must run on the SAME transaction as its batch lock (it does inside withAuth's request tx); outside a request its `FOR SHARE` on the submission row is on another autocommit connection and holds nothing, though the committed claim is still seen. Table: `src/modules/accounting/services/bank/.claude.md`.
- **File THEN Netcash is closed by a bank-file record** (`services/ap/batchBankFileRecord.ts`, no migration): `eft-generate` writes an `audit_log` row (`action='export'`, `entity_type='batch_bank_file'`, `entity_id` = the batch, `metadata.bank`) in the same transaction and under the same batch lock as the file it serves, before serving it (no file without its row; a refused file leaves none). `netcash/submit` reads it under its batch `FOR SHARE` and answers 409 `BATCH_BANK_FILE_GENERATED` while an export is unreleased. `POST /api/accounting/eft-file-release` (owner/admin, `{ batchId, reason }`, reason required; `GET ?batchId=` for any member) writes an `action='update'` row whose `metadata.releases` lists the export ids it releases (comma separated) and `metadata.reason`; it releases by id, not by time, so a file generated afterwards blocks Netcash again. audit_log's action CHECK has no `bank_file_released`, hence `update`; the table is append-only for app_user (migration 880). The batch page shows `BatchBankFileNotice` (who generated it, and for owner/admin an inline reason input and "Release bank file"). No page generates a bank file or submits to Netcash today, so the state is reached through the API.
- **A rejected submission whose settle fails stays `pending`** (the settle is its own transaction; the request answers 500): an operator clears it like any `pending` row. **Pool exhaustion fails closed**: the claim needs a pooled connection before the send, so an exhausted pool fails the request before Netcash is called; the settle needs one after, so an exhausted pool there leaves the row `pending` and the batch closed.

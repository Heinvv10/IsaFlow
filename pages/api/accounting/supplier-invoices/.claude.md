# supplier-invoices/ (PRD-05 — extensions on core AP invoices)

Core CRUD for supplier invoices lives under `/api/accounting/bills/` and `/api/accounting/supplier-payments/`. This subtree holds workflow extensions (3/4-way match).

## Endpoints
- `GET /api/accounting/supplier-invoices/[id]/three-way-match` — cached match state (no recompute)
- `POST /api/accounting/supplier-invoices/[id]/three-way-match` — recompute match via service

## Auth
`withAuth(withErrorHandler(withWriteAccess(...)))` wraps the single handler; GET tolerates the stricter gate.

## Request / Response
GET/POST response (`ThreeWayMatchState`, what `ThreeWayMatchPanel` renders):
```
{ invoiceId, matchStatus, paymentMatched, paymentMatchedAt, hasPurchaseOrder,
  itemResults: [{ invoiceItemId, description, poQuantity, invoiceQuantity, grnQuantityReceived,
                  poUnitPrice, invoiceUnitPrice, qtyVariancePct, priceVariancePct, lineMatchStatus, mismatches }],
  summary: { totalLines, fullyMatched, priceMismatches, quantityMismatches, grnMismatches },
  tolerancesApplied: { qtyTolerancePct, priceTolerancePct } }
```

## Business rules
- `supplier_invoice_items`, `po_items` and `grn_items` have **no `company_id`** column: tenancy goes through `supplier_invoices`, `purchase_orders` and `goods_received_notes`
- GET judges the live bill, PO and GRN (`readThreeWayMatchState`) and writes nothing
- POST also runs `performThreeWayMatch(companyId, invoiceId)`, which stores `line_match_status`, the variances and `match_status`
- Tolerances come from the supplier's coding rule (`qty_tolerance_pct`, `price_tolerance_pct`), else 2%

## The withAuth bug (verified against code at `1783f9ff` this session)
`src/lib/auth/withAuth.ts` (191 lines). Anatomy of the relevant block:
- Lines 163–167: `runHandler` executes the route handler inside `als.run({client, userId, companyId, claims})` — **the handler sends its HTTP response (res.json/res.end) here**, inside the open transaction.
- Line 178: `await client.query('COMMIT')` — runs **after** the handler returned, i.e. after the response has already been flushed to the client.
- Lines 179–181: catch → ROLLBACK + rethrow; 182–189: finally → `client.release()` + slow-request log + Sentry metric.

**Consequence (reproduced twice, WS-C session 2026-06-11):** a client that fires a follow-up request immediately after a mutation can hit the DB before COMMIT lands — a compare GET 404'd 78ms after the import POST's 201; the imports list still showed a row 27ms after its DELETE 200.

**Second latent issue to consider in the same fix:** handlers wrapped in `withErrorHandler` catch their own errors and respond 500 — then return normally to withAuth, which **COMMITs anyway** (line 178 runs unless the error propagates). A 500-but-committed mutation is arguably worse than the race. Decide deliberately whether the fix should also roll back when the response status is >= 400 (probably yes for 5xx; 4xx like notFound after partial writes is murkier — investigate what handlers actually do before locking this).

## Suggested fix shape (not locked — next session designs it)
Defer the response flush until after COMMIT. The standard pattern: before `runHandler`, monkey-patch `res.end` (and `res.write` for safety) to buffer the final flush; after the handler returns, COMMIT, then invoke the captured `end`. Considerations discovered while scoping:
- `res.json()` in Next pages-router ends up calling `res.end` — patching `end` covers `apiResponse.*` helpers.
- Streaming/file-download routes (exports, PDFs) may call `res.write` repeatedly — buffering full bodies is wrong there; consider only deferring the FINAL `end` call, or opting streaming routes out.
- Error paths: if COMMIT fails after the handler "responded" 200, the deferred flush must be replaced with a 500 (the win of this design — today a failed COMMIT after a 200 is a silent lie).
- `withErrorHandler` wraps INSIDE withAuth (`withAuth(withErrorHandler(handler))`) — its catches don't propagate to withAuth's catch.
- Blast radius: withAuth wraps ~750 routes. The fix MUST be behaviorally invisible except for ordering. Full CI + targeted browser verification of: one normal CRUD page, one file-download/export route, one streaming route (if any), SSE/long-poll (check if any exist under pages/api).
- Existing per-page workarounds that can be removed once fixed (grep `settle` / `retry` near refetches): payroll parallel-run page (1 retry + 600ms settle, WS-C), bank-tx-queries queue page (settle+retry, WS-D). Removing them is the proof the fix works — flip the order: write a failing e2e-ish test first if feasible (mock pg client recording call order: end-flush vs COMMIT).

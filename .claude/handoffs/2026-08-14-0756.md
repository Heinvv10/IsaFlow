## Context the next session needs

### Ledger / posting

- **`trg_gl_je_balanced` is a BEFORE UPDATE trigger.** It never fires on INSERT. A header INSERTed directly at `status='posted'` is therefore *never* balance-checked. This is the root cause behind all four direct-INSERT criticals — not a missing constraint, a trigger that cannot see the write.
- **A 4xx COMMITs.** `withAuth` / `bearerPipeline` only finalise-as-rollback on `res.statusCode >= 500`. Returning `apiResponse.badRequest()` from a catch **after** a write has happened commits that write. This trap was walked into twice this session (asset disposal, then `gl-import.ts`). Any validation that can 400 must run before the first write.
- **`withTransaction` (`src/lib/neon.ts`) takes a separate pooled connection** with its own BEGIN/COMMIT, independent of the ALS-bound request connection. `sql`, `sql.transaction` and `withSavepoint` use the ALS client. A registry savepoint therefore *cannot* roll back anything a service did inside `withTransaction`.
- **Migration 509 was built by reading the live CHECK constraint, not by extending migration 422.** 422 omits `auto_bank_transfer`, which production actually accepts — extending 422 would have silently revoked a live source. Read the live constraint before touching this again.
- `opening_balance`, `bank_transfer` and `year_end` still write unvalidated to `status='posted'`. Deliberately out of scope for #244; they are the next tranche.

### MCP

- `registry.ts` wraps `write: true` tools in `withSavepoint`, which rolls back **only if the handler throws**. The MCP transport returns HTTP 200 for every tool result including `isError` — so a `catch → toolError` releases the savepoint and the request commits. That is the whole bug class #247 closed.

### Backups / PITR

- **`/opt/isaflow-ops`, not `/home/velo/isaflow/scripts`.** `deploy.sh` rsyncs the deploy directory with `--delete`. This was verified empirically: the `b06d5aa3` deploy ran and `/opt/isaflow-ops` was untouched. Anything placed in the deploy dir would have been silently removed.
- **The pg_hba replication line lives in the DB container's writable layer, not a bind mount.** One line was added on 2026-08-14 to `/etc/postgresql/pg_hba.conf` inside `isaflow-supabase-db`: `host replication postgres 172.28.0.1/32 scram-sha-256`. It survives `docker restart` but is reverted by `docker compose up --force-recreate` or an image upgrade, and WAL archiving then stops silently. The nightly backup asserts PITR health and emails on regression. Backup of the original: `pg_hba.conf.bak-pre-pitr-20260814`.
- **`max_slot_wal_keep_size = 4GB`** — Postgres invalidates the replication slot rather than filling the disk. Production can't be taken down by the slot; the cost is a PITR gap reported as `wal_status = lost`. If you see that: take a fresh base backup immediately.
- Full procedure, including the verified point-in-time restore, is in `scripts/ops/README.md` under `#backups`.

### Things tried that did not work

- **`active::text` returns `'true'`, not `'t'`.** The first PITR health check pattern-matched `*/t` and reported INACTIVE on a perfectly healthy slot every night. Fixed; don't reintroduce.
- **`SMTP_PORT=465` is implicit TLS.** `alert-email.py` originally spoke plain SMTP to 465; the server never sent a greeting and the failure surfaced as a bare `TimeoutError` that looks nothing like a TLS problem. Alerting was completely dead until this was found. Also needs `SMTP_TLS_SERVERNAME` — the cert is `*.jnb1.host-h.net` while the host is `mail.isaflow.co.za`.

This was found by blind review and confirmed live via `ps aux`.

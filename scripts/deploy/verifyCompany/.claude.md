# scripts/deploy/verifyCompany/ — the Deploy Verification company

**Purpose:** production's post-deploy verification (`scripts/verify-deploy.sh`, run by `deploy.sh`, `restart-colours.sh`
and `cutover.sh`) runs the 24 non-dev-only golden-path specs in a hidden company of its own instead of the production Demo
company. The specs find-or-create `0GP-Golden-*` masters, post invoices, payments, journals, depreciation and a payroll
run, and use the `0GP Golden Migration Sandbox` company; none of that lands in Demo (Willie's and the prospects' company).

**Files:** `identity.ts` (the two logins, company and sandbox names, env keys: constants only, imported by the golden
helpers too), `config.ts` (argument and input guards), `password.ts` (which password a run uses), `envFile.ts` (create-or-update
the verify keys, pending keys, 0600), `lock.ts` (run lock), `provisionDb.ts` (users, company, approver membership, fiscal
years, one transaction), `seedBlocks.ts` (the blocks and their marker queries), `seedVerifyCompany.ts` (the wrong-company guard and
the block loop), `budgetReadiness.ts`, `readiness.ts`, `run.ts` (the order of the run, effects injected). CLI:
`scripts/deploy/provision-verify-company.ts`; production wrapper `scripts/deploy/provision-verify-company.sh`.
Tests: `tests/unit/ci/verifyCompany*.test.ts`, `tests/unit/scripts/verifyDeployCredentials.test.ts`,
`provisionVerifyCompanyWrapper.test.ts`, `tests/integration/deploy-verify-company.int.test.ts`.

**Contract:**
- Two logins, GoTrue users created through the admin API (email confirmed, no MFA, random passwords never printed), on
  `isaflow.co.za` (its mail goes to a server we run; an unregistered domain such as isaflow.dev would hand a password reset for a
  production owner login to whoever registers it): `deploy-verify@isaflow.co.za` (the owner, default company, raises everything)
  and `deploy-verify-approver@isaflow.co.za` (an `admin` member of the same company: above the pay-run rule's `manager`, so the
  company has two eligible people and R-035's sole-approver exception does NOT apply: h-payroll-run proves self-approval refused
  (SELF_APPROVAL_FORBIDDEN) and a second user approving). Company `Deploy Verification`, `is_demo = true`: out of platform
  metrics, MRR and trial counts, shown "internal" in the admin console, invisible in every other user's company switcher.
  Not filtered by is_demo: `src/lib/landing/landingStats.ts` counts ALL customer and supplier invoices (`invoiceCount`) and all
  posted bank transactions (`transactionAmount`), so the seeded rows and each deploy's golden invoices add to the public landing figures
  (a `COALESCE(is_demo,false)=false` filter there is the fix; not done here).
- The company is made by `create_company_with_owner` (as `seed-demo.sql` does), then financial years for the previous, current and
  next year of the run's date plus the fixed 2025-06, 2026-06, 2027-01, 2027-06 dates the specs post into (the payroll sandbox month is
  2027-02). A re-run in a new year adds that year; periods that exist are untouched.
- Seed (`seedBlocks.ts`): the hosted CI seeders (`scripts/ci/golden-hosted/seed-demo-app.ts`, `seed-golden-fixtures.ts`) with small counts,
  through the app as the verify user, never by table writes. Every block finds its records by marker (`seedMarkers.ts`: a builder the
  seeder writes and a pattern the query matches, one place) with BOUND parameters, and is RESUMABLE: it makes only what is absent and
  finishes what was made and not completed (an invoice not approved, a journal not posted: posted GL cannot be deleted, so a re-run
  must never double it). Also: a cost-of-sales account (the default chart has none; z-budget-drivers needs one), original budget versions
  for the current AND next budget year (keyed by year; the year changes on 1 March: **re-run the provisioner each year after 1 March, it
  tops up only the new year**), one posted journal in the PREVIOUS financial year (prior-year actuals for the budget specs whatever
  month it runs: January/February otherwise leave none), and the migration sandbox, made through the SAME request the spec sends
  (`tests/e2e/golden-paths/helpers/sandboxSetup.ts`) and flagged `is_demo`. After seeding, `budgetProblems` mirrors the budget specs'
  prechecks: a company they would skip on fails provisioning.
- Idempotent and additive: nothing that exists is updated (exceptions: the two `user_preferences` keys moved only the way the app moves them;
  the sandbox's `is_demo` set once). One run at a time: a session advisory lock refuses a second run, and the database transaction takes a
  transaction advisory lock first (two runs cannot both create the company).
- Order (`run.ts`): GoTrue per login, the new password saved to the env file's PENDING key straight after the create (and before any
  password change), then the database transaction, the seed, the readiness gate (`slotProblems` + the two-member shape + budgets), and
  the `E2E_VERIFY_*` / `E2E_VERIFY_APPROVER_*` keys LAST (the pending keys removed in the same write), so a deploy never reads a
  half-made company and a run that died is re-run plainly. `--reset-password` is only for a login whose password the file does not
  hold. The env file must be mode 0600 (anything group/other-readable is refused); it is replaced through a `wx` temp file.
- Nothing is defaulted: the owner database url, GoTrue url and service key come from `VERIFY_COMPANY_DATABASE_URL`, `GOTRUE_URL`,
  `SUPABASE_SERVICE_ROLE_KEY` (environment, never argv); `--expect-database`, `--base-url`, `--env-file` are required, and
  `current_database()` must equal `--expect-database` (`assertDatabaseUrlNames` / `assertConnectedToDatabase` in `slotConfig.ts`; the
  slots' `...Dev...` guards are thin wrappers that still pin isaflow_dev). The `.sh` wrapper resolves them as `deploy.sh` does
  (`owner_database_url_for`: `/etc/isaflow/owner.env`, else `/home/velo/isaflow/.env.local`; GoTrue from the latter; CR and quotes
  stripped). `--dry-run` runs the database step in a rolled-back transaction, reads GoTrue, and writes nothing anywhere.
- verify-deploy.sh: `E2E_VERIFY_*` set: `E2E_ADMIN_*` becomes the verify pair, `E2E_APPROVER_*` becomes `E2E_VERIFY_APPROVER_*` (the
  Demo approver dropped), z22 gets `GOLDEN_PLATFORM_ADMIN_*` (or the old `E2E_ADMIN_*` pair); half a pair of any of them, or no platform
  admin anywhere, fails; a skipped budget spec fails (`VERIFY_ALLOW_BUDGET_SKIP=1` waives). Neither set: unchanged, plus one
  `deploy checks will run on the Demo company` line. The suite's global setup then proves the company (active = "Deploy Verification",
  `is_demo`, the login owns no company that is not `is_demo`) and fails red otherwise.

**Review round 2 (decisions):**
- The approver is a `manager` (not `admin`): migration 951 seeds the company's pay-run rule `approver_role = 'manager'`, the decide path
  needs rank >= max(request snapshot, rule today) and `manager` is in the default write roles, so `manager` is the least that can
  decide. `chooseApproverRole` reads the company's actual rule and would give `admin` only if the rule were raised above manager (never an
  owner; today a trigger makes the pay-run rule fixed at `manager`, so `manager` is always right and `admin` is a guard), and `companyProblems` re-checks the rank before the env keys are written.
- Every sandbox company a prod-verify spec creates must be in `sandboxes.ts` (pre-created and `is_demo`): `verifyCompanySandboxCensus.test.ts`
  fails when a non-dev-only spec (not quarantined) creates a company that is not listed; the global setup failure names the company and
  points at it. Today only m-migration-wizard creates one.
- A real run holds `/tmp/isaflow-deploy.lock` and `/tmp/isaflow-colours.lock` (the deploy's own, via flock(1)) from before the first GoTrue write
  to after the env file is written, and is refused while a deploy, rollback, restart or cutover runs (a verification in the window would
  log in with a password the env file does not yet hold). `--dry-run` takes neither.
- A GoTrue login that exists and whose `user_metadata.purpose` is not ours is never adopted (not even with `--reset-password`); a reset
  also ends the login's sessions (GoTrue global logout; needs `JWT_SECRET` and `SUPABASE_ANON_KEY`, passed by the wrapper from the app env, both required by the CLI
  for `--reset-password` before anything is changed). Readiness and the suite's global setup check that the approver belongs to the verify company only and that
  the verify login belongs only to it and demo sandboxes.
- The suite's global setup prints a `WARNING:` when the verify company has no budget version for the current budget year, or none for the next
  one within 60 days of its start (the specs would then skip a year later, which now fails the gate).
- `h-payroll-run` now proves self-approval refused in every environment where `E2E_APPROVER_*` is set (the Demo fallback included): a company
  where the suite user may approve their own run fails that spec.

**What the verify company covers differently from the long-lived Demo (accepted):** legacy Demo data shapes (years of imported or
hand-made rows) are no longer exercised by the post-deploy run; the VAT-registered path is covered, a non-VAT company is not; a company
this young has no closed periods, no old-year history and small lists; two-person approval IS covered again (the approver login).

**Runbook:**
- GoTrue is ONE instance for dev and production. Never run the provisioner with `--reset-password` casually: it resets the real
  production login's password. A known email can be locked out by 10 bad login attempts per 15 minutes (the verify run then goes red at
  login): wait the window out, or fix the password in `/home/hein/isaflow-deploy.env`; a lost password is `--reset-password`.
- The secrets (owner DB url, service key, the new passwords) sit in the provisioner process's environment during a run (readable by the
  same Unix user, like the deploy's): accepted.
- Old `0GP-Golden-*` rows and sandbox companies already in the production Demo company are NOT cleaned by this change; the Demo reseed
  tool (`scripts/lib/demoReseed`) is the path, and Hein's call.
- Do not give the verify user another company by hand: the suite's global setup fails the run for any company that is not `is_demo`, and
  login opens the default (first) company, which must stay `Deploy Verification`.
- The dev slot guards (`isaflow_dev`, `601d000g` ids) are not loosened for this.

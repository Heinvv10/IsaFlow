# scripts/lib/demoReseed/: IsaFlow Demo company reseed

**Purpose:** replace every transaction of the IsaFlow Demo company
(`00000000-0000-0000-0000-000000000001`) with fictional, date-safe data, in one
transaction, and prove the result with read-only post-checks. Entry point
`scripts/reseed-demo-company.ts` (`bun run db:reseed-demo`); the retired
`seed-demo-data.ts`, `seed-payroll-data.ts` and `seed-practice-data.ts` run the same thing.

**Caller contract:**
- `--company <Demo id>` is required; any other id, or none, exits 2. No env override for the id.
- The database URL comes ONLY from `DEMO_RESEED_DATABASE_URL` (never `DATABASE_URL`, never `.env.local`).
  The run prints host, port, database, user, `current_user`, `session_user` and whether the role bypasses
  RLS; never the password or the URL.
- `--dry-run` (counts to delete, insert and keep) and `--check-only` (the post-checks) run in a
  `BEGIN READ ONLY` transaction and write nothing. `--today YYYY-MM-DD` (not after the database's SAST
  date) and `--seed N` make a run reproducible: the same date and seed give the same data.
- Exit 0 done or clean, 1 a post-check failed (rolled back) or `--check-only` found a failure, 2 refused
  before any write.
- Refuses when: the company is missing or not `is_demo`; the role neither bypasses RLS nor is a
  superuser; a table with Demo rows is in neither the wipe nor the keep list (`censusUnclassified`);
  the wipe plan names a table the database lacks; `intercompany_transactions` name Demo journals;
  `supplier_payment` approval is enforced (paid payments cannot be seeded without forging approvals); a
  child row of a multi-FK wipe step names a Demo parent AND another company's parent (`crossTenantChildren`).
- `runReseed({ client })` runs inside the caller's open transaction (a SAVEPOINT), for the integration test.

**Main signatures:** `runReseed(opts) -> { exitCode, inserted, deleted }` (run.ts);
`generateDemoData({ today, seed, accounts, docs, payroll, ... }) -> DemoData` (generate.ts, pure: no
database, no clock, no unseeded randomness); `runPostChecks(tx, { companyId, win, before?, extraChecks? })`
(postCheck.ts); `WIPE_STEPS`, `KEEP_TABLES`, `KEEP_PREFIXES`, `stepWhere` (wipePlan.ts);
`findDeniedNames(text)` (denylist.ts).

**Business rules:**
- Wipe: every DELETE is `company_id = $1`, or for a child table without one "an FK names a Demo-scoped
  parent row". Order is the catalog's FK order, children first; the integration test re-derives it from the
  live catalog. `gl_account_balances` goes last and is rebuilt after the seed. Kept, never written: setup
  (chart, fiscal calendar, cost centres, business units, settings, payroll components and leave types),
  identity and access (`company_*`), budgets (`budget_*`), approval configuration and requests
  (`approval_*`), audit and change history (`audit_*`, the entity change history, `tax_return_versions`
  and the `sars_submissions`/`vat_period_locks` rows it names), billing and platform rows. Generated AFS
  documents (`afs_documents`, `afs_sections` and their children) are wiped: they restate the old data.
  Paystack/Stitch `customer_invoice` payment requests go with their Demo invoice (a CHECK forbids
  unlinking them); `supplier_bank_verifications` cascades with the suppliers and is counted (`CASCADE_WITH`).
- Post-check N6 scans every kept table that is not append-only, row by row, for denylisted names and fails
  the run on a hit; append-only tables (`audit_*`, `entity_changes`, `bank_rule_changes`,
  `tax_return_versions`) cannot change and are reported by R1. A preserved SARS submission (named by an
  append-only return version, which requires status `submitted`: filed by the user) is listed by V1; V1
  fails when one claims a live eFiling submission (it needs a human decision).
- Seed: a rolling 24-month window ending on the run date (`DEMO_MONTHS_BACK = 23`, `DEMO_MONTHS_FORWARD = 0`).
  No transaction or posting date after the run date; only due dates (at most 60 days), open quote
  expiry, practice job due dates (14 days) and the current month's draft pay run end may be later
  (`dated.ts` states the rule; post-check D1 enforces it).
- Every document posts its journal, every bank-account journal line has exactly one bank line, bank
  reconciled to last month end, current month 60 percent matched and the rest to do. 12-18 open
  invoices, none more than 150 days overdue; supplier bills paid within 60 days of due.
- Payroll figures come only from the app's engine (`calculatePayrollLine`, the tax tables,
  `applySdlToLines`); a tax year without tables aborts the run. Paid runs carry
  `approval_grandfathered_at` (the seed convention for history), never an `approval_requests` row.
  The current month has one draft run; nothing later (the golden payroll sandbox month stays empty).
- Depreciation history is posted by the app's own depreciation service on the reseed's transaction
  (`appContext.ts` binds our client in AsyncLocalStorage); closed months are skipped, never forced.
- Invoices and bills are inserted through the app's `withApprovalGateExempt` (the import exemption, with
  its rank check), never by setting the gate's setting by hand; credit notes are not seeded.
- No `vat_returns`, no `sars_submissions`: nothing claims a submission to SARS.
- Fictional data only: names web-checked, `.example.co.za` emails, `0XX 555 XXXX` phones, no registration,
  VAT or bank numbers; every bank-subtype account becomes "Demo Bank", account `0000000000`, and a bank
  account whose name names a bank, a QA test or a date is renamed generically. Assets carry no tax life
  or method (the app reads them from its asset category table). Employee SA ID numbers have a real date part
  and a check digit that deliberately FAILS Luhn (`buildInvalidSaId`); tax numbers `000000000N`, UIF
  `U000000N`. `denylist.ts` holds every real name the Demo company carried; the unit test runs it over
  every generated string.
- No text carries a full ISO-style date (the golden money spec fails on one).
- The reseed writes no `audit_log` row (one INSERT site exists, on the app's pool). Its record is the
  entity change history the database writes in the same transaction, plus the printed run record.
- Every file stays under 300 lines; no `Math.random`, `Date.now` or zero-argument `new Date(` here.

**Tests:** `tests/unit/scripts/demoReseed/*.test.ts` (generator, denylist, employees, CLI, wipe plan);
`tests/integration/demo-reseed.int.test.ts` (dirty Demo plus a second tenant in one rolled-back
transaction: dry run, refusals, rollback, census, real run, untouched tenant, every post-check and the
16 deploy integrity checks, idempotence, catalog order, three app services the deploy gate reaches).

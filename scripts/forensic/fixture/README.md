# The integration-test fixture database

`tests/integration/**` needs a PostgreSQL database with this application's schema. This directory
holds it as a checked-in snapshot so any session can rebuild the fixture from the repository alone.

## Run the integration tests

```bash
bash scripts/forensic/fixture-up.sh          # allocates a free port; ~30s (28-37s measured)
bash scripts/forensic/fixture-verify.sh      # must print "MATCH" and the 838 check must say OK
eval "$(bash scripts/forensic/fixture-env.sh)"
bun run test:integration                     # serial by default; see vitest.integration.config.ts
bash scripts/forensic/fixture-down.sh        # removes that container BY NAME, nothing else
```

**With no argument `fixture-up.sh` ALLOCATES a free port** in 33150-33199 and prints it;
`fixture-env.sh` and `fixture-down.sh` with no argument use this machine's most recently created
fixture. That is deliberate: the container name must be exactly `isaflow-forensic-<port>` because
`validateFixtureTarget` requires the label to match the port, so the port *is* the identity — and
when every session defaulted to 33150, one ran `fixture-down.sh` and removed a fixture another was
testing against. Pass a port explicitly to pin one (`fixture-up.sh 33155`, then the same port to
`fixture-env.sh`/`fixture-down.sh`).

`fixture-down.sh` also refuses a container whose creating run does not match the state file —
that is somebody else's and may be in use — unless you pass `--force`.

**33149 is deliberately never allocated**: it is the address of the legacy
`isaflow-forensic-pg-20260909` container that earlier sessions' notes refer to, and of the
`--apply` guard in `schema-match.ts`.

`--apply` (regeneration only) is refused against a fixture that has run tests: it rewrites function
bodies and reverts migrations, and doing that under a running suite turns its failures into
nonsense.

`tests/integration/controls/*` take real row and table locks on one database and deadlock each
other in parallel, so the vitest config sets `fileParallelism: false`. For speed, shard across
separate fixtures — they contend on nothing:

```bash
for i in 1 2 3 4; do bash scripts/forensic/fixture-up.sh; done   # each allocates its own port
# then per shard, with that shard's env:
vitest run --config vitest.integration.config.ts tests/integration/controls --shard=$i/4
```

## What is here

| File | What it is |
|---|---|
| `schema.sql` | `pg_dump -s` of the fixture, ownership preserved. **Generated — never hand-edit.** Its header states its provenance and the commit it was verified against. |
| `reference-data.sql` | Rows the *migrations* insert into `permission_modules`, `feature_flags`, `asset_categories`. **Hand-maintained — nothing generates it.** |
| `definers.txt` | Manifest of every `SECURITY DEFINER` function and its owner, checked by `fixture-verify.sh`. Generated by `fixture-dump.sh`. |
| `roles.sql` | The three cluster roles, hand-written. `pg_dumpall --roles-only` emits password hashes, which must not enter the repository. |
| `reverts/*.sql` | Undo scripts for migrations that exist on other branches but not on this one, consumed by `schema-match.ts`. |

Ownership is preserved on purpose. Counted on a fresh build: the dump carries 238
`OWNER TO migration_admin` statements (statements, not objects — `pg_dump` emits one per table and
indexes and constraints follow their table; `migration_admin` actually owns 1,064 relations and
functions in `public`). Of the SECURITY DEFINER functions, **20 are in `public`** — 10 owned by
`migration_admin` and 10 by the superuser `postgres` — and **23 across `public`, `auth` and `app`**,
which is the scope `definers.txt` and the verify check use. Both counts are right; they differ only
in scope, and the earlier "12 SECURITY DEFINER" in this file was the `migration_admin`-owned subset
across `public`+`auth` stated as if it were the total. Dumping `--no-owner` would silently re-own
all of them and change what they can do.

`reference-data.sql` is not test data: `pg_dump -s` drops rows, and routes validate against these
tables — without `permission_modules` the control routes answer `400 Unknown moduleKey: audit` and
`authorityLockLiveness` fails for a reason that has nothing to do with locks. All three tables are
company-agnostic (none has a `company_id`; every `asset_categories` GL column is NULL).

**`reference-data.sql` is maintained entirely by hand.** Its first section was originally produced
by `pg_dump -a` against the ancestor and has been edited since; nothing in `scripts/` or
`package.json` regenerates it, and `fixture-up.sh` only reads it. That is exactly how it came to be
missing 13 of 23 `permission_modules` keys — see the row-level divergence below.

So `fixture-verify.sh` checks it: every `module_key` the migrations INSERT must be present, sourced
from the migration files at verify time rather than from this list. Proved by deleting the 13
business modules and watching `schema-match` report MATCH while verify exits 1 naming them.
`permission_modules` only, because it is the one the routes *validate* against
(`pages/api/accounting/permissions.ts` answers `400 Unknown moduleKey`); `feature_flags` and
`asset_categories` are read rather than validated, so a missing row degrades instead of refusing —
worth adding to that check if it ever changes.

It also carries migration 841's reserved unattended principal, the identity a Paystack webhook
settlement is attributed to. Hand-added rather than dumped because `users` also holds people and
must never be dumped wholesale into this repository. Keep it in step with 841 by hand; a fresh
fixture must contain exactly one user, and that is it.

The `\restrict` / `\unrestrict` lines `pg_dump` emits are stripped: the token is a fresh random
nonce every time, and leaving it in makes each regeneration diff look like a change.

## Why a snapshot and not `bun run db:migrate`

**A from-scratch apply of the migration set does not reproduce this application's schema**, and it
is not close. Measured 2026-09-14: 116 of 411 migrations fail on an empty database.

Most of that is one bug cascading. `company_users.user_id` is TEXT in the live schema and no
migration converts it from the UUID that `236_multi_entity.sql` creates, so
`348_rls_and_auth_helpers.sql` dies building `tenant_isolation` on `user_id = auth.uid()` and ~90
later migrations die with it. Apply that one repair, and re-run failures as a fixed-point loop
because the file numbering is not the apply order (`220` references `companies`, created by `236`),
and it drops to 12. Those 12:

| Migration | Why it fails from scratch |
|---|---|
| `251_demo_seed_data`, `479_subledger_recon_brightsphere`, `606_backfill_system_account_roles` | Data backfills; no empty database can satisfy them. |
| `253_missing_tables` | Creates `stock_items` as a VIEW over `products.sku`. `products` has no `sku`. |
| `255_fix_missing_schema`, `440_app_settings_view`, `436_sent_mirror_connections`, `672_capture_posting_claim_fence`, `816_bank_statement_attestation_intents` | Downstream of `253` failing. |
| `284_bank_rules_columns` | `RENAME COLUMN match_value TO match_pattern` unguarded, after `256` already created `match_pattern`. |
| `311_missing_indexes` | Indexes a column that does not exist at that point in the order. |
| ~~`841_gateway_receipt_principal`~~ | FIXED in `976457568`. It named `users.password_hash`, dropped by `349_users_profile_shadow.sql` at the GoTrue cutover, so it failed at parse and could never apply anywhere. Found by this fixture within minutes of the fixture existing; now verified to apply in full and to be idempotent. |

So a migration-built fixture would model what the migrations *say*, not what the code *runs
against*, and would produce exactly the unattributable failures that make a bad fixture worse than
none. This snapshot descends from the live schema instead.

### The divergences found so far

Places where the live schema holds something no migration produces. This is a **lower bound** —
the from-scratch comparison ran against an incomplete schema (12 migrations never applied), so
anything downstream of those is not comparable.

| Divergence | Note |
|---|---|
| `company_users.user_id` UUID → TEXT | Load-bearing: every `tenant_isolation` RLS policy depends on it. |
| `admin_audit_log.admin_user_id` uuid → varchar | Same class. |
| `admin_audit_log.target_id` uuid → varchar | Same class. |
| `system_announcements.created_by` uuid → varchar | Same class. |
| `exchange_rates.{from_currency,to_currency,source}` text → varchar | Cosmetic in PostgreSQL. |
| `stock_items` VIEW → BASE TABLE | Structural; see `253` above. |

The first four are one decision, not four accidents: `users.id` is `character varying`, and the
migrations declare `uuid` for the columns that hold user ids. The live schema was corrected by
hand; the migrations were not.

#### Row-level divergences — a third class, origin undetermined

The two classes above are about *shape*. This one is about *rows the migrations INSERT that the
live-descended schema does not have*, and it is not the same finding.

| Divergence | Note |
|---|---|
| `permission_modules` holds 10 of 23 keys | The ancestor fixture has only the forensic-control modules (`access, approvals, assets, audit, beneficiaries, controls, imports, locks, payroll_sensitive, release`). `270_granular_permissions.sql` inserts 13 more business modules (`dashboard, customers, suppliers, items, banking, accounts, vat, accountant, reports, sars, tools, group, payroll`). No migration deletes from this table. |

**Its origin is genuinely undetermined and the two possibilities are not equally benign:**

1. the ancestor dump was partial, and production has all 23 — a fixture-provenance issue, now moot
   because `reference-data.sql` carries all 23 and verify enforces it; or
2. production genuinely lacks 270's rows, in which case the live system is missing 13 permission
   modules its own migration inserted and something later removed them, and every
   `pages/api/accounting/permissions.ts` grant against a business module has been answering
   `400 Unknown moduleKey` in production.

**What settles it: `SELECT module_key FROM permission_modules ORDER BY 1;` against production.**
Nobody working on this branch may run that — only Hein can. 23 rows means (1) and the matter is
closed. 10 rows means (2), which is a production defect and not a fixture question at all.

Until then, treat the fixture as modelling intent (all 23, as the migrations specify) rather than
as evidence about what production holds.

Excluded after checking, because they are artefacts of the fixed-point retry loop rather than real
divergences: `app_settings` (TABLE from scratch, VIEW live) and `dunning_communications` (present
from scratch, absent live) — both are tables `253` creates, and re-running `253` late reverses a
later migration that replaced or dropped them.

**This is a disaster-recovery finding, not a fixture problem.** Fixing it is separate work.

## Regenerating after new migrations land

`fixture-verify.sh` fails with `missing: …` naming what the snapshot lacks. Then:

```bash
bash scripts/forensic/fixture-up.sh 33151              # a FRESH fixture, see the warning below
eval "$(bash scripts/forensic/fixture-env.sh 33151)"
for f in scripts/migrations/sql/<the missing ones>; do
  docker exec -i isaflow-forensic-33151 psql -U postgres -d isaflow_schema_fixture \
    -q -v ON_ERROR_STOP=1 < "$f"
done
bash scripts/forensic/fixture-verify.sh 33151 HEAD --apply   # reverts anything ahead
bash scripts/forensic/fixture-dump.sh 33151 HEAD             # verifies again, then writes schema.sql
bash scripts/forensic/fixture-down.sh 33151
```

**Dump only from a fixture that has never run a test.** The guard exists because a
`synthetic_comparison_source_suppress()` trigger function, carrying two hardcoded UUIDs in its
body, was created by the controls suite and made it into a dump taken from a used fixture.

`fixture-dump.sh` detects "used" by three independent signals, any one of which refuses the dump:

1. any row in `companies` — every tenant-scoped suite provisions one, since
   `provisionForensicFixture` always does;
2. any row in `users` other than the single reserved gateway principal above;
3. any relation OR function in `public` named `synthetic*` — the convention the suites use for
   objects they create, and the one that actually leaked.

Each of the three is verified to refuse by adding the thing and watching the dump be rejected.

**But all three are PROXIES, and all three can be clean on a dirty fixture.** The premise "tests
always create companies" confuses *creates* with *leaves behind* — a suite that tears down
properly, as the k-046 teardowns in `5a09fb442` do, leaves `companies` at zero. And `synthetic*`
is a naming convention, not a guarantee. So the guard that actually matters is the content check
on the dump itself:

**No UUID-shaped and no email-shaped literal may appear anywhere in `schema.sql`, function bodies
included.** That is not a proxy for "was this fixture used" — it asks directly whether the artefact
contains something that must never be in it. The historical leak was two tenant UUIDs inside a
plpgsql trigger body, which is *schema*, not data, so every statement-shaped check (`^COPY`,
`^INSERT INTO`, SCRAM, `ALTER ROLE`, connection strings) passes it. Proved by reconstructing that
function under a name the `synthetic*` signal cannot see, on a fixture with zero companies and one
user: all three used-fixture signals read clean and the dump was still refused, naming the line.

The dump is built into a temp file and moved into place only after every guardrail passes, so a
refused dump never lands on disk looking like the committed one. Verified: `schema.sql` is
byte-identical after a refusal.

The live schema has zero of either literal across all 36,538 lines, so this is a hard refusal
rather than a threshold. A migration that legitimately adds a UUID `DEFAULT` or `CHECK` will fail
it closed and wants an explicit allowlist in `fixture-dump.sh` — the correct direction to fail.

A migration that fails to apply forward here is telling you it was written against a state that no
longer exists. Fix the migration; never hand-edit the dump.

### `CREATE OR REPLACE FUNCTION` silently resets `proconfig`

**Anyone who reverts or re-applies a function in this schema loses its `SET` clauses unless they
re-assert them.** This has cost the same setting three times: in the revert step that built the
first cut of this snapshot; in the legacy fixture, where the Sage branch re-created
`control_approval_authorities` after the bound was set; and originally — which is why
`838_control_authority_lock_timeout.sql` exists at all and does nothing but re-issue
`ALTER FUNCTION … SET lock_timeout`.

So after regenerating, **re-apply every settings-only migration** — `838` is the only one today.
`fixture-verify.sh` asserts 838's invariant directly and fails if any `control-authority` lock
holder has lost `lock_timeout=5s`; a second settings-only migration needs its own check added
there, because nothing else in the pipeline can see it.

## What verification does and does not cover

**`MATCH` is a statement about four things and nothing else.** `observe()`
(`schema-match.ts:152-158`) reads exactly: table names where `relkind IN ('r','p')`, column
*presence* by `attname`, function `proname` + `prosrc`, and trigger `tgname` on a table. Plus the
`-- detect:` query in each revert file. Everything else in the schema is invisible to it.

Measured, not inferred — each of these ten mutations was applied to a verified fixture and
`schema-match` printed **MATCH** and exited 0:

| Mutation | Now caught by |
|---|---|
| `ALTER FUNCTION … SECURITY INVOKER` | `fixture-verify.sh` definers check |
| function owner → `app_user` | `fixture-verify.sh` definers check |
| `ALTER TABLE … NO FORCE ROW LEVEL SECURITY` | nothing |
| `ALTER TABLE … DISABLE ROW LEVEL SECURITY` | nothing |
| `ALTER TABLE … DISABLE TRIGGER` | nothing |
| `DROP POLICY tenant_isolation` | nothing |
| `DROP INDEX …entity_canonical_idx` (mig 835) | nothing |
| `DROP EXPRESSION` on `entity_id_canonical` | nothing |
| `REVOKE ALL … FROM app_user` | nothing |
| `DROP CONSTRAINT users_role_check` | nothing |

Also invisible: constraints, indexes, column *types*, `NOT NULL`, defaults, generated-column
expressions, identity, sequences and their state, views and matviews, extensions, every non-`public`
schema (so all of `auth`, including `auth.uid()` itself), `provolatile`, `proleakproof`, function
overloads (matched by NAME, so any overload's body passes), `BEGIN ATOMIC` bodies (`prosrc` is
NULL and line 165 skips them), and everything last touched before migration 600.

Four of those ten are security-relevant and two are now covered by the `definers.txt` assertion.
The rest are not, and a reader must not treat `MATCH` as evidence about them. The `proconfig` case
is the worked example of why: `schema-match` reported MATCH with `lock_timeout` missing, and an
integration test — not the verifier — is what caught it.

Extending `schema-match` to compare `proconfig` properly is not cheap: `838` sets it from a
`DO` block using `format()`, so there is no static `ALTER FUNCTION` statement to parse. The
targeted assertions in `fixture-verify.sh` are the affordable substitute, and they run **even on a
MISMATCH** — `schema-match`'s exit code is captured with `|| STATUS=$?` rather than allowed to trip
`set -e`, because the moment the fixture is known wrong is the moment you most want to know which
invariant broke.

### `prosecdef` and ownership behave differently, and only one of them is safe

An earlier version of this file claimed neither drifts, because `CREATE OR REPLACE FUNCTION`
preserves the owner. **The ownership half is true and the `prosecdef` half was false**, and the
reasoning was a non-sequitur: they are independent catalog fields with opposite behaviour.
Measured on a probe function owned by `migration_admin`, `SECURITY DEFINER`, `SET lock_timeout`:

| Operation | owner | `prosecdef` | `proconfig` |
|---|---|---|---|
| `CREATE OR REPLACE`, not restating `SECURITY DEFINER` | `migration_admin` (kept) | **`f` — lost** | **null — lost** |
| `DROP` + `CREATE` | `postgres` (**reassigned**) | `t` | null |

So a definer bit is lost by exactly the mechanism `proconfig` is, and a reader that silently
becomes `SECURITY INVOKER` — or whose owner stops bypassing RLS — **fails OPEN**.

`fixture-verify.sh` therefore checks both, against `fixture/definers.txt`, a manifest
`fixture-dump.sh` writes from the fixture it dumps: every function in the manifest must still be
`SECURITY DEFINER` with the same owner, and no live definer function may be owned by a role that
neither bypasses RLS nor is superuser. Proved by `ALTER FUNCTION control_guard_approval_birth()
SECURITY INVOKER` — body untouched, so only the bit changes — and watching `schema-match` report
**MATCH** while verify exits 1 naming the function. An assertion nobody has watched fail is a
decoration.

Treat a green integration run as the stronger signal of the two, and when a control test fails in
a way that smells structural, check the fixture before the code.

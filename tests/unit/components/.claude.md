# tests/unit/components/ (vitest + happy-dom + testing-library)

Run by `bun run test:components` (`vitest.components.config.ts`), inside `bun run ci`.

## Gotchas
- **Wait on the END state, never on something vanishing.** `waitFor(() => expect(queryByText('Save')).toBeNull())`
  already holds while the button reads `Saving...`, so the next synchronous `getBy*` races the
  refetch and fails only under CPU load (R-150). Wait with `findBy*` for an element that exists
  only after the whole flow finished (e.g. `Edit` back after save + refetch), then assert the
  refetched data rendered.
- Same class: `vi.waitFor` on a callback spy followed by a synchronous DOM assertion — a spy
  called right after `setState` (e.g. `AutoPostRunsPanel`'s `onUndone`) fires before React
  commits, so the DOM assertion can see the old render. Wait on the DOM instead — in
  `AutoPostRunsPanel`, the button reading `Undo` again (not `Undoing…`) is the end state (R-154).
  Such a test can also pass wrongly: the old render can hide a notice that should not be there.
- Before `fireEvent.change` on a `<select>`, wait for the OPTION (`findByRole('option', …)`), not the
  select: its placeholder shows before the options' fetch lands, and changing to a value with no
  option leaves it at `''` — nothing is selected and a later waitFor times out (R-138). Waiting on
  the report or another fetch is not enough; each option list is its own fetch. Same for reading a
  restored option label: `await findByDisplayValue('CC2 — Project')`, not `getByDisplayValue`.
- Reproduce a load flake without loading the box: pin only your run, e.g.
  `taskset -c <idle core> bunx vitest run --config vitest.components.config.ts --maxWorkers=12 <target> <heaviest ~11 files>`.
  `DEBUG_PRINT_LIMIT=200000` makes the failure print the whole DOM (default cuts at 7000 chars).
- Keep workers per core near the gate's when you pin. The gate passes no `--maxWorkers`, so vitest
  runs `availableParallelism() - 1` = 31 workers on 32 cores; under `taskset` that count shrinks to
  the pinned cores. At 16 workers on one core, the `_app` tests that `await import('pages/_app')`
  inside the test body (appFontWrapper, serviceWorkerExclusion, shareProviderFetches,
  trackerExclusion) take 4–5 s cold and hit the 5000 ms timeout. That is starvation, not a bug:
  with `--testTimeout=60000` they pass, and at 1 worker per core they take 0.1–0.3 s (R-154).

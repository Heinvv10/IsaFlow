## Triage of each audit claim

### Claim 1 — P0: "Time entry work item dropdown never populates"
**Harness:** `time_entry/work_items_for_category[*]` — **PASS** for all 4 categories (2-3 active items each, e.g. "Transaction Capture", "Bank Reconciliation").
**Verdict:** The query the API uses (`listWorkItems`) returns rows when called with a real `categoryId`. **Cannot reproduce as a data/query bug.** If reproducible in browser, the bug lives in the UI layer (e.g. category selector emitting the wrong id, or the fetch happening before the category is known).
**Recommended next step:** Browser-driven cycle (Playwright) calling the actual `/api/accounting/practice/work-items?categoryId=...` endpoint with auth, to confirm the API returns rows over HTTP. If yes, the bug is in the React component.

### Claim 2 — P0/P1: "Staff Member dropdown empty in client rate overrides"
**Harness:** `rate_overrides/staff_member_dropdown` — **PASS**, 4 users returned (admin/staff identities redacted).
**Verdict:** `listCompanyUsers` query returns the expected users. **Cannot reproduce.** Same shape as Claim 1 — likely a UI fetch wiring issue, not a query bug.

### Claim 3 — P0: "Customer payment creation fails with generic 'Validation failed'"
**Harness setup verified:**
- `bank_gl_account_present` PASS — bank GL account 1110 exists
- `vat_output_account_present` PASS — VAT output GL account exists
- `approved_unpaid_invoices_present` PASS — 6 approved-unpaid invoices

**Verdict:** All known prerequisites for posting a payment journal are in place. The validation failure is **NOT** caused by missing setup. Either:
- (a) The API rejects a specific request shape (e.g. allocation amount precision, missing `payment_method`, missing `bank_account_id`)
- (b) A check inside `customerPaymentService` fails with no field-level detail surfaced

**Recommended next step:** Read `src/modules/accounting/services/customerPaymentService.ts` and search for `apiResponse.badRequest` / Zod validators that don't echo `error.flatten()`. Add structured field errors. This is a **real fix** — even without a live repro, the audit's complaint about generic "Validation failed" being a poor UX is correct and broadly applicable.

### Claim 4 — P0: "Date persistence — invoice due date saves as blank, invoice date shifts a day, job due date doesn't persist, approvals filter shows December rows when filtered to April"
**Harness:** `approvals/date_filter_correctness` — **INFO** — 8 entries in current month, 0 outside. Date filter SQL is correct.
**Verdict:** Two distinct claims bundled here:
- **Server-side date filter math:** correct. Cannot reproduce.
- **Form date inputs not persisting:** harness can't test this — it's a browser-form-to-DB roundtrip bug. The audit's evidence (visible 2026-04-27, saved 2026-04-26) is consistent with a **timezone bug** in the date picker — likely the form sends a Date object that gets `.toISOString()`'d in UTC and shifts back a day for SAST. Worth investigating but not reproducible from data.

**Recommended next step:** Spot-check `<DatePicker>` component for `.toISOString().slice(0,10)` patterns vs. local-date formatting. This is the most common culprit.

### Claim 5 — P1: "Approvals row count is suspicious — 2013 entries when filter is 1 month"

## What this cycle proved

1. **The original tenant ("ISAFlow Demo") is unreliable as a workflow QA bed.** Its seed data is optimized for sales demos (36 months of backloaded transactions, 2013 time entries), not for a clean monthly-close walkthrough. Several "P0 bugs" in the audit are the seed showing through, not the code failing.
2. **The dropdown population queries (work items, staff users) work correctly at the DB level.** If the audit reproduces them in the browser, the bug is in the UI layer — most likely the React fetch happening before the category id is known, or a stale auth context.
3. **The two recommendations worth implementing now** — independent of any specific repro — are: (a) field-level validation errors from the API, and (b) a Practice Setup Health panel.
